## 二、日常检查与排障

#### 步骤 1 · 看运行状态

在 R730xd 的 `/opt/powersystem` 执行：

```bash
docker compose --env-file .env -f stages/04-frontend/deploy/compose.yaml ps prometheus alertmanager feishu-adapter
docker compose --env-file .env -f stages/04-frontend/deploy/compose.yaml logs --since=10m alertmanager feishu-adapter
```

> 分享日志前先脱敏；不要输出或转发机器人 URL、签名密钥、群标识和完整事件载荷。

#### 步骤 2 · 按链路定位

- **规则未 firing：** 核对 Prometheus targets、`alerts.yml` 表达式和持续时间。
- **已 firing 但适配器无请求：** 核对 Alertmanager 配置、服务发现和 Compose 内网连通性。
- **适配器返回 502：** 核对私有文件存在性及权限、服务器到飞书 443 的连通性；只记录错误类型，不打印私密值。
- **适配器返回 200 但群里没有消息：** 由群成员核对群机器人是否仍在目标群、消息是否被策略拦截；仅保存脱敏时间和结果。

## 三、改动后复测

改 `app.py` 或消息格式后运行适配器全部本机测试；改 Compose、Prometheus 规则或 Alertmanager 配置后做对应配置检查。更新镜像后核对 API、Prometheus、Alertmanager 与适配器的健康状态和日志。需要重新声明“实际送达”时，在约定时间注入可控故障，记录触发/恢复、适配器响应和群成员确认；失败与复测分别保留。密钥轮换只在服务器私有文件操作，完成后重启适配器并重新验收，不把新值写入笔记。

## 四、第一版业务告警复测记录

设备越限、AI 风险现在是阶段五主要业务，不沿用上文 API 宕机的群内证据。源码已实现 `004_business_notifications.sql` 投递表、Go API 同事务入队与退避重试、适配器令牌校验及业务文案；本地 Go 与 Python 测试通过。

**第一版部署后的现场核对，2026-09-29：** R730xd 统一 Compose 已构建运行，`business_notification_outbox` 迁移存在。运行 `stages/05-feishu-notification/deploy/verify-business-notifications.py`，使用临时合成规则和设备完成下列记录，并在结束后清理临时规则：

| 事件 | 现场结果 |
| --- | --- |
| 设备 1 越限触发 | 暂停适配器后任务留在表内，`attempts=1`、`sent_at` 为空；恢复适配器后标记送达 |
| 操作员确认 | 独立确认事件任务被适配器接受并标记送达 |
| 遥测自然恢复 | 独立恢复事件任务被适配器接受并标记送达 |
| 设备 2 越限触发 | 任务被适配器接受并标记送达 |
| 停用临时规则 | “配置关闭”事件任务被适配器接受并标记送达，不冒充自然恢复 |

脚本输出五项 PASS；投递标记只在适配器收到飞书机器人 HTTP 成功响应后写入。另以合成 AI 风险模板直接测试适配器，HTTP 200；该项只验证消息格式和机器人路径。

**真实模型业务事件复验：** 新建唯一编号的合成逆变器 `INV-M4-AI-20260929114339`，30 个前兆分钟点入库，API 真实调用已部署模型后得到高风险概率 0.9942，并生成 `ai_failure_risk` 告警 ID 9；`alarm:9:triggered` 投递表 `sent_at` 非空。再用同一模型预检正常合成 30 分钟窗口，概率 0.0125、阈值 0.35、等级 `low`；经 MQTT、网关和时序库入库后，API 预测记录变为低风险，告警 9 自然恢复，`alarm:9:recovered` 的 `sent_at` 非空。两次事件都由真实模型和业务事务产生，不是直接向适配器伪造 AI 事件。测试设备按 ID 与编号双重核对后软删除，历史事件保留作审计。由于测试通过补入合成历史分钟点与重启 API 触发首轮预测实现，此结果只证明该合成场景的链路，不外推真实场站模型准确率或生产常态预测时效。

项目所有者随后确认目标飞书群**能看到设备和 AI 新消息**。该确认与上文 outbox 触发/恢复、机器人 HTTP 成功响应共同构成本轮合成业务通知的群内送达证据；确认未逐条列出事件编号，故消息逐条对应以投递表记录为准。真实场站预测准确率仍不在此次验收范围。

后续重复遥测不得产生新的同状态任务；若机器人或群配置变更，应再次按事件 ID 对账并请群成员确认。告警内容只使用合成设备，不在公开证据中保存机器人凭据或群成员信息。

```bash
docker compose --env-file .env -f stages/04-frontend/deploy/compose.yaml exec -T postgres \
  psql -U powersystem -d powersystem -Atqc \
  'SELECT COUNT(*) FILTER (WHERE sent_at IS NULL), COUNT(*) FILTER (WHERE sent_at IS NOT NULL), MAX(attempts) FROM business_notification_outbox'
```

此查询只统计任务数量，不输出消息负载。飞书群内可见性需项目所有者确认；适配器 HTTP 200 本身不能证明群成员已经看到消息。网络确认丢失时，同一事件 ID 可重复投递，不能宣称严格一次。
