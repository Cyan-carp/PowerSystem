# 03 · 阶段五测试与交付

> 2026-09-29 北京时间。本页把原先分散在“验证与运维”、阶段四 P0 和服务器现场记录中的阶段五测试证据集中为正式交付笔记。阶段五不单设 M5，其通过项作为第一版主业务纳入 M4。

## 一、测试对象与数据

- 本机适配器单元测试使用内存构造的 Alertmanager 与业务事件，不访问真实机器人。
- 服务器设备业务测试使用现有合成设备 ID 1/2 和临时温度规则；规则在测试后清理。
- AI 业务测试使用临时合成逆变器 `INV-M4-AI-20260929114339`，先后写入 30 个前兆分钟点和 30 个正常分钟点；设备测试后软删除。
- 旧平台监控测试通过暂停/恢复真实 API 服务产生 firing/resolved 消息，不使用真实设备故障。

完整资产分类见 [[测试数据与测试资产/01-阶段1至阶段6测试资产台账]]。

## 二、本机测试

`feishu-adapter/test_app.py` 共 4 项，全部通过：

1. 签名载荷生成、机器人失败响应与测试文案。
2. Alertmanager firing/resolved 状态文案。
3. 设备告警触发、预测风险恢复与非法业务载荷拒绝。
4. `/business` 私有令牌校验，缺失或错误令牌不能投递。

Go 后端 `go test ./...` 全部通过，但当前没有专门针对业务 outbox 的单元测试；outbox 与告警状态同事务、失败保留和恢复投递由本轮服务器现场用例核对。配置层另通过 Compose、Prometheus 和 Alertmanager 校验。

## 三、平台监控通知测试

11:39:38～11:41:29 暂停并恢复 API，Prometheus 依次进入 pending、firing 和 resolved。适配器在 11:41:14、11:42:14 收到 Alertmanager POST 并返回 200；项目所有者确认群内触发与恢复两条消息可见。

原始摘要保留在 `artifacts/stage4/p0m4-20260929-113809/remote-operations.md`。这组证据只证明 API 不可用规则；`PowerSystemDiskHigh` 的真实磁盘越限群消息尚未演练。

## 四、设备业务通知测试

`verify-business-notifications.py` 输出五项 PASS：

| 场景 | 结果 |
| --- | --- |
| 设备 1 越限触发 | 暂停适配器后任务保留，`attempts=1`、`sent_at` 为空；恢复后送达 |
| 操作员确认 | 独立确认事件由适配器接受并标记送达 |
| 遥测自然恢复 | 独立恢复事件由适配器接受并标记送达 |
| 设备 2 越限触发 | 新任务由适配器接受并标记送达 |
| 停用临时规则 | 生成“配置关闭”，没有冒充自然恢复 |

投递表只在飞书机器人 HTTP 成功响应后写入 `sent_at`。失败时任务保留并退避重试；相同业务状态由唯一事件键去重。

## 五、AI 业务通知测试

真实部署模型处理临时合成设备的前兆窗口，得到高风险概率 0.9942、阈值 0.35，生成 `ai_failure_risk` 告警 ID 9，`alarm:9:triggered` 标记发送成功。随后正常窗口预检概率 0.0125、等级 `low`；经 MQTT、网关和时序库入库后，告警 9 自然恢复，`alarm:9:recovered` 标记发送成功。

两条事件由模型预测和业务事务产生，不是直接伪造适配器请求。项目所有者确认目标飞书群能看到设备与 AI 新消息。逐条对应以 outbox 事件记录为准；本次合成窗口不代表真实场站准确率或常态预测时效。

## 六、交付物与判定

**交付物**

- 业务 outbox 迁移与 Go 投递逻辑。
- 飞书适配器 `/business` 与 `/alertmanager` 两个内网入口。
- 4 项本机单测、现场设备业务脚本、AI 准备/恢复/清理脚本。
- 服务器私有的机器人地址、签名密钥与业务令牌挂载方案。
- 群内可见性确认、失败重试和配置关闭语义记录。

**判定**

阶段五第一版主业务在合成场景下测试通过：设备触发、确认、自然恢复、配置关闭、失败重试、AI 高风险与恢复均完成投递核对，目标群可见性已由项目所有者确认。磁盘真实越限、机器人更换后的回归、真实场站模型效果属于未覆盖边界，不推翻本次阶段五交付结论。
