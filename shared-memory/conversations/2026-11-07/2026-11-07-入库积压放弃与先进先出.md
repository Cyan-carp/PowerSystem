# 入库积压放弃与先进先出（会话纪要）

> 承接 `2026-11-06/2026-11-06-入库积压划界交接.md`。交接方案在执行中被推翻两次，最终结论与原始方案不同，差异记在第三节。

## 一、最终做了什么

1. 10-30～11-03 的 881 万条未处理样本标 `owner_abandoned`（`processed_at` + `business_state='quarantined'`），**一行未删**；界下残留 0。
2. 取任务由「每设备最新优先（id DESC）」改回「最旧优先（id ASC）」。
3. 增加 **7 天时间窗**（`ts_ms >= now()-7d`），每轮现算，无需人工设界。
4. 两段取任务与事务内队头复核共用常量 `inboxPendingPredicate`，并由单测守住同向同谓词。

## 二、关键事实（推翻了几个既有判断）

| 判断 | 依据 |
| --- | --- |
| 队列不是「处理不过来」，是「策略不选」 | 处理 84,088 条/小时 vs 新收 83,318，余量仅 0.92%；界上未处理仍从 2,989 涨到 3,827 |
| 最新优先在稳定制造永久空洞 | 每设备每轮只取最新一条，两轮之间积 3 条就漏 2 条；一年自然积 200 万条 |
| 2,230 条 `td_missing` 是**假缺失** | 抽 3 条核 TDengine（`t_device_285`/`t_device_289`）全部命中且 seq 一致；失败后因最新优先再未被选中 |
| 积压处理没有告警价值 | `Freshness` 15 秒分水岭，超时一律 `historical_suppressed`；唯一产出是补 11-01～11-03 发电量 |
| 交接的 #4「队龄查询加 ts_ms 条件」不可用 | 实测 71.98 秒、回表 881 万行；探针预算 4 秒、间隔 5 秒，会静默打掉队列告警 |
| `publish --skip https_wss` 不能免备份 | `--skip` 只含 identity/environment_match/https_wss；无 `--backup` 时唯一出口是写死候选名的 `backup_deferral` |

## 三、与交接方案的差异

| 交接写的 | 实际采用 | 原因 |
| --- | --- | --- |
| 加列 `inbox_floor_ms` + 人工设界 | 7 天滚动窗口（Go 侧算） | 无需迁移、不会忘记回滚、自动止损 |
| 保留最新优先 | 改回先进先出 | 最新优先会持续漏样本，且 7 天窗口已保证不会重演 11-03 死锁 |
| 队龄指标加 `ts_ms` 条件 | 不改，靠队列清空自然归零 | 原方案实测 72 秒，会打掉告警 |
| `prepare → publish --skip` | 手工激活 | 备份闸门不可跳过 + 备份目标机不可达 + 上次全备失败在 `queues_snapshot` |
