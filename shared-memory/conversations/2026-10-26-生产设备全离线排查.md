# 生产设备全离线排查（2026-10-26）

## 现象
公网 `https://www.cyancarp.cn/` 全部 143 台设备显示离线；本地 mock（5173/8080）正常，142/143 在线，与服务器无关。

## 结论（已实核）
**不是采集断了，是 API 的遥测处理循环被卡死。**

- 数据面正常：TDengine 最新 ts 与当前时间一致；`telemetry_inbox` 最近 10 分钟收到 143 台设备、16072 条。
- 处理面停摆：`telemetry_inbox.processed_at` 最后一条为 `2026-10-25 05:48:52Z`（北京 10-25 13:48），此后全部 NULL。
- Redis `device:<id>:latest` 全部陈旧（最新 received_at `2026-10-25 05:46Z`）。dashboard 的 online 判据是「received_at 15 秒内」，故 0/143 在线，健康页全「离线」。

## 触发链
1. 10-25 05:47Z（北京 13:47）起 TDengine 侧写入中断约 18.1 小时（至 10-25 23:52Z / 北京 10-26 07:52，gateway 容器重建时刻）。逐小时计数：05 点 38172 条后直接跳到 23 点。
2. 同期 API 的 MQTT 消费未停，样本照常写入 `telemetry_inbox`（该表按小时 96k 稳定增长）。
3. `processPending` 每 500ms 取「每设备最老的一条未处理行」（`DISTINCT ON (device_id) … LIMIT 500`），命中 `HasSample` 为 false 时只 `continue`，不标记、不跳过 → 143 台设备的头部行永久卡住，每轮重复检查同一批，永远推进不到新数据。
4. 积压 2,228,299 条未处理，按 96k/小时继续增长。

## 证据点
- 抽查 device 244/253/300/335 的头部行 ts，在各自 `t_device_<id>` 中均不存在（`rows:0`）。
- 143 台活跃设备均有 TDengine 子表（152 张含 9 台已删除），不存在缺表设备。
- 未处理行的时间分布：全部落在 10-25 13:46–13:48（北京）。
- API 无 `inbox_*`/`tdengine_verify_failed` 报错，因为 `!found` 分支静默；容器 healthy、重启 0 次。

- TDengine 仍缺 10-25 05:47Z–23:52Z 约 18 小时数据；原始样本保存在 `telemetry_inbox`（已标记 processed，未删）。
- 该 34 小时窗口的告警未生成（本就不存在），告警历史存在空档。
