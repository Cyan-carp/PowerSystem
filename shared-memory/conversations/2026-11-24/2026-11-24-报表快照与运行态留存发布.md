## 设计与评审结论（15–18 号）

- 场站总览挂载时本来就要算一次「最近 7 天 / 全部设备」的可用率报表，与统计报表默认查询同口径。快照方案复用这一次结果，预加载的边际查询成本为 0。
- 单槽交接：`putSnapshot` / `takeSnapshot`，取走即清空；指纹为 `token|用户 id|角色`；未登录显式返回空串，否则三个空值拼出的 `"||"` 会让 `!owner` 守卫失效。
- 明确不做：后端改 SQL、前端预取、全局缓存、分页加载、并发度调整。15 号实测结论为「不建议以调并发度作为发布项」——4 客户端以上差距缩到 15% 内，8 客户端下 8 路反比 3 路慢 5%。
- 删掉两个「看起来正确但站不住」的推理：① 两个并发度 3 的请求 ≠ 一个并发度 6 的请求（完整计算量 286 台 vs 143 台）；② 45.137 s / 2.5 s 是生产同窗口，0.90 s / 1.44 s 是隔离环境，跨环境不能相除（第二代→第三代只有 1.6 倍，不是 2.8 倍）。

## 踩坑（可复用）

- **假后端字段口径**：`dev/mock-server.mjs` 的 `availabilityReport()` 原先返回 `start: ''` / `end: ''`，前端拿快照的起止回填输入框时 `Date.parse('')` 得 NaN，按「没有快照」走正常查询——看起来像快照没生效，实际是假数据骗了验收。真后端 `reportWindow()` 会原样回填（RFC3339Nano，9 位小数）。已按真后端口径修假后端。V8 的 `Date.parse` 能吃纳秒并按毫秒截断，生产链路无此问题。
- **源码快照的 CRLF**：本机 `core.autocrlf=true` 时 `git archive` 把 697 个文件里的 624 个写成 CRLF，`FROM node:24-alpine\r` 在 Linux 直接构建失败。解法是建 `git clone --config core.autocrlf=false --config core.eol=lf` 的临时克隆再 `export`，复检 0 个 CR 才推。
- **取证方式**：`grep $'\r'` 在 Git Bash 里模式会被吃掉、变成全匹配（误报 697/697），必须用 Python 读字节。
- **`deploy()` 的隐藏副作用**：`refresh_registry()` 每次发布都重载 ops-executor，容器 `started_at` 前移。断言只能要求 id / 镜像 / 重启数不变；第一次激活就是被过严的断言拦下，指针没写、系统停在旧指针，改完重跑才过。
- **`ma_tasks` 在 `ma_ops` 库**，不在默认库；用 `docker exec <pg> sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" …'` 查默认库会报 relation does not exist，别误判成表被删。
- **浏览器工具**：标签页失焦后 `dom_cua_click` / `tab_screenshot` 会 `CDP timed out`，`tab_focus` 救不回来；改用 `cua_execute` 的坐标点击与 screenshot。
