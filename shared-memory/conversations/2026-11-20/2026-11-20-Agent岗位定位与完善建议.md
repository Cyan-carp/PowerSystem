# Agent 岗位定位与完善建议

- 本对话跨日续记，前序简历讨论见 2026-11-19/2026-11-19-新增业务后的简历评审.md。
- 用户询问 PowerSystem 是否适合投递 Agent 开发、是否需要完善 Agent 内容；本轮为分析建议，不实施代码、不部署、不调用真实模型或生产写操作。
- 已现查唯一状态与运行能力/限制分卷、阶段 08 README、工具循环代码及第四版评测规范。既有 LangGraph 模型/工具循环、本地 E5/Qdrant 检索、任务持久化/SSE、本人批准的有限业务动作、定期只读任务；已有评测规范及回归脚本，不建议另造一套。
- 定位为 Agent 应用开发/AI 后端，不能把当前项目等同于 Agent 算法训练或强化学习研究。公开官方职位显示同名 Agent 岗职责差异大，需按具体 JD 判断。
- 建议先调整简历呈现，再复用现有评测补当前版本固定样例、多轮追问、工具失败和拒答结果，记录完成率/事实错误/工具选择参数/延迟/Token 等；知识检索优化以基线与失败样例驱动，混合检索/重排按收益决定。
- 演示建议围绕异常设备查询、取证、资料检索、处置建议、本人批准动作与回执；未开放运维重启不扩权。附件仍为站内片段检索，自动告警为固定模板，生产登录态验证缺口保留，均不包装为更强模型能力。

## WeKnora 二次开发难度

- 用户询问修改腾讯 WeKnora 难度，未要求克隆或实施。
- 查阅官方仓库现行架构与开发指南：Go 主服务、Web 前端、Python 文档解析，以及 PostgreSQL/Redis；支持各服务独立开发。与用户技术栈有重叠，但不能从项目规模推断其独立源码修改水平。
- 建议按范围评估：配置/UI 较低、业务只读工具接入中等、检索策略及可复现缺陷修复中等偏高、核心 Agent 引擎和租户权限改造高。优先固定版本、跑通基线、选一个小范围可验证改动并补测试；个人 fork 二开、API 集成与上游合并贡献分别表述。
