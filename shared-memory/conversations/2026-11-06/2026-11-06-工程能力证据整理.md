# 工程能力证据整理（本会话）

## 任务与边界

- 用户目标：把项目里所有优化与修复整理出来，用于**证明工程能力**、以及论证「项目经不断调试、具备较高鲁棒性」。
- 前置对话：曾讨论部署运维日志是否按「优化/修复」二分。给出的结论是**不二分**——两词不互斥（21 号报表提速既是优化也是修慢查询），改为「性质标签（fix/perf/feat/change/revert/observe，可多选）+ 变更清单表 + 索引加性质列」。
- 边界：只读 `notes/`、`artifacts/`、`shared-memory/`；产物写入 `artifacts/工程能力证据-20261106/`；未改任何日志页、未动生产、未提交 Git。

## 方法

1. 解析根索引时间轴 → 85 行批次条目（编号/日期/版本/指针/结论）。
2. 脚本压取 80 个批次页的 H2 结构、量化行（带单位数字）、引言结论 → 得到可判读的线索集，避免逐页全文精读。
3. 人工按「性质 × 能力维度」打标，生成 80 行台账。
4. 按 9 个能力维度重构叙述；鲁棒性单列「盲区收敛链」论证。

## 核心论点（本会话形成）

- **不主张「没出过故障」，主张「盲区收敛」**：每次故障暴露一类监控盲区，下一批补上对应观测点。链条：27 → 45/46 → 56/66 → 75 → 85/89/90 → 94/95。
- 三条可量化收敛证据：①故障半径 整链停摆 10h42m → 单点静默 40 分钟；②修复动作从「换实现」转为「加约束」；③发现方式从「用户投诉」转为「主动只读核对」。
- 诚实边界单列：入口探活测不到语义错误、慢速泄漏仍可能长期不告警、开发期备份主动停用（最近可用密文 10-30）、模型窗口口径与批次口径并存。
