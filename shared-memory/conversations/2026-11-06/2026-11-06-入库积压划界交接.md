# 入库积压划界（放弃 10-30～11-03）：完整计划与流程

> 交接给新会话执行。本文是**方案与步骤**，不是验收依据；执行完须回写 [[00-当前系统状态]] 并写一篇部署日志。
> 未改任何代码、未动生产数据（本文写作时仅做只读查询）。

## 一、目标与非目标

**目标**：把 `ts_ms < 2026-11-04 00:00 北京时间` 的未处理样本排除出调度与统计，让队列账面归零。
**硬约束**：**一行数据都不删**。原始 `payload` 全部保留，界往回挪即可重新处理。

**非目标**：不改实时入库路径的吞吐、不改日聚合算法、不动前端、不做备份。

## 二、为什么要放弃（所有者已确认）

- 积压是 10-30 起的回放数据，按现行调度根本轮不到，**不会自愈**（机制见第四节）。
- 放弃的业务影响只有"报表里 11-01～11-03 没有数据"：告警、预测、实时功率都不读这张表的历史。
- 代价已确认接受：M1 2160/2160 对账、143/143 当前样本等结论会失去可复算的数据源，只剩笔记文字。
- **"清库重来"不做**：模拟器是 `--continuous` 按当前时间生成的（`--samples`/`--time-scale` 也只是压缩节奏），**没有回填过去时间戳的模式**；清库只会让历史变空，不会让历史变干净。

## 四、机制（不看会踩坑）

1. **取任务不是"取最旧"，而是每设备取最新一条未处理**：`internal/api/telemetry_scheduler.go:85`
   `WITH RECURSIVE heads AS (SELECT * FROM telemetry_inbox WHERE processed_at IS NULL AND device_id>? ORDER BY device_id,id DESC LIMIT 1) ...`
2. 所以新样本一直插到队头，**老行永远当不了队头** → 积压不动。近 1 小时新收 8.1 万、近 10 分钟处理 1.17 万，处理能力基本被新数据吃满。
3. **2026-11-03 停摆 40 分钟**的成因就是这里：`inboxHeadProbeSQL`（`server.go:494`）与选取方向不一致，每条都被判"已不是队头"，走 `errInboxDeferred` 静默返回。
   → **凡改选取谓词，必须同步改队头复核 SQL，两处条件一字不差。**

## 五、设计：加一个界，不改数据

**不要 UPDATE 881 万行**（撑大表、锁表数分钟、还要 VACUUM）。用"选择条件 + 一行配置"。

| 项 | 做法 |
| --- | --- |
| 存放 | `telemetry_scheduler` 单行表加一列 `inbox_floor_ms bigint NOT NULL DEFAULT 0` |
| 默认值 | `0` = 现行为完全不变。**先上代码，再改值**，两步之间可停 |
| 语义 | 只处理 `ts_ms >= inbox_floor_ms` 的未处理行 |
| 回退 | `UPDATE telemetry_scheduler SET inbox_floor_ms=0` 立即恢复原行为，**不用重新发布** |

用 `ts_ms`（数据时间）而不是 `id`（入库顺序）：设备可能乱序上报，两者不同向；日聚合也按 `ts_ms` 分日。

## 六、需要改的四处

| # | 位置 | 改什么 |
| --- | --- | --- |
| 1 | `deploy/postgres/021_inbox_floor.sql`（新建）+ `internal/store/store.go:58` 的 `MigrationPaths` | 加列。单条 `ALTER TABLE ... ADD COLUMN ... DEFAULT 0`，PG 11+ 只改元数据，秒级；**不必**登记 `atomicMigrations` |
| 2 | `internal/api/telemetry_scheduler.go:85-96` `inboxHeads` | 两处 `processed_at IS NULL` 之后都加 `AND ts_ms>=?`，并把 floor 加进两段 `args`（顺序：after → floor → through，注意 `through>0` 的分支） |
| 3 | `internal/api/server.go:494` `inboxHeadProbeSQL` + `:523` 调用 | SQL 加 `AND ts_ms>=?`，调用改为 `tx.Raw(inboxHeadProbeSQL, item.DeviceID, floor)`。**必须与 #2 完全一致** |
| 4 | `internal/api/telemetry_monitor.go:155` | `queue_at` 子查询加 `AND ts_ms >= (SELECT inbox_floor_ms FROM telemetry_scheduler WHERE id=1)`，否则页面仍显示 10-30 的队龄 |

floor 的读取：`telemetry_scheduler.go:118` 每个 tick 已经读 `telemetry_scheduler WHERE id=1`，在同一句里多读一列 `inbox_floor_ms`，存到 `Server` 的 `atomic.Int64`；`inboxHeads` 用参数传入，`processInboxItem` 的复核用原子值。
**竞态说明**：若两次读之间界被抬高，最坏结果是该条被判"非队头"→ `errInboxDeferred` → 下一 tick 不再被选中。不丢数据、不写错行。
