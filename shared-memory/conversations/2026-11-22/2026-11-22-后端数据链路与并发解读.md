# 后端数据链路与并发解读

- 日期：2026-11-22（用户时区）。
- 目标：根据唯一状态入口、后端源码、部署配置和已有性能证据，解释数据链路、技术栈实际作用与当前并发口径。
- 边界：只读分析；不连接生产、不启动后端或 Docker、不执行压力测试。仅创建与维护本对话记忆。
- 已读：当前系统状态入口、共享记忆 README、协作约定、项目公共记忆。
- 核对重点：区分源码默认值、已发布能力、历史实测与当前在线并发，避免把 200 台容量验证称为 200 用户并发。

## 已核对结论

- 源码主链：同一 MQTT device/telemetry 主题由阶段二 gateway 与 API 独立订阅；gateway 经 SQLite WAL/FULL 持久队列写 TDengine，API 持久接收至 PostgreSQL telemetry_inbox，再按 TD 精确确认推进实时快照与历史业务。不能画成网关→TD→API的单一路径。
- 实时快照/Redis缓存、当前告警与历史FIFO/能源处理分离；实时恢复不证明历史积压完成。状态页保留11-18缺口及积压快照，不能将其当11-22实时观测。
- 技术栈已从源码核对：Go/Gin、GORM/PostgreSQL、Paho MQTT/EMQX、SQLite、TDengine、Redis Lua、WebSocket；Python/FastAPI/XGBoost预测；LangGraph、E5/Qdrant、DeepSeek问答；Nginx/FRP、Docker Compose、Prometheus/Grafana/Alertmanager运行支持。
- 当前源码并发：历史处理从PG读history_parallelism，范围1—8；实时快照固定8；TD跨设备4组、每批50；网关接收128、SQLite最多32条/20ms合批；Go数据库池每实例28。以上为实现/默认或可调范围，不冒充生产当次参数或用户容量。
- 助手新旧路径必须分开：V4 RunWorker每实例最多8个在途任务，PG claim限制每用户2个运行任务、其余排队；旧chat默认Redis全局4/单用户1/每用户每分钟10次，不能拿旧值描述V4当前任务路径。
- 性能证据：10-21隔离200台/5秒/30分钟72000条四路对齐；10-28 TR-S04隔离143/286台，完整吞吐28.6/57.2条每秒、业务P99 3.196/4.960秒；11-07 IR-S04无真实gateway/MQTT夹具48/s三轮通过、72/s完成但P99波动到7.35秒、96/s未通过。不同环境不可直接拼成同一容量曲线。
- 11-07生产只读观测接收24.12/s、成功24.04/s仅属历史窗口；143台每5秒理论28.6/s。尚未找到现行版本HTTP用户并发/QPS、WS连接上限或助手吞吐完整压测，不能报支持几百/几千用户。
- 本轮未连接生产、未启动服务、未执行压测或测试；只读现有证据与源码并写本对话记忆。未修改业务代码或长期记忆。
