# 04 · 竞品分析

> 回到 [[00-索引·行业调研与产品分析]]

每个竞品按「六问」拆解：**服务谁 / 功能模块 / 技术栈 / 最强点 / 没做什么 / 我能抄什么**。目的是既看清别人的底牌，也找出我们可直接借鉴的成熟做法。

## 一、竞争格局总览

新能源智能运维市场高度**碎片化**：

- 头部五家合计份额仅 **19.6%**，CR10 为 31.2%；
- 设备运维占营收 62%，数据平台与软件服务 23%，人工代运维及增值 15%；
- 三类玩家：**通用 IoT 底座**（云厂商）、**开源平台**（自建）、**新能源垂直平台**（行业龙头）。

碎片化意味着没有一家吃透市场，**中小场站长尾需求存在明确缺口**。

## 二、开源竞品

### 1. ThingsBoard

- 🎯 **服务谁**：需要私有化、数据不出内网的 IoT 方案商、系统集成商、有开发能力的中小团队。
- 🧩 **核心功能模块**：设备接入、设备管理、规则链（Rule Chain）、仪表盘、多租户、审计日志。
- 🔧 **技术栈**：Java + TypeScript/Angular；Netty + Akka Actor 消息流转；存储 PostgreSQL / Cassandra / TimescaleDB（GitHub ~22.5k star，Apache 2.0）。
- 💪 **最强点**：功能最全的开源 IoT 平台，600+ 可视化 Widget，规则链可视化编排，一站式覆盖接入到展示。
- ❌ **没做什么**：无原生 AI 预测能力；无新能源业务语义（告警闭环、故障前兆）；单体架构需自拆集群才扛得住大流量。
- 📋 **我能抄什么**：
  - *功能划分*：规则链「事件→条件→动作」的编排范式 → 借鉴到我们的告警规则引擎（设备/指标/阈值/级别可配）。
  - *界面布局*：多租户层级（Tenant→Customer→Asset→Device）的实体关系 → 借鉴设备分组筛选。
  - *文档结构*：仪表盘 Widget 的分类组织 → 借鉴实时大屏的组件化设计。

### 2. EMQX

- 🎯 **服务谁**：车联网、智能制造、智慧能源等需要海量设备长连接的企业，以及我们这种自建平台者。
- 🧩 **核心功能模块**：MQTT 消息接入与路由、SQL 规则引擎、多协议网关、集群管理、Dashboard 监控。
- 🔧 **技术栈**：Erlang/OTP（Mria + RLOG 集群架构），GitHub ~16.4k star；单集群 1 亿连接、<5ms、MQTT over QUIC 首创。
- 💪 **最强点**：全球最强 MQTT 消息服务器，高可用与水平扩展能力无出其右。
- ❌ **没做什么**：只是消息中间件，**不含**设备台账/告警/AI/业务可视化，需自搭整套平台。
- 📋 **我能抄什么**：
  - *功能划分*：`device/telemetry` 主题命名规范 → 直接沿用我们的 MQTT 主题设计。
  - *文档结构*：SQL 规则引擎「过滤→转换→转发」的数据管道思路 → 借鉴网关的数据校验与丢弃逻辑。
  - *界面布局*：Dashboard 连接/消息速率的监控视角 → 借鉴我们监控大屏的指标呈现。

### 3. JetLinks

- 🎯 **服务谁**：国内工业、园区、能源等需私有化交付的项目方。
- 🧩 **核心功能模块**：统一物模型、设备连接管理、多协议适配、实时数据处理、告警、数据转发、可视化。
- 🔧 **技术栈**：Java + Spring Boot + WebFlux + Netty + Vert.x + Reactor（全响应式），GitHub ~6.5k star。
- 💪 **最强点**：「产品—设备—物模型」三层抽象 + 多协议插件化，国内协议生态最贴近工业实际。
- ❌ **没做什么**：无原生 AI；社区与文档弱于 ThingsBoard；新能源场站业务语义仍需自建。
- 📋 **我能抄什么**：
  - *功能划分*：统一物模型（产品定义 → 设备实例 → 物模型属性）→ 直接借鉴我们的设备数据建模。
  - *文档结构*：多协议插件化适配清单 → 借鉴我们「MQTT 统一 + 预留 Modbus TCP」的写法。

### 4. ThingsPanel

- 🎯 **服务谁**：中小型物联网项目、需要快速出可视化演示的团队。
- 🧩 **核心功能模块**：设备接入、物模型、远程 RPC、拖拽组态大屏、告警联动、多租户。
- 🔧 **技术栈**：Go + Vue，Apache 2.0，轻量高性能。
- 💪 **最强点**：低代码拖拽组态大屏，界面现代化，演示效果好。
- ❌ **没做什么**：AI 预测、复杂告警闭环、大规模集群。
- 📋 **我能抄什么**：*界面布局*：拖拽式组态大屏的交互 → 借鉴实时监控大屏的卡片式布局。

### 5. FastBee

- 🎯 **服务谁**：中小企业、智慧农业、动环监控等轻量场景。
- 🧩 **核心功能模块**：内置 MQTT、Modbus/TCP 接入、设备管理、大屏、告警通知、定时任务。
- 🔧 **技术栈**：Java + SpringBoot + Vue，Gitee 高星（AGPL3.0，商用需授权）。
- 💪 **最强点**：一键 Docker 部署、上手门槛极低。
- ❌ **没做什么**：生态社区小、规则引擎灵活性弱、无 AI。
- 📋 **我能抄什么**：*功能划分*：「一键 Docker 部署」的开箱体验 → 印证并强化我们的 docker-compose 一键部署。

## 三、非开源竞品

### 1. 华为 FusionSolar / 数字能源

- 🎯 **服务谁**：大型新能源基地、央企/国企业主，追求全栈自控与顶级诊断。
- 🧩 **核心功能模块**：构网型光储、智能组串式逆变器、FusionSolar Agent 智能体、智能 I-V 诊断、AI 功率预测。
- 🔧 **技术栈**：端-边-云全链路 + 构网算法 + 目标驱动 AI 智能体（非开源）。
- 💪 **最强点**：硬件+AI 深度耦合，I-V 诊断获行业首个 L5 认证，端到端闭环最完整。
- ❌ **没做什么**：第三方品牌设备适配弱；成本高、偏向大客户，中小场站难复制。
- 📋 **我能抄什么**：
  - *功能划分*：端-边-云三层职责划分 → 借鉴我们的云边协同分层。
  - *文档结构*：目标驱动智能体「设定目标→拆解→执行→迭代」叙事 → 借鉴"预测-预警-处置"闭环的话术。

### 2. 远景 EnOS

- 🎯 **服务谁**：大型新能源基地、跨国集团、零碳园区，需能碳管理与电力交易。
- 🧩 **核心功能模块**：设备接入、数据治理、资产管理、功率预测、能碳管理、电力交易。
- 🔧 **技术栈**：云原生微服务 + 「通用组件 CBBs」抽象 IT/OT/ET（非开源）。
- 💪 **最强点**：3000+ 设备模型、360+ 算法、适配 90%+ 协议，能源领域协议覆盖最广。
- ❌ **没做什么**：本地协调控制（AGC/AVC）依赖第三方或 EMS；对中小场站过于沉重昂贵。
- 📋 **我能抄什么**：
  - *功能划分*：通用组件 CBBs「可配置、可组合」的模块化思想 → 借鉴我们的模块化设计。
  - *文档结构*：设备模型库的组织方式 → 借鉴我们的遥测数据模型库。

### 3. 金风科技「金风慧能」SOAM

- 🎯 **服务谁**：风电业主，追求资产价值托管与无人化运营。
- 🧩 **核心功能模块**：预测性维护、AI 多模态监测、多源故障预警诊断、AI 电价交易、资产托管。
- 🔧 **技术栈**：GTSim 机理仿真 + 数据智能融合，「端-边-场-云」协同（非开源）。
- 💪 **最强点**：风电预测性维护最成熟（非计划停机降超 40%）、电价预测试点 >93%、27 年数据积累。
- ❌ **没做什么**：以风电为主、绑定自家机组，跨品牌光伏/储能覆盖弱。
- 📋 **我能抄什么**：
  - *功能划分*：「机理模型 + 数据智能」融合路线 → 直接印证我们的"机理仿真 + XGBoost"。
  - *文档结构*：故障案例专家库的结构化沉淀 → 借鉴我们的告警/故障案例归档方式。

### 4. 阿里云 IoT

- 🎯 **服务谁**：大型项目、需深度二次开发的企业。
- 🧩 **核心功能模块**：标准物模型、规则引擎、IoT Studio 低代码、设备影子。
- 🔧 **技术栈**：云原生，千万级并发（非开源）。
- 💪 **最强点**：低代码能力最强、生态最全。
- ❌ **没做什么**：离新能源运维业务远，需大量二次开发；高频上报账单易失控。
- 📋 **我能抄什么**：*功能划分*：标准物模型 JSON 定义 + 设备影子 → 借鉴遥测字段 JSON 建模。

### 5. 腾讯云 IoT Explorer

- 🎯 **服务谁**：消费电子、需微信小程序快速交付的团队。
- 🧩 **核心功能模块**：设备影子、规则引擎、微信生态打通。
- 🔧 **技术栈**：云原生（非开源）。
- 💪 **最强点**：微信生态打通、计费清晰。
- ❌ **没做什么**：工业高频采集消息成本高，能源纵深不足。
- 📋 **我能抄什么**：*文档结构*：设备激活码 + 清晰计费的说明方式 → 借鉴部署授权/成本说明。

### 6. 华为云 IoTDA

- 🎯 **服务谁**：政企/国企、需信创合规的项目。
- 🧩 **核心功能模块**：设备接入、工业协议适配、数据转发。
- 🔧 **技术栈**：云原生（非开源）。
- 💪 **最强点**：工业协议（Modbus/OPC UA/电力规约）适配强、信创合规好。
- ❌ **没做什么**：起步门槛高、中小项目单价不占优。
- 📋 **我能抄什么**：*文档结构*：工业协议适配清单化 → 借鉴「预留 Modbus TCP 扩展接口」的写法。

## 五、差异化机会（我们的切入点）

从对比中提炼明确的市场缺口：

1. **通用平台「重而不专」**：阿里云/华为云 IoT 是底座，离新能源运维业务远，需大量二次开发。
2. **开源平台「全而不易」**：ThingsBoard 功能全但二次开发/运维门槛高，无原生 AI 与业务闭环。
3. **垂直平台「强而绑定」**：华为/金风/远景深度绑定自家硬件或单一能源品类，难低成本复制到异构中小场站。

**本项目的差异化**（详见 [[05-产品定位与差异化]]）：

- **小数据可解释 AI**：XGBoost + 特征重要性，用对照实验说话，而非追逐大模型黑盒；
- **低成本可复制**：全栈 Docker 化一键部署，边缘网关软件化适配现有设备，部署成本较商业平台降 50%；
- **云边协同 + 告警闭环**：断网零丢失 + 遥测越限秒级告警 + 确认闭环，直击中小场站真实痛点。
