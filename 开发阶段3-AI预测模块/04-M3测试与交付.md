## 二、M3 入库、告警与恢复联调

2026-09-28 在桌面项目目录的同一台 Windows 电脑上运行 Docker Desktop：EMQX、TDengine、PostgreSQL、Redis 容器就绪，Go API/网关与 FastAPI 在本机运行。Docker CLI 位于用户目录的 Docker Desktop 安装路径，即使不在 `PATH` 中，也不能将其判作 Docker 未安装。阶段二 API `-migrate-only` 成功，`prediction_records` 表已建立。

| 检查点 | 本机实测结果 |
| --- | --- |
| 回放标识 | `stage3demo20260928020637`；`INV-1001`；窗口截至 10:06:00，实际故障起点 10:09:00（北京时间） |
| 故障前预测 | 10:06:55 产生高风险预测，概率 0.9942，阈值 0.35；在故障点上报前约两分钟完成 |
| 判断依据 | 主要正向因素为末端温度残差 `temperature_residual_last=39.28725`，对应模型贡献约 6.257；该解释只针对本次合成窗口 |
| 入库与 JWT 查询 | 带 JWT 的预测接口返回上述窗口；PostgreSQL 该窗口恰有 1 条预测；完整回放的 `telemetry_inbox` 为 70 条、序号 0～69，预测窗口共 14 条 |
| 告警与实时流 | 创建 `ai_failure_risk` 告警 ID 16；WebSocket 收到 `prediction`、`alarm_created`，REST 告警详情可查且确认操作成功 |
| 故障与恢复 | 实际发送 10 个故障分钟及 30 个恢复分钟；末端低风险概率 0.0280；告警 ID 16 为 `recovered`，WebSocket 收到 `alarm_recovered`；低风险窗口恰有 1 条预测 |

本轮自动脚本的前述断言全部通过；其最后一步调用旧 `stop-stage2.ps1` 时遇到 Windows PowerShell `Stop-Process` 空引用，故原始 `summary.json` 如实标记为 `failed`。随后修复停止脚本，后端已正常停止并重启。原始高、低风险窗口在重启后仍各只有一条，告警 16 保持恢复状态。**不能将原始 `summary.json` 单独称为“完整自动通过”。**

为补足新鲜窗口上的重启去重，另在独立测试设备 `INV-M3-B58280A8E806` 运行 `--restart-check`：只发送 30 条前兆历史数据，不发送故障点；窗口截至 13:06:00。在两分钟有效期内重启后端并等待预测工作器再次轮询。重启前后预测记录均为 1 条、AI 告警均为 1 条，JWT 接口仍返回未过期的高风险结果。此独立测试设备的告警属于模拟测试记录，不能当作真实故障。

两段证据合并，**M3 的预测入库、故障前告警、WebSocket、确认、恢复与重启去重联调已通过**；单次完整自动脚本尚未在修复停止脚本后再跑一遍。原始证据均在 Git 忽略目录，保留失败原因和补测结果：

| 证据 | 路径 |
| --- | --- |
| 完整故障与恢复回放 | `artifacts/stage3/integration-20260928-live/summary.json`、`websocket.jsonl`、`replay.stderr.log` |
| 新窗口重启去重 | `artifacts/stage3/integration-20260928-restart/restart-check.json`、`environment.json` |

## 三、待补验证

公开数据尚未交付，独立外部验证未执行。合成数据上的召回率与误报率不能视为真实设备性能；最终 M3 模型泛化结论待公开数据的字段、时间和真实故障标签核对后再写。若公开数据无法构造“未来一小时故障”标签，只做故障识别对照，不与主模型成绩合并。
