# 06 · 阶段三待收尾工作

> 对应路线图第 9–12 周与 M3。本页只记录尚未完成的验证、报告和环境复现；勾选须依据实际运行产物，不能用计划代替结果。操作命令以 [[stages/03-ai-prediction/README.md|阶段三运行说明]] 为准。

## 一、当前状态与验收边界

合成数据生成、XGBoost 训练、FastAPI 推理、Go 定时预测、PostgreSQL 入库，以及故障前告警、WebSocket、确认、恢复和重启去重已经实现。2026-09-28 的完整故障回放与独立重启补测共同验证了核心链路，见 [[04-M3测试与交付]]。

| 已有证据 | 当前结论 |
| --- | --- |
| `artifacts/stage3/integration-20260928-live/summary.json` | 预测、入库、告警、恢复等断言通过；最后的旧停止脚本报错，整次状态仍为 `failed` |
| `artifacts/stage3/integration-20260928-restart/restart-check.json` | 新鲜窗口的重启去重另行补测通过；不能代替完整回放 |
| `artifacts/stage3/model/evaluation.json` | 有合成数据的时间切分、参数试验与测试指标；不是外部场站效果 |

> **当前不能写“M3 全部验收通过”。** 修复停止脚本后尚无一次从预检到收尾均返回 `passed` 的完整运行；公开数据的独立验证也尚未完成。阶段四可以继续开发，但 `main`、M3 标签与 Release 仍按 [[项目工程规范]] 的里程碑规则处理。

## 二、按顺序执行的待办

### 1. 恢复可复现的本机环境

- [ ] 确认 Python 3.12 的可执行路径、版本和阶段三锁定依赖可用；解决中文项目路径下 `.venv` 启动器不可用问题，或记录一条**实际验证过**的等价启动命令。不要仅写 `python` 而不确认它指向哪个解释器。
- [ ] 按 [[项目工程规范]] 第七节和阶段二、三 README 复查四个容器、Go API、网关、FastAPI、模型文件及 `.env`。先检查已有 `powersystem_stage2` 库和 Docker 卷，不运行会新建隔离库的阶段一完整验收脚本，不清理 M1/M2 数据或 `artifacts/` 证据。
- [ ] 从标准命令重新执行预检、构建、迁移与健康检查。把解释器版本、命令、退出码、健康检查结果及失败原因记入新的 `artifacts/stage3/<运行编号>/environment.json` 或同目录说明；私有配置值不入 Git。

**完成标志：** 新环境检查记录可复查，`verify-m3.py --preflight-only` 返回就绪；仅端口开放或 `/ping` 成功不算整条预测链路就绪。

### 2. 完整自动 M3 再跑一次

- [ ] 另建一个 `artifacts/stage3/integration-<时间>/` 输出目录，先执行 `verify-m3.py --preflight-only`，再执行不带 `--skip-restart` 的完整验证；预计约 43 分钟。运行期间不要向同一设备并行发送其他模拟遥测或手动回放。
- [ ] 核对故障发生前已有高风险预测及 AI 告警，JWT 能查询预测，PostgreSQL 每个窗口恰有一条记录；核对 WebSocket 的预测、告警创建与恢复事件，以及告警确认、恢复和服务重启后的去重。
- [ ] 检查完整运行退出码为 0 且本次 `summary.json.status` 为 `passed`；保留 `environment.json`、`summary.json`、`websocket.jsonl`、回放日志和必要的数据库核对结果。若失败，记录失败步骤并修复后用**新的运行编号**重跑，不覆盖 2026-09-28 的原始失败报告。

**完成标志：** 有一次从预检、故障与恢复回放到停止、重启检查全部通过的完整自动记录。单独的 `--restart-check`、`--skip-restart` 或人工拼接证据均不能勾选此项。

### 3. 补齐模型解释与可读报告

- [ ] 从已保存模型和测试窗口输出全局特征重要性排序或图，逐项解释主要特征的业务含义；明确区分全局重要性与单次预测返回的 `top_factors` 贡献，均不写成已经证实的故障原因。
- [ ] 把 `artifacts/stage3/model/evaluation.json` 中三组参数试验、选型理由、日期切分、测试集混淆矩阵、召回率、误报率及误报代价整理成可读报告，逐个数字对照原始产物。
- [ ] 写《阶段三总结》：数据与标签、特征防泄漏、模型和服务架构、M3 运行编号、故障前预测证据、遇到的问题与未验证边界。解释选择 XGBoost 的数据规模、算力和可解释性理由；没有做 LSTM/Chronos 实验时，不写成已有实测对照。

**完成标志：** 报告能追溯到模型文件、评估 JSON 和 M3 证据目录，公开笔记不包含密钥或原始运行账本。

### 4. 公开数据的独立核对与验证

- [ ] 取得有明确许可的公开数据后，运行 `prediction.inspect_external`，记录来源、许可、设备/场站、字段、单位、采样间隔、缺失情况、故障类别与独立故障起点；审计产物放在被 Git 忽略的 `artifacts/stage3/`。
- [ ] 先写清外部字段到电压、电流、温度、功率的映射与单位换算，再判断能否构造“截至此刻 30 分钟数据 → 未来一小时首次故障”的因果标签；不得把故障发生后的信号放入预测窗口。
- [ ] **若可构造标签：** 固定独立时间段，单独报告样本数、混淆矩阵、召回率和误报率，并说明与合成训练数据的差异；不把外部结果混入合成测试集成绩。
- [ ] **若不可构造标签：** 只做字段适配或故障识别对照，写明无法验证提前预测能力及缺少的标签/时间信息；不得据此宣称真实场站泛化通过。

**完成标志：** 有可复查的数据审计和独立结论；若数据尚未取得，本节维持未完成，并在阶段报告中明确依赖与影响。
