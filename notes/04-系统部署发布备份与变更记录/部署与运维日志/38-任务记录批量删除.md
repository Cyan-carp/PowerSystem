# 38 · 智能助手任务记录批量删除（软删除）

## 当前结论

「智能助手」页右侧抽屉「任务记录」新增批量删除：进入「批量删除」后逐条勾选、全选可删任务、确认后串行调用 `DELETE /api/v1/agent/tasks/:id`。删除是**软删除**——只写 `ma_tasks.deleted_at`/`deleted_by` 并从列表隐藏，步骤、工具调用、事件、审批、执行尝试、安全审查全部保留；详情 `GET /api/v1/agent/tasks/:id` 不过滤，对话内的任务卡片照常可打开。

已于 2026-10-23 01:03（北京时间，17:03Z）发布为 `task-delete-20261023-r1`，`pending=false`，门禁 `passed=true`。

## 需求口径（用户确认的三条）

| 项 | 结论 |
| --- | --- |
| 删除语义 | 软删除；不物理删除，不断审计链 |
| 可删范围 | 仅终态 `succeeded`/`failed`/`cancelled`/`timeout`；进行中不可勾选，服务端同样拒绝 |
| 删除后可见性 | 只有列表过滤；详情与报告不受影响 |

选择软删除而非物理删除的原因：`ma_tasks` 被 9 张表以 `REFERENCES` 引用且**全部没有 `ON DELETE CASCADE`**（`ma_task_steps`、`ma_tool_calls`、`ma_task_events`、`ma_outbox`、`ma_approvals`、`ma_execution_attempts`、`ma_security_reviews`、`ma_security_review_events`、`ma_security_gate_contexts`）。物理删除需要单事务按依赖序删 9 张表，并会销毁安全审查这类不可变审计材料，与阶段 9 现有取证承诺冲突。

## 接口与错误码

| 方法与路径 | 行为 |
| --- | --- |
| `DELETE /api/v1/agent/tasks/:id`（Go JWT 入口）→ `DELETE /internal/ma/v1/tasks/:id`（09） | 本人终态任务软删除 |
| 200 | `{"task_id","deleted":true,"already_deleted":false/true,"deleted_at"}`；重复删除幂等，返回 `already_deleted:true` 且时间戳不变 |
| 409 `task_not_terminal` | 任务仍在排队/规划/执行/待审批 |
| 404 `task_not_found` | 不存在或非本人（同码，不泄露存在性） |
| 409 `task_delete_unsupported` | 库中缺 `deleted_at` 列（restore-readonly 旧备份），防御性分支 |

**09 侧恒返回 200 而非 204**：Go 的 `opsProxy` 只把 `200` 当成功，其余按 `400/401/403/404/409/429` 白名单透传，204 会被降级成 503。

## 代码改动

- **09 运维**：新增 `deploy/008_task_deletion.sql`（`ADD COLUMN IF NOT EXISTS deleted_at/deleted_by`，无外键——`backup-ma.py` 的 dump 只含 `ma_*` 表，restore 库没有 `users`）；`store.py` 在 `Store.open` 的迁移块内注册 008，并在块外用 `information_schema` 探测 `task_tombstone`；`listing()` 按探测结果追加 `AND deleted_at IS NULL`；新增 `soft_delete()`（事务内 `FOR UPDATE` → 归属/终态/幂等 → `UPDATE` + 追加 `ma_task_events(reason='user_deleted')`）；`main.py` 新增 `@app.delete(...)`。
- **Go 网关**：`server.go` 的 JWT 组新增 `a.DELETE("/agent/tasks/:id", s.opsProxy)`；`agent_ops.go` **未改**（已逐行确认 DELETE 不进入 POST 分支，`forwarded` 为空、路径正确、三头齐备）；`cmd/ma-local-api/main.go` 本地放行规则补 `DELETE /api/v1/agent/tasks/`。
- **前端**：`lib/api.ts` 增加 `deleteOpsTask`；`lib/ops-task.ts` 增加 `canDeleteTask`/`toggleSelection`/`retainedSelection`/`allDeletableSelected`；`TaskRecordsPanel.vue` 增加选择模式、行容器 + 兄弟 checkbox（`<button>` 内嵌 checkbox 属非法 HTML）、`.checked`/`.locked` 样式与删除流程。

### restore-readonly 的专门处理

`Store.open` 的迁移整块被 `runtime_profile != "m4-restore-readonly"` 包裹，恢复库角色 `ma_restore_reader` 只有 SELECT 且 `default_transaction_read_only=on`，不可能补 DDL。若列表硬写 `deleted_at IS NULL`，用升级前的历史备份做恢复演练会 `UndefinedColumnError` → 503。因此改为运行期探测列是否存在，缺列时退回原 SQL（此时所有任务都可见，恢复场景下是正确行为）。

## 残留风险与未做

- **全选只覆盖已加载记录**：分页按 20 条增量加载，「全选可删任务」仅覆盖当前已加载且终态的项；按钮与确认框都会复述数量。
- **删除后强制重置分页**：删除成功即 `loadRecords(true)` 重建游标，避免 offset 前移漏读；不做增量 offset 修正。
- **刷新导致选中项消失**：每次加载后用 `retainedSelection` 收敛，并提示「部分已选任务已不在当前列表中，已自动取消选择」。
- **未做批量接口**：仍是前端串行循环单条 DELETE（与历史会话批量删除同策略）。一次选中上百条时会较慢，但每条独立幂等，部分失败只计数提示。
- **未做详情隐藏**：这是刻意设计，不是遗漏。
- **`create()` 幂等键对已删任务的行为未调整**：同一 `idempotency_key` 重放仍返回原 `task_id`（键由 Go 每次新生成，实际不触达）。
