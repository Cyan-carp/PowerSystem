# 入库积压放弃与先进先出发布（96）

> 承接 [[85-遥测入库积压与发电量归零排查]]、[[88-入库取任务改为最新优先]]、[[90-入库队头复核与取任务同向]]。
> 88 用「最新优先」把实时链路救活了，代价是每轮只取最新一条、中间样本永远轮不到——本批处理这个代价。
> 生产当前状态只认 [[00-当前系统状态]]。

## 一、判定：这批积压处理了也没有业务价值

`processInboxItem` 里有一条硬分水岭：`telemetry.Freshness` 要求「收到时间 ≤ 15 秒且采样时间 ≤ 15 秒」才算 `fresh`，非 fresh 一律标 `historical_suppressed`，**跳过整个告警评估**（`server.go:548-574`、`service/alarm.go:156-159`）。

因此 10-30～11-03 的 881 万条：

| 维度 | 处理它们能得到什么 |
| --- | --- |
| 告警 | **零**（全部 historical_suppressed） |
| 实时推送 | **零** |
| 可用率 | 计入，但历史窗口早已出账 |
| 发电量 | 唯一产出：补 11-01～11-03 的 `energy_daily` |

按 84,088 条/小时的处理速度追 808 万条要 **437 天**，结论是不追。所有者 2026-11-07 决定放弃。

## 二、机制：为什么「最新优先」必须改回去

| 事实 | 数值 |
| --- | --- |
| 界上未处理（18:01） | 2,989 |
| 界上未处理（21:22） | 3,827 |
| 界上未处理（22:13） | 3,683 |
| 处理速率 vs 新收 | 84,088 / 83,318 条每小时（余量 0.92%） |

处理能力基本等于产生速度，而每设备只取最新一条：两轮之间积了 3 条就只处理第 3 条，前两条永远轮不到，除非设备彻底停报。这就是「队列看起来健康、却在稳定制造永久空洞」。

抽样（`tablesample system(0.5)`）证实空洞随日期累积：10-30 约 91 万、10-31～11-02 各约 220 万、11-03 约 132 万。即使没有 10-30 的 TDengine 空洞，按每小时约 240 条的速度，一年也会自然积出 200 万条——**这是设计必然，故障只是放大器**。

**副产物**：界上那 2,230 条 `td_missing` 是**假缺失**。抽三条核对 TDengine，`t_device_285` / `t_device_289` 全部命中且 seq 一致。当初核对时 TD 尚未写入或超时，判失败后因最新优先再也没被选中，就冻在 `td_missing` 状态。

## 三、改动

| # | 位置 | 改什么 |
| --- | --- | --- |
| 1 | `internal/api/telemetry_scheduler.go` | 新增 `inboxWindow = 7*24h`、`inboxPendingPredicate = "processed_at IS NULL AND ts_ms>=?"`；`inboxHeads` 由 `id DESC` 改 `id ASC`，两段都带时间窗；抽出纯函数 `buildInboxHeadsQuery` 供测试 |
| 2 | `internal/api/server.go` | `inboxHeadProbeSQL` 改用同一常量、同向 `id ASC`；`Server` 增 `inboxFloor atomic.Int64`，复核读该值 |
| 3 | 每轮 | `processPendingBudget` 现算 `now-7d` 存入原子值，取任务与逐条复核同源 |

时间窗与方向是一对：去掉窗口不能改回 ASC（立刻堵回 11-03），改回 DESC 则继续漏样本。

**不做的事**：不改 `telemetry_monitor.go`。队列清空后 `queue_oldest_age_seconds` 由「最老未处理行」自然归零，不需要额外改口径。

## 四、数据动作（不可逆，一行未删）

```sql
UPDATE telemetry_inbox
   SET processed_at=clock_timestamp(), business_state='quarantined', failure_code='owner_abandoned'
 WHERE processed_at IS NULL AND ts_ms < 1793721600000;   -- 2026-11-04 00:00 +0800
```

- 分批 2 万条执行，共标记 **8,809,844** 条；界下残留 **0**
- `business_state='quarantined'` 不进 `energy_daily` 的 success 口径，`failure_code` 保留可追溯

- 脚本在空批次后因 `UPDATE 0` 命令标签被 `wc -l` 计为 1 而空转，已手工停止；以「界下残留 0」为准

### 为什么不是 prepare → publish

`publish` 的备份闸门不可跳过：`--skip` 只接受 `identity / environment_match / https_wss`；不给 `--backup` 时唯一出口是 `frozen_backup_deferral`，而它硬编码只认三个候选名（`v4-production-compat-20261026-r1` 等）且服务集合必须恰为 `agent-rag+api+ops-agent+security-agent`。本批 api 单服务、新候选名，两条都不满足。

备份本身也不可用：目标机 `powersystem-backup@8.138.10.222` 从 VM117 **ssh 不可达**；上一次全备（11-05）`failed_stage=queues_snapshot`、`failed_line=374`，`/var/backups/powersystem/` 只剩 `.timing.json` 与 `.v4-maintenance.json`，没有任何归档。跑一次只会先暂停遥测维护、dump 32 GB，再在队列快照或上传处失败。

所有者 2026-11-07 在两种失败路径之间选择手工激活。`--skip` 与 `--deviation` 的免门禁语义按 `manual_activation` 如实登记，不冒充门禁通过。

## 七、未执行与遗留

- **未做发布前全备**：所有者开发期决定不做，且目标机不可达。
- **未跑发布前后定向测试**：按所有者「直接看效果」授权；单测 `TestInboxPredicateSharedByHeadsAndProbe` / `TestInboxHeadsQueryWrapsWithWindow` / `TestInboxHeadProbeMatchesSelectionDirection` 在本地通过。
- **`energy_rebuild_incomplete` 每 70 秒一条**：3 秒预算内只重建 10-11 个设备日，`energy_dirty_days` 现存 146 行 / 3 天，属预算内正常节流（旧批次已存在同类日志），未处理。
- **`idx_inbox_pending` 收缩后未 `VACUUM`**：21 GB heap 中约 4.3 GB 为本次 UPDATE 产生的新版本，autovacuum 会回收复用，文件不会自动缩小。
- **加固三项未做**（提高未来抗性，建议单独立项）：并发 8→16、`tdMissingGrace` 10→2 分钟、td_missing 参与熔断。当前 `tdCircuit` 只在**查询报错**时熔断，而空洞时查询成功但返回 false，熔断不触发——这正是 10-30 没被自动拦住的原因。
