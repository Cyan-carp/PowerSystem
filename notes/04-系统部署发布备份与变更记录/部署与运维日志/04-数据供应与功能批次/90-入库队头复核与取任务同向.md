# 入库队头复核与取任务同向（90）

> 承接 [[88-入库取任务改为最新优先]] 与 [[89-energy不确定性探针只看已处理行]]。本批修的是 88 留下的回归：取任务方向改了，事务内复核没跟着改。

## 一、症状：调度器照常转，但一条都进不去

2026-11-03 23:14 发布 89 后观察到：

| 观测项 | 值 |
| --- | --- |
| `last_device_id` | 15:28:44 仍在推进（UTC，下同） |
| 最近 10 分钟处理数 | **0** |
| 最后一条成功处理 | 14:38:21（88 发布前 7 分钟） |
| 网关 `tdengine_batch_written` | 正常，15:25:30 仍在写 |
| api 日志 | 无 error、无 warn 失败项 |
| DB 活动会话 | 只有 `idle / ClientRead`，没有卡住的 SQL |

表面现象互相矛盾：数据在进（`received_at` 追到 15:26:51）、游标在动、日志干净，但成功数不动。这是最容易误判成「上游没供数」的形态——当天早些时候也确实这样误判过一次。

## 二、根因：两处排序方向不一致

`inboxHeads`（取任务，88 改成最新优先）：

```sql
ORDER BY device_id, id DESC LIMIT 1     -- 每设备取最新一条
```

`server.go` 事务内复核（88 没改，仍是最旧优先）：

```sql
SELECT id FROM telemetry_inbox
WHERE device_id=? AND processed_at IS NULL ORDER BY id LIMIT 1   -- 每设备取最旧一条
...
if head.ID != item.ID { return errInboxDeferred }
```

积压 940 万条时，每设备最旧一条永远是 10-30 的行，而取任务给的是 11-03 的新行，两者必然不等 → 每条样本都返回 `errInboxDeferred`。这个错误走的是静默分支：

```go
case errors.Is(err, service.ErrInboxTerminal), errors.Is(err, errInboxDeferred), errors.Is(err, errDependencyOpen):
    // 故意不分类型处理：不打日志、不写 business_state、不计 attempts
```

所以「选行 → 加锁 → 复核失败 → 静默丢弃」每轮回一遍，游标照常推进，看起来一切正常。

**为什么没有测试拦住**：`inboxHeads` 与复核是两条独立 SQL，前者是常量拼接、后者写在 `server.go` 里，没有任何断言要求两者同向；当时的用例也只覆盖单条路径。

## 三、修复

1. 复核改成 `ORDER BY id DESC LIMIT 1`，抽成常量 `inboxHeadProbeSQL`，与取任务放在同一个包的相邻位置并写明「方向必须一致」。
2. 新增 `telemetry_head_order_test.go`：断言常量含 `ORDER BY id DESC`、且不含 `ORDER BY id LIMIT`，防止再退回最旧优先。
3. 其余逻辑（事务、锁、TD 核对、告警判定）一行未改。

## 五、结论与后续

- **历史积压不用再删**：新数据已能正常处理，旧行随最新优先自然沉淀，不需要再经历一次 3 小时表锁删除。9.4M 仍占空间，按当前 120 条/秒的净消化速度约一天量级逐步下降，但会先撞 10-30 的 TD 空洞，单设备会在那里停 10 分钟转隔离。
- **11-01 / 11-02 的发电量仍是空**：这两天的消息还在积压里没轮到，等队列下探到那一段才可能补出数，不能承诺。
- **教训（已写进代码注释与测试）**：凡改动「按哪个方向取一批」的语义，必须同批检查所有「我还是不是那一条」的复核点；静默降级分支不会自己报警。
