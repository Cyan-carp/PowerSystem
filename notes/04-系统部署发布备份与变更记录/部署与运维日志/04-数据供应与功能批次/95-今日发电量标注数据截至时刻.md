# 今日发电量标注数据截至时刻（95）

> 承接 [[94-日聚合按上次重建时间轮转]]。94 修的是「算得慢」，本批修的是「看不出慢」：页面上的今日发电量没有任何时点提示，用户会默认它是实时值。

## 一、改了什么

| 层 | 改动 |
| --- | --- |
| `internal/energy` | `Summary` 增 `OldestTodayAt`：当天有有效段的设备日里**最旧**的 `updated_at`（同一条 SQL 里加 `MIN(...)`，不新增往返） |
| `internal/api` | 总览摘要新增 `energy_oldest_at`；原 `energy_updated_at`（全表 `MAX`）保持不动 |
| 前端 | `Summary` 类型加字段；总览「今日发电量」标签后显示「数据截至 HH:MM」；新增 `.stat-note` 小字样式 |

**为什么取最旧而不是最新**：`MAX` 只会告诉你「最强的那台刚更新过」。恰恰在出问题时——某台设备落后 40 分钟——`MAX` 仍显示「刚刚」，标签就变成了误导。取 `MIN` 才能给出真正的下界。

副作用说明：`MIN` 只统计当天已有 `segments_count>0` 的设备日。若某台设备当天完全没出段，它不参与取最小值，标签会偏乐观；这属于「历史空日」的已知缺口，本次不处理。

**没有做的页**：前端没有发电量报表页（`energy-report` 接口目前只有后端与助手在用），所以标注只落在总览首屏一处。

## 四、未完成：服务器端发布记录没有回填

激活成功后、执行记录脚本之前，VM117 的 **QEMU guest agent 掉了**：`qm agent 117 ping` 连续 5 分钟 DOWN，`qm guest exec` 全部超时。SSH 直连（root/admin/debian）均 `Permission denied (publickey)`，因此**没有第二条进 VM 的通道**。

另外查到一条易误判的事实：本机 `~/.ssh/config` 里的 `home-dev`（`8.138.42.212:6002`）现在落到的是 **Windows 主机 `DESKTOP-LHHD9GR\admin`**（`OpenSSH_for_Windows_9.5`），不是 VM117。所以 `docker --context home-dev` 也一并失效——它不是备用通道，是一条漂移了的旧配置。

后果与现状：

- 容器已经在跑新镜像（上节已验证），但 `/opt/powersystem/runtime/production-stack/active.json` 仍指向 `energy-order-20261105-r1`，候选目录 `releases/energy-clock-20261105-r1/` 停在没有 `manifest.json` 的半成品状态；
- 站点与业务不受影响，受影响的是**发布台账**：本批没有 `owner-acceptance-without-gates.json`、没有 `manifest_sha256`，回退基线只能按镜像 ID 手工比。

**待补**（guest agent 恢复后一条命令即可）：把候选目录的 `manifest.json`、`owner-acceptance-without-gates.json`、`acceptance-pointer.json` 与 `active.json`/`previous-active.json` 写全；脚本已在本次会话准备，参数固定为两个镜像 ID 与本批快照/回执。

## 五、发布工具链该不该修：该，但只修两处

`production-stack.py` 现在坏在「账本不可信」而不是「发版能力消失」——镜像构建、compose 激活都能手工完成（本批就是），坏的是 `immutable()` 因为清单里一个已不存在的 `agent-rag` 镜像先失败，连带 `prepare`/`publish`/`rollback`。判据是：不修会不会持续付出代价。会——每批手工拼清单约 20–30 分钟，且 `manifest_sha256` 必须现算，抄错就 `active_manifest_changed`；同时 `rollback` 失去一键回退。

按投入产出排，只做两件：

1. **补账（一次性，10 分钟）**：用实际运行镜像重建 active 清单的 `images` 映射并重算 `manifest_sha256`，让 `immutable()` 重新可通过。不必找回原 `agent-rag` 镜像，也不必 `docker commit` 造假 ID。
2. **先记账后激活（结构性，约 30–60 行）**：今天真正的坑是「激活成功后才能在 VM 内写记录，通道一断就变成动作已发生、账没记」。改成激活前先落盘预期 manifest 与 pointer、激活后只追加 `activated.json` 确认；最坏情况由「做了没账」变成「有账没做」，后者 `status` 能查出来并可纠正。

不做的部分：不重写发布器、不新增门禁、不为了「第二条通道」另开隧道——`home-dev` 那条 SSH 已漂移到一台 Windows 主机，修它属于另一件事。
