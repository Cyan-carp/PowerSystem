# 今日发电量标注数据截至时刻（95）

> 承接 [[94-日聚合按上次重建时间轮转]]。94 修的是「算得慢」，本批修的是「看不出慢」：页面上的今日发电量没有任何时点提示，用户会默认它是实时值。

## 一、改了什么

| 层 | 改动 |
| --- | --- |
| `internal/energy` | `Summary` 增 `OldestTodayAt`：当天有有效段的设备日里**最旧**的 `updated_at`（同一条 SQL 里加 `MIN(...)`，不新增往返） |
| `internal/api` | 总览摘要新增 `energy_oldest_at`；原 `energy_updated_at`（全表 `MAX`）保持不动 |
| 前端 | `Summary` 类型加字段；总览「今日发电量」标签后显示「数据截至 HH:MM」；新增 `.stat-note` 小字样式 |

**为什么取最旧而不是最新**：`MAX` 只会告诉你「最强的那台刚更新过」。恰恰在出问题时——某台设备落后 40 分钟——`MAX` 仍显示「刚刚」，标签就变成了误导。取 `MIN` 才能给出真正的下界。

副作用说明：`MIN` 只统计当天已有 `segments_count>0` 的设备日。若某台设备当天完全没出段，它不参与取最小值，标签会偏乐观；这属于「历史空日」的已知缺口，本次不处理。

**没有做的页**：前端没有发电量报表页（`energy-report` 接口目前只有后端与助手在用），所以标注只落在总览首屏一处。

`production-stack.py` 坏的从来不是「发版能力消失」——镜像构建、compose 激活都能手工完成；坏的是账本与校验链。按投入产出只动三处，其中两处已落地：

| A · `--skip` + `deviation` | **已做并安装到服务器**：`publish --skip {identity,environment_match,https_wss}`，有 `--skip` 必须给 `--deviation`，回执写入 `skipped`/`deviation`/`profile=deviation`，另落一份 `deviation-*.json` |
| B · `immutable()` 镜像降级 | **已做并安装**：本批替换的服务仍要求镜像在库（不在库即 `fixed_local_image_required:<服务>`）；非替换服务允许镜像已被裁剪，条件是仍有容器以该 ID 运行，且记入回执 `pruned_images`；既不在库又无容器运行则报 `pruned_image_not_running:<服务>` |
| 先记账后激活 | 未做 |

**B 的实测（2026-11-06 01:0x，VM117）**：`immutable`/`accepted`/`current_matches` 全部通过，`status` 自动列出 `pruned_images=[agent-rag]`；反向三例均按预期拒绝（把该服务声明为本批替换、编一个既不在库也无容器的镜像 ID、镜像存在但 ID 不符）。

**A 已落地（外部服务）**：编排快照缺的 `ai-trainer`（11-02 起在跑，定义在 `stages/04-frontend/deploy/compose.yaml`，运行命令由 23 个 `-f` 叠加）不再整链报错。规则改为：编排声明但没跑 → `project_service_missing:<服务>` 仍致命；在跑但编排没声明 → 记为 `external_services` 放行，且不允许出现在本批替换集里（`external_service_cannot_be_released`）。配套跳过三处按 `config['services'][service]` 取值的遍历（匿名卷固定、端口/持久卷核对、环境比对），清单 `images` 补上外部服务的实际镜像。

**prepare 越过两道，停在第三道**：`project_service_set_changed` 已解，现在停在 `running_baseline_drift` —— 02:52 的定时全备做了 pause/resume，重启了 `gateway`/`agent-rag`/`ops-agent` 三个写者（ID 与镜像不变，只有 `started_at` 变）。这属于设计内行为，`maintenance_states_match` 本就允许这三个服务重启；正规修法是 `verify-backup --backup <archive>` 重签基线，它返回 `fast_baseline_missing`。

**回执卡住的根因：定时全备连续 6 天失败**。最近可用密文是 10-30 批次（10-31 03:01 完成，2.3 GB）；此后 10-31 `release_assets`、11-01~11-04 `disk_headroom`（可用空间低于 4 GB 门槛，秒失败）、11-05 `queues_snapshot`（耗时 505 s，其中 `postgres_dump` 单项 395 s）依次失败。当前 `/dev/sda` 已有 72 GB 余量（63%），`disk_headroom` 不再是瓶颈，但 11-05 的失败点变成了队列快照，未取到 stderr（journal 无记录）。这条与发布链无关，但比发布链更值得先修：**现在没有 6 天内的恢复点**。

**A 与 B 的分工**：`--skip` 故意不含 `immutable` —— 它是账本地基，跳过等于让指针描述一份没人验过的清单。所以「跳过某个验收」用 A，「让账本能容纳已消失但仍在跑的镜像」用 B。两者都做完，`prepare` 的前两步才真正跑通。

控制器变更影响：`controller_sha256` 由各候选在冻结时各自记录，不追溯历史版本；旧脚本备份为 `stages/04-frontend/deploy/production-stack.py.bak-20261106T0045Z`（sha `30242076…`），新脚本 sha `fce60820…`。
