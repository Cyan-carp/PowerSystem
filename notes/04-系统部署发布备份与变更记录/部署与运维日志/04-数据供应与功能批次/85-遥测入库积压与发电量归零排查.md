# 遥测入库积压与发电量归零排查（85）

> 本页只记录 2026-11-03 的排查过程与实测证据，不改活动指针。生产当前状态见 [[00-当前系统状态]]。

## 一、触发

2026-11-03 14:53，在智能助手（08-agent-rag）提问「哪个场站今天出力下降最明显？」，回答没有结论，直接把查询参数和后端原始汇总贴了出来：

```
查询条件：{"start_date": "2026-11-03", "end_date": "2026-11-04", "scope": "all",
          "group_by": "station", "format": "csv"}
后端发电量汇总（空值表示缺失）：{"groups": [{"record_type": "group_total",
  "station_code": "PV-01", ..., "kwh": null, "complete": "false"}, ...],
  "missing_device_days": 143, "summary_truncated": false}
```

`missing_device_days=143` 表示全场 143 台设备当天都没有有效发电量。

## 二、表层原因：助手用模板覆盖了回答

`stages/08-agent-rag/rag_agent/v4.py` 的 `finish()` 中，只要本轮 `result['reports']` 非空，就无条件执行：

```python
result.update(answer_markdown='\n\n'.join(lines))
```

`lines` 由固定模板拼成，其中包含 `json.dumps(report['energy_summary'])`。模型自己生成的解释在这之前已被丢弃，也没有对 `complete=false`、全部 missing 做任何判断。

调用点：`rag_agent/engine.py:199`，`guarded = v4.finish(...)` 返回 True 即视为定稿。

## 三、数据原因：`energy_daily` 从 10-31 起没有任何有效段

生产库实测（`energy_daily`，按天统计有行数与 `segments_count>0` 的设备数）：

| 日期 | 有行设备 | 有效段设备 |
| --- | --- | --- |
| 2026-10-28 | 143 | 143 |
| 2026-10-29 | 143 | 143 |
| 2026-10-30 | 143 | 143 |
| 2026-10-31 | 143 | **0** |
| 2026-11-01 | 143 | **0** |
| 2026-11-02 | 143 | **0** |
| 2026-11-03 | 142 | **0** |

`energy_daily` 由 `internal/energy/energy.go` 的 `rebuildDay` 从 `telemetry_inbox` 聚合，条件为 `business_state='success' AND processed_at IS NOT NULL`。有行无有效段，说明当天所有设备都聚合不出样本，不是统计口径问题。

## 四、根因：入库队列积压 891 万条，处理到的都是 10-30 的旧消息

### 4.1 入库成功率

`telemetry_inbox` 按 `processed_at` 分天的状态分布：

| 日期 | 总数 | success | quarantined | retry |
| --- | --- | --- | --- | --- |
| 2026-10-30 | 480,215 | 465,627 | 14,588 | 0 |
| 2026-10-31 | 19,615 | **0** | 19,615 | 0 |
| 2026-11-01 | 19,877 | **0** | 19,877 | 0 |
| 2026-11-02 | 19,734 | **0** | 19,734 | 0 |
| 2026-11-03 | 5,863 | **0** | 5,863 | 0 |

近 30 分钟的失败码只有一个：`failure_code='td_missing'`，`attempts=14`，最早失败时间 `2026-11-03 06:00:05Z`。

`td_missing` 的判定在 `internal/api/server.go:538-549`：入库前先 `s.td.HasSample(device_id, ts, seq)`，TDengine 里查不到该条就判缺失，14 次后退避期到点转 `quarantined`。

### 4.2 队列积压

```sql
select coalesce(business_state,'(pending)') st, count(*),
       min(ts_ms), max(ts_ms) from telemetry_inbox
where processed_at is null group by 1;
```

| 状态 | 条数 | 最早消息 | 最新消息 |
| --- | --- | --- | --- |
| pending | **8,917,744** | 10-30 13:51 | 11-03 15:20 |
| retry | 143 | 10-30 13:51 | 10-30 14:01 |

即：**从 10-30 13:51（北京时间）起，入库队列积压 891 万条未处理，且仍在增长**。每天被处理掉的约 2 万条全部来自这段积压的头部。

### 4.3 被判缺失的样本在 TDengine 里确实不存在

取一条被隔离的样本（device 273、`ts_ms=1793339483864`、`seq=124584`、今天 07:13 处理）：

```sql
select to_iso8601(1793339483864);  -- 2026-10-30T05:51:23.864+0000
select ts,seq from powersystem_stage2.t_device_273 where ts=1793339483864;  -- 0 rows
select ts,seq from powersystem_stage2.t_device_273
  where ts >= 1793339400000 and ts <= 1793339520000;  -- 0 rows
select min(ts),max(ts),count(*) from powersystem_stage2.t_device_273;
-- 2026-10-20 14:30:38.295 | 2026-11-03 07:20:01.053 | 175730
```

该表跨越 10-20 到 11-03，库 `keep=365d`（`information_schema.ins_databases`），不是保留期删除。10-30 05:51 这一段是**真空洞**：网关当时没有把这段写进 TDengine，而 api 的 inbox 收到了。

结论：**不是 seq 口径错位**。序列号差异（TD 最新 186914 vs inbox 124584）只是"TD 已写到 11-03、inbox 还在处理 10-30"的表象。真实原因是入库吞吐崩溃后，队列里 10-30 那段永远核对不上，卡在队头反复重试并逐步隔离，后面的数据排不上来。

## 五、影响面

- 发电量：`/reports/energy`、总览发电量、助手 `business_report(kind=energy)` 全部只能返回缺失。
- `energy_daily` 无有效段 → 依赖它的可用率/预测/健康类派生统计同样失真。
- 预测、告警：取决于各自是否直接读 TDengine；TD 里有实时数据（07:20 仍在写），读 TD 的路径未受影响；读 inbox 派生表的路径受影响。
- 未影响 TDengine 写入本身：网关日志持续输出 `tdengine_batch_written`，且该设备 max(ts) 追到 11-03 07:20。

## 六、本轮没有做的事

- 没有清空或截断 `telemetry_inbox` 积压（891 万条属历史数据，放弃需所有者定明确截点）。
- 没有修改入库代码、没有重启任何容器、没有改 TDengine 配置。
- 没有改助手的模板渲染（属第二项待办）。
