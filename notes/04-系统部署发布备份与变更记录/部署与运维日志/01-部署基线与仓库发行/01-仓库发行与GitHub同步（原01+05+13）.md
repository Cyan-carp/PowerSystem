### 公开仓库与服务器安全审查

远端 `main`、`dev` 的 45 个可达提交按私钥头、GitHub 令牌、AWS 密钥和飞书机器人 Webhook 常见格式扫描，均为零命中。当前候选的 199 个文本文件按常见凭据格式扫描未命中；服务器现用的 9 项密码、签名、令牌和备份口令与候选文本逐项比对未命中；跟踪文件名未见 `.env`、私钥、数据库转储或备份包。扫描是给定模式和范围内的检查，不等于对所有秘密形式的保证。

远端两分支均无 `.github` 工作流；GitHub 公开 API 所列阶段一、二、三三个 Release 均没有上传资产，未发现可下载的配置包或数据库包。公开源码本身不会自动执行个人服务器部署。服务器的 SSH 密码登录已关闭；数据库、MQTT、API 和监控服务未直接映射公网。旧地址、FRP 端口和备份路径属于可见的攻击面线索，但目前未发现可据此直接登录或控制服务器的凭据。尚未取得 GitHub 仓库设置、协作者、Webhook、分支保护和 Deploy Key 的管理端核对结果；这些权限设置应由仓库所有者在发布前或发布时检查。对有写权限的人执行高权限部署仍会运行其代码，须固定审查过的提交。

### 仍阻止第一版正式发布的事项

项目所有者明确回复：异地加密备份的**独立离线解密口令副本尚未完成**，稍后自行处理。当前口令仅在 R730xd；整机丢失时，只有云端密文不能恢复。工程内 `备份口令离线交接与整机恢复步骤.md` 给出不向仓库或聊天披露口令的交接及 `MATCH` 核对方法。在所有者确认副本位于 R730xd 以外且核对显示 `MATCH` 前，M4 不能最终签收，也不应推送第一版、合入远端 `main`、打标签或创建 GitHub Release。

完成该步骤后，先重新 `fetch` 并复核两远端引用、提交树与敏感信息，再把本地候选推送到 `dev`、合并至远端 `main`、创建第一版标签和 Release，最后核对公开内容及部署提交 SHA。视频复盘和对外材料不属于第一版主业务门槛。
