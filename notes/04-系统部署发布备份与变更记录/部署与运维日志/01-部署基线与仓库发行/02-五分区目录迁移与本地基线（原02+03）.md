## 原日志 02 · 五分区迁移后的兼容修复（2026-10-13）

> 2026-10-13：修复本机五分区迁移后的知识来源、容器文档挂载、发布/备份兼容和真实失效链接。本轮只改本地文件，未部署服务器、构建真实镜像、导入知识或提交Git。

### 一、已修复内容

| 项目 | 修复与边界 |
| --- | --- |
| 阶段7/8知识来源 | 物理path改为手册/资产/内容，title保持原文档逻辑标识 |
| 阶段7构建器 | 文档/片段标识采用逻辑title；未改现有index.json |
| 阶段8生产挂载 | 新宿主路径与容器/documents路径均对齐同版本来源清单 |
| 阶段8发布基线 | 优先新规范/内容目录，保留旧布局读取；缺必需文档先失败 |
| 阶段8候选镜像 | 包内更新的scripts/knowledge随镜像复制；旧增量包沿用基线未变文件 |
| 阶段7发布/同步 | 新公用Markdown、版本内容、设备参考进入对应有限白名单；不开放任意部署代码或资产 |
| 手册安装与备份 | 优先05-设备知识设计素材与历史归档资产/设备知识清单，旧布局回退；服务器运行目录不迁移 |
| 文档链接 | 8处实际目标存在但相对层数错误的链接已逐项重算 |

兼容不是整仓库发布权限扩大。私有目录、runtime、artifacts、凭据及原始数据仍拒绝进入发布包；历史包、失败记录和签收数字不改写。路径回退只服务尚未迁移的服务器，新清单存在但无效时不偷偷采用旧材料。

### 二、运行数据与归档

- `artifacts/历史归档/`仅为本机历史压缩包归档。
- 服务器继续使用`/opt/powersystem/runtime/`及现有私有配置的实际挂载源，保存模型、审计、知识缺口和发布材料。
- `stages/`保存代码；知识来源搬迁不等于索引重建。后续部署必须将新来源实体、清单和Compose作为同一候选核对，本轮不执行该发布。

工程约定已并入[[02-工程规范边界与验收治理/项目工程规范/00-索引·项目工程规范]]，避免将服务器runtime统一替换成资产归档。

### 三、本地验证

13项离线兼容测试通过，覆盖新旧/混合布局、缺文档失败、完整挂载与清单对应、逻辑ID保持、发布白名单与私有拒绝、候选Dockerfile生成、旧增量包、真实Bash路径选择和运行路径保持。Docker、Git打包均为fixture模拟，没有接触真实daemon或改Git索引。

五个修改Shell脚本的bash -n语法检查通过；全库文档链接、JSON/YAML和Python语法由本轮审计核对。软件兼容检查不代替真实服务器发布、知识重建、回退或备份恢复验收，不增加MA/SEC业务通过数。

首次测试的Windows默认临时目录ACL及沙箱Bash启动限制是测试环境问题；独立项目测试目录与获准离线复验后通过，没有修改业务逻辑以绕过权限。失败摘要和独立重跑日志保留。

### 四、证据与后续

私有批次artifacts/根目录布局兼容-20261013/保留654份公开文件初始摘要、原文件副本、初始Git索引记录、8处链接映射、测试日志和最终审计/变更清单。该目录被Git忽略，不包含服务器运行成果。

现有暂存/未跟踪改动仍混合保留，本轮不重置、不重新整理用户暂存区，也不提交或推送。MA-M4仍延期，安全Agent仍规划；实际部署与知识变更按原授权、候选冻结和独立验收流程另行开展。

## 原日志 03 · SEC-M3 开发前本地回滚基线（2026-10-13）

> 2026-10-13：按所有者明确指令整理目录迁移和既有开发成果，固定本地开发检查点。该检查点不是新阶段签收或服务器发布。

### 一、版本与范围

- 基线附注标签：`pre-sec-m3-20261013`；完整提交SHA由标签解析，避免在提交正文中引用自身尚未生成的SHA。
- 本地功能分支：`feature/stage10-sec-m3`；提交说明：`chore(baseline): 固定目录重构及SEC-M2本机验收基线`。
- 收纳最终目录布局、既有阶段7～10及前后端开发、部署兼容修复、测试与笔记；SEC-M3仍只有既定规划，不记为实现或签收。
- 不推送Git、不合并main、不发布服务器、不导入知识、不开放写窗口。

### 二、提交检查与整理

初查715个候选文件、336个未跟踪文件；29个索引旧路径均找到迁移后的最终文件，未发现实际丢失。重新暂存最终状态，避免单独提交迁移中间索引。

部署路径的LF规则随目录迁移同步；Obsidian备份workspace从索引移除并忽略，本机原文件保留。其他既有Obsidian配置不因本轮改动而迁移或修改。

初查已取得25个私有凭据值及所检查敏感格式均未命中；暂存后重新核对实际Git对象。SEC-M2最终运行清单116个文件逐项同摘要；225篇笔记的双链初查仅有工程规范示例占位链接，没有实际断链。运行材料、密钥、截图、原日志和数据库仍不入Git。

### 四、整理中发现的问题

完整暂存后发现13处既有文件末尾空行：12篇笔记及阶段9的platform.py。初查未跟踪内容未进入diff --check范围，不能以初查通过替代最终暂存门禁。已保存原文件，清理末尾空行；唯一运行源码改动的前后Python语法树一致，内容仅少一处末尾空行。SEC-M2原116份运行清单仍保留原摘要，最终基线115份逐字同摘要、1份格式变化独立登记，不把新字节摘要冒充旧候选。

首次暂存命令列入已不在索引中的第一版旧目录而失败，没有丢失文件；按当前跟踪删除及最终现有路径重建暂存后完成。相关失败与原索引保留私有审计，最终以实际Git对象的检查结果判断。

### 五、回滚与后续

标签只固定源码、配置模板与可公开笔记，不包含私有运行配置、任务/审查数据库、向量数据或容器卷。核对标签目标与本地提交后才作为代码回退入口；实际回退需先保存后续工作，不能用重置工作区替代数据库迁移方案或生产发布流程。

私有整理材料归`artifacts/安全阶段前基线-20261013/`，含原文件副本、初始索引、最终暂存审计与提交/标签核对。Git忽略该目录，保留失败及正式运行证据。

后续SEC-M3沿用已确认的本机隔离验收、现有证据规则，不新增资源告警阈值。安全前三阶段签收后先SEC-M4本地集成，再评估MA-M4发布；本检查点不启动第四阶段。
