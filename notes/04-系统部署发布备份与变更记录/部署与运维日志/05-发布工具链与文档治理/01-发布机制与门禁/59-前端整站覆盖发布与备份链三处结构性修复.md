# 59 · 前端整站覆盖发布与备份链三处结构性修复

> **版本归属**：V4 第四版维护。现行指针只认 [[00-当前系统状态]]。本轮不改变生产 R0 权限档位，不新增动作、调度或写入开关。

## 一、实际问题与归因

本轮目标是把 2026-10-29 完成的前端整站覆盖（`stages/04-frontend/src` 独立浅色版 + 八轮能力补齐）发布到生产 VM117。源码先完成两次提交：`72c3f5b`（749 文件，含笔记目录与界面规范同步）、`c2d10a5`（`source-build.py` 必需文件清单修正）。

发布链上连撞六个阻塞，**没有一个来自前端产物本身**，其中三个是备份链的结构性缺陷：

1. **导出失败 `source_v4_files_missing`**：`source-build.py` 的 `REQUIRED` 仍列 `src/views/AgentSchedulesView.vue`，整站覆盖后该视图已并入 `SchedulesView.vue`。
2. **`prepare` 被 `undeclared_environment_change:gateway` 拦下**：服务器 `compose.yaml` 的 `gateway.environment` 仍是 `STAGE2_DATA_DIR=/data` 且缺 `MQTT_CLIENT_PREFIX`，而父版冻结与运行容器实际 env 都已是 `/data/fresh-20261029-r1` 与 `powersystem-stage2-fresh-20261029-r1`。这是 10-29 那次 gateway 快发布只改 runtime 未同步模板的结果——**模板落后于运行值，不是运行态漂移**。
3. **`queues_snapshot` 打不开 gateway 库**：`snapshot_queues.py` 写死 `/source/gateway/gateway.sqlite`；gateway 已于 10-29 把数据目录迁入同卷的 `fresh-20261029-r1/`，卷根留着 WAL 但缺 `-shm` 的旧库。
4. **同一阶段第二次失败，原因是「库是静止的」**：备份在 `postgres_dump` 阶段用 `telemetry-maintenance.py pause` 停掉 gateway，等快照时那是一个**被干净关闭的 WAL 库**（无 `-shm`、无 `-wal`）。实测：`mode=ro` 报 `unable to open database file`，`mode=ro&immutable=1` 可读（303 页）。所以选对文件还不够，读法也要跟着状态变。
5. **`release_assets` 校验旧源码快照失败**：`REQUIRED` 改成新文件名后，10-29 改名之前冻结的快照（557/558/577/614 文件各版）一律校验不过；而 `release_assets` 正是用 `verify_receipt` 校验运行镜像对应的历史快照。
6. **收尾健康闸门与 api 的 fail-closed 相撞**：api 的 `/api/v1/ping` 在遥测未就绪时**按设计**返回 503（`telemetry_s02_test.go` 专门锁这个行为），维护窗口一旦超过健康检查的重试预算（12×10s），api 就被标成 unhealthy；恢复网关后健康结论要等下一个探测周期才刷新，而备份紧接着的 `backup_maintenance_snapshot(after=True)` 先过 `healthy()`，读到的正是那个过期结论。**自 api 改成 fail-closed 之后，全量备份结构性跑不完**——之前一直被前三个 bug 挡在前面，看不出来。

另需记明两点：10-28 18:35 那次定时备份失败在 `disk_headroom`，不是盘位不足（当时可用 130 GB，门槛 `POWERSYSTEM_BACKUP_MIN_FREE_KB` 默认 4 GiB），属当时环境变量抬高门槛所致；本批开工时**没有任何可用的新全量基线**，`frontend-fast` 快路径也因最近全备超出 24 小时而不可用，只能走 `full`。

## 四、备份恢复与回退边界

本轮**新建了全量基线** `powersystem-20261029T183003Z`（1.99 GB，双端上传齐全、带回执与 V4 维护回执），它是本次发布的唯一恢复点；前端发布本身不是数据备份，不能外推为 EMQX/Grafana/Prometheus 卷或非前端镜像已增量备份。

回退资产完整保留：直接已验父版 `tr-gateway-fresh-20261029-r1` 及其 `accepted-1793293876628055411…` 等历史门禁、原 R0 前端镜像 `79b8bce4…`（带保留标签）、`r1`—`r5` 五个未发布候选、14 份冻结源码快照。失败只走 `production-stack.py` 直接父版回退，不降表、不恢复业务数据、不直接启动已产新数据后的源宿主旧副本。

**本轮新增的两条已知限制，必须在下次发布前复核**：

1. api 的 `/api/v1/ping` 在遥测维护期返回 503 是**设计行为**（`telemetry_s02_test.go` 锁定），因此「维护窗口 → 恢复后立即要求全健康」这条链路天生有时序竞态。现已由 `backup.sh` 的 300 秒有界等待覆盖；若将来维护窗口显著变长或 api 恢复更慢，需重新评估该预算，而不是放宽 `healthy()`。
2. 服务器 `stages/04-frontend/deploy/` 与仓库并不同步（本轮缺 `telemetry-repair.py`）。**只下发单个脚本会引入对它不存在兄弟文件的引用**；今后改动 backup.sh 一类聚合脚本时，必须同时核对该脚本引用到的全部同目录文件是否在场。
