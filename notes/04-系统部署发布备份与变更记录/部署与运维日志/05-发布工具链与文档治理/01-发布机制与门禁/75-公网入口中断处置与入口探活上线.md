# 75 · 公网入口中断处置与入口探活上线

> 本批不是发布，没有镜像变更、没有改 schema、没有动数据。它记录一次**公网入口 10 小时 42 分不可用**的处置，以及同批补上的入口探活。生产指针与发布状态见 [[00-当前系统状态]]。

## 一、事件

| 项 | 事实 |
| --- | --- |
| 现象 | `https://www.cyancarp.cn/` 与 `/api/v1/ping` 均返回 **502**；本地 5173/8080 正常 |
| 起始 | 2026-11-01 03:44:18 CST（新云 nginx error.log 首条 3667 拒绝） |
| 发现 | 14:24 CST，所有者报告「网页进不去」 |
| 恢复 | 15:02 CST 左右，所有者按指引修改轻量防火墙后隧道重连 |
| 持续 | 约 10 小时 42 分 |
| 业务影响 | **仅在公网入口**。19 个容器全程 healthy，供数、告警、写入、模型链路未受影响；无数据丢失 |

## 二、根因（两层，缺一不可）

**第一层 · 出口 IP 变化**

R730XD 出口由 `120.82.32.121` 变为 `120.82.32.222`（家宽重拨）。轻量应用服务器防火墙的 7000 入方向只放行旧 `/32`，客户端 SYN 连新云网卡都到不了。

证据链：nginx 反代 `127.0.0.1:3667` → 3667 无人监听 → VM117 `frpc-primary` 每 20 秒 `dial tcp 8.138.42.212:7000: i/o timeout` → 新云 `tcpdump` 抓 7000 端口 **0 个包** → 排除主机 iptables（计数器零增长），锁定云侧。

**第二层 · 自动维护已失效 4 天**

`powersystem-source-refresh`（1.1.1 SAS）本应在换址后自动改防火墙，但它从 **2026-10-28 10:45** 起每分钟失败，失败码 `non_target_cloud_change`。逐条排除定位到具体规则：

```
MATCH_WITHOUT: d5c2f320bead40f59f20674972767619  6000/6050  备用主机
```

即 10-16 建立基线之后，防火墙新增了一条 `6000/6050`（frp-remote 用）。机制把「非目标规则变化」视为入侵并把自身锁死，于是换址时无人接管。**触发器早已损坏，这次只是被 IP 变化引爆。**

## 三、处置动作

| # | 动作 | 位置 | 可回退性 |
| --- | --- | --- | --- |
| 1 | 放行当前出口 `120.82.32.222` 到 7000（所有者操作） | 轻量控制台 → 防火墙 | 删规则即回退 |
| 2 | 临时补一条主机规则验证；随后发现它破坏「目标规则唯一」，已由第 3 步清理 | 新云 `POWERSYSTEM_EDGE` 链 | 已清除 |
| 3 | 把持久化来源文件改为 `.222` 并用 `powersystem-edge-firewall` 重建链 | `/etc/powersystem-edge/allowed-client-ipv4` | 备份 `/root/allowed-client-ipv4.bak-20261101` |
| 4 | 归档旧基线并重建，恢复自动对账 | `/var/lib/powersystem-source/` | 归档 `baseline-archive-20261101.json`（600，root:powersystem-source） |

第 3 步必要：该文件是**开机重建防火墙的唯一来源**。只改控制台不改它，云主机下次重启会按旧的 `121` 重建，故障复现。

第 4 步的约束：`reconcile.py:25` 硬校验 `baseline.json` 不存在才允许 `initialize`（`baseline_already_exists`）。README 明确禁止覆盖或删除基线。因此**不删除证据**：旧基线原样归档，新基线由 `initialize` 以当前状态生成。

## 四、A1 · 自动对账恢复后的核验

| 检查 | 结果 |
| --- | --- |
| `initialize` | `{"changed": false, "initialized": true}` |
| `check` | `{"pending": false, "ready": true, "sources_match": true}` |
| 新基线 | cloud `9bd98903…282b42`（旧 `2fd25b2a…b0994`）；host `2a72c2b5…c22c53` **未变**，说明主机侧一直正确 |
| 端到端 `client` | `{"allowlist_updated": true, "changed": false, "entry_recovered": true}` |
| systemd | `Finished`，不再失败 |

`host_policy` 未变这一点很重要：它证明这 4 天里主机 iptables 与基线一致，只有云侧多了一条规则。

## 五、B2 · 公网入口探活上线

**为什么放 VM117 而不是新云**：VM117 实测能直连 `https://www.cyancarp.cn/api/v1/ping` 返回 200，因此无需把飞书 webhook 复制到第三台机器，直接复用 `/etc/powersystem/` 下既有密钥。

| 组件 | 位置 |
| --- | --- |
| 探活脚本 | `/opt/powersystem-probe/entry-probe.py`（755，sha256 `46e64c20…6a2658`） |
| service / timer | `/etc/systemd/system/powersystem-entry-probe.{service,timer}` |
| 状态文件 | `/var/lib/powersystem-probe/state.json` |

**判定**：公网 `api`（需 `code=0` 且 `telemetry_ready=true`）与 `web` 均 200 为正常；另统计主通道 `frpc` 近 5 分钟 `connect to server error` 次数，≥3 即视为隧道异常——**这能在入口彻底中断之前先发现**。连续 2 次失败才告警，持续故障每 30 分钟重提醒，恢复时发一条恢复消息。

**自检（故障注入，非真实故障）**：副本指向不存在的接口连跑两次，得到 `alerted=false` → `alerted=true`；再指向正常接口跑一次，得到 `alerted=true` 并发恢复。告警与恢复两条分支均经真实飞书通道验证，无 `notify_failed`。自检产物已删除。

**现有告警为何全程没响**：10 条规则全部基于容器内指标（`up{job="api"}`、磁盘、遥测水位）。本次 api 一直健康，故障在它视野之外的「门外」，所以内部视角的探针天然测不到。

## 六、残留边界

1. **VM117 整体宕机时 B2 报不出来**（探针与被监测对象在同一台机）。云侧整机故障仍需外部拨测（阿里云站点监控或第三方），本轮未做。
2. **source-refresh 自身失效仍无告警**。它的失败只写 `/var/lib/powersystem-source/last-error.json`，这次安静坏了 4 天。建议后续把它纳入云侧监控。
3. 家宽出口仍是动态 IP。本轮只是把当前值写死，**下次重拨若自动对账再失效，仍会重复**。根治方向是 443 + SNI 分流，彻底摆脱 IP 白名单，尚未实施。
4. 防火墙里 `6000/6050`、`21`、`23`、`3306`、`1433`、`3389` 等对 `0.0.0.0/0` 开放，属历史遗留，本轮未动。
