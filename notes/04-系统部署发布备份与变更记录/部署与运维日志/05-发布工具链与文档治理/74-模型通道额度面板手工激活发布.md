## 三、为什么没有走 prepare

| 阻塞 | 具体原因 | 处理 |
| --- | --- | --- |
| `running_baseline_drift` | 实际 `started_at` 与上批回执不一致：gateway、agent-rag、ops-agent 三处在 10-30 18:55–18:56Z 被引擎重启刷新 | 新写 `running-state-reconcile-20261031.json`，只允许 `started_at` 变化；容器 ID、镜像、重启数任一不同即中止。原回执文件保留不动 |
| `undeclared_environment_change:gateway` | 候选编排来自 `v4-business-schedule-20261026-r1` 模板，gateway 前缀/数据目录与 simulator 的 `--window-mode on` 都是旧值 | 按 `docker inspect` 实测值写 `runtime-align.compose.json` 追加进参数链，保证冻结结果等于现网；这两个服务本批不重建 |
| `source_build_required:agent-rag:…` | `source-build.py build --service` 的白名单是 `{agent-rag, api, frontend, gateway, ops-agent, security-agent}`，**不含 agent(07)**；且 07/08 是基线镜像增量构建，工具无法生成回执 | 放弃 prepare，改为手工激活。manifest 以 `manual_activation` 字段如实标注，`source_builds` 留空数组 |

前两处是可对齐的环境事实；第三处是工具能力边界，无法在不改发布工具的前提下绕过。

## 五、激活

用 overlay 覆盖四个服务的 `image` 为完整 sha256，追加到参数链末尾，执行：

```bash
docker compose … -f activate.compose.json up -d --no-deps --force-recreate api frontend agent agent-rag
```

不修改服务器上的原编排文件。四个容器全部 `Recreated → Started`；api 约 30 秒转 healthy，agent-rag 约 60 秒转 healthy（08 要加载 embedding 模型），比状态页记录的 235 秒冷启动快，现场未见异常。
