## 原日志 33 · 分段计时与发布前短检（2026-10-22）

> 本次只改发布工具链：加分段计时、加发布前短检。不改任何门禁判定，不跳过备份、异地副本或回退验收。**尚未发布**，生产指针仍为 `ui-devcode-20261022-r1`。

### 一、结论先行

用既有证据（版本目录、备份文件 mtime、`up-*.log`/`https-wss-*.log`/`accepted-*.json` 的纳秒时间戳）把近三次发布拆开，结论比"总时长"清晰得多：

| 版本 | prepare→备份开始 | 备份生成 | 备份完成→开始重建 | 重建服务 | 门禁 | 总计 |
|---|---|---|---|---|---|---|
| `ui-paging-20261022-r1` | 0:32 | 5:08 | **20:28** | 0:55 | 0:09 | 27:12 |
| `ui-devcode-20261022-r1` | 0:21 | 4:57 | **4:31** | 1:30 | 0:09 | 11:27 |
| `interpretation-official-20261021-r4` | 0:44 | 4:57 | **3:37** | 1:49 | 0:10 | 11:16 |

三点判断：

1. **备份生成非常稳定**：4:57–5:08，三次波动不到 4%。它不是波动源。
2. **波动全部集中在"备份完成→开始重建"这一段**：3:37、4:31 和 20:28。27 分钟那次比另两次多出约 16 分钟，占它超出部分的 87%。这段包含两次异地 `scp` 上传，以及 `publish` 启动前的等待、650 MB 归档的 SHA256 校验。
3. **重建与门禁不是瓶颈**：重建 55 秒（只改前端）到 1 分 49 秒（五个服务）；门禁稳定 9–10 秒。

关于 27 分钟那次，现有记录**不能**断定就是上传慢：这段里也包含人工在备份完成后隔了多久才执行 `publish`，而备份脚本与控制器都没有留下这一点。这正是这次要补的计时：`upload_primary`/`upload_secondary` 的秒数，和控制器侧的 `prepare_to_publish_seconds`，可以直接把"网络慢"和"人手慢"分开。

另一个已经可以量化的事实是备份包本身：密文包 637–650 MB，其中多语嵌入模型目录实测 **469 MB**，占包体约 72%；每次发布都要把它重新压缩、加密、上传两遍，而它几乎从不变。这条是后续优化的最大杠杆，但按当前优先级先测量、后改动。

### 二、这次改了什么

#### 1. 控制器分段计时（`stages/04-frontend/deploy/production-stack.py`）

- 新增 `Timeline`/`Span`：每个阶段记 `name / offset / seconds / ok`，可附 `bytes`、服务数、资产数等标量；失败阶段额外记 `error`（`Blocked` 记原因码，其他只记异常类型）。
- 每个 phase 结束写一条 `runtime/production-stack/timing/<ns>-<phase>.json`（0600，原子替换，保留最近 200 条），成功与失败都写；失败时同时保留 `failed` 阶段名与原因码。
- phase 结束时 stdout 增加 `total_seconds / timing_file / slowest`，便于直接粘进发布记录。
- 新增 `timing --limit N` 只读子命令，列出最近记录的总时长、最慢 5 段，以及合并进来的备份摘要。
- 埋点覆盖：`prepare.resolve_active / confirm_running_baseline`；`freeze.origin_args / inspect_running / compose_config / pin_images / write_candidate / roundtrip`；`publish.resolve_active / confirm_baseline / candidate_manifest / verify_backup`（带字节数）/ `backup_ordering / drain / transaction_write / deploy / gate / activate`；`deploy.compose_up`（带 `up-*.log` 字节数与重建服务数）/ `nginx / registry_snapshot / registry_helper_load / registry_refresh / registry_verify / readiness`（逐服务距重建开始的就绪秒数）；`gate.immutable / inspect / identity / compose_config / environment_match / https_wss / final_inspect / persist`；`rollback.*` 全套。
- `publish` 会把 `backup.sh` 写的旁车记录合并进 `notes.backup`，并记 `prepare_to_publish_seconds`，所以一条 publish 记录就能覆盖"准备→备份→上传→重建→门禁"。

#### 2. 备份分段计时（`backup.sh` + 新增 `backup-timing.py`）

- 每个阶段落一行 NDJSON 到 `$run_id.stages.ndjson`，退出时由 `backup-timing.py` 合成 `$run_id.timing.json`（0600，与密文包同目录）。成功、失败都写；失败时带 `failed_stage`、`failed_line`，`EXIT` 里先写计时再清理暂存。
- 阶段划分：`preflight / disk_headroom / postgres_dump / tdengine_dump / queues_snapshot / model_copy / config_copy / agent_credentials / redis_snapshot / agent_audit / agent_knowledge / manuals / rag_vectors / rag_postgres / rag_model / rag_environment / ops_assets / production_state / staging_permissions / staging_manifest / compress / encrypt / archive_digest / upload_primary / upload_secondary / retention`。
- 字节数：每个阶段记产出物大小，另记 `staging_bytes`、`archive_bytes`；两个上传阶段记归档字节与 `megabytes_per_second`，这是判断"带宽不足"还是"单流受限"的直接依据。
- 新增 `disk_headroom`：开始前用 `df` 检查剩余空间，不足 `POWERSYSTEM_BACKUP_MIN_FREE_KB`（默认 4 GiB）就直接退出。原先空间不足要等到 dump 或加密阶段才炸，那时已经花掉大半时间。
- 只记录耗时、字节和阶段名，不落任何命令输出、路径或凭据；`--archive` 只存基名。

#### 3. 发布前短检 `preflight`

三项只读检查，放在**冻结候选之后、生成备份之前**：

| 检查 | 抓什么 | 上次踩的坑 |
|---|---|---|
| `preflight.private_layout` | 私有 env 必须在 `<ma-m4-*>/private/`，`private/executor/` 必须存在且有 `executor.json`，`ops-executor` 的 `/run/ma-executor` 挂载源必须与前者同一目录 | 2026-10-21 r2：新驱动把私有 env 移到新批次目录，冻结 helper 按父目录找 `private/executor/registry.json` → `FileNotFoundError`，备份做完才失败 |
| `preflight.asset_ledger` | 主机 `registry.json` 的容器资产版本不得超过 DB 已提交版本 +1 | 同日 r2：回退期间未提交版本连续递增，最终比 DB 高 3，触发禁止跳号冲突 |
| `preflight.migration_entry` | 从 **API 镜像内** `/app/deploy/postgres/*.sql` 取出真实迁移，按 `store.Migrate` 的规则（按 `;` 全切、逐段 TrimSpace 执行）复算：注释内分号、`$$` 块、切分后不能以 SQL 关键字开头的碎片都拒绝；并确认 `telemetry_inbox` 建表语句在包内 | 2026-10-21 r1：010 迁移注释里的分号被当语句执行，PG 报 5 次语法错，API 起不来，统一控制器回退，整轮白跑 |

调用点三处，保证不会被绕过：

1. `prepare` 末尾（`freeze` 内，写完 manifest 之前）——失败时**还没创建候选目录**，可以原 id 重跑；
2. `publish` 在 `drain` 之前再跑一次——已冻结的候选也不能跳过；
3. `preflight --id <release>` 独立子命令——可在备份前单独复核。

失败返回形如 `preflight:migration_split:010_interpretation_v2.sql:4:semicolon_in_comment`，直接指出文件和行号，不需要翻容器日志。

### 三、验证

- **离线单测 23 项全过**（`test_production_stack_preflight.py`）：现有 11 份迁移 + `backfill_energy.sql` 在真实切分规则下 0 问题；注释内分号、`$$`、字符串内分号、脏碎片四类反例均被拒绝；私有布局四种错位、账本三种异常、计时器成功/失败/慢段排序、旁车解析均覆盖。
- **服务器只读执行** `preflight --id ui-devcode-20261022-r1`：三项通过，`private_layout` 0.001 s、`asset_ledger` 0.25 s（24 项资产 / 20 个容器）、`migration_entry` 冷 11.4 s、热 2.7 s（12 个文件、67 条语句）；整条命令冷 14.0 s、热 5.2 s。相对 11–27 分钟的发布，这个代价可以接受；重跑一次仍全部通过。
- **备份计时机制冒烟**：用脚本自身的函数段跑成功/失败两条路径，成功时 `failed_stage` 为空，失败时正确记到 `upload_primary` 与行号，`staging` 与 NDJSON 均被清理。
- `bash -n backup.sh` 通过；`production-stack.py` 编译通过。

### 四、按证据强度排的优化候选（本次均未实施）

1. **上传（已证实）**：两次串行 `scp` 共 1.3 GB，正常约 4 分钟，异常 20 分钟。有独立计时后才能判断是链路降级还是单流限速；并行上传只是候选之一，还要确认带宽上限与两处目标的恢复校验是否等价。
2. **静态载荷（已量化）**：469 MB 模型占包体 72%，每次重传不变内容。可行方向是把它做成内容寻址的独立工件，发布包只引用哈希；这不减少保护范围，但需要同步改恢复脚本与备份清单，属于独立一轮。
3. **`immutable()` 的镜像校验（实测约 2.2 s/次）**：对 12 个镜像逐个 `docker image inspect`，一次 publish 里会被调用 4–5 次（`active`、候选、`deploy`、`gate` 两次），合计约 10 秒。合并成一次批量 inspect 即可，改动小、风险低。
4. **`deploy.registry_refresh`（待测）**：资产刷新会重启 `ops-executor` 并轮询健康（最长 90 秒），只改前端也要付这份代价。是否只在资产身份变化时才刷新，需要先看这次记录的秒数再定。
5. **门禁（已证实很小）**：两个公网入口串行检查，合计 9–10 秒，并行最多省 4–5 秒。优先级最低。

### 五、下次发布怎么用

本机检出为 CRLF，同步到服务器后必须先转 LF，否则 `backup.sh` 会因 `#!/usr/bin/env bash\r` 直接失败：

```bash
sed -i 's/\r$//' /opt/powersystem/stages/04-frontend/deploy/production-stack.py \
  /opt/powersystem/stages/04-frontend/deploy/backup.sh \
  /opt/powersystem/stages/04-frontend/deploy/backup-timing.py
```

```bash
# 1) 冻结候选（内部已跑短检，失败会停在 preflight:*）
python3 /opt/powersystem/stages/04-frontend/deploy/production-stack.py prepare \
  --id release-YYYYMMDD-rN --image frontend=reviewed-ui:release-YYYYMMDD-rN

# 2) 可选：单独复核
python3 /opt/powersystem/stages/04-frontend/deploy/production-stack.py preflight \
  --id release-YYYYMMDD-rN

# 3) 备份（自动写 powersystem-<run>.timing.json）
bash /opt/powersystem/stages/04-frontend/deploy/backup.sh

# 4) 发布
python3 /opt/powersystem/stages/04-frontend/deploy/production-stack.py publish \
  --id release-YYYYMMDD-rN --backup /var/backups/powersystem/powersystem-YYYYMMDDTHHMMSSZ.tar.gz.gpg

# 5) 看分段
python3 /opt/powersystem/stages/04-frontend/deploy/production-stack.py timing --limit 5
```

发布记录里建议固定抄三行：`total_seconds`、`slowest` 前 3 项、`notes.backup.uploads`（两段的秒数与 MB/s）。两次真实发布之后，再决定上传与静态载荷怎么改。

## 原日志 36 · 快路径首次启用与报表时长格式（2026-10-22 22:09）

### 当前结论

2026-10-22 22:09 北京时间，前端-only 改动经**分级发布快路径**（`--tier frontend-fast`）发布成功：`active=report-duration-20261022-r1`，父版本 `natural-alarm-20261022-r2`，`pending=false`。这是快路径在生产上的**首次真实使用**，同时暴露并修复了控制器一个使快路径必然失败的凭证命名缺陷。

### 变更内容

- `src/lib/format.ts` 新增 `durationText()`：毫秒转「X时Y分Z秒」，为零的时/分单位省略，秒恒显示，`0<值<1000ms` 显示 `<1秒`，`null`/负值/非数显示 `—`。
- `src/views/ReportsView.vue` 的运行、停机、**故障**、**未知**四列，以及场站未知时长、均值/中位数/P90 全部改用该函数（原为 `xx.xxx 秒`）。
- 单测：`src/lib/format.test.ts` 新增 5 项；`vitest run` 全量 **74 项 / 22 文件通过**，`vue-tsc --noEmit` 无错误。
- 镜像构建产物内已确认模板为 ``${h?`${h}时`:''}${m?`${m}分`:''}${s}秒``，线上容器 `format-C71Ucvjw.js` 含 `<1秒`。

### 快路径为何此前不可能成功

`production-stack.py` 的 `verified_full_baseline()` 与 `backup_summary()` 用 `备份文件名 + '.timing.json'` 找凭证，即 `/var/backups/powersystem/powersystem-<UTC>.tar.gz.gpg.timing.json`；而 `backup.sh` 实际写出的是 `powersystem-<UTC>.timing.json`（无 `.tar.gz.gpg`）。因此任何全量包都无法被认定为基线，`prepare --tier frontend-fast` 必然停在 `fast_baseline_must_follow_current_release`。这解释了“规则已改、离线短测通过”却从未在生产跑通——**第二步（基线＋隔离演练）从未真正执行过**。

修复：新增 `timing_receipt()`，把 `powersystem-<UTC>.tar.gz.gpg` 映射到 `powersystem-<UTC>.timing.json`，并保留旧式后缀名兼容；两处调用改为经该函数解析。控制器本地与服务器 SHA 一致（`e533c829…`），`py_compile` 与 `--help` 通过，旧件存 `/tmp/powersystem-controller-fix-20261022/prior/`。

### 配套：轻量连续性检查（续基线时用，不替代演练）

| 检查项 | 内容 |
| --- | --- |
| 密文 | `.sha256` 旁车比对 |
| 解密 | 用 `/etc/powersystem/backup-passphrase` 实际解开 |
