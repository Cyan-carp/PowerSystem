# 69 · 统计报表左对齐与直接发布

> 本页记录统计报表三张表的对齐改动、按生产快照派生来源的做法，以及所有者免备份、免门禁、免测试的本批发布。当前状态见 [[00-当前系统状态]]。

## 一、定位与改动

截图的三张表原先把数值列做了对齐分层：场站表与设备表的时长列右对齐（`th.r` / `td.r`），时效分布表的计数与时长居中（`th.c` / `td.c`），只有首列标签左对齐。数值短、位数不齐时，竖排扫读反而被拉到列的右端。

统一改为左对齐，标题与数值同一起始线：

- `ReportsView.vue` 模板去掉三张表全部 `class="r"` / `class="c"`；`.num`（等宽数字）保留。
- scoped 样式删除 `.rp-table .r`、`.tm-table .r`、`.dv-table .r`（right）与 `.tm-table .c`（center）两条死规则，改为只在 `.rp-table/.tm-table/.dv-table` 上注释对齐口径。
- `.avail-cell b` 由 `text-align: right` 改 `left`，可用率百分比与进度条起点对齐。
- 全局 `shell.css` 的 `.table .r` / `.table .c` 未改：其他页面仍按各自口径使用。

构建日志中 `vue-tsc --noEmit` 与 `vite build` 均通过（构建本身不等于测试通过）。

## 二、来源与范围控制

工作区在动手时已存在 22 项未提交前端改动，其中 20 项与生产运行镜像同源，另 2 项是 `deploy/README.md`、`deploy/fleet.compose.yaml`。施工期间另一会话又改动了 `format.ts`、`interpretation.ts`、`AlarmInsight.vue` 并新增 `interpretation-mode.test.ts`——即工作区正在被并行修改，不能直接整树导出。

因此本批不用工作区整树，改用「按生产快照派生」：

- 基线为生产运行镜像 `f0854822f526` 的来源快照 `7004c43c…fee4d8`（revision `6e1ecf2` + 20 项 overlay，595 文件），它就是当时现网的真实源码。
- 只把 `stages/04-frontend/src/views/ReportsView.vue` 换成新版本，其余 594 文件逐字节不动；`source-manifest.json` 只更新该文件的 sha256，`reviewed_overlays` 保持 20 项。
- 派生结果 `595d8704…ed880`（595 文件），服务器 `source-build.py verify` 通过。
- 受控构建 `powersystem-frontend:ui-align-20261030-r1` → 镜像 `sha256:df942ce44999…dae872`，来源回执 `108db5c5…256eb`。

这样本批相对现网的差异严格等于一个视图文件，另一会话的未提交改动没有被绑进来源。

## 三、候选冻结

首次 `prepare` 直接报 `complete_ordered_stage4_7_8_9_stack_required`：父版 `alarm-chain-20261030-r1` 是手工激活的，其 `private/origin-args.json` 是单文件冻结编排形式，不满足控制器要求的「五份基础编排顺序」。

提供 `--from-args`（沿用 `v4-business-schedule-20261026-r1` 的 16 文件参数链）后 prepare 通过：8.39 s，`freeze.frontend_chunks` 通过，候选 `ui-align-20261030-r1`，父版 `alarm-chain-20261030-r1`，`services=[api,frontend,gateway,simulator]`。

模板编排解析后与现网编排服务集完全一致（20 个），差异只在镜像与两处非前端字段：

| 项 | 模板值 | 现网值 | 处置 |
| --- | --- | --- | --- |
| api / gateway / simulator 镜像 | locked-images 旧值 | 现网实际 ID | `--image` 显式覆盖为实际 ID |
| frontend 镜像 | 旧镜像 | 新镜像 | `--image frontend=<新标签>` |
| gateway `environment` | 旧 | 含 alarm-chain 批次新增项 | 未改，本批不重建 gateway |
| simulator `command` | 旧 | 现网命令 | 未改，本批不重建 simulator |

候选 `private/compose.json` 与现网只在上述 frontend 镜像、gateway env、simulator command 三处不同；其余 19 个服务定义逐字段相同。

## 四、激活与核验

  up -d --no-deps --no-build --pull never --force-recreate --wait frontend

- 新容器 `c8743803c784…e8bcb0`、镜像 `sha256:df942ce4…dae872`、healthy、重启 0。

### 随批传下去的两处配置漂移

本批候选编排由 `v4-business-schedule-20261026-r1` 的 16 文件链拼出，`gateway` 与 `simulator` 两行是模板旧值（第三、四节「未改，本批不重建」）。`alarm-fixed-demo` 直接以本批候选为基础（其 `private/origin-args.json` 只引用自身 `private/compose.json`），旧值继续向下传递。UTC 11:5x 逐键核对现网容器与当前候选 `compose.json`，差异只有三处：

| 服务 | 字段 | 候选/现批配置单 | 现网运行值 | 按配置单重建的后果 |
| --- | --- | --- | --- | --- |
| gateway | `MQTT_CLIENT_PREFIX` | `powersystem-stage2-fresh-20261029-r1` | `powersystem-stage2-ackfix-20261030-r1` | 退回上一代前缀，旧会话与重复订阅残留，ackfix 期的修正失效 |
| gateway | `STAGE2_DATA_DIR` | `/data/fresh-20261029-r1` | `/data/ackfix-20261030-r1` | 指向上代数据目录，读不到 ackfix 批写入的文件 |
| simulator | `command` | 无 `--window-mode` | 含 `--window-mode on` | 重建后窗口模式关闭，五时窗调度退化 |

其余键（PG/Redis/TDengine/JWT 等）逐项相同。**重建 gateway 或 simulator 前必须按现网 `docker inspect` 的值显式覆盖，不能直接对候选编排 `up -d`。** 现网这两个容器分别启动于 5 小时前与 4 小时前，未被 `ui-align` 与 `alarm-fixed-demo` 两批重建，当前运行态无影响。

### 下一批 prepare 仍会卡在同一处

`alarm-fixed-demo` 的 `origin-args.json` 同样是单文件冻结编排形式，与父版 `alarm-chain` 同病，不满足控制器要求的「五份基础编排顺序」。下一批 `prepare` 仍会报 `complete_ordered_stage4_7_8_9_stack_required`，需再显式提供 16 文件链 `--from-args`。要根治得让手工激活的批次同时落一份合规 origin-args，本批未做。

### 代码落地

对齐改动已作为独立提交进入版本库：`1dd7309 fix(frontend): 统计报表明细列统一左对齐`，父 `6e1ecf2`，已推送 `origin/main`（`6e1ecf2..1dd7309`），1 文件、27 增 38 删。

该提交的基线是 `6e1ecf2` 版视图文件，`blob b1ae6ce`，因此与线上文件 `8e208470…f446521` **不相等**：线上那份同时含并行会话对同一文件的请求去重重构（`useLatestRequest`、按页签复用请求、`reportParams`），本提交刻意不含。两者对齐口径完全一致（各 0 处 `text-align: right` / `center`，仅 `avail-cell b` 一处 `left`），差异只有重构部分。这样处理的原因：同一文件中两类改动交织，整体提交会把别会话的成果挂在本提交名下；工作区恢复为线上版本后，该文件仍显示 `M`，差异恰好等于重构部分，待该会话提交时自然合上。

工作区文件提交前后哈希未变（`8e208470…`），线上容器内仍是同一份，不涉及重新构建或发布。
