# 66 · 全设备离线复发与网关停摆复盘（2026-10-30）

> 本页只记本次故障的现场、判据与未覆盖项，不给修复承诺。生产指针只认 [[00-当前系统状态]]。**截至 UTC2026-10-30T06:45Z 故障未恢复，未对生产做任何变更。**

## 一、结论

TDengine 引擎、Postgres、MQTT 三条通路本身都健康，问题出在 **网关进程从 05:00 起停止消费**：进程还活着，但不再读 MQTT、不再写 TD、不再动队列，也不打任何日志。上游数据一直在进，下游一个字节没落地。

界面上"143 台设备全部离线"不是设备的问题，是 **Redis 快照的 `received_at` 冻在 04:59:58**，而前端只认这一个字段判在线。

## 二、现场证据

| 环节 | 实测 | 判定 |
| --- | --- | --- |
| 模拟器 → MQTT | inbox 每秒新增约 26 条（1550/min），消息自身时间戳即当前时刻 | 正常 |
| 网关进程 | `State: S(sleeping)`、16 线程、9 个 fd；`gateway.sqlite` 与 `-wal`(4.1 MB) 停在 05:00 | **停摆** |
| 网关日志 | 最后一条 `tdengine_batch_written` 在 `ts=1793336402`（05:00:02），之后 100 分钟零输出 | 静默 |
| EMQX 侧 | 该客户端 `connected=true`、`inflight=1`、`delivered_msgs=316901` 不再增长 | 卡在一条未 ACK |
| TDengine 引擎 | REST `select server_version()` 20 ms 返回；`show queries` 无长查询；vgroup applied=committed | 正常 |
| TDengine 数据 | `last(ts)=2026-10-30 05:00:01.155` | 断流 |
| Postgres | inbox 19,011,724 行 / 16 GB；`pending` 13.4 万只增不减；heads 递归查询单次 10.8 s | 积压 |
| Redis 快照 | `device:244:latest` 的 `received_at=04:59:58`、`snapshot_source=td_confirmed`；TTL 被续到约 430 s 但内容不动 | **冻结** |
| api | `/ready` 503；`telemetry_state td_missing`；`energy_rebuild_failed` 每 10 s 一次 | 降级 |

## 三、传播链

1. 网关停摆 → TD 无新数据（05:00 起）。
2. api 的处理链要先用 `select seq from t_device_XXX where ts=? and seq=?` 确认 TD 已落地才提交业务、才写快照。TD 没有那条数据，确认永远失败，inbox 全停在 `pending`。
3. `sourceSamplesSQL` 与 `uncertainExistsSQL` 都按 `device_id + ts_ms` 打 inbox（16 GB），`energyWorker` 10 秒一轮、零退避地重建 143 个 dirty day，持续和主链抢 Postgres。
4. 快照写不进去，`received_at` 冻住；`snapshotIsCurrent()` 用 `telemetry.Freshness(now, received_at, ts)` 判定，全部判 stale，`online` 归零。
5. `/ready` 要求 `fresh_ratio == 1`（全部设备新鲜），任何一台过期即 503，健康检查因此长期 `unhealthy`。

注意：快照 key **没有消失**，TTL 一直被续期，只是 `received_at` 不动。因此这不是"缓存过期"，是"缓存冻结"——更容易被误当成有效旧值。

## 四、未覆盖项（本次要回答的部分）

| 编号 | 缺口 | 归属 |
| --- | --- | --- |
| TR-R13 | **写入侧没有健康信号**：成功打 `tdengine_batch_written`，失败打 `tdengine_batch_deferred` 且不带 error；这次连失败日志都没有。网关自身无 readiness、无写入侧 metrics、无 watchdog | S01 盲区 |
| TR-R14 | **冻结被渲染成离线**：S01 契约要求区分"缓存失鲜"和"设备离线"，但界面只有一个状态，平台自身故障表现为设备全坏 | S01 → 界面 |
| TR-R15 | **发现 ≠ 恢复**：`td_missing` 报了 100 分钟，没有任何自动动作（重连、重启、告警升级） | S01/S04 |
| TR-R16 | **电量重建旁路未纳入调度**：`energyWorker` 固定 10 s ticker、无退避无熔断，与主链抢 Postgres；S02 的预算与 S03 的公平调度都没覆盖它 | S02/S03 |
| TR-R17 | **inbox 没有容量上限**：16 GB / 1900 万行才让 heads 查询涨到 10 秒。S01 冻结了状态口径，没冻结保留与归档策略 | S01/S04 |
| TR-R18 | **队头阻塞实际发生**：`SetAutoAckDisabled(true)` + `SetOrderMatters(true)` + 单条 `inflight=1`，一条未 ACK 全订阅停。S02 已预警 TR-R09，但未落地超时与跳过 | S02 |
| TR-R19 | **`flush` 取连接无超时**：`g.queue.QueryContext(g.runContext, ...)` 用永不过期的 ctx 去抢 SQLite 单连接（`SetMaxOpenConns(1)`），admission 一旦占住事务，writer 无限等待 | S02/S03 |

## 五、05:00 的触发原因：未定论

网关在该时刻之前一直正常（`tdengine_batch_written` 连续），之后彻底静默，没有留下任何错误行。因此**不能断定**是队头阻塞还是 SQLite 单连接死等，两者都能产生同样现象：

- 若 admission 在写 SQLite 时被卡（WAL 4.1 MB、单连接），writer 的 `QueryContext` 会无限等，不再 flush；
- 若一条 QoS1 消息没 ACK，`OrderMatters` 会让后续投递全停，`acceptTelemetry` 不再被调用。

要定性需要 goroutine dump（需重启前抓，或加 `SIGQUIT` 但会导致进程退出）。本次未做，如实记录。

## 六、处置建议（未执行）

最小动作是**只重启 gateway 容器**：TD 正常，重启后重放 SQLite 约 4 万条积压，1 分钟内 TD 恢复写入，快照随 `td_confirmed` 重新刷新。重放幂等（`PRIMARY KEY(run_id,device_id,seq)`），不会产生重复。

重启后盯三件事：TD `last(ts)` 是否前进；`device:*:latest` 的 `received_at` 是否跟上；inbox `pending` 是否由增转减（13.4 万积压要一段时间才消化得掉）。

不做：不重启 TD、不清 inbox、不改 energy 调度、不动发布指针。
