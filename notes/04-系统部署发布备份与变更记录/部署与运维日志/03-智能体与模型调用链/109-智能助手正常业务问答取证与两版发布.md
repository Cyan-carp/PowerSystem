# 109 · 智能助手正常业务问答取证与两版发布

## 问题盘点

用户要求优先保证正常提问能得到回答，再讨论不可回答边界。本批沿“用户提问 → 主助手分流 → 运维工具 → 事实校验 → 答复”检查前端推荐问句及常见平台查询，确认以下可复现的缺口：

1. 除健康分、序号设备和最新一条告警等少数特例外，主助手可在明确的当前业务问题上由模型直接结束而未委派查询；09 运维模型也可能无工具调用却以成功状态结束，08 最后只能显示“本轮未取得平台业务证据”。
2. 前端推荐“未处理告警里最久的是哪一条？”需要最早记录，现有告警接口按触发时间、ID 倒序返回；取首页会拿到最新记录。列表无反向排序参数。
3. 前端推荐“哪个场站今天出力下降最明显？”所需的历史对比基准不在当前场站总览中；总览只提供当前功率快照。把当前功率最低说成下降最多会误答。
4. “已确认告警有多少条？”会被宽泛的“确认告警”动作词规则误判为写请求。
5. “今天发电量”在旧提示中被直接引向“尚未结算”；实际总览已有当日电量暂计值、更新时间和完整性字段。程序聚合答复原来还会把 JSON 截到 160 字，正常数字不易读。

这些是静态代码和定向回归发现的能力/分流缺口，不宣称覆盖所有自然语言表达，也不把生产某轮模型行为当成已逐条取证。

## 修复与边界

- 08 对明确的当前设备、场站、告警事实问题优先委派只读取证；健康分原有确定性路径保留。常见在线/离线设备数、场站功率、当日电量由 09 直接读现有 `get_dashboard_overview`，不依赖模型选择工具。
- “未处理告警最久”由 09 先读首页总数，再按倒序分页读末页；两次总数必须一致，行 ID、状态、时间及排序须有效。08 仅从该实际记录生成答案。查询期间总数变化时失败并要求重试，不声称最早记录。
- 已确认和未处理告警计数分别使用 `status=acked`、`status=unhandled` 的分页接口 `total`；前者明确为“已确认但未恢复”。读取问句不再进入业务写动作提议。
- 09 对其他明确平台事实问题若首次零业务工具调用，给一次有界补查机会；仍无证据则任务失败，不再以“成功查询”包装。08 的聚合事实改为可读数字和各场站当前功率；当日电量标为暂计，附数据更新时间及完整性，不冒充全天结算。
- “今天出力下降最多”先返回当前各场站功率快照，并明确缺少同口径的较早基准；要求用户指定一小时前或昨天同一时刻等对比基准。现有接口尚不能准确排名下降幅度，后续应提供按场站聚合的可比历史功率，不能拿当前功率替代。

无 API、数据库、权限、工具风险级别或前端变更。普通知识解释、能力说明、审批与写权限仍沿原路径。现有全量告警/设备列表的分页及工具预算仍限制任意大范围复杂分析，需按提问目标取证；未承诺所有自由表达都自动覆盖。

## 本地验证

对具体问句补了无数据库假执行器与主助手回归：在线设备数、场站当前功率、今日暂计电量、已确认/未处理告警计数、最久未处理告警（含末页）、健康分、零工具补查与失败出口、普通解释不误触发。最终定向结果 `78 passed, 29 skipped`，跳过项因独立数据库未配置；源文件编译与差异检查通过。未执行生产登录态问答测试，不能据本地结果宣布用户端完整链路已验收。

## 使用建议

用户可在新会话分别提问“现在有多少台设备在线？”、“已确认告警有多少条？”、“未处理告警里最久的是哪一条？”、“今天发电量是多少？”。旧会话结果不会自动重算。若仍出现正常问题只给“未取得证据”，应保留问句、任务 ID 和时间以定位漏识别表达或工具失败；不能凭截图推断是哪一层失败。合成设备数据不等于真实场站运维判断。
