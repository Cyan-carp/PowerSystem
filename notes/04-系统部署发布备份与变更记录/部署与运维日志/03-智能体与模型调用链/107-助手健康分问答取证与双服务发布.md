# 107 · 助手健康分问答取证与双服务发布

## 问题与证据

用户在智能助手中询问“哪些设备的健康分低于 80？”，任务显示完成，答复却是“本轮未取得平台业务证据，不能报告当前设备状态”。截图只能证明该轮没有可用于答复的业务证据，不能单凭截图确定模型当时的工具轨迹。该问句是前端内置推荐提问。

静态核查确认：API 已有逐台健康分接口 `GET /api/v1/health/devices`，健康页和设备页也在使用；原 09 运维工具清单却没有该接口，08 的实时取证触发器也不匹配本问句。对截图原问句做纯函数复现，原分流为 `intent=conversation`、`needs_current_evidence=false`、`business_request=true`，零工具调用时的保护答复与截图一致。因此确认的是**助手能力缺口**；不把该轮具体模型故障当成已取证根因。

## 修复范围

- 08/09 各注册只读 `get_health_devices`，映射现有健康分接口；无数据库、权限或写动作变更。
- 对“哪些/查询/查……健康分低于 N”的当前数据问句直接委派 09 读取，跳过模型自行决定是否调用工具的环节；09 对该类任务直接调用平台工具，保留原 actor 与只读权限校验。
- 对返回的全量逐台评分、计算时间、规则版本、完整性与设备唯一性做结构校验；只列有效 `score < N`，等于阈值不列入，未知分单列，不将 0 分解释为已确认硬件故障。答复由已验证事实确定性生成，不以模型文本填充缺失数据。
- 09 在裁剪工具结果前投影必要字段，覆盖 200 台容量口径；08 对本次有效评分证据提高事实容量，避免后段设备被截断。

源码改动限 `stages/08-agent-rag` 与 `stages/09-ops-agent`；前端推荐语与 API 本身未改。定向本地测试结果：`65 passed, 29 skipped`，跳过项为未配置独立数据库的测试。7 个生产源码文件编译检查及 `git diff --check` 通过。未执行生产登录态问答验收，不能据此宣称截图中的既有任务已变更；需用户发起新会话重问才会使用新代码。
