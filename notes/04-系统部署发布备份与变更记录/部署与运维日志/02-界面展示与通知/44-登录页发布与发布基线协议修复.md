## 一、本批做了什么

43 号留下的死结是：候选冻结之后跑全备，全备停复 RAG/Ops 导致 `StartedAt` 变化，于是「当前状态 == 父版门禁快照」「当前状态 == 候选冻结快照」两条规则必然失败；先 `verify-backup` 重签又会把指针 `updated_at` 推到全备之后，使快路径的时间边界也失效。

本批没有放宽任何一条规则，而是补上「停写窗口」这条缺失的协议：

| 位置 | 原行为 | 现行为 |
| --- | --- | --- |
| `publish` 父版基线 | 只比对 `current == 门禁 states` | 相等即通过；不等时要求回执 `before` == 门禁 states 且 `after` == 当前状态 |
| `publish` 候选基线 | 只比对 `current == manifest.before` | 相等即通过；不等时要求回执 `before` == `manifest.before` 且 `after` == 当前状态 |
| `publish` 全量档 | 校验密文摘要、时效、晚于候选 | 增加 `maintenance_receipt()`：绑定父版本与冻结清单、密文摘要与双副本、候选自身快照 |
| `set_active` | 只写 `updated_at` | 另写 `published_at`（应用激活时间），维护重签时继承原值 |
| `choose_fast_baseline` | 以 `updated_at` 为边界 | 以 `published_at` 为边界；历史指针经 `backup-maintenance-*.json` 回溯激活时间 |

`maintenance_states_match()` 原样复用：只有 RAG/Ops 两个写者允许变 `started_at`，ID、镜像、重启次数与其他全部服务严格不变。门禁、冻结清单、回滚路径均未改动。

> 43 号结尾曾估「约 8 行」即可修复；实际需要同时改两处基线判定、回执绑定、指针时间语义与快路径边界，并补相应用例。估时作废。

## 二、回执为什么能证明「只是停写」

`backup.sh` 在暂停前写 `.v4-maintenance.json` 的 `before`（并先过 `current_matches`），复服后补 `after` 与 `resumed_at`，再由备份脚本把 `archive` / `sha256` 落进同一份回执。本批发布实际使用的回执：

| 字段 | 值 |
| --- | --- |
| 绑定父版 | `v4-s09-r0-20261024-r1`，`manifest_sha256` `f2dff638…` |
| 绑定备份 | `powersystem-20261025T101427Z.tar.gz.gpg`，`sha256` `f342bee5…`（`.sha256` 旁车一致） |
| 停写窗口 | 2026-10-25T10:14:30.644640Z → 10:17:54.796830Z |
| `before` | 与候选 `manifest.before` 逐服务一致（RAG `07:34:17.928…`、Ops `07:34:00.436…`） |
| `after` | 仅 RAG `10:17:29.307…`、Ops `10:17:11.279…` 的 `started_at` 变化 |

因此「候选冻结快照 → 当前运行状态」的差异被完整解释，且只能解释这一种差异：换任何一个服务重启、换镜像、换容器 ID、改重启次数，`maintenance_states_match` 都会拒绝。

## 三、快路径时间语义

`updated_at` 是指针写入时间，`verify-backup` 每重签一次就会前进；用它当全备边界，等于要求「备份晚于它自己触发的重签」，永远不成立。

现在指针另存 `published_at`（应用激活时间），`verify-backup` 重签时继承而不刷新。没有该字段的历史指针（R0 两次重签）通过发布目录里的 `backup-maintenance-*.json` 链回溯，本批实测回溯两跳得到 `2026-10-25T07:13:47Z`——即 R0 的真实激活时间，而不是 07:34Z（那是全备复服 RAG 的时间，43 号正文曾把它当作换镜像时刻，此处更正）。

回溯后 `choose_fast_baseline` 立刻可用：边界 07:13:47Z < 备份 10:22Z，快路径基线解析为 `powersystem-20261025T101427Z`。也就是说，此前 `fast_baseline_must_follow_current_release` 的根因不是备份不合格，而是边界取错了字段。

## 七、边界与遗留

- **`prepare` 仍是严格口**：不做回执匹配。正常顺序是 `prepare → 全备 → publish`；若先跑了全备再 `prepare`，仍需 `verify-backup` 重签或换新候选。
- **旧回执不可重签**：`verify-backup` 要求回执里的 `active` 与当前指针完全相等；带 `published_at` 的新指针与 43 号那两份旧回执天然不等，旧回执只能作为历史证据。
- **快路径需另出小包**：基线已可用，但 `frontend-release-backup.py` 生成的胶囊与 `baseline` 绑定，需在新指针下重新生成才能走 `--tier frontend-fast`。
- 本批只改控制器与登录页，未改冻结清单、私有配置、数据库或模型。
