# 45 · 前端构建上下文过期导致 V4 界面回退与恢复

> **版本归属**：V4 · 智能体行动化重构（2026-10-25 同日第二次前端发布）。**本批是一次事故的复盘与修复**：11:03 的登录页发布顺带把第四版界面换回了旧版，12:53 已恢复；根因是服务器前端源码树停在 10-22，而那次镜像正是用它构建的。

## 一、现象

11:03 发布 `ui-login-20261025-r1` 后，所有者反馈「第四版界面在网页上看不到」。核对运行镜像的产物：`/usr/share/nginx/html/assets` 只有 37 个文件，**没有** `AgentSchedulesView`、`RunAnswer` 等第四版路由分块；`/assistant` 仍能打开，但工作台、动作审批、运行视图、定期任务页全部消失。

## 二、根因

服务器 `/opt/powersystem/stages/04-frontend` **不是**第四版源码：

| 证据 | 事故前服务器 | 仓库 HEAD |
| --- | --- | --- |
| `src/**/*.vue` 数量 | 33 | 36 |
| `src/lib` 中 agent 相关 | 2（`agent-chat`、`rag-chat`） | 8（含 `agent-runs`、`agent-artifacts`、`agent-schedules` 等） |
| `src/views` | 无 `AgentSchedulesView.vue` | 有 |
| 最近修改时间 | 除 7 个文件外全部 ≤ 2026-10-22 21:38 | 2026-10-25 |

也就是说，10-23 之后的第四版前端（S04–S09）未同步到该服务器源码目录，R0镜像来自受控工作区构建产物。当时记录称按镜像列表未找到 `79b8bce4`，据此推断已删除；后续完整ID复核发现该镜像仍在、但无标签，不能继续把“已被清理”当事实。仅凭后续存在也不能证明事故时刻可用；本批实际采取的是重建恢复，后续保留措施见 [[46-V4完整源码快照与误构建阻断]]。

11:03 那次发布只把 3 个登录页文件 `install` 进这个目录，随后 `docker build` 就地构建——于是「登录页是新的、其余是 10-22 的」，V4 界面被静默丢掉。门禁没有问题：它校验容器身份、健康与双公网 HTTPS/WSS，但**不校验镜像里有没有少页面**。

## 三、恢复

| 步骤 | 结果 |
| --- | --- |
| 源码整棵同步 | `git archive HEAD stages/04-frontend` → 服务器覆盖（92 个文件），旧树备份 `/tmp/src-backup-frontend-20261025b`；`deploy/production-stack.py` 摘要复核仍为 `5df1212a…` |
| 重建镜像 | `powersystem-frontend:ui-v4-restore-20261025-r1`，ID `sha256:0d4785296705…`，42 个产物（含 `AgentSchedulesView`、`RunAnswer`、`LoginView`） |
| 冻结候选 | `ui-restore-20261025-r1`（15.9 s，`full`，仅 `frontend`） |
| 全备 | `powersystem-20261025T123351Z`，1,161,845,867 B，`f71e7c59…`，967.6 s，双端 `status=ok`；回执只有 RAG/Ops 启动时间变化 |
| 发布 | 106.2 s，门禁 `accepted-1792932832684304066.json`，`published_at` 2026-10-25T12:53:52Z |

公网核对：`AgentSchedulesView-DEA6Rp8k.js` 200（46,694 B）、`RunAnswer-D6bz-Zjv.js` 200（102,586 B）、`LoginView-By5KEgWA.js` 200 且含 `login-scrim`；入口 `index-BdManFCw.js` 已引用这两个分块。

## 四、门禁补强

`prepare` 现在会在冻结候选前比对：候选前端镜像的逻辑分块集合必须**包含**当前运行镜像的集合，缺一个就报 `frontend_assets_missing:<名字>` 并停止；分块哈希由构建产生，比对时统一剥掉 `-<hash>.js|css`。确实要下线页面时显式加 `--allow-asset-shrink`。

用事故镜像做的反向验证：

```
事故镜像缺: ['AgentSchedulesView', 'RunAnswer', 'api']
现行镜像缺: []
```

## 五、教训

1. **服务器目录不是构建基线**。它停更了三天，却因为没有版本标记而看不出来。本批用完整归档恢复；现行完整快照及来源回执流程见日志46，不再覆盖旧目录后直接build。
2. **发布门禁只证明「服务活着」，不证明「功能还在」**。这次所有门禁都通过，界面却少了一半。补的是产物清单这一层。
3. **旧镜像按完整ID核查并保留**。无标签不等于不存在；原R0镜像后续查实存在并加保留标签。实际恢复耗时约30分钟，但不能将其归因于已证实的镜像删除；统一回退仍受直接父版与门禁约束。
4. **补丁式同步风险高**。11:03 只覆盖 3 个文件，正是这种「只同步改动文件」的做法掩盖了底树过期。

## 六、边界与遗留

- 本批恢复时前端源码与 `ec986b9` 同源；现行构建基线及历史目录阻断见日志46，不将当时HEAD名称当后续构建指令。
- 当时发现08/09/02旧源码缺少 `run_api.py`、`schedule_contract.py`、`agent_runs.go`。后续五阶段完整源码快照与六服务镜像来源检查已处理误构建路径，详见 [[46-V4完整源码快照与误构建阻断]]；没有因此升级09/10运行镜像。
- 全备目标剩余空间约 1.7 GB（41 GB 分区，88% → 预计 91%），下一次全备前需要清理过期包。
