## 三、发布过程（含事故）

本批比前几批曲折，如实记录：

1. **二进制没有执行位**：Go 二进制在 Windows 交叉编译，`COPY server /app/server` 不带 `+x`，容器启动报 `exec: "/app/server": permission denied`。此时 api 已被 recreate、旧容器已删，**服务中断**。
2. **迁移 30 秒超时**：修权限后重启，api 卡在 `phase: schema`，日志 `migration: timeout: context deadline exceeded`。查库发现大量会话阻塞在 `CREATE INDEX IF NOT EXISTS idx_energy_dirty_changed ON energy_dirty_days`（`wait_event_type=Lock`）——**反复 recreate api 导致多个实例并发跑同一批迁移，互相阻塞**。这不是 021 引入的，是重启风暴的连带效应。
3. **回滚**：先把 api 用父候选镜像 `4cbf4c6b…` 拉起，`docker stop` 打断重试循环，`pg_terminate_backend` 清理阻塞会话；确认 `energy_dirty_days` 索引已 valid、只剩 286 行。
4. **手工迁移**：`psql -f 021.sql` 秒级完成（`ALTER TABLE` ×3、`CREATE INDEX`、`COMMENT` ×3），因为 `prediction_drift_events` 只有 17 行——**021 本身不慢，慢的是并发迁移争锁**。迁移移出 30 秒启动预算后再切新 api。
5. **最终激活**：新 api `19c12fd7…` + 新 frontend `09d7544f…` 一起起来，容器均 healthy。

累计不可用约 25 分钟。所有者此前已接受短时停摆，但本批的实际中断时长与原因必须记在此处，不用「顺利」掩盖。

## 五、教训（后续批次直接适用）

- **跨平台二进制必须显式 `chmod 0755`**，写在 Dockerfile 里，不能依赖 `COPY` 的权限继承。
- **改服务时不要连续 `up -d --force-recreate`**：每次失败重启都会再跑一遍全量迁移，容易在同一张大表的索引上排队互锁。失败后先 `docker stop` 打断重试，再排查。
- **大表相关 DDL 不要留在 30 秒启动预算里**：先在 psql 手工执行并确认，再切镜像。
- QGA 的 `--pass-stdin` 单次上限 1 MiB；6 MB 二进制要用 `split -b 900k` 分片后拼接。
- 迁移 SQL 必须幂等（Migrate 无版本表、每次启动重跑）。
