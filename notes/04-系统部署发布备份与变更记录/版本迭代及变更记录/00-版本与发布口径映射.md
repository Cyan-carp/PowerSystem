# 00 · 版本与发布口径映射

> 本页解决一个反复出现的混淆：**文档里的“第几版”、Git 标签、生产批次、安装包版本是四套编号，不能互相换算**。生产指针与镜像仍只看 [[00-当前系统状态]]，本页不复制镜像表。

## 一、四套编号各是什么

| 编号体系 | 谁在用 | 例子 | 能否互推 |
| --- | --- | --- | --- |
| 文档版本 V1～V8 | `notes/01-*/` 的规划分区 | 第二版-智能体升级 | 不能；一个文档版本常跨多个 Git 标签 |
| Git 标签 / commit | 仓库发行 | `v3.0.0` @ `152b15b` | 不能；标签是提交快照，不等于生产指针 |
| 生产批次（release） | 发布控制器与部署日志 | `supplement-attachments-20261118-r1` | 不能；批次号由发布工具生成，可无对应标签 |
| 安装包版本 | 桌面端与安卓端 | 桌面 `0.2.0`、安卓 `1.0.0` | 不能；包版本独立于网页版本 |

> 证据时间：本页 Git 标签于 **2026-11-22** 在本地仓库用 `git for-each-ref` 核对；生产列沿用 [[124-展示业务功能补充分批发布]] 与 [[06-当前系统状态/01-生产快照与发布指针]] 的回执，**未连接服务器重新验收**。`updated` 是本页编辑日期，不是生产观测日期。

## 三、第二版与 `v3.0.0` 的历史关系

这是最容易误解的一处，单独说明：

1. **文档的“第二版”是一个建设阶段**，起于智能体升级立项，收于三智能体协作联合验收；它自然跨过两次仓库发行。
2. `v2.0.0` 是 V2-M1～M4 通过时的发行点（2026-10-06），此后第二阶段仍在继续（BND、多智能体、联合验收）。
3. `v3.0.0` 的提交说明是“三智能体协作大版本：联合第四阶段验收与公开源码交付”（2026-10-14），才是文档第二版的**收尾发行**。
4. 因此“第二版 = v2.0.0”是错的；“第二版全部内容 = v3.0.0”也不严谨——`v3.0.0` 是收尾时的仓库快照，之后仍有同阶段的补丁批次（如日志 06 的 API 回退恢复）。
5. 部署日志索引把 V2 的判据写成“`v2.0.0` → `v3.0.0`”，正是这个跨度的简写，不是两个并列版本。

## 五、镜像与来源怎么写

- **不在本页复制镜像表**。要看“线上跑的是哪个镜像”，进 [[06-当前系统状态/01-生产快照与发布指针]]；要追溯某次换了什么，进对应批次页。
- 镜像摘要（`sha256:…`）与源码摘要（`source-builds` 回执）是两种东西：前者证明跑的是哪个镜像，后者证明镜像由哪份源码构建。批次页两者都记时，引用时不要混用。
- 手工激活批次通常没有 source-build 回执，登记为“无来源回执”，不得用镜像摘要代替。

## 六、日期与适用范围的写法

| 字段 | 含义 | 不能拿来证明 |
| --- | --- | --- |
| 笔记 `updated` | 该页最后一次编辑日期 | 事实新鲜度、生产观测时间 |
| 证据日期 / 观测日期 | 实际执行检查或发布的时间 | 之后仍然有效 |
| 适用批次 | 结论绑定的 release 名 | 其他批次 |
| 验收范围 | 当时实际测过的对象与项数 | 未测部分 |

> 本页只做映射，不新增验收结论。任何“已上线”“已通过”的表述必须能回到具体批次页或状态分卷；查不到就写“未查到”，不写“应该”。
