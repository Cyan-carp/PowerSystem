## 二、每条线最值得讲的三件事

给别人讲项目时，从这几条切入最省力——它们都有「原来不行 → 改了 → 好了」的完整弧线。

**后端**
- 告警从只读列表到写闭环：归档是打标记不删数据，确认只接受未处理的（否则 409），因为「认领」动作不能被覆盖
- 判警从固定阈值到自然规则：同一场站设备正常温度能差 4℃，统一阈值必然一边太松一边天天误报
- 设备从 3 台到 143 台，逼出了强制分页与按区域独立加载

**智能体**
- 解读从「模型自由写」改成「事实由后端渲染，模型只写分析」——因为模型会改写时间戳，让人误以为设备还在告警
- 第一版问答 Agent 整体退回重做（2026-10-11），理由不是修不动，是「修好也不对」
- 审批的 `step_no` 曾能让前端自己盖章，后端改成本地生成后堵住

**模拟器**
- 故障注入改了四次：固定突变 → 窗口注入 → 加前兆 → 前兆 30→60 分钟 → 温度目标 65→80℃
- 每次都因为同一件事：训练时喂的形态和线上出现的形态对不上
- 设备从「三台同参」到「各有各的效率与偏移」，解决「整站升温就整站报警」

**预测模型**
- 模型版本 `6eac6e3e → 89e6530c → ae1f508f → 9d5056e4 → 20a7486c`
- 阈值 `0.35 → 0.325 → 0.225 → 0.575`，降低是在噪声里挣扎，升高说明特征终于清晰
- 评估口径试了三回：加容差（失败回滚）、补设备差异（有效）、调阈值（最快见效）

## 四、为什么这样组织

**日志是按时间横切的**：某天发了什么、指针切到哪、门禁过没过。适合复盘「那次发布」。

**变更史是按技术线纵切的**：一个技术点从起点到现在的完整弧线。适合回答「为什么是这样」。

两者不能互相替代。找「上周五发的那批」去日志，找「告警为什么有归档没有删除」来这里。

## 五、写作口径

1. **只写确实变过的**，一次成型的不要写——那属于设计说明，不属于变更史
2. 每个技术点必须有「触发」：什么问题让它必须改，要具体到现象或数字
3. 改过的参数写**旧值和新值**，只写新值等于没写
4. 写清**代价**：改完之后多了什么麻烦，否则读者会以为改完就完美了
5. 结论要能复核：给查询或文件路径，不只给判断
