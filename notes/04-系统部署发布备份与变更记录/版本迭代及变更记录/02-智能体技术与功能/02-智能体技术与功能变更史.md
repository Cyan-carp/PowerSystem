# 02 · 智能体技术与功能变更史

> 一句话：**这条线的每一次改动都在做同一件事——把「模型能说什么」一步步收窄到「它只做擅长的那部分」，其余的交给代码与门禁。**

## 〇、技术清单一览

| 技术项 | 变过 | 变成了什么 |
| --- | --- | --- |
| 模型供应商 | **没变** | 始终是外部网关 + DeepSeek 系模型 |
| 解读输出形态 | 变过 3 次 | 模型自由生成 → 强制 fact block → 事实/分析分栏展示 |
| 输出预算 | 变过 2 次 | 不限 → 4096 → 固定 4096 并区分截断原因 |
| 智能体架构 | 变过 1 次（整体退回） | 单体多关卡 → 07/08/09 三体拆分 |
| RAG 检索 | 变过 1 次 | 词面检索 → 向量检索 + 来源阅读 |
| 审批机制 | 变过 2 次 | 前端传 `step_no` 盖章 → 后端生成并逐次消费 |
| 网关调用方式 | 变过 1 次 | 全部非流式 → 流式 + 按 Content-Type 分流 |
| 答案结构 | 变过 1 次 | 一段自然语言 → 结论 / 已核验事实 / 未核验解释三层 |
| 动作权限分档 | 变过 1 次 | 无分档 → R0 自动 / R1 本人批准 / R2 管理员批准 |

下面按主题展开。表中「RAG 检索」与「动作权限分档」只保留结论——它们的决策记录在第二版的批次笔记里，本文不重复推演。

## 一、告警解读的形态：自由生成 → 强制 fact block（2026-10-13 重构）

**起点**：大屏联动的第一版，模型直接生成整段解读，服务端自己拼提示词。

**触发**（三件事同时发作）：
1. 答非所问——模型纠结「大屏是否带声光报警」这类细节，核心结论被淹没；
2. 时间戳被改写——原文 `2026-06-17 15:22:01` 被模型按「当前时间」重排，用户以为设备还在告警中；
3. 无法追溯——出了问题分不清是数据错还是模型错。

**改法**：
- 后端先渲染强制 fact block（设备编号与名称、场站、告警类型、级别、起始时间原样、持续时长、当前值 vs 阈值、规则快照）；
- 模型只能分析 part，**不得复述时间戳、不得改写设备事实**；
- 输出改用结构化字段 + `fallback_used` 版本标识；
- **原文无法渲染时返回 422 而不是 200**，避免前端拿空壳。

**现在**：解读页分「事实 / 分析」两栏，`fallback_used=true` 时页面上标出用的是哪一版提示词。

证据：[[06-问题记录与解决方案·02-告警智能解读与大屏联动]]

## 二、输出预算与失败可见性

**起点**：输出长度不设限，取最稳定的硬上限。

**触发**：不同告警的解读 token 消耗差十倍，长告警会吃满预算；更麻烦的是上游超时后页面**什么都不显示**。

**改法**：
- 把预算降到 4096，并区分「计划预算」与「实际被上限截断」两种情况；
- 主备模型切换的顺序（320 → max）写进代码而不是提示词；
- **失败时保留事实、把失败原因写在解读区**，整条告警不消失。

**代价**：4096 之后的异步草稿方案跑完了却没上线——170 个任务只有 13 个完成，其中 123 条未通过校验，被判定为与 4096 单跑无显著差异，且一致性风险更高。这条能力**至今没上生产**。

证据：[[18-解读模型通道兼容与输出预算（原18+28+29）]]

## 三、一次整体退回：第一版问答 Agent 被废（2026-10-11）

**起点**：2026-10-06 建的第一版问答 Agent 已修复过 CORS、错误率与展示层问题。

**触发**：把演示里「问一个现场问题答不出」和「模拟数据混入真实结论」两条放在一起看，判断根子在静态快照生成全部答案、模型没有拆问题、RAG 不检索技术手册——**是架构级错误，不是 bug**。

**改法**：整体归档为废案（仅留档），从 10-13 起自研双循环主智能体。

**代价**：10-05 到 10-11 的开发生成物全部不计入交付，已修复的问题记录保留供复查。

**为什么值得记**：这是全套系统里唯一一次「推翻重做」。判断依据不是「修不动了」，而是「修好也不对」。

证据：[[00-废案声明与弃用原因]]

## 四、07 解读 / 08 检索 / 09 执行的三体拆分（2026-10-18）

**起点**：一个智能体既解读又给操作建议，用户点一下就可能执行。

**触发**：动作不可逆（重启采集、限功率），一旦误判没有后悔药。

**改法**：拆成三个职责单一的服务——

| 编号 | 能力 | 不做的事 |
| --- | --- | --- |
| 07 | 告警解读、值班问答 | 不执行动作 |
| 08 | 知识检索与来源阅读 | 不碰实时业务数据 |
| 09 | 提议并执行受限操作 | 不经审查与批准不执行 |

**边界**：每个服务只拿得到自己需要的信息，07 拿不到执行权限，09 拿不到自由生成权。

证据：[[01-总体架构与智能体职责]]、[[04-能力目录与权限边界]]

## 五、受控执行的审批漏洞与补法（2026-10-21）

**起点**：审批在前端做，后端只认「批准过了」这个结论。

**触发**：审查发现 `step_no` 可以让前端传上来，等于**前端自己盖章**——只要构造一个合法 `step_no` 就能绕过审批。

**改法**：`step_no` 改由后端在每次任务创建时生成并落库，前端只能透传、不能赋值；缺失时 409 `OPS_TASK_STEP_MISMATCH` 整体拒绝，不允许部分通过。

**现在**：「审批」是后端的状态机，前端只是触发器。

证据：[[04-问题记录与解决方案·03-受控运维执行]]

## 六、模型网关兼容：一次性返回不可用（2026-10-25）

**起点**：所有调用都用 `stream: false`，等完整响应。

**触发**：上游网关不再支持非流式，实测返回 **13 字节的 keepalive JSON** 就断流，三服务全部报「响应不完整」。

**改法**：三服务统一改为 `stream: true` + 边收边解析，按 `Content-Type` 分流；超时从 45 秒放宽到 60 秒。

**遗留**：07 的 `agent/llm.py` 当时没有一并加固，是唯一还走非流式的入口——这条缺口一直留到 11 月才被发现。

证据：[[37-模型网关兼容式改造三服务]]

## 七、答案分层的由来

**起点**：助手回答是一段自然语言，查到的和猜的混在一起。

**触发**：用户无法判断哪句该信。一次「设备离线了吗」的回答里，事实与推测五五开，但读起来一样确定。

**改法**：拆三层——

```
直接结论      ← 一句话
已核验事实    ← 来自数据库，可点开看原始记录
未核验解释    ← 模型推测，明确标注
```

**这一层拆分不是为了好看**，是让「查出来的」和「猜的」一眼可辨。没有它，用户只能整体信或整体不信。

## 八、这条线现在的边界

- 解读质量取决于事实完整度，字段缺失时只能给笼统判断
- RAG 只答语料覆盖到的问题，问没写过的会明确说「未找到」
- 09 的动作集是白名单，不在名单里的一律拒绝，不做「尽力而为」
- 异步长文解读至今未上线，4096 是硬上限
