## 必须执行的发布门禁

**提交前**

- 检查 `git status` 和 `git diff --cached`，核对新增文件、图像、归档、日志与文档。
- 禁止提交：`.env`、私钥、公钥以外的 SSH 凭据、JWT/数据库/Grafana 密钥、飞书 Webhook 与签名、备份口令、真实账号口令、生产数据、会话令牌和可还原这些值的截图。
- `.gitignore` 只是辅助，不能替代人工审查。

**服务器私有文件**

- 仅放在服务器受限目录，权限按最小访问原则设置。
- 不得写在 Compose 文件、命令参数、GitHub Actions 日志、issue、PR、README 或录屏里。
- 若发现误提交，先吊销/轮换凭据并检查访问日志，再清理仓库历史；仅删除最新文件不代表旧提交失效。

**GitHub 权限**

- 写权限和部署权限分开管理，启用双因素认证与最小协作者权限。
- 保护实际部署分支，审核 PR 后固定提交 SHA/发布标签部署。
- 服务器以高权限执行 `docker compose up --build` 会运行仓库 Dockerfile 与代码，因此对仓库有写入权的人可以借部署流程影响服务器。

**生产入口**

- 仅开放必要的 HTTPS/WSS 端口，并限制来源；SSH 使用密钥和最小权限账号，限制来源地址，保留经过验证的应急入口。
- 数据库、MQTT、Redis、TDengine、AI、Prometheus、Grafana 和 Docker API 不直接暴露公网。
- 每次改 FRP、云安全组或防火墙后在主机与外部各核对一次监听端口。

**登录与账号**

- 当前 Nginx 对 `/api/v1/auth/register` 返回 403、登录限速；每次发布后重新测试，不能仅凭配置文件推断生效。
- 管理员只通过本机交互脚本建立，演示账号与管理员分开，离职或演示结束及时停用账号和令牌。

**备份**

- 必须加密，接收端只允许写入必要目录，SSH 主机指纹先独立核对；定期在隔离环境做恢复演练。
- 修改备份目标、FRP 配置和服务器密钥时先确认现有任务与回退路径。

**公开文档**

- 尽量用占位符描述真实公网 IP、账号、内网拓扑和绝对路径。
- 现有历史已公开的信息不能靠修改最新文档消除；需要结合实际资产状态判断是否迁移入口或轮换凭据。

## 复核命令与证据边界

**复核命令**

本机（核对远端引用、未提交内容、可提交文件）：

- `git ls-remote --heads --tags origin`
- `git status --short`
- `git ls-files`

服务器（检查实际暴露）：

- `ss -lntup`、`docker compose ... ps`
- 云安全组与 FRP 配置

检查命令不要输出 `.env`、密钥和令牌明文。远端代码与服务器运行状态是两套证据；没有登录服务器时，不应把本文件中的源码结论写成在线安全验收。

**GitHub 权限核对（2026-09-29）**

- 协作者只有仓库所有者 `Cyan-carp`；Webhook、Deploy Key、Actions 工作流均为零。
- `main/dev` 当前未设置分支保护规则。
- 这是本次账号权限范围内的状态快照；后续增加自动部署、协作者或密钥时应重新核对。

## 新增安全审查Agent的公开与发布要求（2026-10-13规划）

安全服务将使用独立私有认证、模型配置与许可范围，只有项目内网/回环入口；不把新服务端口暴露公网。审查模型不获得主机/数据库执行凭据，原数据外发授权不扩展到新字段或目的地。
