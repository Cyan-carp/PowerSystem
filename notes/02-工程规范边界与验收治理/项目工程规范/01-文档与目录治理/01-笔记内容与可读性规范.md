# 笔记内容与可读性规范

目的：让每篇笔记能被第一次阅读的人理解，并让结论与证据分清。

## 笔记排版规范

统一沿用已有笔记风格（需求分析、技术选型、架构设计、开发阶段1 均为同一套）。

**文件骨架**

1. **frontmatter**：文件开头 YAML 块必须包含 `tags`、`status`、`scope`、`updated`；`status` 只能是 `现行/历史/废弃/草稿`，`updated` 使用 ISO 日期。
2. **标题**：`# 一级标题`；专题用 `# NN · 主题`；索引用 `# 模块 · 索引`。
3. **引用说明**：标题下用 `>` 写「本页说明什么 + 对应手册/路线图任务」。
4. **分节**：正文用 `## 一、二、三…` 分节，每节一个小主题；小节用 `###`、步骤用 `####`。
5. **导航**：笔记末尾以「相关笔记」小节标明上游/下游/下一章。

**正文元素**

6. **表格**：内容简短的并列信息、对照和清单用 Markdown 表格；长句或成组数字改用标题与列表。
7. **说明框**：关键提醒、设计决策的「为什么」用 `> 说明文字`。
8. **图**：Mermaid 内联源码 + 重要图另渲染白底 PNG 存 `diagrams/`。

**链接与术语**

9. **双链**：同目录互链用短链 `[[01-xxx]]`；跨目录用全路径 `[[01-项目调研规划与开发建设记录/01-第一版-平台主体/05-功能开发与阶段交付/01-数据链路/01-环境与Git]]`（避免同名歧义）。
10. **术语**：编号（FR/NFR/任务号）与已有笔记严格对齐，不重号。

### 反堆叠写法（信息密度高的笔记必读）

笔记出现「整段灰墙、表格过宽、代码连片」的观感时，按下列规则重排，语义、命令、路径、编号一律不改：

**整段长文 → 列表**

- 一句话里串了多个并列事实、结果或边界声明时，拆成 2～4 条短列表。
- 每条只讲一件事；关键数字单独成行并加粗。

**宽表格 → 加粗标题 + 列表**

- 表格某列单元格塞进长句、多组数字或命令/路径时，放弃表格，改用「**加粗小标题** + 明细列表」。
- 典型场景：测试结果（`检查项 | 结果`）、现象排查（`现象 | 处理`）、联调记录（`检查点 | 实测值`）。
- 保留表格的前提：每格内容都是短词、短路径或单个数，读起来无需换行。

**代码块 → 步骤化**

- 连续多段命令堆在一起时，每段前加 `#### 步骤 N · 动词短语` 标题（如「步骤 1 · 预检并启动」）。
- 命令的关键注释（何时执行、环境要求、副作用）用 `>` 引用框紧跟其步骤，不埋进正文。

**边界与结论 → 引用框**

- 「不能只凭 X 判定通过」「此数据不代表真实场站」这类否定/限定结论，单独放 `>` 引用框与正文隔离。
- 需要列举判定依据时，在引用框内再嵌列表。

**分组小标题**

- 超过 6 条的无序列表，按主题拆成若干组，每组配一个加粗小标题（如「文件骨架 / 正文元素 / 链接与术语」）。
- 超过 6 行的表，按主题拆成多张表，各配加粗小标题。

### 状态只写一处（2026-10-23 起硬性；2026-11-08 改为入口 + 分卷）

- **现行状态只在 [[00-当前系统状态]] 及其分卷（`notes/06-当前系统状态/`）维护**：入口页只放七行生产摘要与分卷索引；生产快照、阶段状态、运行能力、已知限制、口径与开发环境各自一页分卷。其它页面只允许写一句 `当前状态见 [[00-当前系统状态]]`。
- **摘要与分卷同批一致**：发布、回退或能力变更后先改分卷、再改入口摘要行，两者不得互相矛盾；入口页不产生分卷之外的新结论。
- **单页 15,000 字上限**（治理检查器硬约束）：接近上限时按主题拆新分卷，不得为压字数删事实，也不得把明细复制回入口页。
- 入口文档（`README.md`、两本手册、验收清单、运行产物说明、规范总纲、各阶段 `README.md`）顶部**不得**按日期堆叠发布批次；需要保留的批次事实写进 `04-系统部署发布备份与变更记录/部署与运维日志`，由索引摘要。
- 可以留在原页的"状态"只有两类：**验收里程碑**（一次性、不再变化，如 M1 2160/2160）与**该页自身的维护说明**。
- 发布或回退后，在同一批次内回写状态页；漏改视为该批次未完成，不得"下次一起补"。
