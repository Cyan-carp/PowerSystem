# 阶段联调与验收规范

目的：把环境前提、复现证据与阶段签收判据放在同一入口。

## 跨阶段联调的环境前提与复现边界

### 环境前提与复现边界

**环境前提**

- 依赖：Docker Desktop Engine、Go 1.24+、Python 3.12+；端口 `1883`、`18083`、`6041`、`5432`、`6379`、`8080` 不应被其他服务占用。
- 仓库根目录 `.env` 为本机私有文件；新环境按 `.env.example` 准备，已有 Docker 卷必须使用与该卷匹配的密码。
- 四个基础容器（EMQX、TDengine、PostgreSQL、Redis）端口均映射到 `127.0.0.1`，仅供本机程序连接；数据库密码保存在被 Git 忽略的 `.env`，不写入笔记。

**复现边界**

- `artifacts/`、`.env`、Docker 数据卷不随 Git 迁移；换机器必须重新准备环境与生成数据，旧运行编号不会自动出现，以新运行编号保存证据。
- Docker CLI 未在 `PATH` 中不能直接判定 Docker Engine 不可用，应检查安装路径、服务端和容器状态；阶段一脚本的 `Get-DockerExe` 会尝试查找用户目录的 Docker Desktop 安装路径。
- Compose 容器与本机启动的 API/网关进程不要混为一谈；`ping` 只说明 API 接口可达，四容器状态、进程启动结果和烟测全通过，才能证明基础链路就绪。
- 烟测会在指定数据库创建测试账号、设备和遥测；完整 M2 两小时注入故障属于历史里程碑证据，后续开发按 [[02-工程规范边界与验收治理/项目工程规范/03-协作联调与验收/03-开发测试与运行观察规范]] 和所有者授权决定是否做受影响短测，不自动重跑。
- 停止服务分别用 `stop-ai.ps1` 与 `stop-stage2.ps1`；两者不会删除数据库卷，勿用 `docker compose down -v` 清理历史数据。
- 阶段一新建验收库报 `954 Vnodes exhausted` 时，既有 TDengine 容器 vnode 已满；不要删除 M1/M2 库或卷，短回归用 `stages/02-backend/scripts/regress-stage1-isolated.ps1` 的临时容器。
- `.venv` 启动器在含中文的仓库路径下可能失效：不删除既有 `.venv` 或验收数据，改用可工作的 Python 3.12 执行脚本。
- 若当前环境没有可用的 Docker Engine：只做离线单测、代码审查和文档，将该环境的 M3 复验记为未完成，转到有权限的主机重跑；这不改写已保存的 2026-09-29 M3 验收结论。

> **不能只凭模型离线成绩或 `/health` 判定 M3 通过**，需在故障点发送前记录：
>
> - 预测产生时间
> - PostgreSQL `prediction_records` 入库
> - 带 JWT 的 `GET /api/v1/devices/{id}/prediction`
> - AI 告警及 WebSocket 推送
>
> 故障后还需记录恢复、重复窗口去重，并检查重启后的行为。验收结论必须对应具体证据，原始失败报告应保留。

## 验收清单的持续维护

[[02-工程规范边界与验收治理/项目验收与收尾清单/00-索引·项目验收与收尾清单]]是项目级状态入口，必须随项目推进更新。先写当前跨版本判定，再依次保留第一版阶段一至六与项目总结，随后按日期记录第二版 V2-M1～M4、历史批次和现行长期待办；阶段内写清已完成内容、可复核证据、验收结论和未覆盖边界。历史未勾选项必须标明当时日期，不能误作当前阻塞。阶段五是第一版业务能力，阶段六是第一版公网安全与恢复亮点，二者均纳入 M4，不另设 M5/M6。项目总结不把部分功能上线、单次冒烟或合成数据指标外推成全项目验收；视频复盘与对外材料不属于第一版发布门槛。

**更新时机**

- 每完成一个阶段里程碑、关键功能、联调或部署验收，即更新对应阶段和项目总结；失败后的修复与补测也要更新，保留旧失败证据。
- 日常修复不走本节的全链回写：只留一份变更记录，涉及生产变化时同批更新 [[00-当前系统状态]]；只有接口、用法或资产变化才更新对应手册与台账。分档见 [[02-工程规范边界与验收治理/项目工程规范/01-文档与目录治理/03-文档同步与链接维护规范]]。
- 需求范围、FR/NFR 实现、公开数据适用性、服务器状态或发布范围改变时，同步更新受影响的阶段结论和当前待办。
- 每次新增或改变 `artifacts/` 中的长期保留证据、模型、外部数据目录时，同步更新 [[02-工程规范边界与验收治理/运行产物说明/00-索引·运行产物说明]]；原始大文件、密钥和运行账本仍由 Git 忽略。

**填写与复核规则**

- 每条"已完成"须指向笔记、源码、测试结果或具体运行编号，并记录核对日期；"已实现""已测试""已验收""真实环境已验证"分别表述，不互相替代。
- 本机证据未入库时标明 `artifacts/` 路径与复现入口；远端服务器未复测时写明最后实测日期，不能默认为仍在线。
- 现行未完成项单列并按 P0/P1/P2 或明确后续归属排序；历史未完成项保留批次日期与后续结果链接。完成后勾选并归入对应阶段的证据与结论，新增由本轮工作暴露的风险。
- 更新清单时同时核对根 README、阶段索引、运行产物说明和相关双链；阶段发布时核对 `main`、标签及 GitHub Release 的准确提交范围。
- 阶段收尾前必须核对独立问题记录页：已解决项附验证结果，未解决项附后续归属和阻塞判断；不得只在聊天、终端日志或测试交付表格中临时描述。
