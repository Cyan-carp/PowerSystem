# 05 · 上传服务器与分级发布规范

> 本页统一规定变更分档、上传、发布、备份及恢复边界。命令与参数只在 [[06-代码工作区导航与链接映射/stages-04-frontend-deploy-README|部署 README]] 维护；生产实际支持的工具版本与未完成事务只认 [[00-当前系统状态]]。本次优化依据和验证归 [[54-开发测试发布与备份流程提效]]，旧批次不能充当新能力已生效的证据。

## 开发阶段执行优先级

当前开发阶段的效率、测试与观察要求唯一见 [[03-阶段联调与智能体长期约定]] 第五章。下面的备份/门禁序列描述既有工具默认路径；所有者明确授权免门禁、免测试或暂不备份时，优先执行该授权，不将默认路径重新作为前置阻塞。

直接接受时保留实际版本、来源与配置，接续原事务，记录所有者授权、未执行项和接受依据；更新实际active并归档pending/恢复标记，避免后续发布反复被旧事务阻塞。所有者接受回执不伪装成技术通过，不编造未实现的skip参数，不为一次性收尾扩建发布平台。既有定时备份除非另有明确要求继续运行。

历史积压放弃只按明确固定截点处理，保留原始记录与审计；本规则不允许擅自清卷、扩大权限或反复延后截点。

## 一、四条开工条件

- **指针现查**：同时核对已验 active、实际运行镜像与 pending；验收状态与部署事实分开记录。
- **范围明确**：先选本地开发、兼容普通发布或高风险变更；不按文件大小判定风险。
- **构件已定**：完整源码快照和受控构建回执绑定固定 image ID；发布不重复构建、不拉取依赖。
- **恢复依据明确**：按冻结档位核对新全备或“有效全量基线＋候选构件小包”，不把已有数据备份说成本次数据增量。

## 二、先核对服务器当前指针

| 核对项 | 判据 | 不满足时 |
| --- | --- | --- |
| 已验 active | 清单、门禁与私有引用摘要有效 | 先查登记与实际运行的差异 |
| 实际运行 | 全部镜像、配置、容器身份可解释 | 普通候选不得覆盖未知现场 |
| pending | 普通发布要求不存在 | 只允许绑定原事务的回退或前滚恢复 |
| 父版本 | 候选 parent 等于现查已验版本 | 重新准备候选 |

不兼容 schema 已生效时禁止启动旧 worker；恢复应前滚或冻结待修复，不机械执行回旧镜像。任何事务恢复均保留失败证据，不删 pending 或伪造验收。本次效率改造不代签已有未验版本。

定时全备只改变已登记写者的启动时间时，可用成功密文及精确停复回执执行 `reconcile-backup`：同版本、同镜像、同容器、同重启数、当前健康与配置均须匹配。它继承原功能验收，记录未重跑 HTTPS/WSS，不重建服务；失败备份、未知重启或换实例不适用。

## 三、判定变更范围

| 场景 | 档位 | 必要验证与恢复依据 |
| --- | --- | --- |
| 本地开发、文档、排版预览 | 不发布 | 构建或受影响检查；不触发生产备份与门禁 |
| 兼容应用修复 | `standard-fast` | 定向测试、兼容评估、有效全量基线＋构件小包、主域名短验 |
| 仅前端静态展示 | `frontend-fast` 或普通档 | 原前端档兼容保留；普通档须满足其来源及评估约束 |
| 迁移、数据修复、持久化语义、权限或契约变化 | `full`＋对应专项 | 候选后新全备、受影响隔离验证、完整发布门禁 |
| 密钥、端口、卷、服务集合等基础设施变化 | 独立计划 | 原入口仍拒绝未声明变更 |

`standard-fast` 仅允许 api、gateway、frontend、agent-rag、ops-agent、security-agent 的固定镜像替换；编排、环境、挂载、端口、卷与父版精确相同。必须保留父/候选来源；迁移、SQL、schema、契约、策略/权限及构建依赖等保护文件变化直接拒绝普通档。无法确认兼容性时升级为 full，不临时修改已冻结档位。

兼容评估绑定候选、父版、实际测试镜像、生产关键配置核对及定向测试证据摘要，并明确无 schema/数据修复/权限/存储/契约变化、可回旧应用、接受最多24小时数据恢复点。源码保护检查不能代替对写链路语义的判断；ACK、幂等、历史重放等改动必须做相应可靠性专项，不能仅因没有 SQL 就按普通修复放行。

## 四、文件上传前的换行符与摘要

- 从明确提交＋已审增量导出完整源码快照；文本增量统一 LF，导出即记录逐文件摘要。不从服务器历史 stages 零散覆盖后构建。
- 上传到本轮独立暂存目录，核对目标身份及目录定位卡；受控工具先验证完整快照，再构建一次并生成绑定 image ID 的来源回执。
- 以内容区分 CRLF 差异，正式冻结与构建后按实际字节核哈；不能用本机摘要代替服务器实核。
- 不覆盖其他会话或未审旁路改动；冻结之后不原位改源码、私有引用或清单。

## 五、私有配置与镜像

- 凭据、完整配置和原始运行材料只留受保护目录，不打印、不提交。私有布局与真实 `/run/` 挂载逐项核对。
- 配置变化使用新路径与新候选；仍被引用的旧私有目录、镜像、构建来源和备份基线不能按缓存清理。
- 全部服务固定实际 image ID，只重建指定应用；不使用 latest、不自动拉取或重建依赖。
- 继续核对 API/RAG/Ops 连接、原权限边界和资产身份。发布提效不增加 S07、运维写权限或敏感出站范围。

## 六、标准发布序列

顺序为：范围与定向验证 → 一次受控构建 → prepare 冻结 → 按档位准备恢复材料 → publish → 一份变更记录。日常开发不套用阶段验收全套流程。

### 6.1 prepare

继续冻结完整编排、来源、私有引用及实际运行基线，运行私有布局、资产登记与迁移解析短检。普通档额外核对兼容评估、保护文件差异和有效数据基线。CLI 保留 full 为保守默认；普通修复须显式选择 standard-fast，不猜测未知风险。

### 6.2 更新前加密备份

- **full**：候选后新全量密文、SHA256及成功双端上传回执，按实际范围记录各引擎一致性快照。
- **standard-fast**：复用24小时内、双端成功且与当前应用基线兼容的全量密文。当前版本之后的基线或兼容快发布链继承的基线才可用；每次仍复核年龄和摘要，不无期限顺延。
- **候选构件小包**：候选后生成并加密保存本次变更镜像、完整源码/构建回执、冻结配置/评估/证据及匹配控制器依赖；新小包双端上传成功才可发布。它不重新导出遥测、向量和数据库。
- **frontend-fast**：保留原前端小包与基线组合，不把历史格式冒充普通应用小包。
- **定时全备**：独立于普通发布运行。既有双目标默认并行上传；已安装 pigz 时默认4线程，否则单线程 gzip；可按资源显式调回串行/单线程。保留原格式、双端失败可见性与锁。

备份与部署仍互斥，失败保留本地密文和恢复信息。全备不是跨引擎同一时刻的原子事务；当前 pg_dump 不是 WAL 增量基线，本轮未新增 PITR 或去重备份格式。

### 6.3 publish 与门禁

所有档位均核对来源、父版、摘要、完整配置、实际镜像与健康、未变更服务身份、任务排空及结束时稳定性；保留部署锁和失败处理。

- **standard-fast**：主域名 HTTPS 的匿名401、真实操作员登录、核心只读业务、会话/任务及可用详情、ticket/WSS101。受影响功能的定向测试证据随候选冻结；不自动调用模型、不重复容量和恢复全矩阵。
- **full / 原frontend-fast**：原双入口完整 HTTPS/WSS 门禁保留；更改边缘网络、反向代理或鉴权不能借普通档缩减入口覆盖。
- **专项测试**：迁移、可靠性、模型/知识、安全、容量等按变更影响做定向短测。开发阶段取消两小时及AI驻守长观察；真实服务器自然运行、本人启动短观察脚本的规则唯一见 [[03-阶段联调与智能体长期约定]] 第五章。缺失与取消项如实登记，不把取消写成通过。

默认路径以门禁通过更新已验active；所有者明确免门禁时，以真实所有者接受回执登记active并标明未技术验证。服务替换成功与功能验收通过分开表述；`status` 同时给出实际镜像及其是否匹配已验版本。

### 6.4 回退与中断

- 普通兼容发布失败，按已验直接父版恢复应用并执行其冻结档位门禁；保留数据、失败和事务。
- 高风险变更在操作前明确可回退还是只能前滚；schema 已不兼容或未知时先冻结，禁止自动启动旧 worker。
- 中断、回退失败或已有 pending 必须沿原事务受控接续。专用 TR 恢复仅适用原绑定候选，不变成普通绕过入口。
- 门禁故障先判断业务、夹具、网络还是校验器缺陷；非阻塞工具改进另排任务，不要求先扩建发布平台再恢复业务。

### 6.5 证据

保留候选/父版、源码与镜像摘要、冻结评估及测试证据、计时、引用备份与小包、门禁范围和未执行项。日常修复只写一份变更记录；运行变化更新唯一状态，接口/用法/资产变化才改对应入口，阶段里程碑才交四件套＋八项交接。

## 七、可恢复性条件（含兼容快路径）

### 7.1 恢复材料分工

全量基线负责其实际覆盖的数据与私有环境；小包负责新应用、构建来源、冻结配置和工具。镜像回退不回灌数据库；恢复副本不自动激活生产指针、凭据、批准、worker或任务。

### 7.2 快路径必须具备的条件

兼容范围闭合、父版已验且实际身份一致、完整可核来源、24小时内双端全量基线、候选后双端小包、匹配档位门禁与可用父版缺一不可。首次使用新的组合格式前做一次对应组合的隔离核对；普通档镜像/源码/配置小包的离线读取不冒称数据库恢复演练。

### 7.2.1 恢复能力复核：按变化及独立周期执行

- 每个新包验证密文、内层摘要和结构；`verify-backup-integrity.py` 只代表可读和结构完整。
- 备份/恢复脚本的行为、范围、格式、加密或存储大版本变化，做受影响恢复专项；普通发布控制逻辑修改只验证其影响，不自动跑全平台恢复。
- 完整隔离恢复按独立维护周期保持不超过30天，交接或对外承诺恢复能力前核对有效证据。周期到期进入备份维护待办；普通兼容发布只要现有材料满足档位条件，不为该日历事项重复全备。
- 真正缺少可核数据恢复依据、迁移兼容性或被影响的恢复能力时，仍阻断相应高风险操作；不能用结构校验代签可恢复。

### 7.3 PostgreSQL增量边界

现有 pg_dump 是逻辑快照，没有可续接 WAL 链。物理基础备份＋WAL归档或其他增量方案需独立设计、恢复验证；本轮通过复用有效基线减少发布等待，没有声称实现数据库增量备份。

### 7.4 不能算作提效的做法

不擅自清队列或删事务，不伪造时间/健康；未获豁免时遵守恢复材料条件，所有者明确豁免时如实登记缺失项；不以声明替代实际来源；不把本地实现、HTTP200或一次短验说成生产长期稳定。

## 八、快慢路径选择

先判影响，再选受影响检查与恢复材料。兼容普通修复优先 standard-fast；前端旧档继续兼容；新迁移、数据修复、权限、契约及可靠性语义调整采用 full 或明确专项。档位与兼容评估冻结后不可原位改写，服务器未安装的新档不可宣称已启用。

## 九、禁止绕过

- 不使用不存在的 `--skip-test`、`--force` 或任何跳门禁开关；入口没有这些参数。
- 不擅自删除事务、锁或伪造技术通过；所有者授权的直接接受可以保存回执、更新active并归档pending/恢复标记。
- 不用单份 Compose、临时 `docker run`、`docker compose up` 或历史脚本覆盖现网应用。
- 不对生产执行 `down -v`，不清卷、不换持久卷、不删已验收镜像与仍被引用的私有目录。
- 不在生产源码目录直接改文件，不用本机摘要替代服务器实际摘要。
- 不把候选失败写成生产失败，也不把生产失败归因到未取证的环节。
- 不用记忆里的指针代替现查，不并发发布，不在 `pending` 未清时普通续发；明确绑定原事务的恢复只按对应入口执行。
- 不用合成数据、单次冒烟或局部绿灯宣称长期稳定或真实业务已修复。
- 不把待清理文件送进回收站：`Remove-Item`、资源管理器删除、拖入回收站**都不算删除**，只是把遗留从工作目录搬到系统目录；临时物必须直删并复核路径不存在（见第十一节）。

## 十、服务器项目目录索引（每次上传当场更新）

> 这是定位入口，不是全盘文件清单。以下固定路径由部署脚本与现有发布记录确认；动态批次须从当前指针和挂载读取，不凭旧日志猜测。只记录路径与摘要，不记录私有文件内容。服务器不可达时不得把旧记录标为“实时已核对”。

| 类型 | 服务器固定入口 | 直接定位方法 |
| --- | --- | --- |
| 项目根、基础环境 | `/opt/powersystem/`、`/opt/powersystem/.env` | 阶段源码和部署工具都从项目根定位 |
| 生产发布指针/锁 | `/opt/powersystem/runtime/production-stack/active.json`、`pending.json`、`deployment.lock` | 先读 `active.json` 与 pending，不遍历 runtime |
| 当前冻结候选 | `/opt/powersystem/runtime/production-stack/releases/<active或候选>/` | 版本名直接来自指针或本次 `--id`；该目录内有 `manifest.json`、`private/compose.json`、门禁记录 |
| 分段计时 | `/opt/powersystem/runtime/production-stack/timing/` | 按候选和时间读取，不扫其他 runtime 批次 |
| 运行私有批次 | `/opt/powersystem/runtime/<ma-m4-批次>/private/` | 当前 `manifest.origin_environment` 给出精确 env 路径；其父目录定位 `private/executor/` |

| 密钥及备份目标 | `/etc/powersystem/` | 仅核对目标文件存在、权限与摘要；不读值、不上传到 Git |
| Ops 只读登记 | `/etc/powersystem-ops-read/registry.json` | 直接核对登记版本与数据库已提交版本 |

## 十一、临时文件与删除纪律

> **本节是硬性要求，不是建议。** 直接来源：2026-10-23 本机回收站累积约 15 万个条目，导致资源管理器与文件枚举明显卡死；追查确认为历次上传、构建、比对遗留的临时副本与旧产物被“删进回收站”而非删除。**往回收站丢不等于清理，只是把垃圾从工作目录转移到系统目录，并且会一直累积到拖慢整机。**

### 11.1 四条不许

- **不许把回收站当清理手段**。删除本批次产物时，不允许用资源管理器删除、拖入回收站、`Remove-Item`、`del`、`rd` 等任何会被删除拦截层或系统转存进回收站的方式。
- **不许批外遗留**。本批次创建的临时目录、暂存文件、对比副本、镜像导出、日志，必须在同一批次内清除，不得留给下一次任务。
- **不许以“命令没报错”作为删除成功**。唯一判据是路径不存在：Windows `Test-Path` 返回 `False`，Linux `test -e` 返回非 0。
- **不许用清空回收站代替清理**。它掩盖遗留事实，并销毁“哪些文件曾被删”的唯一记录。确需清空属于独立动作，须单独说明影响后再做。

### 11.2 允许的删除方式

| 环境 | 对象 | 方式 |
| --- | --- | --- |
| Windows 本机 | 单个文件 | `[System.IO.File]::Delete($path)` |
| Windows 本机 | 目录（含子树） | `[System.IO.Directory]::Delete($path, $true)` |
| 服务器主机 | 文件或目录 | `rm -rf <path>`（Linux 无回收站） |
| 服务器容器内 | 容器内临时文件 | `docker exec <容器> rm -rf <path>` |

本机装有删除拦截层，`Remove-Item` 会被改写为“移入回收站”且失败率较高。**永久删除一律走上表的直删方式**，执行前确认目标确属本批次产物。

### 11.3 边界（不许顺手扩大）

- 只清自己本批次创建的东西。`artifacts/`、`node_modules/`、`.git/`、历史归档快照、`notes/` 笔记与用户个人文件**不在本节授权范围内**，不得以“清理”名义删除。
- 服务器 `/tmp/<批次>/`、`/tmp/src-before-*`、`/tmp/src-backup-*` 一类暂存与原件备份：核对完成后批内删除；确需留作回退证据的，写进部署日志并注明保留到何时。
- 删除前若目标是他人创建或来源不明，先停并确认归属，不得凭“看起来像临时物”就删。

### 11.4 收尾必答三项

每次任务收尾陈述必须逐条回答，缺任一项视为未收尾：

1. 本批次创建了哪些临时路径（本机与服务器分别列出）；
2. 每个路径用什么方式删除、复核后的结果；
3. 是否有刻意保留的中间物，保留到什么时候、依据是什么。

> 附带的取证事实：回收站每个条目旁的 `$I` 元数据文件是原始路径与删除时间的唯一记录。一旦删除即无法还原，NTFS USN 日志查询需管理员权限。因此“先删再说”会让事后追查彻底失去依据。
