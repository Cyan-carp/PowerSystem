# 05 · 上传服务器与分级发布规范

> 本页规定“把已审代码送上服务器并切换生产”的最小必要条件、快慢路径的选择依据和不可绕过的边界，供今后每次上线遵循。具体命令、参数和当次基线只在 [[06-代码工作区导航与链接映射/stages-04-frontend-deploy-README|阶段四服务器部署说明]] 维护，本页不复制命令。
>
> **当前状态（2026-10-22）**：分级发布快路径已于当日 22:09 完成**首次生产启用**（`report-duration-20261022-r1`，仅前端）：prepare 17.8 s、前端小包 21.5 MB、publish 100.4 s，全批约 2.5 分钟；基线 `powersystem-20261022T134233Z` 已完成“全量基线＋前端小包”隔离恢复短演练（`ma_restore_passed=true`）。启用过程中修复了控制器的凭证命名缺陷（原按 `*.tar.gz.gpg.timing.json` 查找，`backup.sh` 实际输出 `*.timing.json`），此前快路径必然失败。快路径仍非默认档，须显式 `--tier frontend-fast`，基线有效期 24 小时。

## 一、四条开工条件

同时满足才可以开始发布，缺一项就停在原地：

- **指针现查**：`status` 显示的 active 版本与 pending 状态是唯一依据，聊天记录、笔记和记忆里的版本名都可能过期。
- **范围受控**：变更只落在发布入口支持的应用服务内，不夹带迁移、卷、端口、服务集合或私有配置变更。
- **构件已定**：候选镜像已独立构建、审查并取到实际镜像 ID，发布时不构建、不拉取。
- **备份在后**：完整路径的新全量密文，或仅前端快路径的新加密镜像/配置小包，均须晚于候选冻结且摘要可核。快路径另须引用当前版本之后、24小时内已双异地上传的全量基线。

## 二、先核对服务器当前指针

- 只把 `status` 的现查结果当作基线：active 版本名、pending 是否存在、active 门禁文件是否通过。
- `pending` 存在表示上一轮事务未结束，禁止 `prepare` 与 `publish`，只能先 `rollback` 把事务收尾。
- `prepare` 产出的 `manifest.parent` 必须等于刚查到的 active；不等就说明候选过期或期间有人发布过。
- 设备台账、迁移文件、私有配置任一漂移，都会在冻结或门禁阶段被拒绝；不要先构建完再回头补查。

| 核对项 | 判据 | 不满足时 |
| --- | --- | --- |
| active 指针 | `active.json` 指向的版本可被 `immutable` 校验 | 停止，不入场 |
| pending | 文件不存在 | 只执行回退事务 |
| 门禁文件 | `passed=true` 且摘要与 manifest 一致 | 该版本不能作为父版本 |
| 运行基线 | 当前容器状态与父版本门禁记录逐项一致 | 先查漂移来源 |

## 三、判定变更范围

| 变更类型 | 允许的服务 | 路径 | 额外门槛 |
| --- | --- | --- | --- |
| 前端模板、样式、文案、展示辅助函数、静态资源 | `frontend` | 前端快路径（2026-10-22 已启用） | 类型检查、展示相关单测、路由分块内容核对 |
| API/Go 业务逻辑、配置读取、鉴权、统计口径 | `api` | 完整路径 | 定向测试、真实入口短核对 |
| SQL 迁移、表结构、数据修复 | `api` + 数据操作 | 完整路径，另行授权 | 真实迁移入口隔离短测，psql 通过不能代偿 |
| Agent、RAG、运维、安全、模拟器等 | 对应服务 | 完整路径 | 该阶段既有专项与定向测试 |
| 已引用私有文件的原位修改、密钥轮换、挂载、端口、持久卷、服务集合 | 不在本入口直接支持 | 单独计划 | 控制器会拒绝；私有 env 变更须换新路径并重新冻结 |

**前端-only 的严格定义**：只改 `stages/04-frontend/` 的模板、样式、组件和展示辅助函数；一旦涉及 API 请求、鉴权、路由权限、订阅与历史补查、统计口径、原始时间戳或模型计算，就按 [[02-工程规范边界与验收治理/项目工程规范/02-发布仓库与界面验收规范|界面验收规范]] 单独说明并按影响范围验证，不再属于“仅前端”。

## 四、文件上传前的换行符与摘要

### 4.1 换行符

- 直接复制到 Linux 主机运行的脚本和配置由 `.gitattributes` 固定 LF；Windows 本机检出可能是 CRLF。
- 判漂移用内容比较，不直接用 md5 或 sha256 比字节：CRLF 差异会让大量未改文件报“内容不同”。
- 确需上传的文本文件在服务器上统一转 LF 后再参与构建；CRLF 混入会改变镜像内容，使实际镜像 ID 偏离已审候选。
- 提交前跑一次空白检查，避免把行尾空白和混行带进生产。

### 4.2 摘要

- 候选的 `manifest.json` 记录冻结文件、镜像 ID、私有引用摘要、控制器摘要和冻结时的运行基线；`immutable` 会逐项复核，冻结后原位修改任何一项都会失败。
- 私有引用摘要按服务器实际文件计算（含 `/run/` 挂载目录下的全部文件），所以“本机摘要一致”不代表服务器一致，也不代表内容相同。
- 发布后核对运行镜像 ID 与 manifest 是否一致；不要只看容器是否 running。

### 4.3 源码覆盖

- 不在生产源码目录直接编辑；改动先落 `/tmp` 暂存目录。
- 覆盖前与仓库对应版本做内容比对，不一致先查差异来源，确认是旁路改动前不得覆盖。
- 覆盖后再复核一次；原文件另备份，便于回看。

## 五、私有配置与镜像

### 5.1 私有配置

- `.env`、各类令牌与密钥文件、`/run/` 挂载目录、资产台账都属于私有运行材料：不入 Git、不进笔记、不打印、不写入命令历史。
- 私有 env 必须位于 `runtime/<批次>/private/`，且真实 Executor 的 `/run/ma-executor` 挂载源与该批次 `private/executor/` 一致；布局不符会在 `prepare` 的 `private_layout` 检查处停止。
- 已被当前版本引用的私有文件不可原位修改；需要变更就复制到新路径、生成新候选。仍被引用的旧批次目录不能按“旧文件”清理。
- 发布过程只在日志里记录路径、摘要和计数，不记录值。

### 5.2 镜像

- 先独立构建、审查、跑定向测试，再在 `prepare` 时以 `--image 服务=标签` 传入；入口会解析成实际镜像 ID 并写入 manifest。
- 禁止浮动标签、禁止 `latest`、禁止在发布阶段 `--build` 或 `--pull`；发布只重建显式指定的服务。
- 上一版及更早的已验收镜像在下一版签收前必须保留在本地，回退依赖它们；清理镜像等于拆掉回退路径。
- 候选构建失败、超时或上传中断都只属于候选阶段，不得写成生产故障，也不得据此放宽门禁。

## 六、标准发布序列

顺序固定：`prepare` → 按候选冻结档位生成更新前加密备份或快路径小包 → `publish`（含同一套门禁）→ 证据归档。任一步失败即停止，不续跑、不跳过。档位写在候选 manifest，不能在同一候选上临时改档。

### 6.1 prepare

`prepare` 只做只读解析与冻结，不构建、不启动容器。它会锁定全部服务镜像、保留原端口与持久卷身份、拒绝未声明服务的环境漂移，并跑三项前置短检：私有布局、资产台账版本、API 镜像内迁移文件的切分兼容性。三项短检失败可直接用同一 id 重跑，不写候选目录。

> 叠加层不变时不要手工传 `--from-args`，让它继承上一版的完整参数；手工构造容易只带五份基础编排而丢掉官方解读层或扩容层。

### 6.2 更新前加密备份

- **完整路径**：执行下列全量备份；候选之后生成，附摘要并上传主备两处。
- **仅前端快路径**：在已有有效全量基线的前提下，本次仍要生成加密小包，内含固定前端镜像、冻结清单和基线摘要，并上传主备两处。数据库恢复点停留在基线时刻，最长24小时；不称为本次数据增量备份。所有者在本对话明确接受此项 RPO。基线/小包任一条件不满足就停止，改用新候选走完整路径。
- 备份覆盖 PostgreSQL 两个库、TDengine、Redis RDB、两个 SQLite 队列一致性快照、模型、私有配置与令牌、Agent 审计与知识索引、RAG 向量与模型、运维资产、发布状态目录及控制器。
- 备份与发布共用同一把部署锁：全量备份持共享锁，前端小包与发布持排他锁，避免跨版本交叉；任何锁冲突都停止，不自行移除锁文件。
- 备份产物必须有 `.sha256` 旁车；`publish` 会核对摘要、要求密文位于业务机备份目录、生成时间不早于候选。快路径还要求全量基线带成功计时旁车，证明主备两处上传，并在发布时仍小于24小时。
- 上传失败时本地密文保留并返回失败，不把“主目标成功”当完整成功。

> 备份是多引擎按阶段采集的快照集合，不是跨存储的单一事务时刻。写证据时只能用“各引擎各自的一致性快照”，不能宣称全平台同一秒。

### 6.3 publish 与门禁

`publish` 依次确认父版本、候选摘要、基线未漂移、备份有效，然后重跑同一组前置短检、排空未完成任务、写入事务记录，再只重建候选列出的服务。之后自动门禁核对：

- 全部服务健康，服务集合与冻结时一致。
- 每个服务运行镜像等于 manifest；未变更服务的容器 ID、镜像、启动时间、重启次数不变（Executor 仅因登记刷新豁免启动时间）。
- Compose 配置可再次解析并通过同一组生产配置校验，运行环境与冻结声明一致。
- 两个公网入口真实操作员登录、匿名访问 401、核心列表与非空列表详情、一次性 ticket、WSS 101 全部通过。
- 验收结束时运行状态与门禁开始时一致。

全部通过才原子切换 active 指针并删除 `pending`。

### 6.4 回退与中断

- 门禁失败自动回退到直接上一份已验收版本，并重新跑同一套门禁；失败证据与事务记录保留。
- 回退只重建候选涉及的服务，使用上一版冻结编排；不降级数据库、不覆盖业务数据、不恢复已删除记录。
- 人工回退只能指向直接上一份已验收版本；`pending` 未清时禁止新发布，不删标记强行续发。
- 专用恢复脚本是为单一批次写的收尾工具，不是通用重试按钮，换批次必须重新评审。

### 6.5 证据

每次发布至少留：发布前后指针与父版本、`prepare`/`publish` 时间线记录、备份文件名与 SHA256、门禁日志、实际运行镜像 ID、部署日志编号。证据只写阶段名、耗时、字节数和计数，不写命令输出、密钥、JWT、ticket 或完整响应。

## 七、可恢复性条件（含前端快路径）

### 7.1 现行动作留下的可恢复物

- **应用回切物**：上一版冻结 manifest、门禁文件、私有引用摘要、该版全部镜像 ID 与本地镜像。
- **数据恢复物**：本次更新前加密备份及其摘要，可在隔离项目里解密、校验、导入。
- **事务凭据**：`pending.json` 记录上一版、候选、服务集合、变更前状态与备份摘要。

这些是三类不同的东西：备份能重建数据，不等于能回切应用；应用回切也不恢复数据。

### 7.2 前端快路径必须具备的条件

快路径指“只改前端静态资源时缩短发布关键路径”，不是“少做检查”。启用前必须同时满足：

1. **变更面封闭**：候选服务集合严格等于 `{frontend}`；不改 API、Agent、迁移、卷、端口、服务集合与私有配置。
2. **基线可验证**：上一版 `immutable` 通过、门禁 `passed`、manifest 摘要与 active 指针一致、全部镜像仍在本地。
3. **备份基准有效**：存在一份晚于当前非前端版本生效、24小时内完成的全量密文，摘要与成功计时旁车可查，主备两处上传均有凭据；若上一版也是前端快发布，可沿用其同一基线。首次启用前须完成“全量基线＋前端小包”的隔离恢复短演练（2026-10-22 已完成）；此后按下方 **7.2.1 的触发条件**复核，不按日历排期；不把上传成功等同于恢复成功。本次数据库恢复点仍是基线时刻，最多丢失24小时的随后运行数据。
4. **门禁不裁剪**：前置短检、任务排空、全服务健康、未变更服务身份、环境一致、双入口 HTTPS/WSS、结束时稳定性检查全部保留。
5. **审计可追溯**：部署记录写明“本次未新建全量备份”、基准备份文件名与 SHA256、接受最多24小时RPO的依据、前端小包摘要及双异地上传结果；不能只写“走了快路径”。
6. **失败可回退**：回退所需的镜像、冻结编排与指针链完整，且回退后同样重跑全部门禁。

> 快路径已于 2026-10-22 在生产完成首次启用（见 [[04-系统部署发布备份与变更记录/部署与运维日志/36-报表时长格式与快路径首次启用]]）：控制器含显式 `frontend-fast` 档位与小包核验，凭证按 `backup.sh` 实际命名的 `<run>.timing.json` 解析；基线/小包/门禁三段均已有实测耗时。启用不改变本节条件，每批仍需现查基线与回退材料。

> 24小时RPO只覆盖全量基线实际纳入的运行数据，不包括未备份的EMQX/Grafana/Prometheus数据卷；全量包也不含全部非前端Docker镜像。前端小包保存本版前端镜像和控制器，但不能替代这些缺口，恢复演练须逐项记录。

### 7.2.1 恢复能力复核：按触发条件，不按日历

两类动作口径不同，不得互相替代：

| 动作 | 频率 | 内容 | 允许的结论 |
| --- | --- | --- | --- |
| 轻量连续性检查 | 每次续基线后，按需 | `verify-backup-integrity.py`：密文摘要、GPG 解密、内层 SHA256SUMS、必需私有文件、队列快照、`pg_restore -l` 可读性、SQLite 表与行数；不启动业务容器、不导入数据 | 只能写“备份可读、结构完整” |
| 完整隔离恢复演练 | 触发式 | `restore-verify.sh`（隔离项目导入 PG/TDengine/队列/私有文件）＋小包内层核对 | 可写“恢复演练通过” |

轻量检查实测：冷态首次 144 s（其中 `postgres:17.6` 镜像解包约 111 s），热态约 55 s；`pg_restore -l` 按 20 张表 / 17 段表数据判定 dump 可读。

完整演练的触发条件，满足任一即做一次：

- 备份脚本、恢复脚本、备份范围或加密方式变更；
- 控制器（`production-stack.py`）变更；
- PostgreSQL、TDengine、Redis 大版本或镜像标签变更；
- 距上次完整演练超过 30 天；
- 交接给他人，或需要对外声明 RPO 之前。

不做完整演练时，须在部署记录里显式接受三项代价：失效只会在真正需要恢复时暴露，届时没有第二次尝试机会；“最多 24 小时 RPO”只是未经演练的推断；EMQX/Grafana/Prometheus 数据卷与非前端镜像不在备份范围内，容易被误读成“全平台可恢复”。

```bash
python3 /opt/powersystem/stages/04-frontend/deploy/verify-backup-integrity.py \
  /var/backups/powersystem/powersystem-<UTC>.tar.gz.gpg \
  --output /opt/powersystem/runtime/<批次>/integrity.json
```

`--skip-toc` 用于没有 docker 的环境；报告 `status=ok` 仅代表完整性与可读性，不代表可恢复。续基线本身不触发完整演练。

### 7.3 为什么不能用 pg_dump 当 WAL 增量基线

- 现行备份对 PostgreSQL 用的是 `pg_dump -Fc` 逻辑转储，按库各导一次；它给出的是导出时刻的一致快照，文件本身不含可续接的 WAL 链。
- 生产 PostgreSQL 没有开启归档，没有 `pg_basebackup` 基础备份，也没有 WAL 归档上传步骤；备份脚本里不存在任何 WAL 产物。
- 逻辑转储不带可供恢复目标锚定的物理位置；即使将来补了 WAL 归档，也不能把某段 WAL 接到一份逻辑转储后面继续回放。
- 因此“前端只传静态文件，数据库靠 WAL 增量补齐”在技术上不成立；PostgreSQL 只有两条路：每次重新做全量逻辑备份，或另行设计并验证物理基础备份加连续 WAL 归档的时间点恢复。
- 恢复脚本的口径也要说清：它在独立项目里验证密文完整、摘要、私有文件、主要表行数与队列可读，属于“备份可恢复性验证”，不是生产回切，更不是任意时间点恢复。

### 7.4 不能算作“快”的做法

- 仅拿旧备份替代本次小包：快路径仍需候选后新建镜像/配置小包；旧基线只承担最多24小时RPO的数据恢复依据，不能冒充本次增量数据。
- 只备份前端镜像或静态目录：缺少私有配置、发布状态与数据面依据，回退和取证都不完整。
- 跳过排空、跳过双入口门禁、跳过未变更服务身份核对：等于放弃唯一能发现“重建了不该重建的服务”的检查。
- 把一次合成探针或 HTTP 200 当作发布通过：协议可达不等于业务、配置与数据都正确。

## 八、快慢路径选择

| 本次变更 | 选择 | 最低证据 |
| --- | --- | --- |
| 仅前端静态资源，且无 API/数据/配置变化 | 快路径（2026-10-22 已启用，实测整批约 2.5 分钟） | 类型检查、展示单测、小包与全量基线、完整门禁 |
| 前端 + API 展示字段 | 完整路径 | 前后端定向测试、真实入口短核对 |
| 任一 SQL 迁移或数据结构变化 | 完整路径 + 单独授权 | 真实迁移入口隔离短测、新全量备份 |
| 已引用私有配置的原位修改、卷、端口、服务集合 | 不在本入口直接支持 | 先出独立方案，换新路径并重新冻结 |
| 不确定属于哪一类 | 按完整路径 | 不做范围猜测 |

> 选择依据是“可能丢失什么”，不是“改了多小的文件”。只要可能改变持久化数据、身份、权限或配置，就必须走完整路径。

## 九、禁止绕过

- 不使用不存在的 `--skip-test`、`--force` 或任何跳门禁开关；入口没有这些参数。
- 不删除 `pending.json`、不删除部署锁、不手工改写 `active.json` 或门禁文件。
- 不用单份 Compose、临时 `docker run`、`docker compose up` 或历史脚本覆盖现网应用。
- 不对生产执行 `down -v`，不清卷、不换持久卷、不删已验收镜像与仍被引用的私有目录。
- 不在生产源码目录直接改文件，不用本机摘要替代服务器实际摘要。
- 不把候选失败写成生产失败，也不把生产失败归因到未取证的环节。
- 不用记忆里的指针代替现查，不并发发布，不在 `pending` 未清时续发。
- 不用合成数据、单次冒烟或局部绿灯宣称长期稳定或真实业务已修复。
- 不把待清理文件送进回收站：`Remove-Item`、资源管理器删除、拖入回收站**都不算删除**，只是把遗留从工作目录搬到系统目录；临时物必须直删并复核路径不存在（见第十一节）。

## 十一、临时文件与删除纪律

> **本节是硬性要求，不是建议。** 直接来源：2026-10-23 本机回收站累积约 15 万个条目，导致资源管理器与文件枚举明显卡死；追查确认为历次上传、构建、比对遗留的临时副本与旧产物被“删进回收站”而非删除。**往回收站丢不等于清理，只是把垃圾从工作目录转移到系统目录，并且会一直累积到拖慢整机。**

### 11.1 四条不许

- **不许把回收站当清理手段**。删除本批次产物时，不允许用资源管理器删除、拖入回收站、`Remove-Item`、`del`、`rd` 等任何会被删除拦截层或系统转存进回收站的方式。
- **不许批外遗留**。本批次创建的临时目录、暂存文件、对比副本、镜像导出、日志，必须在同一批次内清除，不得留给下一次任务。
- **不许以“命令没报错”作为删除成功**。唯一判据是路径不存在：Windows `Test-Path` 返回 `False`，Linux `test -e` 返回非 0。
- **不许用清空回收站代替清理**。它掩盖遗留事实，并销毁“哪些文件曾被删”的唯一记录。确需清空属于独立动作，须单独说明影响后再做。

### 11.2 允许的删除方式

| 环境 | 对象 | 方式 |
| --- | --- | --- |
| Windows 本机 | 单个文件 | `[System.IO.File]::Delete($path)` |
| Windows 本机 | 目录（含子树） | `[System.IO.Directory]::Delete($path, $true)` |
| 服务器主机 | 文件或目录 | `rm -rf <path>`（Linux 无回收站） |
| 服务器容器内 | 容器内临时文件 | `docker exec <容器> rm -rf <path>` |

本机装有删除拦截层，`Remove-Item` 会被改写为“移入回收站”且失败率较高。**永久删除一律走上表的直删方式**，执行前确认目标确属本批次产物。

### 11.3 边界（不许顺手扩大）

- 只清自己本批次创建的东西。`artifacts/`、`node_modules/`、`.git/`、历史归档快照、`notes/` 笔记与用户个人文件**不在本节授权范围内**，不得以“清理”名义删除。
- 服务器 `/tmp/<批次>/`、`/tmp/src-before-*`、`/tmp/src-backup-*` 一类暂存与原件备份：核对完成后批内删除；确需留作回退证据的，写进部署日志并注明保留到何时。
- 删除前若目标是他人创建或来源不明，先停并确认归属，不得凭“看起来像临时物”就删。

### 11.4 收尾必答三项

每次任务收尾陈述必须逐条回答，缺任一项视为未收尾：

1. 本批次创建了哪些临时路径（本机与服务器分别列出）；
2. 每个路径用什么方式删除、复核后的结果；
3. 是否有刻意保留的中间物，保留到什么时候、依据是什么。

> 附带的取证事实：回收站每个条目旁的 `$I` 元数据文件是原始路径与删除时间的唯一记录。一旦删除即无法还原，NTFS USN 日志查询需管理员权限。因此“先删再说”会让事后追查彻底失去依据。
