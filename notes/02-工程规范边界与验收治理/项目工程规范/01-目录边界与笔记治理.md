# 项目工程规范 · 目录、界面、协作与发布约定 · 目录边界与笔记治理

> 本页由 [[02-工程规范边界与验收治理/项目工程规范]] 分卷维护，原有事实、编号和验收边界保持不变。

## 一句话定位

一个仓库、代码按阶段切分，笔记与代码工作区物理隔离。全部正式笔记进入 `notes/` 的六个编号分区，代码统一进入 `stages/`，边缘部署脚本进入 `deploy/edge-server/`，大型证据保留在 Vault 外的 `artifacts/`。

## 一、本页的维护与增补规则

- **单一声明**：同一约定只在本页声明一次；其他笔记需要时用双链指向本页对应章节，不复制条款。阶段内的具体操作命令以各阶段源码 README 为唯一维护入口，本页不复制命令清单。
- **AI 自动增补（长期约定）**：AI 助手在本仓库协作期间，对话中一旦形成新的工程约定（文件归属、命名、流程、边界、安全要求等具有长期效力的规则），应**主动判断归属章节、直接在本页合适位置增补条款**，并在当次回复中说明增补了什么、放在哪里；用户无需逐条要求"写进规范"。
- **增补前先查重**：写入前先检查本页是否已有同类条款，能并入原条款的不另起新条；拿不准归属时放入最贴近主题的章节末尾，并在回复中说明理由。
- **不写入本页的内容**：一次性操作决定、临时排障结论、阶段内具体实现细节，分别归入阶段笔记、问题记录页或测试交付页。
- **现行与历史分开**：现行条款直接替换过时要求，不只在末尾追加相反结论。带日期的历史批次、失败数字和冻结证据保留；其“未启动”“不发布”“未提交”等只描述当时事实，不能覆盖最新正式交付。业务状态以根验收清单和对应正式交付页为准，运行版本以生产指针及部署记录为准，界面实现以当前前端源码为准。
- **跨版本边界的单一入口**：长期有效的能力、服务器、数据、发布、验收与笔记限制，在本页写清维护规则，并同步 [[02-工程规范边界与验收治理/项目边界与协作红线]] 的具体适用范围、原因和核验前提；使用手册、验收清单及阶段笔记只引用或说明与自身相关的例外，避免同一限制出现互相矛盾的版本。
- 本页自身的修改同样遵守第四、五章的排版与同步要求。

**Vault 边界（强制）**

- Obsidian 只打开 `PowerSystem/notes/`，不得再把仓库根目录作为 Vault。
- `stages/`、`deploy/`、`tools/` 和 `artifacts/` 均在 Vault 外；笔记通过 `06-代码工作区导航与链接映射/` 的代理页访问代码。
- 根 README 和阶段 README 属于代码工作区导航，不复制进 Vault；业务设计、验收状态和正式笔记只在 `notes/` 维护。
- 大型运行证据、历史压缩包、私有配置和原始响应不得复制到 Vault。
- 工作区移动后运行 `python tools/note-governance/build_workspace_links.py` 更新代理页；笔记结构调整后运行 `python tools/note-governance/check_notes.py` 与 `python tools/note-graph/build_graph.py`，检查通过才算完成。
- **检查器已接入 CI**：`.github/workflows/notes-check.yml` 在 `notes/**`、`shared-memory/**`、`stages/**`、`deploy/**` 变更的 push 与 PR 上运行 `check_notes.py --ci`，失败即阻断；`--ci` 只放宽 `artifacts/` 私有证据的缺失判定，不得用它掩盖仓库内断链。

### Codex 与 Workbuddy 共享记忆

- 仓库根 `shared-memory/` 是 Codex 与 Workbuddy 的协作上下文区，位于 Vault 外；它不属于正式项目笔记，也不能替代源码 README、设计文档、测试证据、验收结论或部署记录。
- `shared-memory/project-memory.md` 只保存跨对话长期有效且已确认的项目公共记忆；临时判断、单次任务进度和对话过程不得写入该文件。
- 每个新对话必须在 `shared-memory/conversations/` 新建独立 Markdown 文件，命名为 `YYYY-MM-DD-<简短主题>.md`；不得复用、覆盖或修改其他对话的记忆。同日重名时追加 `-02`、`-03`。
- 当前对话形成重要目标、决定、约束、完成项、验证结果或待办后，协作助手应及时更新当前对话记忆；正式事实仍须同步到其工程真相入口。
- 委派 Workbuddy 前，Codex 必须要求其先读取 `shared-memory/workbuddy-collaboration.md`、`shared-memory/project-memory.md` 和当前对话记忆，再读取任务直接相关的正式材料。Workbuddy 返回任务结果时，如有需要与 Codex 共享的关键发现、修改、验证结果、风险或待办，可以直接追加到当前对话记忆，并在返回结果中声明记忆增量；不得覆盖已有内容或修改其他对话记忆。Codex 负责复核，只有跨对话长期有效且已确认的事实才可进一步同步到项目公共记忆。
- `shared-memory/workbuddy-collaboration.md` 是 Workbuddy 协作流程、执行边界和结果交接格式的唯一维护入口；根 `AGENTS.md` 负责让后续 Codex 会话发现并执行该约定。
- 共享记忆禁止保存密码、令牌、私钥、密钥文件内容、完整隐私数据、未脱敏日志或其他不应进入 Git 的材料。

### 本机归档与服务器运行目录

- `artifacts/asset-archive/`只收纳本机历史归档，例如已有的agent-status-fix-20261009.tar.gz；它不是在线模型、审计、发布材料或数据卷的统一新位置。
- 服务器继续使用`/opt/powersystem/runtime/`及私有配置指定的实际挂载源；本轮不移动这些目录、不改运行数据路径。`stages/`保存源码，两者用途不同。
- 生产发布快照、全部镜像ID、当前指针、未完成事务和私有门禁材料归`runtime/production-stack/`；应用代码归阶段源码。完整导出配置可能含秘密值，禁止放进公开笔记或Git；本机对应证据归忽略的`artifacts/stage4-前端上线/`。
- 知识清单的`path`是新布局物理路径，`title`保持原文档逻辑标识。更新来源路径不等于重建或导入知识；Docker内的文档挂载应与同版本清单一致。
- 发布、备份、知识清单和本地工具只使用本页现行路径；迁移前路径仅可出现在 `migration-map.json` 和历史证据中，不再作为运行时回退分支。新增目录不能扩大到`artifacts/asset-archive/`、凭据、审计或原始日志的公开打包范围；旧批次证据和源码摘要保持原样。

  - **版本标注**：每页 frontmatter 写 `version`（`V1`/`V2`/`V3`/`V4`/跨版本），H1 下用 `> **版本归属**：…` 说明版本、阶段与判据日期。版本边界为 `v1.0.0`（2026-09-29）、`v2.0.0`（2026-10-06）、`v3.0.0`（2026-10-14）、`fleet-release-20261020-r2`（2026-10-20 22:31，进入第三版设备扩容）、V4-S09（2026-10-24）。

### 阶段完成与验收判定（强制）

每个阶段收尾时，除上述"测试交付""问题记录"两份笔记外，还必须形成一份**可复核的阶段验收结论**，集中回答五件事：本阶段做了什么、遇到什么问题、怎么解决的、还有哪些没解决、能否进入下一阶段。判定不通过就不能标记"已完成"，更不能进入下一阶段。

**验收结论必答项**

- **完成任务清单**：对照立项拆分（`01-智能体需求与可行性` 或对应阶段方案设计）逐项列出本阶段交付的任务，明确"已实现 / 已测试 / 已验收 / 真实环境已验证"四档，不得互相替代。
- **问题与解决**：本阶段遇到的错误统一指向独立问题记录页；验收结论只保留"问题 → 解决方式 → 验证结果"的结论性摘要，并链接到问题页。
- **未解决问题**：逐条列出仍未解决的问题，注明**归属阶段**与**是否阻塞本阶段验收**；阻塞项未清，阶段不能签收。
- **进入下一阶段判定**：给出明确结论"可进入 / 不可进入"，不可进入时写明缺什么证据、补什么验收。

**验收判定门槛（不满足不得签收）**

- 本阶段"测试与交付"笔记已形成，结论与证据对应，旧失败批次保留、不覆盖成通过。
- 独立问题记录页已核对：已解决项附验证结果，未解决项附归属与阻塞判断。
- 验收口径与立项口径一致；项目所有者在本阶段追加的增量验收（如联网五题、逐条人工来源审查）未完成时，阶段不得按"已完成"状态进入下一阶段。
- 判定依据必须有具体证据（运行编号、文件路径、镜像指纹、检查条数），不能只凭"HTTP 200""单次冒烟""数字与编号校验通过"或历史成功批次代偿。
- 新增SQL迁移须经实际应用迁移入口的隔离短测；单独psql执行通过不能代偿启动解析、幂等与入口兼容性。验证仅覆盖本次迁移范围，不据此扩大为全后端回归。

> 判定边界：协议通过不等于来源支持；本机通过不等于服务器通过；旧镜像的观察/恢复结论不能转移到新镜像。下一阶段（V2-M4）的整体复核不能代偿本阶段（V2-M3）的增量验收。

## 五、笔记排版规范

统一沿用已有笔记风格（需求分析、技术选型、架构设计、开发阶段1 均为同一套）。

**文件骨架**

1. **frontmatter**：文件开头 YAML 块必须包含 `tags`、`status`、`scope`、`updated`；`status` 只能是 `现行/历史/废弃/草稿`，`updated` 使用 ISO 日期。
2. **标题**：`# 一级标题`；专题用 `# NN · 主题`；索引用 `# 模块 · 索引`。
3. **引用说明**：标题下用 `>` 写「本页说明什么 + 对应手册/路线图任务」。
4. **分节**：正文用 `## 一、二、三…` 分节，每节一个小主题；小节用 `###`、步骤用 `####`。
5. **导航**：笔记末尾以「相关笔记」小节标明上游/下游/下一章。

**正文元素**

6. **表格**：内容简短的并列信息、对照和清单用 Markdown 表格；长句或成组数字改用标题与列表。
7. **说明框**：关键提醒、设计决策的「为什么」用 `> 说明文字`。
8. **图**：Mermaid 内联源码 + 重要图另渲染白底 PNG 存 `diagrams/`。

**链接与术语**

9. **双链**：同目录互链用短链 `[[01-xxx]]`；跨目录用全路径 `[[01-项目调研规划与开发建设记录/第一版-平台主体/05-功能开发与阶段交付/01-数据链路/01-环境与Git]]`（避免同名歧义）。
10. **术语**：编号（FR/NFR/任务号）与已有笔记严格对齐，不重号。

### 反堆叠写法（信息密度高的笔记必读）

笔记出现「整段灰墙、表格过宽、代码连片」的观感时，按下列规则重排，语义、命令、路径、编号一律不改：

**整段长文 → 列表**

- 一句话里串了多个并列事实、结果或边界声明时，拆成 2～4 条短列表。
- 每条只讲一件事；关键数字单独成行并加粗。

**宽表格 → 加粗标题 + 列表**

- 表格某列单元格塞进长句、多组数字或命令/路径时，放弃表格，改用「**加粗小标题** + 明细列表」。
- 典型场景：测试结果（`检查项 | 结果`）、现象排查（`现象 | 处理`）、联调记录（`检查点 | 实测值`）。
- 保留表格的前提：每格内容都是短词、短路径或单个数，读起来无需换行。

**代码块 → 步骤化**

- 连续多段命令堆在一起时，每段前加 `#### 步骤 N · 动词短语` 标题（如「步骤 1 · 预检并启动」）。
- 命令的关键注释（何时执行、环境要求、副作用）用 `>` 引用框紧跟其步骤，不埋进正文。

**边界与结论 → 引用框**

- 「不能只凭 X 判定通过」「此数据不代表真实场站」这类否定/限定结论，单独放 `>` 引用框与正文隔离。
- 需要列举判定依据时，在引用框内再嵌列表。

**分组小标题**

- 超过 6 条的无序列表，按主题拆成若干组，每组配一个加粗小标题（如「文件骨架 / 正文元素 / 链接与术语」）。
- 超过 6 行的表，按主题拆成多张表，各配加粗小标题。

### 状态只写一处（2026-10-23 起硬性）

- **现行状态只在 [[00-当前系统状态]] 维护**：生产指针、阶段状态、设备口径、已知限制、备份与写权限一律写那一页；其它页面只允许写一句 `当前状态见 [[00-当前系统状态]]`。
- 入口文档（`README.md`、两本手册、验收清单、运行产物说明、规范总纲、各阶段 `README.md`）顶部**不得**按日期堆叠发布批次；需要保留的批次事实写进 `04-系统部署发布备份与变更记录/部署与运维日志`，由索引摘要。
- 可以留在原页的"状态"只有两类：**验收里程碑**（一次性、不再变化，如 M1 2160/2160）与**该页自身的维护说明**。
- 发布或回退后，在同一批次内回写状态页；漏改视为该批次未完成，不得"下次一起补"。
