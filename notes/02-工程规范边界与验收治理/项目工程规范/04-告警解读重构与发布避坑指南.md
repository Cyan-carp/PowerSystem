# 04 · 告警解读重构与发布避坑指南

> 本页把2026-10-21—22告警解读重构、受控演示、生产发布与第三版笔记整理中实际踩过的坑，写成下次可执行的排查顺序。它不代替阶段问题记录、部署日志或现行发布门禁；历史失败不能因最终成功而删除。

## 一、先分清故障落在哪一层

同一页面显示“未完成解读”，不等于同一个根因。先核对事件和任务身份，再沿下面的顺序分层取证；不要只凭 HTTP 200、健康绿灯或一次合成成功就改模型、换密钥或跳过门禁。

| 观察点 | 首先核对 | 不可直接推断 |
| --- | --- | --- |
| 供应商请求失败 | HTTP 状态、耗时、请求模式 | API key 一定错误 |
| 返回结构异常 | 内容类型、choices、finish reason、usage | 模型业务判断错误 |
| 模型内容被拒 | schema 子码、事实引用和语义子码 | 网关一定不可用 |
| 任务持续失败 | 租约、持久调用数、暂停/熔断状态 | 可以无限重试 |
| 页面仍显示旧状态 | API 当前记录、前端内存和事件ID | 数据库清理失败 |

证据入口：旧工具兼容问题见 [[04-系统部署发布备份与变更记录/部署与运维日志/03-智能体与模型调用链/18-解读模型通道兼容与输出预算（原18+28+29）|日志28]]；推理预算和截断见 [[04-系统部署发布备份与变更记录/部署与运维日志/03-智能体与模型调用链/18-解读模型通道兼容与输出预算（原18+28+29）|日志29]]；官方通道、r1–r4发布和清理见 [[04-系统部署发布备份与变更记录/部署与运维日志/03-智能体与模型调用链/30-官方独立告警解读与每日五次演示|日志30]]；仅前端的分页改版发布与上线核对见 [[04-系统部署发布备份与变更记录/部署与运维日志/02-界面展示与通知/31-前端列表可读性（原31+32）|日志31]]；设备编码视觉区分发布与分块核对见 [[04-系统部署发布备份与变更记录/部署与运维日志/02-界面展示与通知/31-前端列表可读性（原31+32）|日志32]]。长期发布门禁由 [[02-工程规范边界与验收治理/项目工程规范/02-发布仓库与界面验收规范|发布规范]] 和 [[02-工程规范边界与验收治理/生产发布防回退与自动验收门禁规范|防回退门禁]] 维护，本页只记录故障模式与处置次序。

## 二、模型与事实协议的坑

### 1. 普通问答能用，不代表特定解读请求能用

**当时现象与根因**：旧兼容网关对强制指定 `submit_interpretation` 的请求连续返回502；普通聊天正常。同样的完整schema改为 `auto` 后可通过原业务校验。只能确认“该请求模式与当时网关不兼容”，没有供应商内部证据证明502的具体实现原因。后来官方专属解读通道已改为无tools的JSON模式；旧 `auto` 修复属于历史，不是现行协议。

**下次处置**：用相同证据、相同schema，仅改变一个请求参数做对照；同时保存安全的HTTP状态和响应结构分类。先定位是传输/协议问题，还是返回后的答案校验问题，再决定是否调整协议。不得因普通聊天成功就宣称解读API正常，也不得把历史 `auto` 重新当成官方通道的必需设计。

> 2026-10-22 已补到原字节证据，此前的“子型未知”结论作废：该接口返回 `HTTP 200`、`Content-Type: text/event-stream`、正文恰为 13 字节 `: keepalive\n\n`，没有任何 `data:` 帧。应记为“上游只发心跳的 SSE”，不是泛指“某种网关错误文本”。同一网关 `stream: true` 时 `data:` 帧与 `[DONE]` 正常，而官方 `api.deepseek.com` 的 `stream: false` 仍返回 JSON；因此判据是“非流式通道被上游停用”，不是全网关故障。修复与三服务口径见部署日志 37。

### 2. 推理token吃掉预算，截断会伪装成schema错误

**当时现象与根因**：旧推理模型的 `reasoning_tokens` 计入 `max_tokens=1500`；失败样本的 `finish_reason=length`、`completion_tokens=1500`，正文或工具参数因此不完整，曾被笼统记作 `invalid_answer_schema`。提高到4096改善了截断，但后来仍有独立的语义校验失败，不能把“预算不足”解释成全部问题。

**下次处置**：同时看 `finish_reason`、usage中的推理/输出计数、实际预算和耗时；明确截断才归截断，并在任务持久上限内有限重试。调整预算时一并核对模型、Agent和外层API的超时链与成本。不要对所有schema失败盲目加token或无限重试；不记录推理正文。

### 3. JSON合法、schema合法与事实正确是三道不同的门

**当时现象**：旧答案曾被数字/时间守卫拒绝；新官方六例的早期批次又出现 `limitations` 被生成为字符串数组，以及“建议确认是否故障”被误判为确定性因果断言。供应商HTTP 200不能证明任一后续门禁通过。

**下次处置**：按“响应信封 → JSON解析 → 字段schema → 事实ID/时间/概率/阈值 → 因果与操作边界”分别记录安全子码。对合法否定句和真实编造分别做正反例短测；修提示词或校验器时保留严格的非法引用、跨事件事实和实质编造拒绝。不要拼接残缺JSON、删掉错误字段假装通过，也不要把程序事实模板冒充模型成功。

### 4. 健康探针太小，会漏掉生产规模故障

**当时现象**：旧探针用单条短合成证据，真实告警却含多条证据和约100点曲线；健康正常时，生产解读仍可能因预算、格式或事实守卫失败。后续固定六份合成证据全部通过，也只证明本批短验收，不证明长期100%或真实设备诊断质量。

**下次处置**：`/health` 保持零模型调用；管理员检测单次使用与生产规模相当的证据和同一专属Provider，并报告协议、schema与业务子码。把合成、真实模型调用、生产自然事件分别标记，不用其一代偿其余。控制探针频率，避免额外制造告警或模型流量。

### 5. 专属密钥与网关隔离，不等于供应商永不波动

**已落实边界**：阶段7独立官方 `deepseek-flash`、关闭thinking、非流式JSON、无tools，不与阶段8问答或阶段9运维复用配置和暂停状态；没有隐式备用网关。专属应用密钥不能证明供应商账号配额、限流或可用性也独立。

**下次处置**：对429、5xx、超时、空内容、SSE/非JSON、认证或额度错误分类；可用性失败走有限重试/熔断，认证和额度错误暂停专属通道，事实拒绝不算供应商故障。Redis保护状态不可读时停止新调用并明示故障，不默默放开保护。供应商故障时保留事件事实并展示“AI未完成”，不切到未验收网关或模板假答案。

## 三、发布、备份与数据切换的坑

### 6. SQL单独执行通过，应用迁移入口仍可能启动失败

**当时根因**：010迁移注释里有英文分号，既有 `store.Migrate` 按分号切语句，把注释后半句当作SQL，导致r1 API启动失败并安全回退；单独以 `psql` 执行成功不足以覆盖这个入口。

**下次处置**：新增迁移先用真实应用的迁移入口做隔离短测，覆盖启动解析、重复执行和本批表结构，再冻结候选。失败时先保留错误批次与自动回退证据，只修迁移兼容缺陷；不能把API启动失败归咎模型，也不能为抢发布跳过门禁。此项长期门槛已写在 [[02-工程规范边界与验收治理/项目工程规范/01-目录边界与笔记治理|目录与验收治理]]，这里不另设相反标准。

### 7. 未提交的主机临时版本，不是数据库资产历史

**当时根因**：r2/r3失败重试和回退曾继续递增未完成的主机登记版本，使五个资产的临时版本超前于DB已提交版本，触发Store禁止跳号；r2首次失败其实另有配置文件路径错误，版本冲突发生在其后的回退。两类问题不能混成一个“发布门禁过时”。

**下次处置**：以DB已提交版本为权威，新增身份从 `retained+1` 连续分配；不直接改DB历史、不清 `pending` 强行续发。先取得冻结失败凭据和首个异常，再查回退的次生故障。恢复持统一部署锁，核对父版本、服务身份和任务排空，仍走原Store导入与完整HTTPS/WSS门禁；专用恢复器不得当通用重试按钮。

### 8. 私有env的父目录也是运行契约的一部分

**当时根因**：新驱动把 `integrated.env` 移进新批次私有目录，旧helper却按env父目录寻找 `private/executor/registry.json`；实际Executor的bind仍指向原批次。文件内容正确、权限正确也会因布局变化出现 `FileNotFoundError`。r2/r3反复失败的首因是这个路径适配遗漏。

**下次处置**：prepare前只读核对env父目录、registry存在性、实际容器bind、属主与权限；新文件使用独立文件名且拒绝覆盖原文件。引用仍存活的旧私有目录不得按批次年龄清理。若需改变布局，先同时改造并测试消费者的路径契约，生成新候选和备份；不得把私有配置搬进Git或打印完整值。

### 9. 加密快照“能列目录”不等于完整流已认证

**当时现象**：首轮PG快照的 `pg_restore --list` 成功后提前退出，驱动关闭剩余GPG解密流而出现Broken pipe；删除门槛因此阻断，旧业务告警未被删除。已证实是读取方提前结束，不应直接归咎密文损坏；只读到TOC不能证明整个密文流完整可读。

**下次处置**：先冻结/排空、记录删除前数量和高水位；解密流必须完整排空并检查GPG最终退出状态，备份摘要和可读性通过后才进入单事务删除。读取或校验失败整体停止并保留首轮证据，不改成无审查的分批删除、不生成明文磁盘副本。清理后核对业务告警及依赖为零、平台监控和遥测等保留、告警序列与扫描水位不回退；恢复历史数据是独立备份操作，不随镜像回退自动执行。

### 10. 跨日调度是最终一致过程，不应造数据凑门禁

**当时现象**：r4发布和清理跨过北京时间零点，00:02当天五槽尚未落库；调度器按十分钟重查后，00:09:37五槽自然落库且 `fired=0`。首次断言未满足不等于配置失效，也不能直接改断言为通过。

**下次处置**：先核对时区、下一次调度时间、日槽唯一键、暂停状态和调度告警；在已知正常刷新窗口内只读等待，再运行同一断言。不要手工插入槽位、补发错过时段或创建第六条告警。五槽落库也不等于五条已触发、已解读或十分钟结束已验证，运行结论按实际自然事件另记。

### 11. 手工传 `--from-args` 会让候选丢掉叠加编排层

**当时现象与根因**：现行栈不是五份基础编排本身，而是基础编排 + 官方解读层 + 扩容追加层 + 私有 `integrated.env` 的叠加结果。入口 `prepare` 在缺省时自动取上一版 `private/origin-args.json` 继承完整参数；若手工构造 `--from-args` 且只放基础 compose，冻结出的候选会缺少叠加层，等同于配置倒退，而 `validate` 未必拦得住。

**下次处置**：叠加层不变时**不传** `--from-args`，让它继承上一版；确需变更时才构造，且必须保留原顺序的五份基础编排与私有 env。`--image svc=tag` 会自动把该服务并入 `services`，不必再加 `--service`。prepare 后核对 manifest 的 `services`、`images` 与实际镜像 ID。

### 12. 备份必须晚于候选，且连接中断不等于备份失败

**当时现象与根因**：本次 637MB 密文 + 双目标异地上传约 20 分钟；期间 SSH 连接被远端关闭（SIGTERM），但脚本仍在运行并持有部署锁，最终 12:46 正常完成。若据此判定失败并重跑，会与在跑的脚本争锁、覆盖同名密文，还把仍有效的旧密文当成废件。另：等待循环用 `pgrep -f 'backup.sh'` 会匹配到自己的 `bash -c` 命令行而永不退出，本次因此空等约 9 分钟。备份时间戳若早于候选 `created_at`，`publish` 会直接拒绝（本次 prepare 04:21:17Z → 备份 04:21:49Z，顺序正确）。

**下次处置**：连接断开后先只读判断，不要立即重跑——`ls -lt` 备份目录看密文与 `.sha256` 产物、`[ -d /proc/<pid> ]` 判断脚本存活、`pgrep -af 'scp -o BatchMode'` 看上传是否在进行。确认已停止再重跑，且使用新时间戳，不覆盖旧密文。等待循环只用已知 PID 的 `/proc/<pid>` 判断，不用 `pgrep -f`。顺序固定为 prepare → backup → publish，发布前 `sha256sum -c` 校验摘要。

### 13. 覆盖生产源码前，先与仓库摘要比对

**当时现象与根因**：生产源码目录与仓库可能出现旁路边动；直接 `cp` 覆盖会把服务器上的差异静默抹掉，事后难以还原。本次覆盖前比对一致（两份视图与仓库 `HEAD` 摘要相同），才确认无旁路改动。

**下次处置**：改动文件先落到 `/tmp/src-sync`，再 `cp` 进生产目录；覆盖前对目标文件与仓库 `HEAD` 版本做 md5 比对，不一致先查差异来源且不得覆盖；原文件另备份到 `/tmp/src-backup-ui-<日期>`；覆盖后再 md5 复核一次。

### 14. 发布后只查主 index chunk，会误判“未上线”

**当时现象与根因**：路由是懒加载，视图代码被打进 `assets/<View>-<hash>.js` 独立分块。本次先 curl 主 `assets/index-*.js` 并用新文案 grep，五个特征串全部 0 命中，看起来像没发布；实际改动在 `HealthRankingView-*.js`、`ReportsView-*.js` 分块里，逐一 curl 后才命中。

**下次处置**：从主 chunk 的 `__vite__mapDeps`（或 index.html）提取目标分块文件名，逐个 curl 并 grep 本次改动的静态特征串（新文案、新 class、`layout` 字符串）。同时用 `production-stack.py status` 核对指针、pending 与容器镜像 ID。HTTP 200 只证明入口可达，不证明分块内容已更新，也不排除中间缓存命中旧资源。

### 15. 记忆里的生产指针可能早已被别人更新

**当时现象与根因**：准备发布时按记忆里的指针 `assistant-ui-20261019-r1` 判断父版本，实际 `status` 已是 `ui-paging-20261022-r1`——前端在当天已被连续发布过两版。多智能体协作下别人会先发布，指针是高频变动项，写进记忆的那一刻就开始过期。

**下次处置**：发布前先跑 `production-stack.py status` 现查 active release、pending 与门控文件；prepare 后核对 manifest 的 `parent` 是否指向刚查到的那一版。指针、父版本、pending 三项全部确认后再动源码，不要用记忆值代替现查。

### 16. 直接 md5 比对会把换行符差异全报成内容漂移

**当时现象与根因**：本机 `core.autocrlf=true`，工作区文件检出为 CRLF，服务器上同为 LF。全量比对 81 个 `.vue`/`.ts`，24 处报“内容不同”，其中 `App.vue`、`main.ts`、`PredictionsView.vue` 等从未改过，看起来像生产源码大面积漂移。按内容抽查后确认全部只是换行符差异。

**下次处置**：比对用 `diff <(tr -d '\r' < A) <(tr -d '\r' < B)` 判内容，不要只看 md5；确认是换行符差异就不必同步。确需同步的文件上传后统一 `sed -i 's/\r$//'` 转 LF，再与本地规范化摘要复核，避免把 CRLF 混进生产源码。

### 17. `grep -c -F --st-t1` 会被解析成选项

**当时现象与根因**：验证线上 CSS 是否含新变量时，六个 `--st-t*` 全部报 `grep: unknown option -- st-t1`，命中数为空，一度以为变量没打进产物。前导双横线被 grep 当成选项前缀。

**下次处置**：以 `--` 开头的检索串一律写 `grep -c -F -e "--st-t1"`，或用 `grep -o -E` 加正则。判定“特征未命中”前先排除命令本身报错。

### 18. 公网 HTML 看不到分块引用关系时，直接进容器核对

**当时现象与根因**：发布后想确认三个视图分块确实引用了新组件，但压缩产物里 `__vite__mapDeps` 在本次构建中不可见，逐个 curl 分块再 grep 引用关系全部 0 命中，线索断了。

**下次处置**：`docker exec <frontend容器> sh -c 'cd /usr/share/nginx/html/assets && grep -l -F <特征> *.js'`，一次拿到命中文件名，且不必逐个 curl。公网入口只用来确认 HTTP 200 与入口资源可达，分块内容核对在容器内做。

### 19. Vite 会把小组件合并进其他分块，按组件名找分块会 0 命中

**当时现象与根因**：按 `assets/DeviceCode-*.js` 去找组件分块，24 个分块全部扫过仍 0 命中，一度怀疑组件没被打进产物。实际 Vite 把 `DeviceCode.vue` 与 `StationCode.vue` 合并进了同一分块 `StationCode-CGSQwYMG.js`，`DeviceName.vue` 则内联进 `DevicesView` 分块——分块名不等于组件名。

**下次处置**：找不到目标分块时改为全量扫 `assets/*.js` 定位特征实际所在文件，再反查哪些视图引用该分块，不要按组件文件名硬猜分块名。

## 四、供数与笔记迁移的坑

### 20. 容器健康、接口零错误，也可能已经停止供数

**当时现象与归因等级**：扩容旧版7200秒观察中，三档有效观测始终为0、360次请求全为 `partial`，但接口无错误且容器仍运行。只读源码核对与离线复现将问题高可信定位为 `SharedPublisher` 与Paho内部消息锁的ABBA锁反转；未取得生产线程栈，不能写成生产堆栈实证。修复发布后首轮143/140/3有效观测恢复，最终7200秒仍有两档各一轮覆盖不足，严格结论是 `anomaly`。正式证据见 [[04-系统部署发布备份与变更记录/部署与运维日志/04-供数与业务批次/27-共享MQTT发布锁修复上线|日志27]]。

**下次处置**：同时查 `all/business/baseline` 的有效观测与 `partial`、遥测新鲜度、队列 `pending` 和线程等待点；不要用HTTP正常、容器running或CPU低代偿供数。并发发布修复先在隔离真实Broker短探针验证消息数、MID归属与待发清零，再单服务发布；长观察按实际覆盖缺口判定，不把“持续停发已修复”改写成“零缺口长期稳定”。

### 21. 改了路径却不改索引，会留下“可打开但不可维护”的笔记

**当时现象**：第三版十篇正文原先平铺，同一层混合扩容需求、容量观察和后续解读专项；跨目录移动后，旧路径还散在根README、Vault导航、部署日志、手册和阶段README。历史“当前/仍停发”也可能在新索引下继续误导读者。

**下次处置**：先盘点Git跟踪状态和全库入链，冻结旧到新映射；已跟踪文件用 `git mv`，未跟踪文件原位移动并登记映射，不暂存无关脏改动。同一次整理更新根索引、子索引、工程规范目录树、根README、源码README及全部活动链接；日期快照标历史，现行结论以正式交付和运行指针为准。运行笔记治理检查、图谱构建及旧路径扫描；既有无关元数据问题单列，不为“全绿”篡改历史。具体强制规则以 [[02-工程规范边界与验收治理/项目工程规范/01-目录边界与笔记治理|笔记治理]] 为准。

## 五、下次遇到类似问题的最短流程

1. **冻结现场**：确认事件/任务/发布批次、现行指针与最早失败时间；保存脱敏子码、usage、镜像/配置摘要，不输出密钥或供应商正文。
2. **分层定位**：按供应商响应、答案协议、事实校验、任务状态、发布/数据库五层逐一排除；用同证据单变量短测，不把一次健康探针外推到生产规模。
3. **只改已证实层**：修最小可复现缺陷，保留权限、事实守卫、调用预算和自动发布门禁；既有失败批次、回退及后续恢复分别记账。
4. **走原验收入口**：只做受影响的定向短测，但迁移、冻结候选、全量备份、发布门禁和清理前完整密文验证仍是必要条件；顺序固定为准备候选 → 更新前密文备份 → 发布，源码覆盖前先现查指针与仓库摘要比对（换行符差异不算漂移）。发布后按指针、pending、容器镜像 ID 与路由懒加载分块内容核对，分块内容优先进容器直接 grep，不以主入口 HTTP 200 代替内容核对。
5. **同步真相入口**：阶段问题页、正式交付页、部署日志、索引和对话记忆分别写清“已实现/已测试/已发布/自然生产已观察”，不把它们合并成一个“已解决”。
