# IR-S02 · 方案与实施记录

> 本页记录「时效出口（死信）」的本地候选**修订版**：30s/2000/5s 有界排水、过期 worker 不占调度锁、`history_enabled` fail-closed、队头按设备窗口内最旧行。只改后端代码与可观测，不发布、不上传、不改前端、不进入 S03/S04。生产事实只认 [[00-当前系统状态]]；本页引用的生产数字均为历史记录，不是本轮实测。

## 一、范围与基线

### 1.1 本轮交付

- 新增单 worker 过期出口：把 7 天窗外仍未处理的行写为 `business_state='quarantined'`、`failure_code='window_expired'`、`processed_at` 非空。
- 复用 S01 方案 A：不新增 `business_state`，不创建 021，不改 014 约束。
- 排水能力按 96 历史接收 83,318 行/小时设计为 2000 行/30 秒 = 240,000 行/小时，并做隔离持续负载实测。
- 过期 worker 不再持有 `scheduler.mu`；实时路径与过期路径按 `ts_ms` 窗口不相交，行级 `SKIP LOCKED` 兜底。
- `history_enabled=false` 或调度单例缺失时 fail-closed，暂停过期写入；补暂停/恢复测试。
- 队头年龄改为 S01 口径：每台设备取窗口内最旧 pending 行，按 `received_at` 年龄分桶；窗口外行不计。
- 用默认 planner 在 220 万 pending 的隔离数据集测查询计划；记录 021 候选，不在大表/生产建索引。
- 隔离 PG 定向验证；生产、前端、S03/S04 均未触碰。

## 二、方案

### 2.1 终态与判据

| 项 | 取值 |
| --- | --- |
| 候选谓词 | `processed_at IS NULL AND ts_ms<? AND failure_code IS DISTINCT FROM 'owner_abandoned'` |
| 时间下界 | 每轮 `now-7d`，与调度共用 `inboxWindow` 与 `ts_ms` 时钟 |
| history 门禁 | `telemetry_scheduler.history_enabled=true` 且单例行存在；否则不写 |
| 维护门禁 | `service.TelemetryTransaction` 的 enabled/missing/sql_error 继续暂停 |
| 终态 | `business_state='quarantined'`、`failure_code='window_expired'`、`processed_at=clock_timestamp()` |
| 调度字段 | `next_attempt_at=NULL` |
| 保留字段 | `payload`、`attempts`、`first_failed_at`、`reason_since/reason_attempts`、`missing_since/missing_checked_at/missing_attempts`、`td_confirmed_at`、`alarm_evaluation`、`received_at` |

- 不按 `received_at` 过期：S01-Q03 已冻结，否则“旧 ts、新接收”的补传行永远不过期，IR-R01 原样复现。
- `next_attempt_at` 是调度字段，不是历史证据；终态清空它与现有 `recordInboxFailure` 的 quarantine 分支一致。
- 不删除任何行、不 `VACUUM FULL`、不建新索引、不改 TDengine 与 `energy_daily`。

### 2.2 查询与并发

```sql
WITH gate AS (
 SELECT 1 AS ok FROM telemetry_scheduler WHERE id=1 AND history_enabled
), expired AS (
 SELECT id FROM telemetry_inbox
 WHERE processed_at IS NULL AND ts_ms<? AND failure_code IS DISTINCT FROM 'owner_abandoned'
   AND EXISTS (SELECT 1 FROM gate)
 ORDER BY id ASC LIMIT ? FOR UPDATE SKIP LOCKED
), updated AS (
 UPDATE telemetry_inbox AS i
 SET business_state='quarantined',failure_code='window_expired',processed_at=clock_timestamp(),next_attempt_at=NULL
 FROM expired
 WHERE i.id=expired.id AND i.processed_at IS NULL AND i.failure_code IS DISTINCT FROM 'owner_abandoned'
   AND EXISTS (SELECT 1 FROM gate)
 RETURNING i.id
) SELECT count(*) FROM updated
```

- `ORDER BY id ASC` 与旧取任务、事务内队头复核同向；两处旧谓词与 `inboxPendingPredicate` 未改。
- `FOR UPDATE SKIP LOCKED` 不等待正在入库的行，避免清理卡住实时链路。
- 外层 UPDATE 再带一次 `processed_at IS NULL`、`owner_abandoned` 与 `gate` 防护；96 的保留行结构上不可能被命中。
- **不持有 `scheduler.mu`**：过期集合是 `ts_ms < floor`，实时入库只取 `ts_ms >= floor`，两者按定义不相交；若某行恰在边界，行级锁与 `processed_at` 复核仍保证 `ErrInboxTerminal` 或 `SKIP LOCKED`，不会双重处理。共享锁会让每轮清理直接停住实时 tick，而历史净余量只有约 0.92%，不能用维护清理去换。
- 单 worker：只在 `Run` 恢复成功后启动一次 `expiryWorker`；不与第二个历史 worker 并行。
- 事务：复用 `service.TelemetryTransaction`，维护门禁与现有入库路径一致。维护冻结的 `enabled=true` UPDATE 会等待已准入事务的 SHARE 锁；过期单批最长 5s，因此维护冻结最多多等一个 5s 预算。这是有界的，仍短于实时调度 tick 的 30s 上限。

### 2.3 冻结参数与排水能力

| 参数 | 冻结值 | 说明 |
| --- | --- | --- |
| `INBOX_EXPIRY_ENABLED` | `false` | 灰度开关默认关闭；隔离测试显式启用 |
| `INBOX_EXPIRY_INTERVAL_SECONDS` | `30` | 周期；允许 5..3600 |
| `INBOX_EXPIRY_BATCH` | `2000` | 单批上限；允许 1..5000 |
| `INBOX_EXPIRY_BUDGET_SECONDS` | `5` | 单轮事务预算；允许 1..30 |

- 名义能力：`2000 / 30s = 240,000 行/小时`，约为 96 历史接收 83,318 行/小时的 **2.9 倍**；持续过期输入下才有净排水余量。
- 隔离单批：2000 行 **279.5456ms**（< 5s 预算）。这是单批微基准，不是设计能力，也不能外推生产 I/O。
- 隔离持续负载：4 台设备先放 2000 条 8 天前 pending，再以 25 行/秒（90,000 行/小时）注入 1500 条“旧 ts、新接收”行；累计 3500 条在 **90.2718172s** 内排空，观测净速率 **139,578 行/小时**（含等待 30s tick 的对齐时间），仍高于 83,318 行/小时。名义值 240,000 与观测值 139,578 都只代表隔离临时库。
- 生产未测：生产 21GB 表、真实 I/O、并发入库与 8 路历史处理的余量均未验证；不能把 279ms 或 139,578 行/小时写成生产承诺。

### 2.4 `history_enabled` 合同与 fail-closed

- 合同证据：`016_telemetry_realtime.sql` 新增 `history_enabled BOOLEAN NOT NULL DEFAULT TRUE`；`stages/02-backend/README.md` 写明“`telemetry_scheduler.history_enabled`可暂停历史”；`processPendingBudget` 在该列为 false 时直接返回。没有源码或契约证据支持“过期写入独立于操作者暂停”。
- 因此按操作者暂停意图 fail-closed：事务内先读 `history_enabled`，false 或单例缺失返回 `errInboxExpiryPaused`；同一语句的 SELECT/UPDATE 再以 `EXISTS (SELECT 1 FROM gate)` 二次门禁。
- 边界：已开始的单批可能完成，暂停从下一批生效；这与现有调度 tick 在 tick 开始时读取 `history_enabled` 的语义一致。调度单例缺失按暂停处理，不把未知读成放行。
- 验证：T13 覆盖 false 暂停、true 恢复、单例删除 fail-closed、恢复后继续；维护门禁由 T04 单独覆盖。

## 三、可观测

### 3.1 队列观测（默认启用，与灰度开关无关）

| 指标 | 语义 | 准确/近似 | 采样 |
| --- | --- | --- | --- |
| `inbox_pending_rows_all` | `processed_at IS NULL` 总数 | 精确，同一语句同一快照 | 60 秒周期，2 秒预算 |
| `inbox_pending_rows_in_window` | `ts_ms >= floor` | 精确，同上 | 同上 |
| `inbox_pending_rows_outside_window` | `ts_ms < floor` | 精确，同上 | 同上 |
| `inbox_outside_window_oldest_age_seconds` | 窗口外 pending 的最老 `received_at` 年龄 | 该快照精确值；无窗口外行时为 NaN | 同上 |
| `inbox_head_age_devices_total` | 有窗口内 pending 的设备数（每设备一条） | 按设备精确；最多 5000 台 | 同上 |
| `inbox_head_age_devices_lt_1m/1m_5m/5m_15m/15m_1h/1h_6h/ge_6h` | 每设备窗口内最旧 pending 行的 `received_at` 年龄分桶 | 每设备一条；窗口外行不计 | 同上 |
| `inbox_head_age_device_limit` | 设备上限（5000） | 常量 | 同上 |
| `inbox_queue_stats_known` | 1=本次测量可用，0=未知 | 精确状态位 | 同上 |
| `inbox_queue_probe_error_total` | 队列观测失败次数 | 进程内计数，重启归零 | 同上 |

- 队头查询：`devices` 表取未删除设备，逐设备 `LATERAL ... WHERE device_id=dev.id AND processed_at IS NULL AND ts_ms>=floor ORDER BY id ASC LIMIT 1`。每设备最多贡献一条，窗口外行被 `ts_ms>=floor` 排除，不会重复计入同一设备的旧行。
- 查询受 5000 台设备上限与 2 秒预算约束；超时/失败整组计数与分桶写 NaN、`stats_known=0`，不能把未知读成 0 条。设备表超过上限时只覆盖前 5000 台，`inbox_head_age_device_limit` 与 `inbox_head_age_devices_total` 同时导出。
- 逐设备 `LIMIT 1` 仍可能为跳过窗口外前缀而扫描该设备的 pending 行；生产是否可接受必须用真实数据 `EXPLAIN (ANALYZE, BUFFERS)` 证明，不能用隔离小表外推。
- `inbox_queue_age_seconds` 是最近一次观测尝试的年龄；是否可用由 `inbox_queue_stats_known` 判定。

### 3.2 过期出口指标

| 指标 | 语义 |
| --- | --- |
| `expiry_run_total` | 过期 worker 尝试轮数 |
| `expiry_success_total` | 成功提交的批次数（含 0 行） |
| `expiry_rows_total` | 累计写入终态的行数；进程内计数，重启归零 |
| `expiry_failure_total` / `expiry_timeout_total` / `expiry_unknown_total` | 普通失败 / 预算超时 / commit 结果未知 |
| `expiry_skip_total` | 维护门禁 enabled/missing 跳过 |
| `expiry_paused_total` | `history_enabled=false` 或调度单例缺失的 fail-closed 跳过 |
| `expiry_age_seconds`、`expiry_success_age_seconds`、`expiry_rows_age_seconds` | 最近一次尝试 / 成功 / 写行的年龄 |
| `powersystem_telemetry_path_seconds_{sum,count}{path="expiry"}` | 单轮耗时汇总 |

- `expiry_rows_total` 只代表本进程；跨重启累计以 DB `business_state='quarantined' AND failure_code='window_expired'` 计数为准（S01-Q08）。
- commit unknown 不重放业务动作；下一轮按 `processed_at` 幂等复核。

### 3.3 隔离查询计划与 021 候选

- 数据集：143 台设备 ×（700 条窗外 + 700 条窗口内），再压入 200 万条窗口内 pending，共 2,200,200 行，均为 pending；`ANALYZE` 后使用默认 planner，**未设置 `enable_seqscan=off`**。
- 排水 UPDATE：`Nested Loop`，外层 `expired` 2000 行，内层 `Index Scan using idx_inbox_pending` 的 `Index Cond: (id = expired.id)`，每行 1 次探针；SELECT 侧 `idx_inbox_pending` 过滤 2000 行时移除 1400 行窗口内样本。`EXPLAIN ANALYZE` 的 UPDATE 执行约 **61.2ms**，含规划的调用约 **122ms**，低于 5s 预算。这说明在该规模下 UPDATE 由 2000 个 id 驱动，不是全 pending 扫描。
- 无候选最坏情况：所有 pending 都在窗口内，默认计划为 `Parallel Seq Scan`，220 万 pending 约 **116.0ms**。这不是生产 21GB 表的证明；按行数线性外推只能作风险提示，不能当结论。
- 队头查询：`Nested Loop` + `Index Scan using idx_inbox_pending_device`，`Index Cond: (device_id = devices.id)`，每台设备 `Rows Removed by Filter: 700`（窗口外前缀），143 台约 **39.8ms**。设备多、窗外前缀大时成本会上升。
- 结论：现有 `idx_inbox_pending` 与 `idx_inbox_pending_device` 在隔离 220 万 pending 规模可用且被默认 planner 选中；**不能证明生产无需 021 或生产性能可接受**。生产启用前须在生产只读窗口用真实数据 `EXPLAIN (ANALYZE, BUFFERS)`，或先完成 021 决策。
- 021 候选（只记录，不创建、不执行）：
  - 021-A 排水索引：`CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_inbox_expiry ON telemetry_inbox (ts_ms,id) WHERE processed_at IS NULL;` 用于把“无候选”从 pending 全扫降为时间窗索引探测。
  - 021-B 队头索引（条件性）：`CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_inbox_head_device_ts ON telemetry_inbox (device_id,ts_ms,id) WHERE processed_at IS NULL;` 仅在真实设备窗外前缀使队头查询超预算时评估。
  - `CONCURRENTLY` 不得登记到 `atomicMigrations`；须在维护窗口用 `--migrate-only --migration-timeout` 或独立脚本执行，失败不启动新 worker。不得在本阶段对大表/生产建索引。

## 四、零接触与边界

### 4.1 `owner_abandoned` 零接触

1. 结构证明：SELECT 与 UPDATE 都要求 `processed_at IS NULL`，且 `failure_code IS DISTINCT FROM 'owner_abandoned'`；96 的 8,809,844 行 `processed_at` 均非空。
2. 隔离证明：T03 同时放一条 `processed_at IS NULL` 的异常 `owner_abandoned` 行和一条正常终态行；清理后两行原因不变，`count(*)` 与 `max(id)` 不变。
3. 生产前后指纹不在本轮执行；需生产授权、维护窗口与当轮实测，不能用本地结果代替。

### 4.2 不触碰的路径

- 不调用 TDengine 查询/写入；测试中 `td=nil` 仍能完成清理。
- 不调用 `energy.MarkDirty`，不改 `energy_daily` 的 `kwh/source_quality/updated_at`；T10 验证。
- 不改 `telemetry_snapshots`、`telemetry_alarm_progress`、`business_notification_outbox`。
- 不改前端、不进入 S03 熔断、不做 S04 容量。

### 4.3 已知交互

- 过期行变成“已处理但非 success”后，`uncertainExistsSQL` 会在该设备日被重建时把它计为不确定，`source_quality` 可能变为 `provisional`；kWh 不变。这与 96 的 `owner_abandoned` 先例一致。过期本身不标记 dirty，因此不会仅由 S02 触发历史日重建。详见 [[03-IR-S02问题记录与解决方案]]。

## 五、回滚

- 关闭 `INBOX_EXPIRY_ENABLED` 或回退镜像即可停止新写入；单 worker 随进程退出。
- 已是 `window_expired` 的行不会自动回退；确需恢复时按现有单 ID 显式补偿（仅隔离库），并满足“无后继终态”检查。
- 无 schema/索引迁移，不需要回滚 DDL；不建议对大表 `VACUUM FULL`。
- 已写终态不回滚不构成数据删除；payload 与历史证据仍在行内。
- `history_enabled=false` 是独立的操作者暂停开关；恢复 true 后从下一批继续，已提交批次不回滚。
