## 二、逐项说明

### IR-S01-Q01 · 队头年龄的排序与度量不同源

- **现象**：查询是 `WHERE processed_at IS NULL ORDER BY id LIMIT 1`，返回该行 `received_at`；年龄按 `received_at` 计算。
- **原因**：`id` 是队列插入顺序，`received_at` 是接收时间；补传或延迟提交会让两者不同序。
- **影响**：最老接收时间的行若是后插入的，指标会低估；极端情况下队龄看起来健康，但真实最老 pending 已很旧。
- **处置**：S01 冻结“队头 = 最低 id 的 pending 行，年龄 = 该行 received_at”；S02 增补 `pending_oldest_received_age_seconds`，不要改旧指标语义。
- **验证**：源码 `telemetry_monitor.go:155`、`001_init.sql:70`；未执行生产对照。
- **状态**：口径已定，代码未改。**不阻塞 S01**。

### IR-S01-Q02 · 待处理数没有常驻指标

- **现象**：`/metrics` 没有 pending 总数；只有 `observe-telemetry.py:162` 的临时 SQL。
- **原因**：现有监控以“年龄”表达队列，没有把队列长度做成 gauge。
- **影响**：无法按“积压条数”设置告警；96 的恢复过程只能靠人工查询。
- **处置**：S02 增加 `powersystem_telemetry_inbox_pending_rows{scope="all|in_window|outside_window"}`；先按 5 秒/15 秒探针抓取，避免高频全表 count。
- **验证**：本地源码检索无该指标；`observe-telemetry.py` 仅脚本侧。
- **状态**：已定义，待实现。**不阻塞 S01**。

### IR-S01-Q03 · 过期判据必须复用 `ts_ms`

- **现象**：调度谓词是 `processed_at IS NULL AND ts_ms>=?`；队龄指标却按 `received_at`。
- **原因**：时间窗表达“数据时间是否还有价值”，队龄表达“接收后等了多久”，两个时钟混用。
- **影响**：若 S02 按 `received_at < now-7d` 过期，一条旧 `ts`、最近才补传的行会永远不被选中、也永远不过期，IR-R01 原样复现。
- **处置**：S02 过期条件冻结为 `processed_at IS NULL AND ts_ms < now-7d`，与调度谓词同源；队龄指标另按 `received_at` 表达。
- **验证**：`telemetry_scheduler.go:21,27,153`；`telemetry_monitor.go:155`。
- **状态**：已冻结。**S02 的阻塞性口径**。

### IR-S01-Q04 · 014 约束不允许新状态

- **现象**：CHECK 只允许 NULL/pending/retry/success/quarantined，且终态集合只有 success/quarantined。
- **原因**：014 设计时只考虑“成功/隔离”两种终态。
- **影响**：方案 B（独立 `expired`）必须先改约束；方案 A 不需要。
- **处置**：推荐 A：`quarantined + failure_code='window_expired'`；B 的 021 草案见方案页，使用 `NOT VALID`，不回填。
- **验证**：`014_telemetry_reliability.sql:10-15`；8,809,844 行已满足现约束（历史记录，非本轮复测）。
- **状态**：方案已给，未创建迁移。**不阻塞 S01**。

### IR-S01-Q05 · 快照查询不认识 `expired`

- **现象**：`telemetry_snapshot.go:193,223` 只排除 `business_state='quarantined'`；`IS NULL OR <> 'quarantined'` 会放行 `expired`。
- **原因**：读者按现有状态枚举写死。
- **影响**：若方案 B 新增 `expired` 且新旧 worker 混跑，过期行可能被当作实时快照候选。
- **处置**：方案 B 发布前必须停旧 worker，或先改快照查询排除所有终态（`processed_at IS NOT NULL`）；方案 A 无此问题。
- **验证**：本地源码逐行核对。
- **状态**：方案 B 的**阻塞缺陷**；方案 A 不触发。

### IR-S01-Q06 · 补偿只接受 `quarantined`

- **现象**：`service/telemetry_compensation.go:76` 仅在 `business_state='quarantined'` 时回队。
- **原因**：补偿是 S03 的显式人工入口，只覆盖当时的隔离态。
- **影响**：方案 B 的 `expired` 行无法补偿；方案 A 仍按 `quarantined` 可补偿。
- **处置**：方案 A 不新增分支；方案 B 需明确“过期是否允许人工恢复”，并补审计与测试。
- **验证**：`service/telemetry_compensation.go:76-98`。
- **状态**：方案 B 待决。**不阻塞 S01**。

### IR-S01-Q07 · 失败码字典与数据库约束不一致

- **现象**：`failure_code` 无 CHECK；`redis_unavailable` 只出现在指标 allowlist（`telemetry_monitor.go:345`），没有写入点。
- **原因**：失败码由应用层约定，指标 allowlist 预留了未使用的码。
- **影响**：文档若把 `redis_unavailable` 当活跃码会误导排障；未来新增码没有数据库兜底。
- **处置**：S01 字典把 `redis_unavailable` 标为“保留未使用”；不新增 DB CHECK（历史码多、扩展成本高），由代码常量和测试守护。
- **验证**：本地 `grep` 无写入点。
- **状态**：已登记。**不阻塞 S01**。

### IR-S01-Q08 · 进程内计数不是死信累计真相

- **现象**：`telemetryMonitor.failures` 是进程生命周期 map，重启归零；`powersystem_telemetry_failures_total` 也随之归零。
- **原因**：指标设计为运行时观测，不是持久账本。
- **影响**：不能用它证明“今天产生了多少死信”；跨重启会低估。
- **处置**：S02 的死信累计以 DB `business_state='quarantined'` 且 `failure_code IS DISTINCT FROM 'owner_abandoned'` 按原因计数为准；进程指标只做速率/瞬时观测。持久查询先量成本，不为全量旧行建立高成本索引。
- **验证**：`telemetry_monitor.go:48-65,345-347`。
- **状态**：已定义。**不阻塞 S01**。

### IR-S01-Q09 · 021 迁移的执行约束

- **现象**：`store.Migrate` 无版本表、每次启动重跑；014/015/016 被登记为原子迁移；默认启动迁移预算 30 秒。
- **原因**：项目采用可重复执行的 SQL 文件，而非版本化迁移框架。
- **影响**：021 若含 `CREATE INDEX CONCURRENTLY`，不能放进原子事务；按 96 记录的表 heap 约 21 GB（历史，非本轮复测），建索引会超过默认预算。
- **处置**：方案 A 无 schema 迁移。仅当 S02 实测证明需要 021 时，迁移须幂等；含 CONCURRENTLY 时不登记 `atomicMigrations`，用 `--migrate-only --migration-timeout` 或维护窗口执行；失败不启动新 worker。
- **验证**：`store.go:58-112`；`cmd/api/main.go:29,43,159-165`。
- **状态**：执行约束已写。**S02 的阻塞性施工条件**。

### IR-S01-Q10 · 待处理计数的成本

- **现象**：`COUNT(*) WHERE processed_at IS NULL` 需要扫部分索引；96 后 pending 很小，但积压时会线性增长。
- **原因**：PostgreSQL 没有免费的精确计数。
- **影响**：高频抓取会与入库事务争抢 I/O；不能简单每 5 秒全量 count。
- **处置**：S02 分 scope 计数，设置独立预算；必要时用近似值做告警、精确值做人工核对。
- **验证**：索引 `idx_inbox_pending(id) WHERE processed_at IS NULL`；未做生产 EXPLAIN。
- **状态**：已标成本。**可排期**。

### IR-S01-Q11 · 历史 NULL 与新默认 pending 并存

- **现象**：014 默认值为 `pending`，但历史行可以是 NULL；调度谓词只看 `processed_at IS NULL`。
- **原因**：014 明确“不猜测历史成功”，保留 NULL。
- **影响**：任何“只查 business_state='pending'”的查询都会漏掉历史未处理行；监控与清理必须用 `processed_at IS NULL`。
- **处置**：S01 明确选择谓词以 `processed_at IS NULL` 为准；状态展示可把 NULL 显示为 legacy pending，但不得写回历史行。
- **验证**：`014:1-3`；`telemetry_scheduler.go:27`。
- **状态**：已写入口径。**不阻塞 S01**。

### IR-S01-Q12 · 没有真实等待时长直方图

- **现象**：现有数据只有每行 `received_at` 与终态 `processed_at`，没有“成为队头的时刻”字段。
- **原因**：队列设计没有记录每次排班事件。
- **影响**：只能用“当前队头年龄分布”近似，不能得到已完成样本的等待时长 P50/P99。
- **处置**：S02 先做当前队头年龄分布；若确需真实等待时长，再评估增加队头进入时间或审计表，不在 S01 扩表。
- **验证**：模型字段 `model.Inbox` 无 head_since。
- **状态**：限制已登记。**可排期**。

### IR-S01-Q13 · `business_success_age` 不覆盖 legacy 成功

- **现象**：查询只取 `business_state='success'`，历史 `NULL + processed_at NOT NULL` 的 legacy 成功不计。
- **原因**：指标要表达“显式业务成功”，避免把未知历史当成功。
- **影响**：若最近只有 legacy 成功，指标会显示更老甚至 NaN；不能据此判断 worker 停了。
- **处置**：保持现口径；S02 若需要覆盖 legacy，新增 `legacy_success_age_seconds`，不复用旧名。
- **验证**：`telemetry_monitor.go:154`；`energy.go:123` 的 `COALESCE` 是另一条口径。
- **状态**：已标口径。**可排期**。

## 三、阻塞与排期

- **阻塞 S02 的口径/施工条件**：Q03（过期必须用 `ts_ms`）；若实际采用 021，Q09（幂等与 CONCURRENTLY）也成为施工门槛。
- **方案 B 的阻塞缺陷**：Q05（快照读者）、Q06（补偿语义）；因此 S01 推荐方案 A。
- **可排期建议**：Q01 的双指标、Q02 的 pending gauge、Q08 的 DB 累计、Q10 的计数预算、Q12 的真实等待时长、Q13 的 legacy 成功指标。
- **不阻塞 S01 的问题**：以上均未改变本轮文档交付；S01 无代码/迁移/发布，故没有本轮运行阻塞。
