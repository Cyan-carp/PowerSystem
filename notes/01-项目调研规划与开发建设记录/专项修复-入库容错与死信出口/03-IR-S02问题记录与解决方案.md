## 二、逐项说明

### IR-S02-Q01 · 分桶字段未回填

- **现象**：T01 第一次运行时 `inbox_pending_rows_outside_window=1`，但所有队头分桶都是 0。
- **原因**：SQL 别名是 `lt_1m`、`m1_5m`、`m5_15m`、`m15_1h`、`m1_6h`、`ge_6h`；GORM 默认映射不匹配带下划线的别名，`Scan` 静默留零。
- **处置**：六个字段加 `gorm:"column:..."` 显式标签；修订后指标改名为 `inbox_head_age_devices_*`，标签保持显式。
- **验证**：T01/T12 通过；过期前 A 设备只贡献窗口内 30 秒一条，过期后窗口外计数 1→0。
- **状态**：已修复。**不阻塞**。

### IR-S02-Q02 · 隔离库校验误拒 Docker PG

- **现象**：首次 `ir_s02` 运行时全部子测试在 fixture 阶段失败：`{DB:ir_s02_test Address:172.18.0.2 Port:5432}`。
- **原因**：`inet_server_addr()` 返回容器网络地址，不是隧道客户端的 127.0.0.1。
- **处置**：保留数据库名 `ir_s02_test` 与端口 5432 的精确校验，地址改为必须为回环或 RFC1918 私网；不匹配直接 `t.Fatal`，不跳过。
- **验证**：全量 `ir_s02` 通过；临时库测试后已删除。
- **状态**：已修复。**不阻塞**。

### IR-S02-Q03 · 测试编译错误

- **现象**：初稿使用 `time.Time.UnixMillis()`，Go 无此方法。
- **处置**：改为 `UnixMilli()`；`go vet -tags ir_s02` 通过。
- **状态**：已修复。**不阻塞**。

### IR-S02-Q04 · 过期与 `energy_daily` 质量标记的交互

- **现象**：过期把行从 `processed_at IS NULL` 变为已处理非 success；`energy.uncertainExistsSQL` 只排除 success，会把这些行计为“不确定”。
- **影响**：若某历史设备日已因其它原因进入 `energy_dirty_days`，重建时 `source_quality` 可能从 `verified` 变 `provisional`；kWh 不变。S02 自己不标记 dirty，不会单独触发重建。
- **处置**：不调用 `energy.MarkDirty`；T10 验证 kWh、source_quality、updated_at、dirty marker 均不变；把该交互写入方案页与交接页。
- **状态**：已知交互。**不阻塞本地 S02**；若所有者要求历史日永不翻 quality，需另立口径。

### IR-S02-Q05 · pending 计数的成本

- **现象**：`count(*)` 需要扫 pending 部分索引；积压大时耗时上升。
- **处置**：队列观测独立 60 秒周期、2 秒预算；失败整组 NaN、`stats_known=0`；不与 5 秒 readiness 探针共用预算。
- **验证**：T09 在 220 万 pending 下无候选约 116ms；未做生产 1400 万 pending 压测。
- **状态**：已标限制。**可排期**（S04 或积压再现时再量）。

### IR-S02-Q06 · 物理索引不缩小不是失败

- **现象**：清理后逻辑 pending 下降，但 `idx_inbox_pending` 物理文件可能不变，MVCC 死元组仍在。
- **处置**：验收只认逻辑 pending 计数、终态计数与索引可用性；不执行 `VACUUM FULL`。
- **状态**：口径已冻结。**不阻塞**。

### IR-S02-Q07 · 生产 `owner_abandoned` 零接触未复测

- **现象**：8,809,844 条是 96 的历史记录；本轮没有生产连接。
- **处置**：结构证明（双重 `processed_at IS NULL` + `owner_abandoned` 防护）+ T03 隔离异常行 + count/max_id 不变；生产指纹留给发布前维护窗口。
- **状态**：本地证据充分、生产待授权。**不阻塞本地 S02，阻塞生产签收**。

### IR-S02-Q08 · 与实时入库共用调度锁

- **现象**：首版 `expireInboxWindow` 持 `scheduler.mu`；清理持锁时实时 tick 不能运行。
- **原因**：单 worker 语义与 `processPending` 共用一把进程内锁。按 2000/30s 的排水能力，即使每批只有 1 秒也会周期性停住实时路径，而历史净余量只有约 0.92%。
- **处置**：移除过期路径的 `scheduler.mu`。过期集合是 `ts_ms < floor`，实时入库只取 `ts_ms >= floor`，两者按定义不相交；边界行由行级锁、`processed_at` 复核和 `SKIP LOCKED` 兜底。单 worker 仍只启动一个。
- **验证**：T15 在触发器把批次拖慢到数秒时，`scheduler.mu.TryLock()` 仍成功；T05 并发/重复仍 0 双重处理。
- **状态**：已修复。**不阻塞本地 S02**；生产若观察到 DB I/O 竞争，S04 再评估。

### IR-S02-Q09 · `history_enabled=false` 时过期仍写终态

- **现象**：首版 `processPendingBudget` 在 `history_enabled=false` 时返回，但过期 worker 仍运行。
- **合同复核**：`016_telemetry_realtime.sql` 新增该列，`README` 写明“可暂停历史”，`processPendingBudget` 用它直接返回；没有源码/契约证据支持“过期独立于操作者暂停”。首版的“有意设计”不成立。
- **处置**：改为 fail-closed。事务内先读 `history_enabled`，false 或调度单例缺失返回 `errInboxExpiryPaused`；同一语句 SELECT/UPDATE 再以 `EXISTS (SELECT 1 FROM gate)` 二次门禁；新增 `expiry_paused` 指标。
- **验证**：T13 覆盖 false 暂停、true 恢复、单例删除 fail-closed、恢复后继续；T04 维护门禁单独覆盖。
- **状态**：已修复。**不阻塞**。

### IR-S02-Q10 · 是否需要 021/新索引

- **现象**：过期候选按 `processed_at IS NULL` + `ts_ms` + `id` 排序取批；首版只用 `enable_seqscan=off` 证明旧索引可用，不能证明生产计划。
- **修订测试**：T09 用默认 planner，插入 2,200,200 行，均为 pending。排水 UPDATE 为 `Nested Loop` + `Index Cond: (id=expired.id)`，2000 行执行 61.2ms；无候选为 `Parallel Seq Scan` 约 116ms；队头为 `idx_inbox_pending_device`，143 台 39.8ms，每台移除 700 条窗外前缀。
- **结论**：现有索引在隔离规模可用且被默认 planner 选中；**不能证明生产 21GB 表无需 021 或成本可接受**。021 候选只记录、不创建：
  - `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_inbox_expiry ON telemetry_inbox (ts_ms,id) WHERE processed_at IS NULL;`
  - 条件性 `idx_inbox_head_device_ts (device_id,ts_ms,id) WHERE processed_at IS NULL`，仅在真实设备窗外前缀使队头查询超预算时评估。
- **状态**：隔离证据已更新；生产待 `EXPLAIN (ANALYZE, BUFFERS)` 或 021 决策。**阻塞生产签收，不阻塞本地候选**。

### IR-S02-Q11 · 过期指标是进程内计数

- **处置**：跨重启累计以 DB `business_state='quarantined' AND failure_code='window_expired'` 计数为准；指标只做速率/最近时间。
- **状态**：口径已写。**可排期**。

### IR-S02-Q12 · 终态清空 `next_attempt_at`

- **处置**：文档明确它是调度字段；`attempts`、`first_failed_at`、reason/missing 证据均保留；T01 比较历史字段集合。
- **状态**：口径已写。**不阻塞**。

### IR-S02-Q13 · 多 API 实例并行未实测

- **处置**：DB 层 `FOR UPDATE SKIP LOCKED` + 双重谓词 + history 门禁保证不重复写、不触碰 owner；单实例单 worker 仍是主约束。
- **状态**：已知限制。**发布前确认单实例**；多实例需另立方案。

### IR-S02-Q14 · `go build ./...` 的本机干扰

- **处置**：使用 `go build ./cmd/... ./internal/...`；记录在测试页。
- **状态**：环境限制。**不阻塞**。

### IR-S02-Q15 · 队列 watcher 始终运行

- **处置**：独立 2 秒上下文、NaN/known=0、失败计数；不阻塞 5 秒探针与 readiness。
- **状态**：有界设计。**不阻塞**。

### IR-S02-Q16 · 排水能力不足

- **现象**：500 行/60 秒 = 30,000 行/小时，低于 96 历史接收 83,318 行/小时；持续过期输入下窗口外 pending 会单调增长。
- **处置**：冻结 2000 行/30 秒 = 240,000 行/小时（2.9 倍历史接收），预算 5 秒；移除调度锁避免用清理换实时余量。
- **验证**：T11 单批 2000 行 279.5ms；T14 以 25 行/秒（90,000 行/小时）持续注入 1500 条，初始 2000 条，共 3500 条在 90.27s 排空，观测净速率 139,578 行/小时。
- **状态**：已修复。**不阻塞本地 S02**；生产 I/O 与并发未测，不能把 139,578 写成生产承诺。

### IR-S02-Q17 · 队头口径错误

- **现象**：首版取全局最旧 200 条 pending，既重复单设备又含窗口外行；8 天陈货会把队头桶顶到 `ge_6h`，窗口外行还占掉样本。
- **处置**：改为 `devices` 表逐设备 `LATERAL` 取 `processed_at IS NULL AND ts_ms>=floor ORDER BY id ASC LIMIT 1`，按 `received_at` 年龄分桶；指标改名 `inbox_head_age_devices_*`，增加 `inbox_head_age_devices_total` 与 `inbox_head_age_device_limit`。
- **验证**：T12 用 A（窗外 + 两条窗口内）、B（20 分钟）、C（只有窗外）、D（2 小时 + 1 分钟）证明每设备只贡献一条、窗外不计、无重复；T01 证明 8 天窗外行不再顶高队头。
- **状态**：已修复。**不阻塞**。

### IR-S02-Q18 · `enable_seqscan=off` 的证据边界

- **现象**：首版 T09 用 `enable_seqscan=off` 得到 `idx_inbox_pending`，只能证明索引可用，不能证明生产默认 planner 会选择它或成本可接受。
- **处置**：T09 改为默认 planner，220 万 pending；记录排水、无候选、队头三套计划与耗时；文档明确隔离与生产的区别；不创建 021。
- **状态**：证据已更新；生产计划仍未证明。**阻塞生产签收**。

## 三、阻塞与排期

- **阻塞本地 S02 候选的缺陷**：无。
- **阻塞生产签收的事项**：
  - 生产 `owner_abandoned` 前后指纹与真实 7 天窗观察需发布授权；本轮不能代替。
  - 生产真实数据 `EXPLAIN (ANALYZE, BUFFERS)` 未做；021 是否必要尚未决定，未在大表/生产建索引。
  - 生产 5 秒预算下的 I/O、并发与 8 路历史处理余量未验证。
- **可排期建议**：Q04 历史日 quality 口径、Q05 千万级 pending 成本、Q11 跨重启累计对账、Q13 多实例方案。
- **不扩做**：S03 熔断、S04 容量、前端、021。
