## 三、终态状态机

### 3.1 取值与语义

- `business_state` 实际取值：NULL（历史或未写）、`pending`、`retry`、`success`、`quarantined`。
- 新插入行不显式写状态，依 014 默认值为 `pending`；历史行可能保持 NULL。
- `processed_at` 是终态硬标记：014 要求非 NULL 状态中只有 `success`/`quarantined` 可以且必须非空。
- `failure_code` 没有数据库 CHECK，是应用层字典；`owner_abandoned` 是 96 人工批量写入的保留原因。
- `alarm_evaluation` 是告警评估结果，不是业务终态；`historical_suppressed` 不代表失败或死信。

### 3.2 转换表

| 起点 | 触发 | 终点 `business_state` | `failure_code` | `processed_at` |
| --- | --- | --- | --- | --- |
| 插入 | MQTT 接收并提交 | `pending` | NULL | NULL |
| pending/retry | 业务事务提交成功 | `success` | NULL | now |
| pending/retry | `identity_invalid`、`device_deleted`（确定性） | `quarantined` | 对应码 | now |
| pending/retry | `payload_invalid` 连续 3 次且 ≥30 秒 | `quarantined` | `payload_invalid` | now |
| pending/retry | `td_missing` 连续 6 次且 ≥10 分钟，检查间隔 ≤2 分钟 | `quarantined` | `td_missing` | now |
| pending/retry | `td_unavailable`、`device_lookup`、`business_failed` | `retry` | 对应码 | NULL + `next_attempt_at` |
| pending/retry | `ts_ms < now-7d` | **不变**（现状只是不再被选中） | 不变 | NULL |
| quarantined | 显式补偿请求（仅隔离库） | `retry` | 清空 | NULL |
| pending/retry | 96 人工批量截点 | `quarantined` | `owner_abandoned` | now |

> 关键缺陷：现状没有“过期→终态”转换。窗口只影响选择，不影响状态；一条永远失败的样本在 7 天后仍是 `processed_at IS NULL`，队龄指标会继续上涨。这是 IR-R01，S02 处理。

### 3.3 三类失败终态

| 处置 | 定义 | 触发者 | 推荐 A：state / code | 备选 B：state / code | 自动 |
| --- | --- | --- | --- | --- | --- |
| 过期 | 超过 7 天数据窗、不再有业务价值 | S02 过期 worker | `quarantined` / `window_expired` | `expired` / `window_expired` | 是 |

| 死信 | 有界重试后确认无法入库 | 现有 `recordInboxFailure` | `quarantined` / 具体失败码 | 同 A | 是 |

## 四、014 约束与 021 迁移方案

### 4.1 014 的实际含义

- 约束为 `business_state IS NULL OR (state IN ('pending','retry','success','quarantined') AND ((state IN ('success','quarantined')) = (processed_at IS NOT NULL)))`。
- 因此“终态”目前只有 `success` 和 `quarantined`；新增 `expired` 必须改约束，新增 `failure_code` 不需要。
- 约束是 `NOT VALID`：创建时不扫描历史行；新写入仍逐行校验。96 的 8,809,844 行已满足现有约束，不需要重写。
- 历史 NULL 行是合法例外：`business_state IS NULL` 时不校验 `processed_at`，所以旧数据不能简单按非 NULL 状态推断。

### 4.2 方案 A（推荐，S02 零迁移）

- 过期行写 `business_state='quarantined'`、`failure_code='window_expired'`、`processed_at=now`。
- 不新增状态、不改 014、不触碰历史行；与 96 的 `owner_abandoned` 先例一致。
- 指标用 `failure_code` 区分过期/放弃/死信三类失败终态，不需要新列。
- 影响面最小：`telemetry_snapshot.go`、`service/telemetry_compensation.go` 无需为“新状态”改动；只需过期 worker 自己遵守 `processed_at IS NULL` 的写入口径。

### 4.3 方案 B（021 草案，不落文件）

若评审要求把“过期”独立成状态，021 迁移方案为：

- `DROP CONSTRAINT IF EXISTS inbox_business_state_check`；
- 重建约束，允许 `pending/retry/success/quarantined/expired`，并把 `expired` 纳入“必须 `processed_at IS NOT NULL`”的终态集合；
- 使用 `NOT VALID`，不扫描、不回填 8,809,844 行；
- 不新增 `failure_code` CHECK；字典继续由代码和文档约束。

草案约束语义（仅说明，不是可执行迁移文件）：

```text
business_state IS NULL OR (
  business_state IN ('pending','retry','success','quarantined','expired') AND
  ((business_state IN ('success','quarantined','expired')) = (processed_at IS NOT NULL))
)
```

方案 B 的额外成本：

- 旧 worker 不认识 `expired`；`telemetry_snapshot.go:193,223` 只排除 `quarantined`，会把过期行当候选。必须在发布前停旧 worker，或先改所有读者再切新代码。
- `service/telemetry_compensation.go:76` 只接受 `quarantined`；过期行是否允许补偿需单独决定。
- `energy.go:137` 的 `uncertainExistsSQL` 会把非 success 的已处理行计为不确定；过期行可能让某些设备日变成 uncertain，需在 S02 评估。
- 因此本阶段建议 S02 采用方案 A；方案 B 留给确有独立状态需求的后续阶段。

### 4.4 021 执行约束

- `store.Migrate` 没有版本表，每次启动重跑；021 必须可重复执行。约束调整沿用“先 `DROP CONSTRAINT IF EXISTS`，再 `ADD CONSTRAINT ... NOT VALID`”，索引使用适用的 `IF NOT EXISTS`，并验证 014 先于 021 重跑后的最终约束。
- 若 021 只加索引，使用 `CREATE INDEX CONCURRENTLY` 时不得登记到 `atomicMigrations`，且要确认迁移入口是 autocommit；否则拆成独立维护脚本。
- 按 96 记录的表 heap 约 21 GB（历史，非本轮复测），索引构建不能走默认 30 秒启动预算；应使用 `--migrate-only --migration-timeout` 或维护窗口，失败不启动新 worker。
- 本阶段不创建 021 文件；以上仅是迁移设计与评审依据。

### 5.1 口径边界

- **“窗口外滞留”统一定义为** `processed_at IS NULL AND ts_ms < now-7d`，与 `inboxPendingPredicate` 同源；不是按 `received_at` 算。
- `queue_oldest_age_seconds` 的“最老”是按 `id` 取队头，年龄用该行 `received_at`。若后插入的补传行 `received_at` 更老但 `id` 更大，它不是队头，指标会低估；S02 应同时提供 `queue_head_age` 与 `pending_oldest_received_age` 两个名字，避免语义混用。常规 MQTT 入口的 `telemetry.Parse` 会拒绝超过 48 小时的时间戳（`telemetry.go:57-58`），所以“旧 ts、新接收”主要出现在直连/测试/历史行；判据仍应与调度谓词一致。
- `queue_oldest_age_seconds` 在无 pending 时返回 0，不是 NaN；输入停止由 `inbox_receive_age_seconds` 暴露。
- `inbox_receive_age_seconds` 取全表最大 `received_at`，`quarantined/retry/pending` 都算；旧 `ts` 的补传只要最近接收，仍会让输入看起来“活着”，所以它不能替代 `fresh_ratio` 或数据时间新鲜度。
- `business_success_age_seconds` 只统计显式 `business_state='success'`；历史 `business_state IS NULL AND processed_at IS NOT NULL` 的 legacy 成功不计入。若要覆盖 legacy，需另立指标，不能改这个告警口径。
- `fresh_ratio` 的分子只认 `telemetry.Freshness == "fresh"`：`received_at` 和采样 `ts` 都在 15 秒内，未来超过 60 秒判 unknown；Redis 缺键、JSON 损坏、时间戳非法都计入“不新鲜”，分母不变。`expected_devices` 只排除软删除和当前静默窗口，不按 `is_simulated` 过滤。
- `fresh_ratio` 是瞬时探针，不是时间窗平均；`fresh_ratio=1` 同时是 `/ready` 条件之一。探针失败时可能为 NaN，不能用 `<1` 单独判断。

## 六、S02/S03 新增观测项

| 观测项 | 定义/查询 | 成本 | 索引建议 |
| --- | --- | --- | --- |
| 窗口外滞留行数 | `COUNT(*) FILTER (WHERE processed_at IS NULL AND ts_ms < floor)`，同时 `MIN(received_at)` 得最老滞留年龄 | 与 pending 数成正比；积压时上升 | 先复用 pending 部分索引；生产 `EXPLAIN` 证明必要后才考虑 `(ts_ms,id) WHERE processed_at IS NULL` |
| 窗口内待处理数 | `COUNT(*) FILTER (WHERE processed_at IS NULL AND ts_ms >= floor)` | 同上 | 可复用 `idx_inbox_pending` |
| 连续 missing 计数 | `failure_code='td_missing'` 的 `missing_attempts` 分布（1-2/3-5/6+）、`MAX(missing_attempts)`、最老 `received_at` | 只扫 pending 的 td_missing 行 | `(failure_code,id) WHERE processed_at IS NULL` |
| 队头停留分布 | 每设备 `DISTINCT ON (device_id)` 取窗口内最旧 pending 行，按 `now-received_at` 分桶（<1m/1-5m/5-15m/15-60m/1-6h/>6h） | 按 143 台规模约 143 个队头（历史口径）；存在窗口外 pending 时每设备要跳过旧行 | 先用 `idx_inbox_pending_device`，S02 用 EXPLAIN 决定是否加覆盖索引 |
| 过期/死信计数 | `expired_rows_total`、`dead_letter_rows_total{failure_code}`、`expiry_last_success_timestamp`、`expiry_batch_seconds`；死信累计不含 `owner_abandoned` | 进程计数低成本但重启归零；持久累计需有预算的 DB 核对 | 默认不建覆盖 881 万旧行的索引；若确需持久查询，评估排除 `owner_abandoned` 的部分索引 |
| TD 查询结果拆分（S03） | `td_missing_queries_total`（查询成功但无行）与 `td_error_queries_total`（报错/超时）分开；熔断状态 gauge | 进程内计数器，低成本；重启归零 | 无 |
| 系统性连续缺失（S03） | 连续查询成功但无行的次数、涉及设备数、首次/最近缺失时间，以及查询时样本距 `received_at` 的年龄分布；与单行 `missing_attempts` 分开 | 有界进程计数和固定桶直方图；避免按设备 ID 建高基数标签 | 无；判定阈值待 S03 隔离实测，近期写入的 `false` 不直接视为真实缺失 |

## 七、回滚、灰度与零接触证明

### 7.1 S02 过期出口

- **默认关闭**：新增配置开关（建议 DB 单例或环境变量），默认 `enabled=false`；先 dry-run 只统计候选，不写终态。
- **灰度**：隔离库先跑；生产在当轮授权后按有界小批量、单 worker 开启，批量上限须由 S02 实测冻结；观察 `expired_rows_total`、`queue_oldest_age_seconds`、`inbox_receive_age_seconds` 和错误日志，再逐步放大。
- **回滚点**：方案 A 先关开关、停过期 worker，再回退到兼容现有 schema 的镜像。已写终态不会自动回退；确需恢复时按现有单 ID 显式补偿，且须满足“无后继终态”检查并留审计。方案 B 有新状态时不得直接切回不认识 `expired` 的旧 worker，只能冻结写入并回到识别该状态的兼容候选。
- **零接触**：过期 UPDATE 的 WHERE 必须同时含 `processed_at IS NULL`、`ts_ms < floor` 和 `failure_code IS DISTINCT FROM 'owner_abandoned'`；96 的 8,809,844 行 `processed_at` 均非空，结构上不可能被命中。

### 7.2 S03 熔断覆盖

- **默认关闭/影子**：`include_missing` 开关默认 false；先只记录“本应打开”的次数，不改变调度。
- **灰度**：隔离环境制造整段缺失，确认打开/半开/恢复；生产在当轮授权后先由现有单 worker 影子观测，再在同一调度器内小范围启用，不能并行启动第二个历史 worker。缺失信号须先排除 TD 尚未写完的时间差。
- **回滚点**：关开关或回退镜像；熔断状态在内存，重启即清空，无数据库状态需要回滚。若 021 只加索引，索引可保留，不影响回滚。

### 7.3 8,809,844 行零接触证明

1. **结构证明**：S02/S03 所有新写路径的 WHERE 都要求 `processed_at IS NULL`；96 已把这 8,809,844 行的 `processed_at` 设为非空。任何遵守该谓词的代码都不可能命中它们。
2. **前后指纹**：若 S02 维护窗口允许全扫，前后各跑一次：
   `count(*)`、`min(id)`、`max(id)`、`min(processed_at)`、`max(processed_at)`、`sum(attempts)`、`sum(missing_attempts)`，以及可选的 `sum(hashtextextended(id::text||':'||processed_at::text||':'||coalesce(business_state,'')||':'||coalesce(failure_code,''),0))`。全部相等才算零接触。
3. **范围证明**：审计 S02/S03 的 SQL/diff，确认没有 `DELETE`、`VACUUM FULL`、没有以 `owner_abandoned` 为目标的条件；021 若只建索引，不修改行数据。
4. **新增证明**：前后按 `failure_code='owner_abandoned'` 计数，数量不增；该批次的 `max(id)` 不增，排除新写入同码行。指纹是辅助证据，不能代替 SQL 谓词与实际写入审计。

> 以上证明是 S02 的准入条件，不在 S01 执行；S01 只定义方法与判据。

## 八、冻结决定与停止

- 推荐 S02 采用方案 A：`quarantined + failure_code='window_expired'`，零迁移、零新状态、最小读者影响。
- 过期判据必须复用 `ts_ms < now-7d`，不能改用 `received_at`；否则“旧 ts、新接收”的补传行永远不会过期，IR-R01 仍会复现。
- 现有 5 项指标口径按第五节冻结；S02 新增指标必须另起名字，不复用旧名表达新语义。
- 本阶段不写代码、不创建 021、不发布、不进入 S02。
