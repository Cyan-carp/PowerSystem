# S04 · 漂移观测与人工提升

> 本阶段把「模型变差了怎么办」落成可执行的流程：先看得见，再有人决定。

## 一、漂移事件的产生

`qualityWorker` 每小时在回填与聚合同步完成后调 `detectDrift`：

| 检测 | 频率 | 写入 |
| --- | --- | --- |
| `detectDistributionDrift`（L1） | 每小时 | `probability` 均值偏移超 ±15% → `watch`；`high_ratio` 越出 [0.05,0.25] → `watch` |
| `detectMetricDrift`（L2/L3） | 每小时，看近 3 天 | `ece` 高于基线 0.05 连续 3 天 → `triggered`；`precision` 低于基线 10 个百分点且样本 ≥200 连续 3 天 → `triggered` |

去重：同日同 `level+signal` 只写一条。事件只登记事实，**不触发训练、不发通知**。

## 二、人工提升（2026-11-04 起改走试用）

> 下方 promote 流程是历史设计记录。2026-11-04 起直接提升已停用（返回 409），避免只改台账不加载模型；候选统一走 `trial`（实际 reload 并用 `/health` 核对）→ `confirm`（再次核对后转正），回退同样核对运行版本。

`POST /predictions/quality/models/:version/promote`（requireAdmin）：

1. `SELECT ... FOR UPDATE` 锁目标行；
2. 校验 `status='candidate'`，否则 409；
3. 现役（若存在）改 `retired`；
4. 目标改 `active`，写 `promoted_at`、`promoted_by`。

全过程在一个事务里，失败整体回滚。

### 操作人字段（2026-11-01 修复）

提升时写 `promoted_by = 当前管理员账号`；`GET /predictions/quality/models` 返回该字段，版本表在「上线时间」下渲染一行「操作人 xxx」。

**显示规则**：只有经过 promote 的版本才有操作人。用 `import` 直接登记为现役的版本 `promoted_by` 为 `null`，页面不渲染该行——没有提升动作，自然没有操作人，这不是缺陷。

修复前的状态：接口返回里漏了该字段（数据库有、查询结构体没带），导致版本表看不到"谁提升的"，审计链缺一环。修复后走完整 import → promote 复核，返回 `promoted_by=p0-admin`。

## 三、台账与运行态是两件事

这是本版最容易被误解的地方，必须在操作时清醒：

| 动作 | 改了台账 | 改了运行态 |
| --- | --- | --- |
| 页面点「提升为现役」 | 是 | **否** |
| 运维替换 `/model/model.json` 并重启 ai-predict | 否 | 是 |

两者都做完，台账才与实际跑的模型一致。只做前者会出现「页面说 A 现役、容器里跑 B」，后续所有按版本的指标都会错位。

**本版不提供合并操作**：换模型属于发布变更，必须走既有发布流程与回滚机制。
