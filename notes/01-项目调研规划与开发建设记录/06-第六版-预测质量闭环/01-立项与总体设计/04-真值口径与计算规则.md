# 04 · 真值口径与计算规则

> 这一篇是整个模块的地基。真值算错，后面所有指标都是错的，而且看不出错。

## 一、真值来源：确定性注入窗口

模拟器 `--window-mode on` 时，每天在固定时刻对固定场站注入 10 分钟遥测越线，规则完全确定：

| 时刻（北京时间） | 场站 | 注入指标 |
| --- | --- | --- |
| 09:00–09:10 | PV-01 | temperature |
| 11:00–11:10 | PV-02 | voltage |
| 13:00–13:10 | PV-03 | temperature |
| 15:00–15:10 | PV-04 | temperature |
| 17:00–17:10 | ST-01 | temperature |

场站内**每天轮换一台设备**被注入，轮换算法是 `SimulationDeviceIndex(day, count)`——按上海日历日序号对同站设备数取模。窗口外自然恢复。

## 二、判定算法

对一条预测（设备 D、场站 S、窗口终点 `window_end_ms`）：

1. **窗口定义**：`(window_end_ms, window_end_ms + 3600000]` 毫秒，左开右闭。这与训练标签 `end_ms < onset <= end_ms + 1h` 严格一致，不能改。**不得再叠加任何“前兆容差”**；2026-11-03 的 2 小时试验已证明它只会把错误在 TP/FP/FN 之间重新分配。
2. S 不在五个场内 → `actual_fault=false`，`label_source='window_rule'`，`label_rule='window_1h'`，`label_confidence='confirmed'`。
3. S 在五场内：枚举窗口覆盖到的上海日历日（跨日最多 2 天），对每天取槽位起点 `day(H:00)`，若起点落在窗口内：
   - 取该场站设备列表（升序），用 `service.SimulationDeviceIndex(day, len)` 选中当日设备；
   - 若选中的 `device_code` == D → `actual_fault=true`，`fault_onset_ms=槽位起点`。
4. `predicted_high = probability >= threshold`。

## 三、复用的现成实现（不要重写）

| 需要什么 | 用哪个 |
| --- | --- |
| 上海日历日零点 | `service.SimulationDay` |
| 当日轮换序号 | `service.SimulationDeviceIndex` |
| 当日五个槽位 | `service.SimulationSchedule` / `SimulationScheduledAt` |
| 1 小时窗口与判定 | `service.PredictionHorizonMS` / `service.StationDeviceCache.WindowFault` |

`internal/service/simulation.go` 与模拟器的 Python 实现是一一对应的（源码注释明确写了 mirror 关系），复用它们就避免了双份规则漂移。`internal/service/prediction_truth.go` 是训练、回填与历史修正共用的唯一判定实现。

## 四、四个必须遵守的边界

1. **窗口没走完不能标。** 只回填 `window_end_ms + 1h <= now` 的行。提前标 `actual_fault=false` 是不可逆的错标，会把真阳性算成真阴性。
2. **设备列表取 `simulation_alarm_policy_devices`（active，按 `device_code` 升序），不是 `devices` 台账。** 模拟器选设备就是按这张表；用台账在增删设备时会整体错位，真值会错到别的设备头上。
3. **幂等。** 写入用 `ON CONFLICT (prediction_id) DO NOTHING`，每批 500 行，单轮上限 20000 行，避免长事务锁表。
4. **回填窗口 3 天。** 常量化 `qualityBackfillDays`，既不漏（小时级预测），也不无限重扫历史。
5. **旧口径不可混算。** `prediction_outcomes.label_rule` 区分 `legacy`（2026-11-04 之前的 2 小时容差行）与 `window_1h`；质量 KPI、批次、校准、漂移、重训准入只统计 `window_1h` 且 `window_end_ms + 1h <= now` 的行。旧行必须通过 `stages/02-backend/cmd/prediction-label-fix` 显式修正，逐行写审计表；不得用“全表重算”替代，也不得把 legacy 行直接当成新口径。

## 五、为什么不用告警当真值

| 方案 | 问题 |
| --- | --- |
| 用 `alarm_records` 反推 | 告警有去重、确认、维护闸；`ai_failure_risk` 类告警本身就是模型输出的下游，用它当真值等于自我印证 |
| 用 `fault_active` 字段 | 模拟器已把该字段固定为 false，且 `fault-labels.csv` 在生产不存在 |
| 人工标注 | 本版未做界面入口，表里预留了 `label_source='manual'` 与 `label_confidence` |

## 六、已知偏差（如实记录）

1. **注入 ≠ 真实故障。** 遥测越线是被制造出来的异常，不代表设备真的会坏。所以本版算出来的是「模型对注入事件的识别能力」，不是「对真实故障的预测力」。
2. **覆盖率有限。** 每天每站只有一个 10 分钟窗口、一台设备，143 台设备里每天只有 5 台会产生正样本。要积累到足够样本需要数周。
3. **窗口边界敏感性。** 预测 `window_end` 恰好卡在窗口前后时，命中与否取决于毫秒级对齐；这是标签定义本身的特性，不修正，但解读指标时要记得。
