# V6 测试方案与验收清单

> 专门给「另一个会话专做测试」用。按顺序执行，每步都有明确的通过标准；不通过就停下查，不要跳步。

## 零、前置

1. **部署范围**：`api` 与 `frontend` 两个镜像。`ai-predict` 不需要更新（`retrain.py` 不进运行时镜像）。
2. **迁移**：随 api 启动自动执行 018，无需手工跑。若想单独验证：`./api -migrate-only`。
3. **等待**：worker 首次执行在启动后 **90 秒**，回填 3 天、上限 2 万条。**首次追平约需 2 轮（2 小时）**，这期间数据残缺是正常的。
4. 准备管理员与运维员两个账号（运维员用来验证权限）。

## 二、真值回填（最关键）

```sql
SELECT count(*) FROM prediction_outcomes;
SELECT label_source, label_confidence, count(*) FROM prediction_outcomes GROUP BY 1,2;
SELECT min(window_end_ms + 3600000) <= (extract(epoch from now())*1000)::bigint AS no_early_label FROM prediction_outcomes;
```

| 检查 | 通过标准 |
| --- | --- |
| 行数 | 部署 5 分钟后 > 0，且持续增长 |
| 标签来源 | 全为 `window_rule / confirmed` |
| 不提前标 | `no_early_label = true` |

**正确性抽查**（必做，最容易错的地方）：

```sql
SELECT o.device_code, o.station_code, o.fault_onset_ms, to_timestamp(o.fault_onset_ms/1000) AT TIME ZONE 'Asia/Shanghai' AS onset_cst
FROM prediction_outcomes o WHERE o.actual_fault LIMIT 10;
```

预期：`onset_cst` 必须是某天的 `09:00 / 11:00 / 13:00 / 15:00 / 17:00` 整点，且 `station_code` 与时刻对应（9→PV-01、11→PV-02、13→PV-03、15→PV-04、17→ST-01）。**若出现其它时刻或错配场站，真值算法有问题，停下来查**。

再抽一台设备验证轮换：同一场站连续两天的 `device_code` 应不同（按日轮换）。

## 三、日指标

```sql
SELECT day, samples, tp, fp, fn, tn, precision, recall, f1, accuracy, ece
FROM prediction_quality_daily ORDER BY day DESC LIMIT 5;
```

| 检查 | 通过标准 |
| --- | --- |
| 自洽 | `samples = tp + fp + fn + tn` |
| 区间 | `precision/recall/f1/accuracy` 均在 [0,1] 或为 NULL |
| 覆盖 | 最近 3 天应有记录（首轮追平前可能只有 1 天） |

**手工复核一项**：任选一天，用 SQL 手算 `precision = tp/(tp+fp)`，与表里的值比对，差异必须为 0。

## 六、造候选并验证提升（不用真训练）

直接提交一份报告即可，避免依赖 xgboost 环境：

```bash
curl -s -X POST "$BASE/api/v1/predictions/quality/models/import" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"model_version":"stage3-xgb-test0001","data_source":"synthetic","threshold":0.35,
       "metrics":{"accuracy":0.9,"precision":0.7,"recall":0.6,"f1":0.64,"samples":12000,"positives":320},
       "train_samples":12000,"positive_samples":320,"trained_at":"2026-11-01T08:00:00Z","eligible":true}'
```

| 步骤 | 通过标准 |
| --- | --- |
| 登记 | 返回 `status=candidate`，版本表出现该行 |
| 提升 | 点「提升为现役」→ 确认 → toast 成功，状态变 `active` |
| 唯一性 | `SELECT count(*) FROM model_registry WHERE status='active'` ≤ 1 |
| 重复提升 | 再对同一版本调 promote → 409 |
| 覆盖保护 | 对 `active` 版本再 import → 409 |
| 不合格登记 | 传 `eligible:false` → 落库为 `rejected` 且保留原因 |

**注意**：提升只改台账。验证完后记得用 SQL 把测试版本改回 `retired` 或删除，避免测试数据混进正式台账。

## 八、漂移事件

至少观察 1 小时后：

```sql
SELECT detected_at, level, signal, observed, baseline, action FROM prediction_drift_events ORDER BY detected_at DESC LIMIT 20;
```

| 检查 | 通过标准 |
| --- | --- |
| 去重 | 同日同 `level+signal` 只有一条 |
| 语义 | L1 为 `watch`，L2/L3 为 `triggered` |

无事件也是合理结果（说明没漂移），不要为了造事件去改数据。

## 九、回退

本版只新增表与接口，不改既有数据结构。

- 回退镜像即可，**新表保留不影响旧版本**（旧代码不读它们）。
- 若确认要清理：`DROP TABLE prediction_outcomes, prediction_quality_daily, prediction_drift_events, model_registry;`（会丢真值历史，非必要不做）。
