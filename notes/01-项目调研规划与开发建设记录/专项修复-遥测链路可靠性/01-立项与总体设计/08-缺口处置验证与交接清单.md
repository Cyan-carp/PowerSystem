# 08 · 缺口处置验证与交接清单

> 本页列本次实施需要证明的结果及交接模板，不是已经通过的验收记录，也不新增完整发布门禁或长时间驻守要求。当前状态见 [[00-当前系统状态]]。

## 一、开始执行的检查单

- [ ] 读过当前状态、日志121及本组总方案，已重新取得现场证据。
- [ ] 已核对生产实例、运行镜像来源、数据库迁移、实际挂载和并发任务。
- [ ] 已记录备份timer原状态、在途任务与下一次触发安排。
- [ ] 已固定故障候选时间窗、设备范围、inbox扫描上限及批次ID。
- [ ] 已区分现成工具、需适配工具和待开发能力；未把本文当成可直接执行脚本。
- [ ] 已确认操作范围仅为本次事件；原始数据、权限、其他历史批次不改变。

## 二、实施前的定向验证

仅在实际编写或修改相关工具时执行受影响的验证；已有且来源一致的证据可复用，记录理由。本机后端或Docker环境先按 `stages/02-backend/deploy/home-dev/README.md`，不得对生产注入故障。

### 1. 历史隔离工具

采用隔离库构造最小但有区别的数据，至少覆盖：

| 场景 | 应有结果 |
| --- | --- |
| 窗口内、TD明确缺失 | 精确清单内隔离、审计完整 |
| 窗口内、TD实际存在 | 不按缺失隔离 |
| TD超时或错误 | 保留未知/重试，不判丢失 |
| 窗口外、ID越界、非目标设备 | 零修改 |
| 原有成功/隔离/owner_abandoned | 保留原终态与证据 |
| 边界毫秒及迟到旧消息 | 半开窗口正确，增补不自动扩围 |

另做有意义的并发和失败检查：worker先处理、TD迟到、重复应用同批、事务提交返回未知、批间进程中断。预期无双写、无静默漏审计，可从已提交回执续跑；遇未知先查后续。

验证payload/身份/尝试次数摘要不变、隔离不算success、快照不会被隔离行污染、能源dirty正确覆盖边界、旧告警不补发。不要只测试字符串里是否出现某个SQL关键字来代替这些行为。

相关已有入口：`telemetry_s03_test.go`、`telemetry_s04_test.go`、`telemetry_reliability_test.go`、`telemetry_compensation.go`；具体文件均在阶段二API或service原目录，不要求把所有历史测试重新跑一遍。

### 2. 备份失败恢复

使用隔离目录、假容器适配器或受控测试文件系统注入失败；不填满生产盘，也不对生产数据库做断电实验。

| 场景 | 应有结果 |
| --- | --- |
| 启动前容量/inode不足 | 未暂停任何业务即退出 |
| 导出途中空间不足 | 停止本批子进程，恢复自己暂停的写者 |
| 恢复凭据写入失败 | 暂停前拒绝，或已暂停后有原凭据可恢复 |
| 脚本异常退出/被强杀 | 独立检查识别遗留状态，有界接管或明确转人工 |
| 上传失败 | 业务保持恢复，备份如实记失败 |
| 身份/维护版本改变 | 不恢复错误对象，不强行覆盖门禁 |

补核锁竞争、重复恢复、原本停着的服务、零字节/损坏状态文件、旧凭据重放与压缩子进程泄漏。原恢复辅助器的身份负例应继续通过。

已有相关测试：阶段四deploy目录内 `test_v4_backup.py`、`test_v4_backup_integration.py`、`test_backup_upload_parallel.py`。按改动扩展这些测试或新增对应小范围测试，不另建一套通用门禁平台。

## 三、生产实施后的结果判定

### 1. 当前遥测恢复

至少在两个不同采样时刻同时满足：

- 维护状态与当前操作一致，依赖探针正常，恢复阶段完成。
- 每台预期设备的TD样本、API入流和已确认快照都推进到当前；预期数按实际设备口径核对，不能为了通过而缩小。
- 新鲜度符合生产实际readiness实现；本地代码约束约15秒，实施时核对运行版，不临时放宽。
- 健康接口的HTTP状态与JSON语义一致；页面设备状态来自相同新鲜数据。HTTP命令退出码为0不代表接口健康。
- 没有持续净增长的实时队列；短查里未见越积越多不能外推长期容量已足够。

若只有142/143台新鲜，记录缺失设备与原因，结论写“部分恢复”，不能写全面恢复。

### 2. 本次缺口收尾

- [ ] 清单身份、时间窗、ID边界、摘要与实际应用一致。
- [ ] 各类数量可对账；变化后跳过、未知和待处理分别计数。
- [ ] 原始载荷、时间、身份和尝试证据未被改写，范围外修改数为0。
- [ ] 已隔离记录不再无效重试，后继正常样本能按原规则推进。
- [ ] 历史能源/报表仍体现缺样，未补0或跨缺口积分。
- [ ] 没有新增历史设备告警或外部旧通知；当前告警路径仍可用。

“本批候选已处理完”与“系统所有历史业务已追平”分别写。历史积压下降可能来自隔离，不能把队列减少量当成功入库量。

### 3. 备份机制修复

至少有容量不足拒绝、停写后失败恢复、身份冲突拒绝三类证据。成功备份路径要分别记录服务恢复、包完整性和上传结果；仅测试成功路径不能说明防复发措施有效。

重新开启调度前核对实际安装脚本的来源/摘要和timer绑定路径，避免只改本地副本。首轮实际执行由所有者选择时机，保存分阶段容量峰值、停写时长与恢复结果；不承诺通过一次短验就永不复发。

## 四、遇到这些情况先停哪一部分

| 情况 | 停止范围与下一步 |
| --- | --- |
| 连接到错误实例、来源不明 | 停止全部写操作，重新定位 |
| 清单越界或摘要不符 | 停止历史应用，重新预演 |
| TD查询不可用 | 停止缺失判定，不自动隔离 |
| 磁盘逼近保留线/锁等待明显增大 | 停止当前批次扩张，保留当前供数 |
| 备份身份或维护版本冲突 | 停止自动恢复，核对实际操作者与实例 |
| 发现历史告警外发/隔离被算成功 | 停止相关处置，保留证据并前滚修正 |

停止某项处理不等于关闭所有业务服务。操作已经提交时先核审计和当前进度，不直接倒回旧库；从旧全备恢复会影响此后其他业务数据，需独立恢复计划。

## 六、工程文档如何回写

本次仅规划时：更新本组方案、索引与当前对话记忆；不把生产限制改成已解决，不伪造上传定位卡或部署记录。

实际实施后按变化回写最小集合：

1. 在日志121同一故障链补实际结果；若形成独立发布批次，再按日志规范新建编号，保留旧失败证据。
2. 更新 `06-当前系统状态/04-已知限制与未生效改动.md` 的相关限制；镜像、指针或能力变化时，同步相应分卷与唯一入口摘要。
3. 新工具、参数与操作方式写原阶段README；实际上传当场核目录并登记当月定位卡。
4. 对话过程写本次共享记忆；本次临时选择不直接写为项目长期事实。
5. 运行笔记治理检查，确保索引、双链和单页长度合规。

发布门禁、备份与测试的执行情况分别据实际授权登记；本清单不把曾免除的完整流程重新加成门槛，也不以“未测试”冒充“通过”。数据写入的范围、审计和结果核对仍是操作本身不可缺的部分。
