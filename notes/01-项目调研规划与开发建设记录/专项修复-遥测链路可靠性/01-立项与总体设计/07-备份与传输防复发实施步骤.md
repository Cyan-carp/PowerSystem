# 07 · 备份与传输防复发实施步骤

> 本页给出本次事故的防复发设计，均须实施验证后才算生效，不新增项目长期门槛。当前状态见 [[00-当前系统状态]]；本轮只交规划，没有修改定时器、脚本或生产配置。

## 一、先做的止损工作

### D1 · 暂缓存在已知风险的下一次全备

先按 [[06-实时恢复与历史缺口实施步骤]] 核对任务与锁。记录备份timer原状态和计划时间，在修复容量预估前暂缓后续自动触发；不直接强杀正在暂停写者的备份。手动全备也受相同容量限制，不能用手动执行绕过问题。

给这项暂缓指定负责人和恢复条件：完成容量预算、恢复状态可靠写入、异常恢复定向验证后，重新评估调度。暂缓期间没有新恢复点，应记录这个影响，不能忘记长期不开备份。

### D2 · 固定保留对象与清理边界

继续遵循所有者“只留最近一份有效备份”的目标。这里“有效”至少要求密文完成、实哈匹配、解密和内容检查符合约定；双端上传与隔离恢复验证是另外两项结果，不能混在一起。

新备份生成和验证期间可能暂时同时存在旧包、新包及临时载荷，这是生成下一份有效恢复点所需的峰值空间，必须纳入预算。不要为了追求目录始终只有一个文件，先删唯一有效包再开始新备份。

清理时逐一核对目录真实路径、所属批次、锁、容器挂载和发布引用；不把数据库卷、原始队列、来源快照、恢复凭据或镜像回退资产当备份临时目录删除。保留失败阶段和恢复结果摘要，再处理已确认可删的失败载荷。

构建缓存清理可以作为维护措施，但不能成为备份容量算法的一部分：不能假定每次启动前都能回收20GB，也不扩大成删除业务卷或所有镜像。

## 二、修复容量预估，而不是只提高一个阈值

### D3 · 对照当前脚本确定改动位置

主要入口为 `stages/04-frontend/deploy/backup.sh`：

- `disk_headroom` 当前读取备份目录可用空间，默认阈值为4GiB；实际运行是否通过环境覆盖，执行时另核。
- 备份存在staging目录、压缩包、加密包并存的阶段，不能只拿最终密文大小估算峰值。
- 脚本已在压缩、加密、上传前调用 `v4_resume` 和 `telemetry_resume`；这一顺序保留，不把它误列成尚未实现的优化。
- 退出处理已有恢复尝试，但空间完全耗尽、凭据写入失败或进程被强杀仍可能使恢复链失效。

### D4 · 按文件系统计算下一次峰值

建议把容量判定拆成“可用空间测量”和“本批所需新增空间估算”，输出分项预算与拒绝原因。每个实际文件系统分别计算，不能跨盘相加后认为足够。

定义：

| 符号 | 含义 |
| --- | --- |
| F | 该文件系统当前可用字节 |
| S | 本批新增staging峰值 |
| C | 新压缩包峰值 |
| E | 新加密包峰值 |
| W | 期间业务/WAL/日志新增量预算 |
| R | 原容器复起与应急操作保留量 |
| M | 估算偏差余量 |

同盘最保守判定为 `F >= S + C + E + W + R + M`，另核inode和各阶段实际并存关系。已有备份及旧临时目录已经反映在F中，不再重复扣一遍；若清理后再判定，必须重新测量，不能提前把“计划删除”算成已回收。

S应从实际待备份的数据库、队列、模型、构件与私有资产逐项估算；数据库导出、源码/镜像导出与压缩比例并不相同。可借历史完整批次校准，但需加入当前增长量。旧失败staging的尺寸是现场证据，不是未来固定上限。

**仅用于理解的算例**：若S为24GiB、C为6GiB、E为6GiB、W为4GiB、R为8GiB、M为8GiB，则需56GiB。即便某次清理后剩51.3GiB，也应拒绝启动。以上数字不是本项目已实测参数，实施时替换并保存计算依据。

**验收结果**：不足时在任何停写前退出，原服务和维护值不变；无法估算某项时明确失败，不默认按0计算。

### D5 · 独立空间与运行期保护

优先考虑独立备份文件系统或受配额约束的备份空间；另建目录不能隔离同盘风险。若新增磁盘涉及宿主存储，核对thin pool等下层空间，不能只看VM内剩余容量。

恢复身份、运行阶段和最小错误回执应存放在有独立空间保障的受控位置。不能直接把所有备份搬到系统盘消耗系统空间；应区分小型恢复状态与大型载荷。

每个高增长阶段前复查空间；长时间导出/压缩过程中也做有界监测和阶段预算。达到运行保留线时停止本次备份的写入子进程，确认子进程退出及一致性操作结束，再走原写者恢复流程。避免仅让父进程退出、后台导出仍持续填盘。

停止备份时保留已持久化的恢复凭据；临时载荷清理由批次引用和恢复状态决定。不能在失败处理里无条件递归删除整个staging后才尝试恢复。

## 三、让失败恢复不依赖脚本一直活着

### D6 · 在暂停业务之前保存可恢复状态

复用并加强 `telemetry-maintenance.py`、`v4-backup-integration.py` 及现有备份锁：

1. 暂停前登记本批run ID、主机/部署身份、原容器ID与镜像、原运行状态、维护原值及版本、待执行动作。
2. 采用原子写入并确保持久化，验证文件非空可解析；写入失败时不暂停业务。
3. 每次暂停成功后追加已完成动作；动作前意图与动作后结果分开，覆盖“动作成功但回执尚未写出”的崩溃窗口。
4. 恢复只处理本批原本在运行、且由本批暂停的对象；原本停着的服务不自动启动。
5. 维护门禁按原版本比较更新；冲突意味着其他操作者介入，转人工处理，不强制关闭。

不得把全局身份校验改宽来解决单次恢复。确需容忍某类重启差异时，先明确可证明的同一实例条件及负例；未知对象保持拒绝。

### D7 · 设置暂停时限和独立检查

已有trap负责常规失败，额外的检查只补充它处理不了的进程崩溃/主机重启等情形。优先沿用现有systemd与恢复辅助器，不新建发布平台或第二套状态权威。

建议状态至少能区分：准备、已暂停、正在导出、已请求中止、写者已恢复、备份完成、需人工恢复。为每阶段记录开始时间和有效心跳；超时值基于一次实际阶段耗时加余量确定，不在未量测前写死一个过短数值。

独立检查发现超时后：

- 核对本批进程、锁所有者、心跳及暂停对象，不只凭一个旧文件判断。
- 若父任务仍活着，先发出有界中止请求；备份任务确认结束一致性导出并交出锁后才能恢复写者。
- 若任务已经崩溃，获取恢复互斥锁，复核身份后调用原恢复流程。
- 若锁仍由有效任务持有、身份漂移、门禁版本冲突或证据不完整，发出明确通知并保留现场。

不能让看门狗与活着的备份互相抢锁，也不能在数据库快照仍进行时抢先启动写者，最终误把不一致备份记成成功。

### D8 · 分开备份结果和业务恢复结果

单批回执至少有两组独立字段：

- 备份：导出、压缩、加密、完整性、上传各阶段及失败原因。
- 业务：暂停对象、恢复尝试、实际恢复结果、维护恢复结果、仍需人工处理的对象。

允许“备份失败，业务已恢复”；不允许备份失败把业务恢复结果吞掉，也不允许服务恢复就把失败备份改成成功。上传失败不应再次暂停写者。

恢复后的遥测可能需要追平。区分“写者已运行”“实时已新鲜”，分别保留时间，不为让backup成功而放宽API健康判定。

## 四、缩短停写窗口的后续优化

先量测各阶段实际耗时，再判断哪部分必须在跨库一致性窗口内。源数据导出与多个业务库之间有一致性关系，不能随意在PG备完后就恢复网关。

推荐分两步：先保留原一致性协议并解决容量/失败恢复；之后若停写仍过长，再设计一致快照或分层备份。该优化必须说明PG、TD、SQLite队列和业务写者对应的截点，以及恢复时如何识别重复/未提交数据。

压缩加密流式化可减少临时文件，但要验证流水线错误传播、完整性摘要、失败密文识别与上传重试。它是容量优化候选，不替代容量预算，也不作为本次恢复的前置条件。

## 五、传输链路的防丢与追平能力

### E1 · 先核有效会话配置

分别记录API与网关实际client ID、持久会话设置、QoS、订阅、离线过期时间、队列上限、inflight、消息到期与Broker持久化能力。不要只读取默认配置，也不要把会话有效期直接等同于Broker重启后消息必然保留。

以实际峰值产出速率λ、最大可接受离线时间T、消息平均/高分位字节B、余量系数K估算：

- 单订阅所需积压量至少覆盖 `λ × T × K`；各客户端分别核算。
- 存储预算还需乘消息大小并计入Broker索引/协议开销。
- 消费恢复速率μ应大于持续产出λ，近似清空时间为 `积压条数 / (μ - λ)`。

若μ不大于λ，只加大队列会延后失败，不会追平。调整参数先验证内存、磁盘、重启和超时行为，不默认无限队列或无限重试。

### E2 · 不把Broker的PUBACK当作下游完成

现有模拟器收到发布确认后移除outbox，但保留generated；网关在本地持久化后ACK，写TD成功再移除pending。它们分别证明不同一段的持久性，Broker收下消息不等于TD和PG都收下了。

建议后续补充可审计的端到端确认或对账补传能力：

- 身份沿用原设备、run、seq、ts，不生成替代时间戳。
- 分别记录TD落库与API持久接收的完成情况；不能用“最大序号”跳过中间洞，需连续水位或带缺口的确认集合。
- 原始generated保留策略要覆盖承诺的故障恢复时间，清理与端到端确认/受控保留期关联，不能只看PUBACK。
- 补传与实时发送分配独立限速预算，实时优先；接收端继续幂等。

TD设备表的实际唯一性还要单独核验：查询身份包含seq不意味着同一设备同一时间戳能安全保存不同run。补传遇到同时间戳不同身份/载荷时应进入冲突核查，不能覆盖现有值。

这部分是后续开发，不用于本次自动补历史；只有所有者重新选择补传某段数据时，才按独立清单执行。

### E3 · 避免一条坏历史拖住全部处理

维持当前实时确认与历史业务分离、设备间公平调度、有界重试和准确失败分类。单设备明确缺失允许进入已有隔离终态；依赖故障仍重试，不能按失败次数或消息年龄随意丢数据。

检查历史队头是否长期停留、失败原因是否反复切换、调度是否被一个慢查询占据。只对实测瓶颈做最小修复，不整体打开本地未发布的过期清理/熔断/迁移功能。

## 六、监测必须能看到“数据不再流动”

复用现有Prometheus和通知链，先核线上冻结规则的实际挂载。状态页已记录服务器历史stages目录的规则不完整，不能从旧目录重建覆盖现有告警。

建议在现有规则上补足以下观测，指标名以实际实现为准，不凭空假定已经暴露：

| 观测 | 触发含义 |
| --- | --- |
| 可用字节/inode与增长趋势 | 逼近业务保留线或预计耗尽 |
| 备份阶段耗时/暂停持续时间 | 暂停超预算、恢复未完成 |
| TD和API逐设备最新样本年龄 | 写入或接收停滞 |
| 新鲜设备比例和缺失设备列表 | 局部或整体遥测陈旧 |
| 各队列净增长与最旧样本年龄 | 追平能力不足 |
| 历史队头原因与隔离速率 | 重试停滞或异常大批隔离 |

通知聚合成同一事故的打开、持续、恢复，避免每设备重复轰炸。备份/链路告警不依赖“设备产生了业务告警”；最好能在API故障时仍由独立监测路径发现问题。恢复通知以真实新鲜度为依据，不只看容器running。

## 七、建议分批顺序

1. **止损批**：重新核对现场、暂缓风险调度、固定恢复材料与容量记录。
2. **恢复批**：当前链路与本次固定缺口收尾，保持原始数据。
3. **备份修复批**：容量预算、状态持久化、阶段预算及失败恢复；针对失败路径验证后恢复调度。
4. **监测补足批**：必要指标和现有规则增补，可与备份修复一并审查。
5. **传输增强批**：有效会话容量与端到端对账/补传能力，独立设计和验收。

每批按实际来源只叠加需要的文件。不能拿服务器旧stages树直接构建，也不能夹带本地UI、助手会话归档或未授权迁移。上传与实际命令仍以原部署README和上传规范为准。
