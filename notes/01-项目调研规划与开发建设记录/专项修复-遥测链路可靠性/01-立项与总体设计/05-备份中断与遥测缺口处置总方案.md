# 05 · 备份中断与遥测缺口处置总方案

> 本组文档供所有者自行实施：先恢复当前供数，历史缺口允许保留，再修复备份和传输的薄弱环节。2026-11-18仅编写规划，未执行生产修复；当前状态见 [[00-当前系统状态]]。

## 一、建议采用的处理路线

本次建议选择**不追补已确认的历史缺口，保留原始证据，以当前遥测恢复为优先目标**。历史处理与实时恢复分别验收，缺口作为数据质量事实保留。

执行顺序：

1. **重新只读核对现场**：此前诊断是历史截面，先确定现在是否已经自然追平。
2. **防止下一轮备份重演事故**：核对定时器及在途任务；在容量问题解决前，暂缓下一轮自动全备，不突然杀掉正在停写的备份。
3. **恢复当前供数**：确认模拟器、Broker、网关、TD、API入流、实时快照的时间逐段推进。能自然追平就不换会话、不清队列。
4. **固定历史处置范围**：按事件时间窗与精确样本清单分类，隔离明确缺TD且决定不补的记录；原始载荷与审计保留。
5. **核对业务口径**：历史不补发告警，能源与报表保留缺样，不用零值或插值制造完整性。
6. **完成防复发改动**：备份容量预算、运行空间保留、恢复凭据持久化、限时恢复与监测先落地；传输端到端确认随后分批建设。

本组是本次事件的实施设计，不重开TR-S01～S04阶段验收，不自动启用本机未发布的IR改动，也不改写项目长期规范。

## 三、方案依据与尚未证实的部分

历史取证依据是 [[04-系统部署发布备份与变更记录/部署与运维日志/05-发布工具链与文档治理/01-发布机制与门禁/121-服务器备份与构建缓存清理]]。下列数值仅帮助识别同一事故，不能当执行时的现场状态。

**已确认的事故链**

- 备份临时载荷与Docker共用数据盘，空间耗尽；备份暂停的网关等原容器因 `no space left on device` 无法复起。
- 释放空间后原服务恢复，维护关闭，TD开始写当前数据；UTC 2026-11-18 07:04—07:08的API入流仍在回放旧消息。
- 当次143台快照无新鲜样本；另查到真实历史TD缺失。实时落后和历史保序受阻同时存在。

**缺失样本定位锚点**

| 字段 | 历史取证值 |
| --- | --- |
| device_id / inbox_id | 234 / 57103916 |
| ts_ms / seq | 1794940895664 / 392880 |
| 状态 | retry / td_missing |
| 精确TD命中数 | 0 |
| 此后首个可查TD样本 | 2026-11-18 06:49:55.131 UTC |

这是单条证据，不代表143台具有完全相同的缺口。原诊断目录为 `artifacts/telemetry-diagnosis-20261117/`，恢复可能性检查脚本为其中 `recoverability.py`；曾核对一条模拟器generated原始载荷可用，不代表完整时段均可恢复。

**仍需核实**

- EMQX默认2小时会话有效期、1000条离线队列，与长时间停写后缺失相符；逐客户端有效覆盖值和丢弃事件尚未完整审计，不能把默认值写成精确丢失证明。
- 当前API是否追平、多少设备仍受影响、历史候选数量，都必须执行时重新测量。
- 本地代码具有的开关、过期出口和迁移，不能直接当作生产能力；先对照运行镜像的来源清单。

## 四、三个必须分开的结论

### 1. 当前遥测已恢复

代表预期设备的新样本已进入TD，经精确确认更新API快照，页面与健康接口恢复真实新鲜度。它不要求所有历史记录处理成功。

### 2. 本次历史缺口已处置

代表固定范围内的记录有明确分类、缺失记录已停止无效重试、原始数据与审计仍在。它不代表缺口被补齐，也不等于全系统历年积压清零。

### 3. 防复发措施已验证

代表容量不足时备份不会暂停业务、暂停后失败能够有界恢复、问题能被独立监测。单次当前恢复不能证明这一点，故障注入和实际回执应单列。

## 五、可以接受缺口，但如何解释

“这段时间没什么告警”可以作为选择不补历史的业务理由，不能作为设备正常的证据。采集或告警评估中断时，告警本身也可能缺失。

建议保留以下口径：

- 当前设备状态只使用恢复后的新鲜样本。
- 历史图表断开缺样段；需要说明时只标“数据缺口”，不填0功率或0故障。
- 电量显示已有可靠数据的结果与覆盖率；跨缺口不做长跨度积分。
- 可用率区分正常、异常与未知，不能把未知自动算成正常或离线故障。
- 健康分、预测、训练与质量统计按各自窗口标记输入不完整；恢复判据是输入窗口够用，不是简单重启模型。
- 不补造错过的告警，不把旧异常作为当前异常通知；真实的新告警应正常产生。

当前平台是合成设备环境，但原始数据与缺口标注仍按上述原则保留。

## 六、工作拆分与交付物

| 工作包 | 必要产物 | 是否可能需要代码 |
| --- | --- | --- |
| A 现场复核 | 脱敏基线、逐段时钟、影响设备清单 | 复用只读诊断，必要时适配 |
| B 当前恢复 | 两次以上新样本证据、健康与页面结果 | 自然追平可不改代码 |
| C 历史收尾 | 固定清单、逐行审计、批次结果 | 需核验并适配历史处置工具 |
| D 备份止损 | 调度处置记录、容量与恢复修复 | 主要改原备份脚本及辅助器 |
| E 传输增强 | 会话容量预算、持久确认设计 | 分批开发，不阻塞本次实时恢复 |

推荐先完成A、D的调度止损、B、C，再实现D的永久修复，最后推进E。不要把整套本地UI/助手/IR候选一起发布；本次每一批只包含明确需要的差异。
