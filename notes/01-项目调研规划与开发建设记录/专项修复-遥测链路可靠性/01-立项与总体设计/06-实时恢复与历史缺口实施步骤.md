# 06 · 实时恢复与历史缺口实施步骤

> 本页将本次事件分为现场复核、当前恢复和固定范围历史隔离。步骤由所有者后续实施；当前状态见 [[00-当前系统状态]]。先读 [[05-备份中断与遥测缺口处置总方案]]。

## 一、开始前固定范围

### 步骤A1 · 建立本次记录

创建独立批次记录，记下执行人、开始时间、时区、目的和明确不处理的其他历史问题。数据库筛选与时间窗口统一UTC，用户展示时再换算，不混用北京时间和本机时区。

证据放 `artifacts/遥测可靠性/<本次批次>/`，不要把原始载荷、环境文件或完整日志放进notes或Git。正式笔记保存摘要、数量、时间、摘要值与证据目录即可。审计涉及的原始行应在受控数据库或私有证据中留存。

记录实际主机身份、VMID、active指针、镜像ID、来源清单、数据库迁移及当前挂载。历史目标是VM117的 `powersystem-prod`；旧公网7070入口属于上游管理路径，不能因为SSH成功就视为进入生产VM。

**预期结果**：能证明接下来读写的是同一生产实例。若正在发布、备份或存在未解释的pending，先解决操作冲突，不覆盖其锁或状态文件。

### 步骤A2 · 检查空间和备份任务

分别记录Docker数据、备份目录、恢复状态目录所处的实际文件系统，读取可用字节、inode、挂载来源和正在增长的临时目录。两个不同路径可能仍是同一块盘。

2026-11-18 06:50 UTC曾测得数据盘可用51.3GiB，系统盘58.3GiB；这两个值只作历史对照，不能当作本次容量保障。

读取备份timer的启用状态、下次触发时间、实际unit内容及关联service。建议先暂缓下一轮自动全备，保留原调度信息供恢复。若任务正在运行，先读它的阶段、锁、停写清单和恢复凭据，按原恢复流程收尾；停止timer不等于停止正在运行的service。

**停止条件**：空间仍在快速下降、inode耗尽、存在另一份在途备份或来源不明的停写。先按 [[07-备份与传输防复发实施步骤]] 的止损步骤处理。

## 二、只读检查每段数据走到了哪里

### 步骤A3 · 做一张逐段时钟表

每个观测点至少记录“观测UTC、样本UTC、设备、序号、队列量、证据出处”。先查代表设备定位，再覆盖全体预期设备；不能只检查device234。

| 观测点 | 重点读取 | 判断目的 |
| --- | --- | --- |
| 模拟器 | generated最新时间/序号、outbox | 是否仍在产出和发送 |
| Broker | 实际客户端、订阅、会话、队列/丢弃 | 是否在线、是否持续积压 |
| 网关 | SQLite待写量、最旧/最新时间、错误 | 是否正常消费与落TD |
| TDengine | 每设备最新时间/序号、精确样本 | 时序库是否有当前数据 |
| API inbox | 每设备最新接收与样本时间 | API是否仍被旧消息占据 |
| API快照 | inbox_id、ts_ms、confirmed_at | 是否确认到了当前样本 |

读取API维护状态、PG/Redis/TD探针、恢复阶段、预期设备数和新鲜度分类。确认时间 `confirmed_at` 变新不代表样本时间 `ts_ms` 变新；看样本年龄才能判断恢复。

原只读脚本在 `artifacts/telemetry-diagnosis-20261117/`，其中 `probe.py`、`details.py`、`queues.py`、`td-broker.py` 分别覆盖不同层。它们属于那次现场辅助材料，重新使用前检查容器名、表名、挂载与查询范围，不直接当通用正式工具。

**查询约束**：使用只读事务和短超时；按设备、窗口、索引分页查询。不要先对巨大inbox全表排序统计，也不要在运行中的SQLite上随意复制单个db文件忽略WAL。确需一致快照时使用SQLite backup API或现有受控快照方式，并计入磁盘预算。

### 步骤A4 · 判断是在追平，还是已经停止推进

进行至少两次、建议三次短采样。建议间隔30～60秒，实际以设备采样频率与查询耗时调整，不做无期限驻守。

- 对每台设备计算 `入流滞后 = 观测时间 - 最新有效入流样本时间`。
- 计算同一设备两次样本时间的推进量，不能用全局某一台最新消息代替全部设备进度。
- 如果每经过一分钟，样本时间推进超过一分钟且滞后持续收敛，说明正在追平。
- 近似追平时间可按 `当前滞后 / (样本时间推进速率 - 1)` 估算，仅适用于推进稳定且速率大于1；异常值、时钟错误或源切换时不使用。
- 如果样本时间不动，进一步核对接收、落TD与确认错误；增加历史worker并不一定提高MQTT入流速度。

## 三、根据现场选择当前恢复分支

### 分支B1 · 当前数据已经新鲜

保留现有会话与容器，直接做短核验并进入历史缺口分类。不要为了完成旧方案再次重启或重放。

### 分支B2 · TD新鲜，API正在持续追平

维持原会话，让有持久接收保障的回放继续完成。记录估计时间与下一次人工检查时间，同时留意磁盘、PG写入延迟、队列净增量和客户端掉线。

API实时快照与历史业务队列独立：新样本进入inbox且TD有精确记录后，快照有机会先恢复。不能以历史队头仍retry为由，断言必须先清历史才能恢复当前页面。

**不应使用的捷径**：删除MQTT文件存储、设置CleanSession清旧会话、换client ID丢弃旧积压、直接清Broker队列、把旧样本时间改成现在。这些操作会扩大缺口或破坏来源，当前方案不包含它们。

### 分支B3 · TD新鲜，但API入流不推进或越来越慢

先定位API MQTT连接、订阅、持久化ACK、PG写入耗时和磁盘/WAL压力。按实际生产来源对照 `stages/02-backend/internal/api/server.go` 的MQTT接收实现，确认回调是否卡在持久化或依赖等待。

若确认瓶颈，形成一项单独最小修复：例如修复异常连接或阻塞操作，并验证“PG持久接收完成后才ACK”的约束。不要在未量测前直接提高并发、改ACK时机或整体发布本地API候选。

若决定新增优先实时入口，则需另外设计会话隔离、重复消息幂等、身份校验与单调快照；这是开发任务，不是现成开关。本次优先使用原链路恢复，无法恢复时保留本分支为明确阻塞项。

### 分支B4 · API入流与TD都新鲜，但快照仍旧

对同一条样本逐项比对device映射、run_id、ts_ms、seq和载荷有效性；执行精确TD存在性检查。核对维护门禁、快照候选范围、更新条件与设备删除状态。

源码定位：`telemetry_snapshot.go` 中 `refreshDeviceSnapshot`，以及 `telemetry_monitor.go` 的 `readinessSnapshot`。本地实现会读取每设备较新的有限候选，不是扫描全部历史；候选都旧、身份不符或TD确认失败时均不能推进。

禁止为了消除503而延长新鲜度阈值、降低预期设备数、只更新时间戳或伪造 `td_confirmed_at`。预期设备数若确有业务变更，应按原设备口径修改并记录理由。

### 分支B5 · TD也不新鲜

退回模拟器、Broker、网关和TD依赖定位，不直接进入历史隔离。若原服务仍被备份暂停，使用与本次暂停身份匹配的恢复凭据及既有恢复流程；维护门禁版本不匹配时停下核查，不全局解除。

## 四、历史缺口范围如何固定

### 步骤C1 · 建立候选窗口，不马上改数据

以前次网关停写与恢复记录作为候选范围：大致是UTC 2026-11-17 18:41至2026-11-18 06:50。它只是扫描范围，**不是可以整体丢弃的精确区间**。

逐设备记录最后可靠样本、缺失样本、恢复后首个可靠样本，采用半开区间 `[start, end)` 并保留毫秒精度。源run变化、序号重置与设备删除另列，不按序号连续性单独推断缺失。

冻结两个边界：一是故障样本时间窗，二是本批扫描的inbox最高ID。后续迟到的旧消息需要新的增补清单；不能用不断移动的“截至现在”自动扩大放弃范围。

### 步骤C2 · 对候选逐条分类

| 分类 | 条件 | 本次动作 |
| --- | --- | --- |
| 已完成 | 已成功或已有隔离终态 | 不覆盖 |
| TD存在 | 身份有效且精确TD命中 | 正常历史处理，旧告警按原策略抑制 |
| TD缺失 | 查询成功、精确无记录、窗口内 | 进入“不补历史”候选 |
| 无法判断 | TD超时/错误、身份冲突 | 保留重试，列入异常 |
| 范围外 | 时间/ID/设备不在清单 | 零修改 |

“精确”指device、原时间戳、seq一致，并验证inbox身份与原载荷。TD按设备表和时间/seq核对；不能查询某时段“有数据”就视为目标样本存在。

缺失分类需排除仍在途的数据：复查网关待写队列与恢复进度，间隔后再次精确查询；查询错误不计作一次缺失。跨库不能获得原子快照，写入前还要复查，写后发现迟到TD记录时保留审计、进入补偿复核，不静默覆盖既有终态。

### 步骤C3 · 生成只读预演清单

清单最少包含：批次ID、生成时间、主机/发布/数据库身份、窗口、ID上限、设备列表、逐行身份、原状态、载荷摘要、TD核对结果与时间、拟处理原因、各类数量和清单总摘要。

将“不补”的理由写成“所有者选择保留本次已确认缺口”，不要写“设备正常”或“告警为零”。模拟器若仍有原始记录，理由也不能写成“物理不可恢复”。

先核一个设备和边界样本，再核全清单。若发现大量TD实际存在、时间窗跨入正常供数或与原诊断明显不同，停止写入，重新划分范围。

## 五、隔离工具应如何实现

### 1. 优先复用既有状态语义

历史日志56已有固定截点 `owner_abandoned` 的处置先例。本地迁移014允许 `pending/retry/success/quarantined`，并约束终态与 `processed_at` 对应；源码过期清理还专门保护 `owner_abandoned`。

因此建议优先复用：

- `business_state = quarantined`。
- `failure_code = owner_abandoned`，本次事件与理由保存在独立批次/逐行审计中。
- `processed_at` 写实际终止处理时间，`next_attempt_at` 清空。
- 原payload、ts_ms、seq、run_id、attempts、首次失败与缺失证据保持不变；不伪造TD确认。

这里 `processed_at` 表示已经结束调度，**不是业务成功**。所有成功计数、能源来源和回放筛选均须按生产实际语义核查，不能仅凭该字段非空把隔离算作成功。

本地 `telemetry_expiry.go` 是7天过期出口，不能靠改窗口或开启全局过期开关处置本次约12小时缺口。也不需要为本次事件增加一套新的终态名称。

### 2. 工具不是现成可执行命令

历史辅助器须重新定位和审核，不把旧截点、旧ID和旧发布目录照搬。若没有合适工具，建议在阶段四原部署工具目录实现一个小型、有界的处置程序，并在原README维护用法；本页不假定该程序已经存在。

工具需有只读预演、应用固定清单、核对批次结果三种模式。应用时必须绑定清单摘要，不接受默认全库或默认截至当前时间；缺少范围参数即停止。

### 3. 事务和并发要求

实施算法如下，属于开发契约，不是可直接运行的SQL：

1. 核对数据库、清单及操作者；确认未与备份/发布冲突。
2. 读取一批明确ID，重查TD与当前行状态；有变化的行重新分类，不强行写入。
3. 按既有维护锁、每设备锁和行锁约定进入有界事务；锁顺序与worker保持一致，避免死锁。
4. 在同一PG事务先写逐行原状态审计，再通过条件更新写隔离终态；受影响行数必须与已锁定、仍符合条件的清单一致。
5. 按现有能源实现为受影响日期/相邻积分边界登记dirty；审计与业务终态保持原子提交。
6. 提交后记录批次游标和分类计数；审计唯一键绑定批次+inbox ID，重复执行不二次变更。

初始建议每批100～500行、单事务1～3秒预算，先在隔离环境量测；这不是生产固定参数。锁等待、WAL/空间、查询延迟明显上升时减速或停止，不在一个长事务里处理整个事件。

数据库连接在提交时中断，应把结果记为未知；先按批次审计与行状态核对，再决定继续，不直接重放。持久游标只能记录已经核对的提交结果。

### 4. 不应由隔离工具做的事

- 不删除inbox、TD、generated或MQTT原队列；不截断审计。
- 不直接推进全局业务游标越过未分类数据，不修改告警评估进度冒充已评估。
- 不将记录改成success，不把样本改成当前时间，不触发外部历史通知。
- 不自动重置已完成终态；旧 `owner_abandoned` 批次不在本次范围。

## 六、应用与收尾

先对一个受影响设备的小批量应用，再核原始字段、越界行、审计和后继进度；确认无问题才分批扩大。全程保留当前供数，不能为处理历史而持续阻塞实时确认。

核对本次清单：候选总数应等于已隔离、正常完成、原有终态、变化后跳过及未解决数量之和。迟到旧消息另记，不把“某次pending为0”视为所有未来迟到数据也已处理。

历史终态写入后若发现误选，先停止后续批次并保留现场。未提交事务可回滚；已提交且新业务继续推进时，不直接把所有字段倒回旧值。按既有补偿路径评估前滚修正、能源重算与告警抑制，必要时单独制定恢复方案。
