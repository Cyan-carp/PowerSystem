# S04 · 分析漂移空白输出修复

## 现场现象与判断

2026-11-07 所有者在生产网页点“分析漂移”后，提示“解读失败：AI 输出无法解析：”，冒号后没有正文。上一批已把既有解读密钥只读接给 API，因此本次不再是缺密钥。代码只有在模型响应的 `message.content` 为空或空格时才会显示这个空白预览；模型没有给出可解析的分析正文。原始漂移图表与指标不依赖该正文。官方 DeepSeek JSON 模式文档也记录了偶发空白正文的情形；本次没有留存该次真实模型响应，因此“提供商返回空白”属于代码路径与现场提示共同支持的判断，不把它写成直接抓包事实。

## 候选处理

- 质量分析默认关闭 thinking，仍要求 JSON 输出；不影响其他 AI 通道。
- 仅当首次响应正文为空白时，在同一个 90 秒总预算内再请求一次：关闭 thinking，并退出 JSON 模式，但系统提示仍要求严格 JSON。HTTP 错误及非空但无效的正文不自动重试。
- 两次请求的 token 合并计数；两次均为空时给出“模型未返回可用正文，请稍后重试”，不再呈现空白的“无法解析：”。不更改漂移事实、历史分析记录、前端或模型版本。
- 候选从现役 API 源码快照 `fc6e080a…` 隔离，仅含 `prediction_quality_analysis.go`、新增定向测试、`config.go` 默认值三处差异；隔离树及摘要见 `artifacts/quality-analysis-blank-20261107/source/manifest.json`。工作区其它 S03/S04 候选未纳入。

## 验证与发布边界

- 本地与隔离源码树的 `go test -timeout 2m ./internal/api -run '^TestQualityAnalysis' -count=1` 通过。定向用例覆盖首轮空白后成功、两轮空白后明确报错及最多两次调用。
- 一次只读生产提供商小探针使用合成事实，两种 thinking 设置均得到有效 JSON；该探针不能证明真实按钮已经恢复。
- 所有者本轮明确授权发布。生产激活 `quality-drift-blank-20261107-r1`，API 镜像 `sha256:4cbf4c6b…`，其余 20 个服务 ID/image 未变，公网 ping 200、未登录分析 POST 401。真实按钮成功出文仍待登录态点验，不能仅凭服务健康宣布完整修复。部署实况见 [[101-模型质量空白输出修复手工发布]]。
