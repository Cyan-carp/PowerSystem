# 02 · 热加载与原子替换

> S01 的设计依据。目标：换模型不重启容器、不中断请求、失败自动保留旧模型。

## 一、为什么不选蓝绿

蓝绿（两个容器 + upstream 切换）能解决中断，但代价是双份内存、两套日志、nginx 配置与切换脚本，而它防的唯一事故是「新模型加载失败」。

热加载用一次赋值就能防住同一件事：

```python
def reload(self, path: Path) -> bool:
    candidate = ModelRuntime.load(path)   # 完整加载到局部变量
    if candidate is None:
        return False                      # 旧 runtime 未受影响
    self.__dict__.update(candidate.__dict__)  # 成功才替换
    return True
```

Python 的属性赋值是原子的，请求线程要么看到旧模型、要么看到新模型，不会看到半个。

结论：**热加载 + 失败保留** 与蓝绿的安全性等价，复杂度低一个数量级。将来若单容器扛不住并发，再考虑副本，那是容量问题，不是换版问题。

## 二、目录结构

```
/model/
├── current -> versions/stage3-xgb-89e6530c9e29     # 软链，切换只改这里
└── versions/
    ├── stage3-xgb-89e6530c9e29/{model.json,metadata.json}
    └── stage3-xgb-6eac6e3ee856/{model.json,metadata.json}
```

兼容策略：若 `/model/current` 不存在但 `/model/model.json` 存在，按旧布局直接加载——保证改造前部署的镜像仍能启动。

## 三、接口

```
POST /admin/reload
  body: {"version": "stage3-xgb-89e6530c9e29"}   # 可选，缺省读 current 指向
  200: {"ok": true, "model_version": "...", "previous": "..."}
  409: {"ok": false, "reason": "load_failed", "detail": "..."}   # 旧模型仍在服务
```

不做自动轮询：谁改谁调，避免后台线程在训练未完成时读到半个目录。

## 四、切换流程（S03 会用）

1. 新版本文件落到 `versions/<v>/`；
2. 改 `current` 软链（`ln -sfn`，原子）；
3. 调 `/admin/reload`；
4. 成功 → 台账置 `trial`，记 `trial_started_at`；
5. 失败 → 软链改回，台账不动，页面提示「加载失败，已保留 <旧版本>」。

第 5 步是硬要求：**加载失败必须自动改回软链**，否则下次容器重启会加载坏模型。

## 五、进程内的状态

```python
{
  "model_version": str,
  "threshold": float,
  "feature_names": [str],
  "booster": XGBClassifier,
  "calibration": {"slope": float, "intercept": float},
  "loaded_at": datetime,
  "source_path": str,
}
```

`/health` 返回 `model_version` 与 `loaded_at`，顺带覆盖第六版的运行态校验（[[80-模型台账运行态校验与文件路径]]）。

## 六、风险与对策

| 风险 | 对策 |
| --- | --- |
| 新模型特征数不一致，推理时静默错位 | 加载时校验 `len(feature_names)` 与期望值，不一致即失败 |
| 半写入的文件被读到 | 训练端先写临时目录再 `mv`，同一文件系统内 `mv` 原子 |
| 软链被删导致重启失败 | 启动时若 `current` 缺失，回退扫描 `versions/` 取最新可加载版本 |
| 并发 reload | 加互斥锁，后到的直接返回 `busy` |

## 七、不在本版范围

- 多副本与负载均衡；
- A/B 分流（按设备哈希分到两个模型）；
- 模型文件签名校验。
