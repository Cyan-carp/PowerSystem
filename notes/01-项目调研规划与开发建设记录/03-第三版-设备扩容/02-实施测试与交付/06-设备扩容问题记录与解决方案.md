## 一、已解决问题

### 1. 共享发布回调临界区不完整

- **现象**：MQTT 发布回调取得 MID 归属后，确认 outbox 的动作没有完全处于同一锁保护区；
- **原因**：组件初版把映射查询与消息确认分成两个并发步骤；
- **影响**：在回调、断线与补发交错时可能出现竞态，理论上会误判待发状态；
- **处理**：回调改为在同一把锁内完成 MID 命中、移除与对应 `(device_code, seq)` 确认；
- **验证**：共享回执、未知 MID、断线、重连与补发定向测试通过；
- **状态**：原回调临界区问题在单元测试范围已处理；2026-10-21 真实运行暴露的发布/回调锁反转另见第 13 项，不能用本项“已解决”覆盖生产停发。

### 2. 业务证据白名单未识别新增总览工具

- **现象**：阶段 8 调用 `list_stations` 或 `get_dashboard_overview` 后，业务质量判定仍可能认为“未查询”；
- **原因**：证据工具白名单只包含扩容前工具；
- **影响**：智能体已经取得结构化事实，但回答门禁可能错误拒绝；
- **处理**：把两个新只读工具加入证据识别范围，并补充 `fleet_overview` 用例；
- **验证**：新增证据用例 1 项通过；
- **状态**：已解决。

### 3. Workbuddy 前端任务超过单次等待窗口

- **现象**：前端任务在工具等待五分钟后返回超时，但工作区已存在完整改动；
- **原因**：任务含多页面修改与自检，超过单次调用等待窗口；
- **影响**：不能直接把超时当作失败或成功；
- **处理**：Codex 独立审阅实际差异并运行定向 Vitest 与类型检查；
- **验证**：相关 12 项测试与类型检查通过；
- **状态**：已解决，后续仍按“小任务包、短验证”委派。

## 二、环境问题

- **状态**：已绕过。后续 CI 应显式配置可写缓存目录，避免依赖人工重跑。

## 五、2026-10-21 生产停发与共享发布锁修复

### 13. 共享发布锁反转导致生产停发（已发布并恢复供数，观察结果为 anomaly）

- **长观察增量（03:24）**：01:22:59～03:22:59完整7200秒，三档各120次有效观测均为0、360条全部partial；接口无错误不代偿供数。20个容器镜像/重启计数未变化，新版本尚未发布。
- **现象**：生产 143 台模拟器自 2026-10-20 23:41:05（北京时间）后停止遥测；2026-10-21 01:25 三档 `observed` 均为 0，PG `pending` 为 0。容器 running、CPU 约 0，两线程均等待 futex。
- **原因**：主线程 `publish` 持有 `SharedPublisher.lock` 调用 `client.publish`，Paho 内部持 `_out_message_mutex`；PUBACK 回调线程持 `_out_message_mutex` 后反向取 `SharedPublisher.lock`，形成 ABBA 锁反转。Codex 已只读核对生产 Paho 2.1.0 源码，PUBACK 路径确实持内部锁调用 `on_publish`；实际挂起线程栈仍未采集。
- **处理**：Workbuddy 将发布与状态管理拆为 `_publish_lock`、`_state_lock`，回调不获取发布锁；快速 PUBACK 仅暂存 1 个候选；`on_connect` 改为请求后台 flush worker。Codex 补充 `connection_generation`，防止断连期间迟到的旧 MID 被当作下一次发布的 MID+1 登记；清 `publishing` 与登记 mid 位于同一 `_state_lock` 临界区。
- **验证**：本地与镜像内43项通过；真实Paho 2.1.0 Broker探针1430/1430、每台10条、pending/MID均0；发布后首轮三档有效观测143/140/3且均非partial。
- **状态**：`fleet-mqtt-lockfix-20261021-r1` 已发布并完成7200秒观察。供数停发已解决；严格观察因all/business各1轮覆盖不足记为`anomaly`，不等同于零缺口稳定性通过。
- **说明**：早前“`client.publish` 返回后、登记前 ACK 空窗”的报告与实际代码不符，不作为遗留风险记录。

### 14. 真实 Broker 验证探针导入路径错误（2026-10-21 02:15）

- **现象**：独立探针在`/probe.py:10`导入`simulator`时报`ModuleNotFoundError`，退出码1；错误发生在连接和发出1430条验证消息之前。

- **状态**：已解决。重试探针1430/1430通过后才进入备份和发布；容量测试未重复执行，旧失败仍作为验证驱动问题保留。

## 八、2026-10-27 遥测离线路径核查与整改建议

### 18. 八条离线路径的真实性与适用条件

**历史故障与修复证据**

- 2026-10-26 排查记录显示：inbox 持续收到数据，TDengine 历史缺行，各设备最老待处理行无法验证，导致后续样本不能推进；人工标记跳过后恢复。该因果链与旧处理逻辑一致，历史根因可信，但“143条均已逐行核实缺失”不成立：记录仅列出4台抽查。
- 提交 `44649ae` 的本地源码已有两分钟宽限跳过逻辑；同轮记录明确“未构建镜像、未发布”，后续 GitHub 发布记录也不代表 API 生产部署。仅凭这些材料不能承诺线上同一故障不会复发，发布前须把实际 API 镜像与构建来源回执对上。
- `inbox_progress_test.go` 验证年龄判定、常量范围及首个错误保留，未调用 `processPending`；不能表述为缺行跳过、后继处理、TDengine/Redis故障恢复的集成回归已通过。

**判据纠偏**

- 当前仪表盘使用 `/dashboard/overview`，`overview.go:113` 同时检查接收年龄与采样年龄不超过15秒，并检查字段和时间合法性。采样时间向未来容忍60秒，所以“设备时钟偏移超过15秒都离线”不准确：慢30秒失败，快30秒仍可满足判据。
- 健康页 `health.go:39–99` 对合法的旧接收记 `offline`，新接收但旧采样记 `unknown`；Redis缺键/报错、无效载荷也记 `unknown`。时间异常检查早于旧接收检查，故“接收旧就一定offline”还需合法载荷前提。
- 旧 `/dashboard/summary` 在 `handlers.go:301–313` 只检查接收年龄，尚未统一。当前 `DevicesView.vue` 列表没有在线状态列，不能笼统把“仪表盘/设备列表”视为相同实现。

| 路径 | 核查结论 | 需要纠正的表述 |
| --- | --- | --- |
| ① inbox断流 | 成立，空队列分支不报告链路失鲜 | API与gateway分别订阅MQTT；gateway挂主要导致TDengine断写，不必导致inbox没新行。PG查设备/写inbox失败已有错误日志，非所有断流都毫无日志 |
| ② 维护门禁 | 成立，查询错误或enabled=true会暂停worker，无专用状态日志 | 删除表会报错并停；仅删除id=1行时，GORM Raw.Scan空结果通常无错，零值false反而放行，另有失败开放缺陷 |
| ③ 消费落后 | 成立，历史速率显示容量与追赶余量偏薄 | 29–33/s与27/s是旧现场数据，不能当本轮实测；源码编排间隔为5秒，143/5≈28.6/s。并非所有设备必然同时掉线 |

| ⑤ Redis故障 | 成立，总览可能表现为全部离线 | 健康页为unknown；部署模板已启用AOF。恢复时仍受队列积压和处理失败影响，不能保证数秒自愈 |
| ⑥ 设备时钟问题 | 成立，慢钟/停滞导致样本过期 | 只影响受偏移影响的设备；真实设备有风险，不等于必然发生；正负偏移容忍并不对称 |

### 19. 现有两分钟修复仍需补齐的边界

**失败被混成成功处理**

- `server.go:321–380` 将“TDengine查无行、TDengine请求失败、设备查询失败、Redis写失败、告警事务失败”统一交给 `retryOrSkip`。旧积压遇到第一次临时失败就可能立即跳过。
- 跳过只写 `processed_at`，未持久保存失败原因或跳过状态；日志只有批次数量与最老时间。原始payload仍在，属于常规处理与自动恢复路径的遗漏，不是原始数据被删除，也不能称永远无法补救。
- `restoreLatest` 读取 `processed_at IS NOT NULL`，可能把跳过且未经TDengine验证的行恢复成最新快照；电量重建同样按该字段选样本。后续重建可纳入跳过行，而本次跳过又未调用 `energy.MarkDirty`，形成统计口径和刷新时序不一致。
- 应持久区分 pending/retry、成功、隔离跳过，保存原因、首次失败时间、尝试次数和待重试时刻。外部依赖暂时不可用不应直接冒充成功；持久坏数据隔离后允许后继处理，补偿与历史告警重放另行受控。

**超时、公平性与日志频率**

- `processPending` 的30秒context在队列SQL之后才创建，队列SQL未绑定它；告警事务调用 `service.ProcessSample(s.db,...)` 也未传它。故30秒只是部分操作预算，不能约束整轮。
- 每轮按device_id从头处理，30秒到期就退出；即使不足500台，低ID慢请求也可能让后面设备反复得不到服务。单条HTTP最长10秒，不能把2分钟阈值当作每台设备推进的硬上限。
- `inbox_no_progress` 首轮记录，之后按120轮记录；一轮不是固定0.5秒，因此慢依赖下不是每分钟。部分设备成功或单纯跳过会重置计数，持续局部故障仍可被掩盖。
- 应把预算覆盖队列查询、事务和外部I/O；增加单项预算、跨轮设备游标并在到尾后回绕，预算耗尽也推进到最后访问位置，保留同设备处理顺序。记录日志用真实经过时间并记录状态切换。

**同步广播也会拖慢唯一worker**

- `websocket.go:70` 在共享锁内逐连接同步写，每连接写期限2秒；`processPending` 内直接调用广播。多个慢连接会放大处理耗时，且不受轮次context直接约束。
- 将广播交给有界队列和独立写协程，超限断开慢客户端并通过只读刷新恢复。该项是源码确认的额外延迟路径，本轮未做压力复现。

### 20. 实施顺序与验收条件

**第一批：可观测性和失败语义（优先级最高）**

1. 独立watchdog定时检查，而不是依附可能卡住的worker；数据库、Redis探测各自限时，worker只维护必要成功时间和计数。
2. 保留用户提出的三段信号，但分别定义inbox最近接收、成功业务处理、Redis成功写入及实际缓存数据年龄；队列推进/隔离跳过单独计数。缓存年龄不能用“刚执行SET”的时间代替原始received_at。
3. 增加预期活动设备的新鲜覆盖率、最差年龄及缺键数，避免一个设备更新就掩盖其余全部故障；按场站与all/business/baseline汇总。补pending最老年龄、积压趋势、成功/失败/跳过速率、依赖可用性和维护状态。
4. 维护门禁保留保守策略，明确区分enabled、查询失败、缺失单例；缺失也失败闭合。使用限流日志与状态切换告警，正常维护单独标记并设置超期告警；不要自动解除维护。
5. 对三段年龄建议20–30秒预警、60秒严重告警，均为待验收初值；idle且确无预期输入时不单独报警worker无成功。未初始化、探测失败与指标缺失须可见，不填0伪装健康。
6. 除 `/metrics` 与日志，还要补Prometheus规则并验Alertmanager→现有通知适配器。现有 `metrics.go` 只有HTTP计数/耗时，`alerts.yml` 只有API抓取失败与磁盘规则；仅新增指标不会自动通知。现有15秒抓取/求值和5秒group_wait也必须计入发现时间，60秒阈值不等于30秒必达。

**第二批：处理超时、公平调度及低成本减负**

- 按第19项补全context、单项超时和可回绕游标；检查空行RowsAffected以及隔离跳过状态，补完整处理链测试后再发布。普通OFFSET分页和每轮重新归零的游标都不能解决持续饥饿。
- 每行重复查询维护状态、设备及告警规则会放大PG往返。任何批内缓存/检查降频都需保留维护开启后停写和排空的一致性保证，不能为提速绕过门禁。
- 最新快照与告警历史处理共用最老待处理队头，是积压影响在线显示的结构性原因。后续可拆实时最新值通道和有序历史处理，但须明确TDengine确认、维护/备份一致性、告警未完成提示；按设备使用可信接收顺序原子更新快照，避免补传旧样本覆盖新值。

**第三批：扩容前优化与恢复能力**

- 批量TDengine校验或有限并发、减少PG往返，按同设备串行、跨设备有界并行设计；以本轮新测决定优先方案，不预先承诺只改HTTP即可达标。
- 历史速率只作算例：若2,250,000条均可验证且仍顺序处理，输入27/s、消费29–33/s，则净追赶2–6/s，约4.3–13天才能清空；停输入时也需约19–22小时。必须按净消费率估计恢复时间。
- 实际容量验证应覆盖当前143台及计划扩容规模、生产同机竞争条件、一次依赖恢复后的追赶。建议以端到端延迟P99低于15秒且保留裕量、积压不持续增长、成功处理能力至少为目标输入的1.5–2倍为初始验收目标；这些是方案目标，不是已有结果。
- 真实设备接入前定义UTC毫秒语义、服务器NTP、设备/网关对时容差、补传与乱序策略；把连接接收、采样有效性、健康判断分开。调整接口须兼顾旧summary与新overview，不能仅放大15秒来掩盖平台延迟。

**必要的定向回归**

- 缺一条TDengine历史行：宽限内重试、隔离后同设备后继能推进，其他设备不受阻。
- TDengine持续超时与Redis暂时不可用：失败有原因、可恢复，不将暂时不可用伪装成功；缓存与业务处理两种成功分别计数。
- 维护enabled、查询超时、整表缺失、仅缺id=1行：停写语义、错误日志及指标符合设计。
- 501台且前500台持续积压；以及143台、部分低ID慢查询、轮次预算耗尽：所有设备均在约定时限内获得处理机会。
- worker推进但缓存旧、少量设备更新而大部分停更、无输入、watchdog自身探测失败：都可区分且不误报健康。
- 重启恢复不把隔离行当成功快照，历史补传不覆盖新值；电量重建显式按选定数据口径读行。

**本轮验证结果与限制**

- 本地精确定向Go测试通过：`TestInboxVerdictFor`、`TestInboxVerifyGraceStaysBounded`、`TestFirstErrorKeepsEarliest`、`TestHealthSampleAndReceptionFreshness`、`TestSnapshotCurrentRequiresFreshCompleteObservation`。
- `TestMAC19BusinessContinuesWithOperationUnavailable` 因未提供专用PG/Redis夹具而跳过；本轮未做真实依赖集成、生产探测或新增故障注入，不能把跳过记为通过。
- 本轮仅评估与记录，不修改后端/前端业务代码，不上传、不部署、不重放历史告警。上述整改及新验收尚待实施，不作为现有系统已具备的能力。
