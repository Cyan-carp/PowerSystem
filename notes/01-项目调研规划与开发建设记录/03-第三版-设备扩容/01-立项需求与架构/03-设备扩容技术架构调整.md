# 03 · 设备扩容技术架构调整

> 本页专门说明扩容对原有技术架构做了哪些调整。总体策略是增量演进：保留三设备基线和既有服务拓扑，在配置源、供数、范围解析、聚合、前端与智能体工具层增加多场站能力，不进行数据库换型或后端链路重写。

## 一、调整原则

1. **单一事实源**：场站与设备身份只在一份车队清单中维护，避免模拟器、后端、前端各自硬编码；
2. **向后兼容**：未传 `--fleet` 时模拟器仍运行原三设备路径，旧 API 默认仍是 `scope=all`；
3. **聚合优先**：业务范围使用服务端当前聚合，不让前端对 140 台逐台拉取全天历史；
4. **缺失不补零**：没有观测与真实零功率必须区分，聚合响应同时返回完整性；
5. **先本地、后运行**：本轮先完成代码和短测试，真实台账、供数、容量与生产发布独立审批。

## 二、调整前后对照

| 层次 | 调整前 | 调整后 | 调整原因 |
| --- | --- | --- | --- |
| 设备来源 | 三设备常量分散在模拟器与业务逻辑中 | `fleet.json` 为唯一车队来源，Python 与 Go 分别加载同一文件 | 防止编码、场站名、数量和范围漂移 |
| 遥测发布 | 每台设备一个发布器，规模固定 | 车队模式共享一个 MQTT 客户端，增加 MID 回执登记与五秒内错峰 | 避免 143 个连接和瞬时突发，同时保证回执不串设备 |
| 后端查询 | 面向全局设备，无业务/基线边界 | 统一解析 `all / business / baseline` 与 `station_code` | 让统计分母与页面标签一致 |
| 总览 | 旧 summary 服务于小规模展示 | 新增 overview，批量聚合当前快照、活动告警与当日电量 | 避免业务范围逐设备拉取全天历史 |
| 前端 | 默认围绕 `ST-01` 三台展示 | 默认业务范围，支持范围/场站切换与四站对比 | 支持集中运维，同时保留基线曲线 |
| 智能体 | 工具缺少范围和场站参数 | 阶段 8/9 同步范围 schema、场站列表、总览与分页说明 | 防止只取一页却声称覆盖全部设备 |

## 三、配置与设备目录层

### 3.1 唯一车队清单

`stages/01-data-chain/simulator/fleet.json` 同时描述四个业务站与 `ST-01` 基线，冻结设备数量、编码规则、额定功率、范围、运行模式和显式基线身份。业务设备按规则展开，基线三台显式列出，避免扩容逻辑改写原台账身份。

Python 加载器负责模拟器和 dry-run 台账计划；Go `internal/fleet` 负责 API 侧场站目录与范围判定。两端都读取同一 JSON，而不是复制第二份 SQL、Go 常量或前端名称表。

### 3.2 加载失败策略

后端允许清单加载失败时继续提供不依赖目录的旧能力，但 `business`、`baseline` 和场站目录会返回 503，避免悄悄退化成错误统计。清单默认相对路径只适合当前本地启动目录；容器与发布环境必须显式装载文件并设置 `FLEET_CONFIG_PATH`。

## 四、遥测模拟与 MQTT 层

### 4.1 从位置相关改为身份稳定

原样本逻辑依赖三设备列表位置。扩容后，设备特征由 seed、场站编码和设备编码的稳定哈希派生，设备排序变化不会改变其长期差异。同站共享天气与相位，单台只叠加小幅稳定降额、温度、电压和测量噪声。

功率仍受 100 kW 额定值约束，电气量保持 `P=√3×U×I×0.99/1000`。`ST-01` 保留 60 分钟白天循环和既有真实时间故障日程；四个业务站采用真实昼夜，本轮不注入业务异常。

### 4.2 从多客户端改为共享客户端

车队模式新增 `SharedPublisher` 与 `MidRegistry`：

- 一个 MQTT 客户端承载 143 台消息；
- `mid -> (device_code, seq)` 保存回执归属；
- 发布串行锁不由回调获取；短状态锁仅保护 MID/早到 ACK 与连接代次，不跨 `client.publish`。回调离开状态锁后再确认 outbox，连接补发交后台单 worker，避免与 Paho 内部锁反转（2026-10-21 本地修复，已构建并通过43项，尚待真实 Broker 短验证及发布，见 [[01-项目调研规划与开发建设记录/03-第三版-设备扩容/03-容量与稳定性验证/08-容量与长时间测试记录]]）；
- 断线只清空失效 MID 映射，不删除待发消息；
- 重连后按上限补发；
- 一个五秒周期内按设备顺序错开发送，降低同一时刻突发。

未传 `--fleet` 时仍走原三设备与逐设备发布器路径，因此现有演示入口不被车队模式强制替换。

## 五、后端 API 与聚合层

### 5.1 统一范围解析

设备、告警、场站、总览共用范围定义：省略 `scope` 等价于 `all`；非法范围、未知场站或范围与场站冲突返回 400；依赖清单但清单不可用时返回 503。筛选条件进入查询层，不能先查全量再在响应层删行。

### 5.2 新增场站目录与范围总览

`GET /api/v1/stations` 提供期望设备数和已登记设备数；`GET /api/v1/dashboard/overview` 批量读取：

- Redis 中现有当前遥测快照；
- PostgreSQL 中活动告警与设备登记状态；
- 现有 `energy_daily` 中当日电量。

总览不扫描 TDengine 全天原始遥测，也不让前端发起 140 次历史请求。`partial=true` 的固定条件是登记少于清单期望，或有效观测少于已登记；响应同时返回 `expected / registered / observed`。缺失功率、电量和健康度使用 `null`，不伪装成 0。

### 5.3 保留原接口语义

旧 `/dashboard/summary`、健康接口、健康评分版本、排名规则和列表 `id ASC` 排序未被重定义。新字段和参数是可选增量，旧调用不传范围时仍可工作。

## 六、前端展示层

前端新增统一 scope 模型，默认进入 `business`，并让运行总览、设备列表、告警中心使用同一范围和场站语义。范围切换时清除无效场站筛选并回到第一页，防止旧响应覆盖新条件。

业务与全平台范围只展示当前聚合、完整性和场站对比，并明确提示“分时聚合后续提供”；只有 `baseline` 继续请求 `ST-01` 三设备今日曲线。这样避免扩容后请求量随设备数线性增长，同时不破坏原演示能力。

## 七、智能体工具层

阶段 8 与阶段 9 同步增加 `scope`、`station_code`、`list_stations` 和 `get_dashboard_overview`，两端 schema、默认值与路由保持一致。列表工具描述明确单页最多 100 条、响应包含 `total`、全量结论必须翻页；总览工具解释 `partial` 和 `null`，防止模型把未知数据解释成正常或零。

本次调整只扩大只读观察范围，没有增加告警确认、远程控制、脚本执行或生产写入权限。

## 八、告警解读 v2（已发布）

扩容本身没有重写阶段 7。2026-10-21 的解读重构是**独立批次**，现行方案见 [[01-项目调研规划与开发建设记录/03-第三版-设备扩容/04-告警智能解读专项/09-告警智能解读重构计划与架构对照]]，此处只列架构边界：

- 解读使用独立官方 `https://api.deepseek.com/chat/completions`、`deepseek-flash`、thinking disabled、`json_object`、非流式无 tools；独立密钥、独立暂停键、独立探针，**阶段 8/9 不共用**。
- Go 负责事实：`fact_id`、值、单位、精度、UTC 时间、展示时区与派生公式；绑定原始证据 `evidence_hash`。模型只在 `template` 中写 `{{F1}}` 占位，不计算数值，最终由 Go 确定性渲染。
- 调度保持持久异步任务：每任务 `model_calls ≤ 2`、租约 60 s、15 min 截止、单层重试 30 s ± 20%；连续 3 次故障熔断 60/120/240/300 s，半开单请求。无同端点备用模型。
- 143 台每天 09/11/13/15/17 五条受控演示，各站 1 台、稳定轮转、`(day, slot)` 唯一、10 min `simulation_demo_ended`、missed 跳过；真实设备与平台监控旁路。
- 不新增服务、端口、中间件，不改告警状态机、WS 契约与飞书链路；**r4于2026-10-21发布，10-22完成旧业务告警清理**。

## 九、刻意未调整的架构

- PostgreSQL、TDengine、Redis、MQTT职责不变；扩容批次未重建业务数据模型，后续解读专项通过009至011增量增加演示策略/槽位、维护状态及任务协议/调用计数，不是“所有表结构均未变”；
- 遥测消息字段、设备功率方向、健康评分版本和排名语义不变；
- Compose 服务数、公开端口和持久卷不变；
- 原三设备编码、台账身份与遥测曲线不变；后续受控告警专项替换旧模拟故障告警日程，改为全平台每日五槽位，预测数据不改；
- 不新增场站 CRUD、地图、经纬度、储能模型或历史回填链路；
- 不在本轮增加 Redis 分时桶、预测并发、电量任务调度或网关批处理优化。

## 十、后续架构债务

1. 已完成：生产只读装载版本化 `fleet.json`，消除相对工作目录依赖，并纳入摘要与备份；
2. 已完成基本范围：事务导入 SQL、会话临时表重复执行、正式 140 台导入和线上 PostgreSQL/Redis 当前聚合短核对；应用回退保留数据，不自动删台账；
3. 持久化日程已在本次受控演示专项实现：唯一日/槽位、稳定设备轮转、10分钟结束；实际发布与清理状态见部署日志30，不再另建自然异常注入状态机；
4. 业务范围若需要全天曲线，应建设 Redis 五分钟功率桶和小时电量桶，而不是恢复逐设备历史请求；
5. 容量与有界并发优化改为按需事项；最小冒烟通过后即可继续开发，只有出现实际瓶颈时再做专项测试。
