## 八、在用告警模块请求兼容故障（2026-10-21）

> 本节维护仍在线的旧自动告警模块，不恢复已废弃的通用问答方案。状态：兼容修复已上线；13条活动失败任务11条恢复、2条原校验拒绝，限定范围收尾。

### 现象与影响

- 用户实测智能助手对话与运维任务正常；告警解读仍显示不可用。旧 Agent 与主助手实际使用相同模型名、相同模型端点；旧 Agent 普通合成对话也成功，排除密钥无效和模型整体不可用。
- 只读取证时，最新 14 条预测风险解读均为 `degraded/unavailable`、尝试 3 次；审计共对应 42 次失败调用。任务带 Agent 请求编号，证据存在且体积约 6.4 KB。最近审计中的失败耗时约 0.24～0.73 秒，未进入回答校验。
- 原先单凭 `unavailable` 推断供应商模型整体不可用不成立；它是多个错误共用的分类。

### 原因与可复核证据

- 阶段 7 `agent/llm.py` 遇到唯一 `submit_*` 工具，会无条件发送对象形式的强制 `tool_choice`；阶段 8、9 使用 `auto`。阶段 7 告警工具名为 `submit_interpretation`，因此稳定命中该分支。
- 使用现有告警 Agent 的模型配置发出 13 次最小合成协议请求；没有读取或发送真实告警正文，也没有创建告警、任务、设备或修改服务配置。三次强制函数请求均返回 502 `upstream_error`，其中一次已展开 schema 引用，说明不只与嵌套 schema 有关。
- 同一份完整告警提示、合成证据与原始 schema，仅改为 `auto`，首次 503，后两次均 200 且通过现有 `ModelAnswer` 与 `validate_event_answer` 校验。展开引用或只删除 title 的 auto 变体也成功；不能据首次 503 认定 `$defs/$ref` 必不受支持。
- 无 tools 的 JSON 回答也通过原校验。另一次删去 wire schema 约束的变体虽然 HTTP 200，却未通过原回答校验，不能计为有效解读，也不应据此放松服务端约束。
- 直接触发点已复现为当前模型通道对强制指定函数请求的兼容失败；网关内部为何返回 502 尚无供应商内部证据。普通对话可用与该特定请求失败可以同时成立。

### 为什么健康与恢复按钮没有暴露问题

- 模型状态 `ready` 仅说明已配置且没有 Redis 永久暂停键，并不是实时请求验证；现有 probe 测普通聊天和简易工具，没有覆盖告警实际的强制函数请求。
- 502/503 被 `classify_error` 统一映射为 `unavailable`；现有审计没有保留上游状态码，页面只得到模糊提示。
- Go 的恢复 SQL 只重排近 24 小时仍活动且原因为 `not_configured/auth_failed/quota_exhausted` 的任务，不包含 `unavailable`。因此点击“检测并恢复”不会恢复本批失败记录。

### 修复方向、验证与状态

- 最小候选：告警输出使用 `tool_choice=auto`，保留原完整 schema、工具名称校验、Pydantic 约束、证据与数字校验；无需根据当前证据删除 `$defs` 或放宽回答格式。
- 模型探针需覆盖实际告警请求形状；内部审计保留脱敏的上游状态码，避免继续把所有错误解释成整体模型故障。
- 修复上线后，需另外明确受限的活动失败任务恢复范围；原按钮不能自动补回 `unavailable`，不能以检测成功宣称历史记录已恢复。
- 前述诊断阶段仅作合成对照，未修改源码或生产；后续用户明确要求修复后执行下方实施与发布。诊断成功本身未替代发布后的真实链路验证。
- Codex 与 Workbuddy 进行了只读代码交叉审查；后者首轮把 `$defs` 假设与一次 auto 失败外推过度，Codex 通过单变量及重复探针纠正，不直接采纳未复核结论。
- 本机脱敏证据：`artifacts/告警解读诊断-20261021/`；仅保存状态、计数、时间、HTTP 码与验证布尔值，不含模型回答、真实告警、凭据或完整日志。

## 九、推理输出预算与解读误拒绝（2026-10-21）

auto兼容修复后仍有answer_validation_failed。已观测到completion_tokens精确达到1500、finish_reason=length，大量推理token消耗预算，导致工具参数/JSON被截断。预算修复仅用于解读4096；保留flash，模型/总/API超时35/40/45；输出安全元数据进审计，明确截断只在Go侧额外重试一次，其他证据失败不盲目重试。

新代表性探针最初存在告警数值低于阈值、曲线统计不准、采集时间早于曲线等夹具矛盾，已修正。另复现明确“告警阈值40”同时引用预测证据时被误按预测阈值比较；修复仅让明确告警阈值绑定被引非预测证据中的唯一阈值，保留预测值防篡改和全部数字/引用守卫。时间失败子码补齐，避免误记schema失败。

没有证据确认早先每一次校验失败的具体子码，不将全部失败归因API或校验过严。原上游HTTP200非JSON短响应独立保留；一次正常结构响应也不等于业务答案通过。最终候选38项解读测试和完整生产规模合成探针通过，探针模型耗时8.112秒；Docker清理超时保留，通过结果与测试镜像核对后才冻结候选。发布状态与备份证据见 [[04-系统部署发布备份与变更记录/部署与运维日志/03-智能体与模型调用链/18-解读模型通道兼容与输出预算（原18+28+29）]]。

## 十、4096 发布后的真实业务失败与重构评估（2026-10-21）

**现象与影响**：18:05只读快照中，发布后170个预测风险任务仅13个完成，123个答案校验失败、34个响应格式失败。告警728的三次调用已使用4096预算且各约7–8秒，不是上线前旧记录，也不能归为该条调用预算耗尽。

**原因与边界**：240条调用审计含重试，91条数字拒绝、23条时间拒绝、3条预测改值拒绝；响应格式失败102条。自由文本生成与后置数值/时间校验存在职责耦合，仍需区分合法表达误拒绝与真正编造。适配层折叠多类结构错误，缺少原始安全形态子码，不能断言这些失败全由供应商或工具未调用造成。完整分类与架构对照见下方计划。

**处理方案**：保留可靠告警闭环、Go单事件证据、异步队列及权限边界，拟重建模型适配、类型化事实/引用、版本化答案协议与分层展示，不继续靠增大token替代分析。

**验证结果与状态**：这是已有审计/代码的只读复核，不是新通过批次。一次728原证据只读重放返回正常工具答案后被数字校验拒绝，不能倒推原三次响应形态。问题未解决、重构未实施；用户要求先审阅方案，暂停代码修改、模型重跑及部署。计划唯一入口：[[01-项目调研规划与开发建设记录/03-第三版-设备扩容/04-告警智能解读专项/09-告警智能解读重构计划与架构对照]]。
