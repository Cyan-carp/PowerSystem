## 三、真实 PostgreSQL 小时计划

```
--- PASS: TestAvailabilityHourPlanPostgresEdges (1.81s)
--- PASS: TestAvailabilityRollupPostgres (3.97s)
ok  	powersystem/backend/internal/api	6.053s
```

新增 `TestAvailabilityHourPlanPostgresEdges`，与既有 `TestAvailabilityRollupPostgres` 分工：

| 场景 | 期望状态 | 验证点 |
| --- | --- | --- |
| 完整小时全部有效 | ready | 0 次 BoundarySample；每设备 1 次建表确认；常规设备 1 段尾零头、新设备 2 段——证明走的是新读数器与小时计划 |
| 缺桶（删一小时行） | warming | 仅补算该小时，结果与原始扫描逐字段相等 |
| 规则版本不匹配（改成 `availability-v0`） | warming | 旧版本行不被当作当前口径 |
| 时长字段不自洽（临时去掉 CHECK 后写坏行） | warming | 查询侧独立校验，不依赖表约束 |
| 短窗口（47 分钟，不足一小时） | ready | 合并为单段扫描，不发边界查询 |
| 新设备（窗口中间创建） | ready | 窗口从创建时刻起算，首个小时由零头补算 |
| 心跳过期（既有用例） | degraded | `swept_at` 超过 1 分钟即回原始路径 |
| 迟到样本/CAS（既有用例） | warming→ready | 重建期间再写入仍保持脏标记 |

同库连续 `-count=2` 通过。原始输出已留档 `verify/pg-integration-repeat.log`：两用例各跑两遍，4 条 `--- PASS`，`ok powersystem/backend/internal/api 12.171s`。迁移口径按复核澄清：「两次迁移」指**完整迁移入口 `cmd/api -migrate-only` 执行两遍**以核对幂等性，不是只执行 `001` 和 `017` 两个文件；本轮重建环境时该入口连跑两遍，两次均 `exit=0`、`migration_complete`（见第七节），上一轮我手工只应用两个文件才报 `column "remark" does not exist`。顺带修正两个集成测试的清理顺序：`defer pool.Close()` 会先于 `t.Cleanup` 执行，导致清理静默失效；改为先登记连接池关闭、后登记数据清理。仅测试代码，不影响运行逻辑。

## 四、143 台查询、CSV 与等价性

### 4.1 耗时

| 路径 | 结果 |
| --- | --- |
| 新路径 JSON（3 次） | 1069.7 / 992.8 / 918.8 ms，中位 **992.8 ms** |
| 新路径 CSV（3 次） | 952.8 / 947.0 / 982.7 ms，中位 **952.8 ms** |
| 原始全量扫描（同库同窗口，关闭汇总读取） | **29,413 ms**，state=warming |

采样口径：JSON / CSV 各 3 次，属探索性计时，**未按任务书执行「首次 + 5 次顺序」，也未做 3 查询键并发短测**；中位数只描述这 3 个样本，不代表分布。

对照路径是「143 台 × 7 天 × 5 秒」逐台全量扫描（约 1,729 万行），新路径只读带15秒上下文的窗口零头与PG小时汇总。两者统计口径相同、计算路径不同：29.6倍是“汇总命中 vs 全量重扫”的差距，不是本次相对上一版已启用小时汇总的提速比例，也不与合成基准的858→429请求数提升比例混用。

### 4.2 等价性

- JSON 与 CSV：143 台 + 7 场站，设备编码、场站编码、窗口、覆盖/运行/停机/故障/未知毫秒、观测可用率、数据覆盖率、数据不足、规则版本、起止时间全部一致（`equivalence.json`）。
- 新路径与原始扫描：同一批 143 台 + 7 场站，逐字段 0 差异（`equivalence-paths.json`）。

### 4.3 浏览器走查（Chromium，真实渲染）

## 五、限制与未覆盖

1. **采样口径**：第四节是首轮探索性计时；第七节已按「首次 + 5 次顺序」、浏览器两类缓存各 5 次、并发 3 键 × 3 轮补齐。仍**不是长时压测**——没有多分钟持续负载、没有 10 并发以上、没有混合读写。
2. 夹具是合成时序，不是生产台账或现场设备数据；143 台、5 秒采样、7 天与计划口径一致，但状态分布比现场均匀。合成夹具不得写入生产业务库。
3. API 在 home-dev（Windows / WSL2 / 开发机资源）运行，不是生产 VM117；生产 CPU、磁盘与网络未测。
4. 浏览器端为本地 Vite → SSH 隧道 → 远端 API，比同机部署多一跳；服务端 PG/TD 均为回环。
5. 验证环境没有 fleet 清单、也没有 MQTT 采集，`/api/v1/stations`、`/api/v1/dashboard/overview`、`/api/v1/ping` 会返回 503（第七节已按响应 URL 留证）；报表可用率查询不依赖这三个接口。
6. 未验证：生产 143 台真实台账与真实现场数据、长时间使用、真实网关下的 CSV 下载。
7. `TestAccountSettingsPasswordChangeInvalidatesSessions` 仍失败，属 HEAD 既有问题，与本专项无关。

## 七、完整采样（第二轮，2026-11-24 UTC）

环境按第二节同规格重建（一次性 PG 17.6 / TD 3.4.2.8 / Redis 7.4.5，均已 `--rm`），夹具与上一轮逐项一致：143 台、7 场站、17,297,709 行 5 秒采样、23,881 条小时行。两点额外处理：

- **迁移入口连跑两遍**：`stage2-api-verify.exe -migrate-only` 连续执行两次，均 `exit=0` 并输出 `migration_complete`，即复核所说「两次迁移」的幂等性核对。
