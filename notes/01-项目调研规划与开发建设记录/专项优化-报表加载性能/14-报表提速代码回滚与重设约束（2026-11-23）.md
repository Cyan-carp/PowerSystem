## 一、决定

2026-11-23 晚，所有者决定：**放弃第三代实现（小时计划快路径 + 前端会话缓存），代码回滚到第二代，重新设计。**

三条依据，按权重排序：

1. **降级链塌缩（技术硬伤）**。本次改动删除了第二代实现（`availabilitySums` + 整设备回退 + 首尾补算），降级目标变成 `availabilityDevices` → `loadAvailability` 逐台全窗口扫描，即第一代。结果是「快路径 0.9 s ──降级──▶ 第一代 45 s」，中间 2.5 s 那一档消失。故障时性能不是回到上一版，是掉到上一版的 1/18。
2. **复杂度超出维护意愿**。7 个状态维度（records / inflight / sequence / generation / sessionEpoch / runSeq / submittedKey）、891 行业务代码、1,397 行测试，且报表正确性依赖 5 个新概念。所有者判断：后期出问题时无从下手。
3. **外部评审结论**。评审认可后端方向但要求先完成同环境验证与降级风险评估；前端全局缓存判定不通过，建议缩减为页面生命周期内缓存。

## 五、重设时必须遵守的约束

这五条来自本次实测、复核与外部评审，重做时不应重新踩：

1. **降级链必须保留中间档。** 快路径的降级目标应是第二代（读汇总 + 首尾补算 + 脏桶整设备回退），而不是第一代全量扫描。只有「汇总数据本身可疑」（结构校验失败、代数不一致）时才允许退到全量扫描，且全量扫描需要请求级超时与并发上限。
2. **降级必须分类，不能一刀切。** 基础设施故障（worker 心跳、PG 瞬时错误）→ 退第二代；数据可疑 → 退第一代；运维主动关闭 → 预期内。心跳超时不应让历史窗口查询掉到全量扫描——先算计划，全有效就正常返回。
3. **跨挂载缓存不采用。** 模块级单例 + LRU 20 + 全局代数 + 会话代次，换来的只是「离开再回来」从 30 ms 与 900 ms 的差别；页签往返 23 ms 与 30 ms 人眼无差异。只做页面生命周期内的页签缓存。
4. **正确性机制不可随缓存一起删除。** R1（异步竞态）、R2（权限变化后残留）即使没有缓存也必须防；只有 R3（失效后被写回）是缓存特有的。减法减的是状态，不是防护。
5. **新路径上线前必须有降级日志。** 本次两个文件里没有任何 log/metric 埋点，降级发生了、快路径用没用上都不可观测；在这种状态下做灰度等于盲飞。
