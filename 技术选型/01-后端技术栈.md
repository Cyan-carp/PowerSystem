# 01 · 后端技术栈选型（语言 + Web 框架）

> 回到 [[00-索引·技术选型]]
> 对应手册任务 8.1（后端编程语言）、8.4（后端 Web 框架）

## 一、后端编程语言

### 这层解决什么

整个后端服务用什么语言写。设备接入是典型**高并发 IO 场景**（[[需求分析/04-非功能需求清单]] NFR-01：200 台设备每 5 秒上报 ≈ 40 条/秒持续写入），且要编译成可部署产物放到服务器上长期稳定运行。

### 候选横向对比

| 维度 | Go | Java | Node.js | Python |
| --- | --- | --- | --- | --- |
| 需求匹配度 | ★高：goroutine+channel 天然适配高并发收发解耦 | 强但重 | 异步 IO 尚可，CPU 密集弱 | 性能/部署偏弱 |
| 社区活跃度 | 高（云原生/中间件主力） | 高 | 高 | 高 |
| 学习曲线 | 低（语法简单，一周上手） | 高（生态庞杂） | 低 | 低（但非新能力） |
| 生态与文档 | 优秀 | 优秀 | 优秀 | 优秀 |
| 生产验证 | EMQX、Docker、k8s 等大量 Go 项目 | 企业级标准 | 前端/全栈 | AI/脚本 |
| 性能与资源开销 | 低（编译单文件、内存小） | 较高（JVM 启动慢内存高） | 中 | 高（解释型） |
| 许可证 | BSD | GPL 类 | MIT | PSF |

### 最终选择：Go

- **高并发 IO 正是 Go 的主场**：goroutine + channel 天生为「海量连接、收发解耦」设计，直接支撑 NFR-01 的 200 台设备接入；[[行业调研与产品分析/03-技术现状与发展趋势]] 明确边缘网关「Go 协程+channel 天然适配」。
- **编译单文件、部署极简**：交叉编译出二进制直接运行，无需解释器/虚拟机，契合「低成本可复制」定位（[[行业调研与产品分析/05-产品定位与差异化]]）。
- **契合职业目标**：Go 后端岗位是本项目明确加分项。

### 被否方案

- **否 Java**：生态强但 JVM + Spring 全家桶对单人项目过重，启动慢、内存高，与 2 核 4G 服务器矛盾。
- **否 Python**：性能与部署偏弱，新项目应「扩边界」而非复用舒适区。
- **否 Node.js**：与前端同源方便，但 CPU 密集计算（时序处理）与长期稳定性不如 Go。

## 二、后端 Web 框架

### 这层解决什么

HTTP 接口用什么框架组织（前提：语言已选 Go）。

### 候选横向对比

| 维度 | Gin | Echo | go-zero | Kratos |
| --- | --- | --- | --- | --- |
| 需求匹配度 | 单体 REST 起步最顺 | 同类 | 微服务全家桶（过重） | 微服务框架（过重） |
| 社区活跃度 | ★最高（60k+ star） | 中 | 高 | 中 |
| 学习曲线 | 低 | 低 | 高 | 高 |
| 生态与文档 | 中间件最全、教程最多 | 一般 | 中文强 | 中文强 |
| 生产验证 | 海量 | 较少 | 国内多 | 国内多 |
| 性能与资源开销 | 轻量 | 轻量 | 较重 | 较重 |
| 许可证 | MIT | MIT | MIT | MIT |

### 最终选择：Gin

- 生态最大、教程最多、从单体起步最顺；handler/service/model 分层（NFR-11）官方生态成熟。

### 被否方案

- **否 go-zero / Kratos**：微服务框架对「单人首项目」过重，先单体跑通，二期再考虑拆分（写进未来工作）。

## 结论

后端 = **Go + Gin**，配合 GORM（关系库）、zap（日志）、viper（配置）构成企业级单体骨架，满足 NFR-01（并发）、NFR-09~11（可维护/分层/配置分离）。
