# 06 · 部署方案选型

> 回到 [[00-索引·技术选型]]
> 对应手册任务 8.10（部署方案）

## 这层解决什么

系统怎么跑在服务器上，让「我电脑上能跑」变成「任何人都能访问」，且**换台机器五分钟内能完整拉起**。

## 候选横向对比

| 维度 | 裸机直接部署 | Docker 单容器 | docker-compose 多容器 | Kubernetes |
| --- | --- | --- | --- | --- |
| 需求匹配度 | 环境依赖难复现 | 单服务够 | ★多服务编排（本项目 7 服务） | 大规模集群（过重） |
| 社区活跃度 | — | 高 | 高 | 高 |
| 学习曲线 | 低但易踩坑 | 低 | 低 | ★很高 |
| 生态与文档 | — | 极好 | 极好 | 好 |
| 生产验证 | 传统 | 业界标准 | 中小项目标准 | 大厂标准 |
| 性能与资源开销 | 低 | 低 | 低 | 高（集群本身吃资源） |
| 许可证 | — | Apache 2.0 | Apache 2.0 | Apache 2.0 |

## 最终选择：Docker + docker-compose

- **一条命令拉起全部服务**：后端、前端、PostgreSQL、TDengine、Redis、EMQX、FastAPI 预测服务，一个 `docker-compose.yml` 全部编排，演示、迁移、评审现场救急都靠它。
- **环境一致性**：消除「我电脑能跑、服务器报错」的经典问题，直接兑现 [[行业调研与产品分析/05-产品定位与差异化]]「全栈 Docker 化一键部署、部署成本较商业平台降 50%」。
- **数据卷持久化 + restart 自启**：满足 NFR-04 数据完整性与可用性。

## 被否方案

- **否裸机部署**：依赖手动安装、环境不可复现，换机器成本高。
- **否 K8s**：2 核 4G 服务器 + 单人维护，K8s 纯属自虐（手册原话），写进「未来工作」。

## 结论

部署 = **Docker 多阶段构建 + docker-compose 编排**，Go 后端编译成几十 MB 的镜像，前端 Nginx 托管，一条 `docker compose up -d` 五分钟完整上线。

> 以上服务数量和“五分钟”是原选型阶段的方案表达，不能当作当前部署实测。第一版阶段五是主业务：设备/AI 告警由 Go API 经 PostgreSQL 投递表送往内网飞书适配器，平台监控由 Alertmanager 送往同一适配器；统一 Compose 仍在阶段四。新增业务链路的现场验收见 [[开发阶段5-飞书告警通知/03-阶段五测试与交付]]，实现见 [[开发阶段5-飞书告警通知/01-链路与实现]]。公网安全与恢复能力已正式列为阶段六，见 [[开发阶段6-公网安全与恢复能力/00-索引·开发阶段6-公网安全与恢复能力]]。
