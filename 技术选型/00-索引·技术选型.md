# 技术选型 · 索引

> 本文件夹是「源网智联」在**写代码之前**的技术决策文档：把 [[行业调研与产品分析/03-技术现状与发展趋势]] 定下的技术主线，逐层展开成「候选横向对比 + 为什么选 A 不选 B」的选型报告。对应手册第三章（任务 8，子任务 8.1–8.10）。

## 一句话定位

**选型的第一性原理**：没有最好的技术，只有「在你的约束下最合适」的技术。本项目的约束是——单人开发、几个月工期、Go 刚入门、比赛加分点是「Go 后端 + 工业物联网」。所以「学习曲线」「社区活跃度」权重最高；另因电网方向，「国产化」「可解释性」作为两个加权项。

## 选型总览表（10 层结论）

| 层次 | 最终选择 | 一句话理由 | 被否方案 |
| --- | --- | --- | --- |
| 后端语言 | Go | 高并发 IO 主场 + 单文件部署 + 契合 Go 岗位 | Java / Python / Node.js |
| Web 框架 | Gin | 生态最大、教程最多、单体起步最顺 | Echo / go-zero / Kratos |
| 接入协议 | MQTT | 发布订阅匹配设备上报、弱网友好 | HTTP 轮询 / Modbus·OPC UA（二期） |
| Broker | EMQX | 国产中文文档 + Docker 一键 + Dashboard | Mosquitto / VerneMQ / NanoMQ |
| 关系库 | PostgreSQL | 功能强、JSON 好、工业口碑 | MySQL |
| 时序库 | TDengine | 国产化叙事 + 写入吞吐/压缩率高 | InfluxDB / TimescaleDB / IoTDB / MySQL |
| 缓存 | Redis | 数据结构丰富 + 持久化 + 生态 | Memcached |
| 实时推送 | WebSocket | 双向实时、监控标配 | SSE / 前端轮询（降级） |
| 前端 | Vue3 + Element Plus + ECharts | 国内生态最好、后台模板多、大屏案例丰富 | React + AntD / AntV |
| AI 模型 | XGBoost 起步 + LSTM 对照 | 小样本可解释、一周出结果 | 规则阈值（基线）/ LSTM / Transformer / TimesFM |
| 模型服务 | FastAPI | 异步 + 自动文档 + 与 Go 后端解耦 | Flask / Django |
| 部署 | Docker + docker-compose | 一条命令拉起、环境一致 | 裸机 / K8s |

## 统一比较维度（七维度，源自手册 3.3）

每篇笔记的对比表都用这七个维度打分，避免凭感觉：

| 维度 | 含义 |
| --- | --- |
| 需求匹配度 | 核心能力是否正好解决本层问题（杀鸡不用牛刀） |
| 社区活跃度 | GitHub star、最近 commit、issue 响应（死了的项目不用） |
| 学习曲线 | 以现有基础一周内能否跑出官方 Demo |
| 生态与文档 | 中文资料、教程多不多、上下游配合是否成熟 |
| 生产验证 | 哪些公司在用、招聘 JD 出现频率 |
| 性能与资源开销 | 2 核 4G 服务器是否扛得住 |
| 许可证 | 开源协议是否允许本项目用法 |

> 权重提示：学生项目「学习曲线」「社区活跃度」权重最高；本项目另加「国产化」（电网方向叙事）、「可解释性」（AI 层）两个加权项。

## 与上游的衔接

选型不是重新拍脑袋，而是把 [[行业调研与产品分析/03-技术现状与发展趋势]] 的组件结论、[[需求分析/04-非功能需求清单]] 的量化约束，逐层翻译成「选哪个、为什么」：

- NFR-01「200 台设备 / 5 秒上报」 → 决定了语言选 Go、Broker 选 EMQX、时序库选 TDengine；
- NFR-03「告警 ≤ 10 秒」 → 决定了推送选 WebSocket；
- NFR-04「断网 99.9% 不丢」 → 决定了边缘网关断网缓存方案；
- NFR-08「等保 2.0 / 国产化」 → 决定了时序库、Broker 优先国产。
