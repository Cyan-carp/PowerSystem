# 03 · 数据存储选型（关系库 + 时序库 + 缓存）

> 回到 [[00-索引·技术选型]]
> 对应手册任务 8.5（关系数据库）、8.6（时序数据库）、8.7（缓存）

数据分两类：**结构化业务数据**（用户、设备台账、告警规则/记录，写少读多、关系明确）和**高频遥测数据**（带时间戳、写多读少、海量）。二者必须分开存储，这是物联网项目的关键决策。

## 一、关系数据库

### 这层解决什么

用户、设备台账、告警记录等结构化数据存哪。

### 候选横向对比

| 维度 | PostgreSQL | MySQL |
| --- | --- | --- |
| 需求匹配度 | ★功能强、JSON 支持好 | 通用够用 |
| 社区活跃度 | 高 | 高 |
| 学习曲线 | 低（GORM 屏蔽差异） | 低 |
| 生态与文档 | 优秀 | 优秀 |
| 生产验证 | 工业软件口碑佳 | 互联网最广 |
| 性能与资源开销 | 中 | 中 |
| 许可证 | PostgreSQL License | GPL |

### 最终选择：PostgreSQL + GORM

- 功能强、JSON 支持好、工业场景口碑佳；GORM 屏蔽 SQL 差异，换库只改一层（NFR-11 分层隔离）。

### 被否方案

- **否 MySQL**：并非不能用，但 PostgreSQL 在功能丰富度与工业场景口碑上更契合；二者都能满足需求，选择记录理由即可（手册明确「若更熟 MySQL 也可，理由充分即可」）。

## 二、时序数据库

### 这层解决什么

设备遥测数据（高频、带时间戳、写多读少）存哪。这是物联网项目的**关键决策**。

### 候选横向对比

| 维度 | TDengine | InfluxDB | TimescaleDB | Apache IoTDB | 就用 MySQL |
| --- | --- | --- | --- | --- | --- |
| 需求匹配度 | ★专为 IoT 时序设计 | 时序标杆 | 时序（PG 扩展） | 时序（Apache） | 差：写多读少会崩 |
| 社区活跃度 | 高（国产） | 高 | 中 | 高 | 高 |
| 学习曲线 | 低（SQL 类查询 + 中文文档） | 低 | 低 | 中 | 低 |
| 生态与文档 | ★中文文档极好 | 极好 | 好 | 好 | 极好 |
| 生产验证 | 能源物联网广泛 | 全球最广 | 较少 | 工业/能源 | — |
| 性能与资源开销 | ★写入吞吐/压缩率优异 | 2.x 资源占用高 | 中 | 优异 | 数据量上来后查询/存储崩 |
| 许可证 | AGPL（开源版） | MIT（1.x）/闭源（2.x） | Apache 2.0 | Apache 2.0 | GPL |

### 最终选择：TDengine

- **国产化叙事加分**：电网方向 NFR-08「等保 2.0 / 国产化」对齐，TDengine 国产身份是明确加分项。
- **写入吞吐与压缩率优异**：[[行业调研与产品分析/03-技术现状与发展趋势]] 明确「国产 TDengine 写入吞吐与压缩率优异，广泛用于能源物联网」，支撑 NFR-01 的 40 条/秒持续写入。
- **SQL 类查询 + 中文文档**，学习曲线低。

### 被否方案

- **否 InfluxDB**：1.x 生态最成熟，但 2.x 转向闭源（核心功能闭源策略）、单机资源占用较高，与「低成本、开源可复制」定位冲突。
- **否 TimescaleDB**：PG 扩展方便，但写入吞吐与压缩率不及专用时序库，社区较小。
- **否 Apache IoTDB**：同为国产品质优异，但与 TDengine 相比中文文档与生态略逊，作为备选。
- **否 MySQL 存时序**：数据量上来后查询和存储都会崩（[[行业调研与产品分析/03-技术现状与发展趋势]] 明确否定）。

## 三、缓存

### 这层解决什么

设备最新遥测值放哪（前端实时卡片读缓存不打时序库，减轻时序库压力）。

### 候选横向对比

| 维度 | Redis | Memcached |
| --- | --- | --- |
| 需求匹配度 | ★数据结构丰富（存最新值/状态） | 仅 KV 字符串 |
| 社区活跃度 | 高 | 中（发展停滞） |
| 学习曲线 | 低 | 低 |
| 生态与文档 | 极好（go-redis） | 一般 |
| 生产验证 | 行业标准 | 较少 |
| 性能与资源开销 | 低 | 低 |
| 许可证 | BSD 类（RSAL 争议已弱化） | BSD |

### 最终选择：Redis

- 存设备最新状态是行业标准用法；数据结构丰富、支持持久化、go-redis 客户端成熟。

### 被否方案

- **否 Memcached**：仅 KV、无持久化、社区发展停滞，功能不足以承载「最新值 + 状态 + 榜单（健康评分排行 FR-10）」需求。

## 结论

存储三层 = **PostgreSQL（业务）+ TDengine（遥测）+ Redis（最新值缓存）**，各自扬长避短，共同支撑 NFR-01/NFR-03 的性能承诺。
