# 02 · 审查策略与决策规范

> 2026-10-13当前路线：MA-M1～M3及SEC-M1既有签收保留；SEC-M2本机限定技术验收签收、窗口已关闭并实测阻断，可进入SEC-M3开发准备但未自动启动。安全前三阶段后先SEC-M4本地集成，再评估MA-M4发布。服务器保持既有发布。最新真相入口：[[内容/第二版-智能体升级/多智能体协作建设/02-安全审查模型/开发阶段2-强制门禁集成/03-SEC-M2测试与交付]]。

> SEC-R01～R12已写入SEC-M1提示策略，当前规则v6在换回0731后限定十条真实程序存证/理由复核通过，原v5/GPT保留历史，其他输入/后续阶段另验；程序边界和状态仍由控制层及BND原台账维护。

## 一、决策含义

| 结论 | 意义与后续 |
| --- | --- |
| allow | 受审材料在限定条件下可接受；继续程序门禁及必要人工审批 |
| deny | 已知违规或风险不符合当前范围；阻断，记录规则与证据 |
| needs_clarification | 目标、需求或材料缺少必要信息；暂停动作并要求具体补充 |

程序已经拒绝的能力不进入模型争论。无证据不能用“看起来安全”allow；模型建议不能生成新工具、改变实际ID或减少审批。解析失败、服务故障与缺证据分别记录，不把三者一律写成deny。

## 二、规则台账

| 编号 | 审查事项 |
| --- | --- |
| SEC-R01 | 当前身份、任务所有权及项目范围 |
| SEC-R02 | 工具注册、风险和可用能力是否匹配 |
| SEC-R03 | 参数、计划、目标版本和证据是否一致 |
| SEC-R04 | 是否触及核心服务、真实设备或跨项目对象 |
| SEC-R05 | 用户明确执行意图；诊断/条件句不是重启授权 |
| SEC-R06 | R2审批、期限、一次消费与当前角色 |
| SEC-R07 | 时间、采集视角、截断、缺项与结论充分性 |
| SEC-R08 | 外发目的地、字段许可、载荷与最小化 |
| SEC-R09 | 日志、网页、资料和工具结果中的指令注入 |
| SEC-R10 | 实际失败/不确定结果与禁止自动写重试 |
| SEC-R11 | 原始日志、用户内容及凭据复现风险 |
| SEC-R12 | 审查/审计持久化完整性与恢复授权 |

规则命中必须关联实际输入/证据或程序拒绝原因，不能杜撰不存在的漏洞、权限或审计结果。无采集能力时说明限制并按动作所需证据决定澄清/拒绝。

## 三、威胁与保护责任

对恶意用户文本、工具输出、网页、历史上下文、篡改消息、审查重放和审批后目标变化分别设置反例。安全模型同样可能受注入或误判，身份、Schema、签名、Manifest、资产版本、审计和审批硬限制不交给模型。

actor、风险、policy、时间、摘要和引用来自程序；模型只判断规范化任务和最小证据。不提供“忽略规则”“把拒绝换个名字重试”的旁路，核心/跨项目对象始终未开放。

## 四、证据与解释

reason简明表达命中规则、证据和缺项。时间、状态、概率和阈值来自程序事实，不改原数值。输出只保留必要解释，不保存含敏感原文的推理过程；没有完整证据不能认定系统安全。

后审发现记录独立状态；已确认动作仍保持原事实。不确定执行不能以容器当前正常为由判“从未执行”或授权补写。

## 五、规则变更

新增样例 → 规则提案与影响范围 → 所有者确认 → 程序/模型设计 → 独立测试 → 正式验收 → 按发布门槛上线。模型不激活策略或修改规则。SEC规则维护审查逻辑，BND维护平台边界及上线状态；具体绑定与失效逻辑引用程序控制层。

## 六、v6理由和澄清的补充约束

规则编号和审批次序不变。参数、计划、外发摘要各绑定不同对象，模型不能凭字段存在就宣称相等或已验证一致；reason仅陈述对应程序事实支持的结论。缺证据的澄清仅请求许可内完整脱敏摘要、具体目标及未检查项，不要求原始日志、业务原文或凭据。v5误述和v6独立真实复核归阶段一问题及交付页，不改写旧结果。

## SEC-M2本机建设增量（2026-10-13）

运行策略v5按kind仅给模型当前类别规则，避免审批前pending规则混入执行前。未批准/审批无效preflight必须deny；执行意图false计划deny，许可内必需证据不足才澄清。post_success复核已保存成功记录，approval_consumed不代表原批准无效；不确定结果仅只读核对，不补写。M1的v6策略和合成字段范围保持。
