## 七、登录与会话（2026-10-29 晚，缺口 1 已关）

**结构**：`lib/auth.ts` 是登录态的唯一持有者（`authToken` / `currentUser` / `isAuthed` / `isAdmin` / `displayName` / `roleLabel`），
业务代码不再直接读写 `localStorage`；改登录态只有 `saveSession()` 与 `clearSession()` 两个入口。

**401 只有一个出口**：`api.ts` 的 `request` / `rawRequest` / `download` 三条通道在状态码 401 时统一调
`notifyUnauthorized()` → 清会话 → 回调 `main.ts` 注册的处理器 → toast「登录已失效」→ 带 `redirect` 回 `/login`。
并发 401 用 400ms 闸门去重，避免叠多条跳转。

**登录页的 401 不进这个出口**：`api.login()` 单独走裸 fetch，401 表示“账号或密码不正确”，留在原页显示行内错误。

**路由**：`/login` 标 `meta.public`；未登录访问任何页面 → `/login?redirect=<原地址>`；已登录访问 `/login` → 回原地址；
`redirect` 只接受单斜杠开头的站内路径（挡 `//evil.com`）；未知路径落回 `/`。标题随 `meta.label` 更新。

**壳层**：`App.vue` 用 `showShell`（有 token 且非公开页）决定是否渲染侧栏与顶栏，登录页不套壳；
实时链路与顶栏计数原来在 `onMounted` 里无条件启动，改为 `boot()` / `halt()` + `watch(authToken)`，退出时断开 WS 并清零计数。

**顶栏账号菜单**：显示真名 + 角色 chip + 账号 + 会话有效期，底部「退出登录」；头像取真名首字。

**待办**：`/auth/register` 后端有、界面仍未接（账号由管理员创建，属产品决策，不是漏做）；角色只做展示，`requireAdmin` 的 403 还没有对应提示。

## 八、告警处置闭环（2026-10-29 深夜，缺口 2 已关）

**能做什么**：抽屉里对单条告警「确认」或「归档」；列表左侧勾选后出现处置条，一次归档多条（翻页保留勾选，全选只作用于本页）。
两个动作都走二次确认，失败按状态码给中文原因，不再把后端英文原样弹给值班员。

**确认（ack）的边界和后端一致**：只有 `status = unhandled` 且 `recovered_at` 为空才能确认，其余状态按钮置灰并显示「已确认 / 已恢复」。
被别人抢先处置时后端回 409，前端提示「该告警已被确认或已恢复，请刷新后查看」并**立刻重新取数对齐**——不做乐观更新，
因为并发场景下乐观更新会让值班员以为是自己改成功的。

**归档（archive）的语义**：只置 `archived` 标记，不删告警事实、时间线与规则快照。但后端列表固定带 `archived = FALSE`（`alarms.go:193`），
所以**归档等于从列表里移除，且没有撤销入口**——确认框里把这句话写明了。单条归档后详情抽屉自动关闭，勾选集里失效的编号自动剔除。

**批量归档**走 `POST /alarm-archive`（`{ids}`，≤200 条），返回 `{archived, failed, updated_at}`；`failed` 里的编号单列一条 warn 提示，
不阻断其余。假后端同样实现去重与失败回填。

**实时联动**：`store.ts` 在 WS 收到 `alarm_*` 事件时递增 `shell.alarmRevision`，告警页 watch 后静默重取，
所以两个标签页同时开着时，一边处置、另一边自动跟着变（自己正在写时不插手，避免把回包结果冲掉）。

**一个必须知道的后端口径**：统计接口 `aggregateAlarms` **不带** archived 条件，列表带。
因此归档一条「未处理」告警后，列表少一条，但顶部四格的「未处理」不会减少。这是后端按「事件事实」计数的设计，
前端没有擅自在前端过滤，否则本地与生产会分叉。要改得改后端 `aggregateAlarms`。

**改动文件**：`views/AlarmsView.vue`（勾选列、处置条、抽屉按钮、状态机与错误映射）、`lib/api.ts`（`archiveAlarms` + `alarmWriteError`）、
`lib/store.ts`（告警事件计数）、`dev/mock-server.mjs`（ack 409 / archive 404 / 批量归档 / 列表归档过滤 / WS 广播）。

## 九、助手运行态（2026-10-29 第五轮，缺口 4 已关、缺口 5 部分完成）

**一句话**：助手页从「等一次性结果」变成「受理一次运行 + 订阅事件流」，正文、进度、待批准动作、产物都从同一条流上长出来。

### 1. 迁入的客户端（`lib/agent-runs.ts`，约 950 行）

这个模块是**按契约写死的**，不是宽松解析，原样迁过来只改了鉴权入口：

- 只认 `assistant/v4-draft1`；`run_id` / `turn_id` / `session_id` / `protocol` 四元组在初始快照与每次恢复读取时都要一致，不一致直接中止，**绝不显示别人的运行**。
- `seq` 必须严格 +1（`seq_gap` 即视为违约），64 位整数用「16 位以上字面量加引号」的方式保住精度，不超过 2^53 的仍还原成 number。
- 正文 `text_delta` 按 `offset` 拼接，允许重叠但要逐字相同；`reset` 只允许 `offset=0`；版本变化必须从零重建，否则报 `answer_version_mismatch`。
- 事件 `data` 走白名单投影，上游多塞的字段进不来（防止工具原始载荷或内部推理漏到界面）。
- 断线按 500ms→8s 有界退避重连，**不取消运行**；401/403/404 直接抛出（不重连）；400/410 与协议违约才做「重读快照再续」，且连续 3 次无进展才放弃。
- 401 统一走 `notifyUnauthorized()`，与 `api.ts` 同一出口（旧版是 `clearSession()` + `location.replace`，会绕过 router）。

### 2. 运行卡（`components/RunAnswer.vue`）

| 区块 | 内容 |
| --- | --- |
| 头部 | 状态胶囊（排队/运行中/待批准/核查中/已完成/部分完成/失败/已取消）、阶段文案、连接状态、运行编号 |
| 正文 | markdown 流式渲染；空正文时区分「终态未给正文」与「已受理等待中」 |
| 任务结果 | `result_refs`，标注是否为历史结果 |
| 参考来源 | `SourceList.vue`：知识库文档可「阅读章节」，公网页可外跳并提示需人工校对，平台数据只给编号与摘要 |
| 审批与动作 | 每个动作的效果、状态、目标、有效期、核对时间；`pending` 且未终态时挂审批弹窗入口；**有待批准动作时默认展开** |
| 产物 | 名称、大小、可下载/已过期；下载走 `lib/agent-artifacts.ts`，先读元数据核对 `run_id`/`artifact_id`/`status`，再取字节核对 `size` 与 `sha256` |
| 控制 | 停止接收回答 / 恢复接收 / 请求取消任务（取消要二次确认，并写明「已发生的结果不会自动撤销」） |

### 3. 审批弹窗（`components/ActionApproval.vue` + `lib/approval-auto.ts`）

- **自动弹出但只弹一次**：待批准动作出现即弹；同一个 `run:action` 只自动弹一次，关掉后仍保留「核对并决定」按钮；同一时刻只占一个（多动作依次弹）。
- **决定前先重新读快照**：核对绑定、`status=pending`、有 `approval_id`/`plan_hash`、未标过期、`expires_at` 未到期 —— 任一不满足就提示「批准已失效或状态尚待核查」，不给批准按钮。
- **决定失败要回读真实状态**，不本地猜测成功；服务端回 `authority_sync_status=pending_reconciliation` 时提示「决定尚待权威核查，请刷新；不要重复提议动作」。
- 定期任务类动作把 `config` 摊成字段（任务/时区与节奏/范围/原配置版本）再给一句持续授权说明，避免让人对着一串 JSON 点头。

### 4. 助手页接法（`views/AssistantView.vue`）

- 发问 = `createRun`（`Idempotency-Key` 复用同一把 key）→ 拿到 receipt → 用 `run_id` 订阅。**输入框在收到 receipt 后就解锁**，不再锁到终态。
- **重新进页面只重挂最近两轮**：更早的运行几乎都已终态，逐条 GET 只是白花请求；历史轮次直接渲染会话里存的 `answer_markdown` + 来源。
- **会话恢复**：sessionId 存 sessionStorage（按用户隔离），刷新后自动回到上次那段会话。
- **generation 闸门**：切会话/新建会话会让旧回调失效，迟到的快照不会写进新会话。
- 运行读不到（保留期已过，403/404）时**只保留会话里那份回答**，不显示错误、不臆造运行。
- 终态后回读一次会话元数据，把正文与来源换成服务端持久化的那份（运行快照里没有 `sources`）。

### 5. 假后端同步改造（`dev/mock-server.mjs`）

原来 `POST /agent/runs` 直接回终态快照、`/events` 只发心跳，等于**流式与审批都验不到**。本批改成与真后端同形状：

- 运行 = 一条 seq 连续的事件日志；`GET /runs/:id` 的快照由日志尾部派生，`GET /runs/:id/events?after_seq=N` 先补发积压再实时推。
- 问答时间线：`accepted → progress(starting) → tool_started → tool_finished → text_delta×4 → artifact_ready → completed`（约 2.4 秒，够看清流式）。
- 动作时间线：走到 `approval_required` 就停住等人批准；决定/取消才推终态事件。
- 决定校验 `plan_hash`/`approval_id`/`expires_at`，重复决定回 409；产物元数据是裸 JSON、下载真吐 CSV 字节（可被 `sha256` 校验）。
- `GET /agent/sessions/:id` 现在真的返回 turns（含一条无 `run_id` 的早期历史轮次 + 两条来源），否则历史渲染与来源都无从验证。

## 十一、定期任务的方案预演与审查（2026-10-29 第七轮，缺口 9 已关）

**一句话**：先在同一页试算阈值、看命中，再决定要不要建任务；提交的配置审查在列表里就能打开并审批。

### 1. 方案预演（`POST /agent/rule-preview`）

页面在「我的任务」下面新增「方案预演」卡（默认展开，收起状态存 `sessionStorage`），表单按 08 `Preview` 模型逐项对齐：

### 2. 预演结果（读 `rule-preview.json`）

结果不是从正文里抠数字，而是走 `readArtifactJson()` 读产物，且**与下载共用同一道闸门**（`loadArtifact`：核对 `run_id / artifact_id / status` → 校验 `size` 与 `sha256`）。

- 复用 `RunAnswer` + `ActionApproval`，审批弹窗照旧自动弹出（`approval-auto.ts` 的闸门：同一动作只弹一次、同时只弹一个）。
- 「请求取消」走 `askConfirm` 二次确认，取消后回到列表刷新状态。
- 关闭面板只 abort 订阅，不影响服务端运行。

### 5. 假后端按真口径重做（不改就会「界面看着对、时序全错」）

1. `POST /agent/rule-preview` 原来**直接造一条审批运行**（`rule.preview` 根本不需要批准）→ 改成真预演：按 `Preview` 校验入参 → 取 `/devices/:id/telemetry` 同源历史点 → 按 `rule_preview.evaluate` 同口径算 coverage / metrics / assumptions / summary → 产出 `rule-preview.json` → 完成。
2. `POST/PUT /agent/schedules` 原来**提交即写任务表**（`paused / 等待批准`）→ 改成**批准后**才落库，并按配置算 `next_run_at`（每日定时取北京时间下一个该时刻，按间隔从批准时刻起算）、发授权；拒绝时改回「修改未获批，仍按原配置运行」。
3. `GET /agent/schedules` 的 `list` 原来按数组顺序 → 改成按 `created_at` 倒序（真后端 `ORDER BY created_at DESC`）。**否则新批准的任务排在最底下，批完看不见。**
4. 产物下载原来固定回 `text/csv` → 按产物 `mime_type` 返回，JSON 产物才不会被当成 CSV。

### 6. 顺带修掉的两处

1. **`across()` 不会算未来**：`(now - ts)` 为负时直接落到「刚刚」。定期任务的「下次执行」永远是将来，结果全页显示「明天 06:39（刚刚）」；条上的「最近一次执行」也名不副实（那是下次）。已改成 `diff < -10 → span(-diff) + 后`，标签改「下次执行」，实测「21:57:25 / 40 分 27 秒后」。
2. 审批弹窗的定期任务摘要里 `范围` 直接显示后端枚举 `baseline`，「节奏」只给 `09:00`。已补中文（全平台 / 业务设备 / 指定场站）与「每日 09:00 / 每 120 分钟」。

### 7. 实测（无头 Chrome + CDP，780×1000 与 1440×900）

- 预演：默认窗口提交 → 288 / 0 / 81 / 118、采样完整；未来窗口 → 「预演窗口最长 24 小时」；1 小时 + 60 秒间隔 → 12 / 48 / 断点 44、「采样不完整」；收起再展开、从审查列表重开都能还原结果与参数回显。
- 审查：新建任务提交 → 运行面板待批准 + 弹窗自动打开 → 批准 → 运行「已完成」、任务数 4→5、新任务排首位（指定范围 PV-02 · 每 120 分钟 · 下次 23:15）；请求取消 → 二次确认 → 「已取消」，列表同步。
- 三点校验：`vue-tsc --noEmit` 0 错、`vite build` 通过（SchedulesView 24.6 kB / gzip 8.95 kB）、`node --check` 通过。

### 8. 本批没做的

## 十二、AI 告警解读（2026-10-29 第八轮，缺口 3 已关）

### 1. 先取证：生产到底是哪一版

不猜配置，直接进生产 VM 查容器环境变量：

```
[powersystem-stage4-api-1]
AGENT_INTERPRET_PROTOCOL=v2
SIMULATION_ALARM_MODE=controlled
```

库里两类记录并存（`v1: 15 completed + 1 degraded`，`v2: 18 completed + 5 degraded`），说明 v2 在真跑。又从库里取了一条 `answered` 的 result 逐字段核对，才动手写类型——**前端字段按生产实际返回写，不按代码里可能的形状猜**。

### 2. 接口（三条，全部已有，本轮只是接上）

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/agent/interpretations` | 列表，支持 `category` / `alarm_id` / `updated_after` / `attention=true` / `page` / `page_size` |
| GET | `/agent/interpretations/:id` | 单条详情 |
| POST | `/agent/interpretations/:id/read` | 标记当前用户已读（写 `agent_interpretation_reads`） |

三条都走 `ok()` 信封（不是 runs/schedules 那种裸 JSON），所以用 `api.ts` 的普通 `get/post`。**后端一行没改。**

### 3. 关键认知：解读是异步任务

`interpretationScanner` 扫到新告警插一行 `pending` → `interpretationWorker` 抢租约调模型 → 结果写回 `result`，`task_status` 落到 `completed` / `degraded`。所以：

- 刚触发的告警读到 `task_status=pending`、`result=null` 是**正常**的，界面必须说「生成中/排队中」，不能显示「暂无解读」；
- pending/running 时 `result` 可能是上一轮的旧内容，不能当本轮答案渲染；
- 结果落地时后端会推 WS `interpretation_updated`，前端收帧即可提前结束等待，轮询只是没连上时的兜底（4 秒 × 6 次）。

### 4. 四态与降级文案

`lib/interpretation.ts` 把 v1/v2 的 `result` 归一化成 `InsightView`，界面只认四种状态：

| 状态 | 判定 | 界面上怎么说 |
| --- | --- | --- |
| `pending` | `task_status ∈ {pending, running}` | 胶囊「排队中 / 生成中」+ 说明，胶囊下方给模板兜底 |
| `ready` | `result.status === 'answered'` 且结论或建议非空 | 结论 / 关键事实 / 建议动作 / 尚未解释的部分 / 证据快照 |
| `degraded`（拒答） | `result.status === 'unable_to_determine'` | 胶囊「证据不足」+「模型判定现有证据不足，明确不给出结论」 |
| `degraded`（没跑通） | 其余 | 胶囊「未完成」+ `解读未完成：<原因>`，原因码翻成中文（`not_configured` / `auth_failed` / `quota_exhausted` / `circuit_open` / `model_timeout` …共 25 个，认不出的显示原码） |
| `missing` | 接口没回这条告警的记录 | 「后端还没有为这条告警生成解读」 |

两条易踩的坑：

1. **`conclusion.text` 就是把 `findings` 用换行拼起来**（生产样本逐字相等）。两处都渲染等于把同一段话读两遍，所以视图层做去重：相等时只留分条那份。
2. **`limitations` 有时是字符串、有时是对象**（`analysis.limitations` 是 `template + fact_refs`）。`texts()` 两种都收，不然换一版协议就白屏。

### 5. 面板布局（`AlarmInsight.vue`）

告警切换条 → 头部 → 读数块（实测/阈值/越限，未改）→ **解读状态行**（胶囊 + 模型/#id/时间/协议 + 重新读取）→ 说明行 → 结论块 / 关键事实 / 建议动作 / 局限 / 证据快照 → **兜底块**（仅非 ready 时）→ 旁证（健康分/该设备告警/失效风险/来源，未改）。

- 关键事实来自 `facts`（Go 侧从证据提取的权威事实，不是模型编的），标题旁标「取自证据快照，非模型生成」；只铺前 8 条（`device_alarm` 的 facts 可能十几条，全铺会把建议动作顶出视野），多出来的显示「另有 N 条事实未展开」；设备编码这种长值独占一整行。
- 兜底块用虚线边 + 浅底 + 标题「通用排查顺序 / 按指标与级别生成的模板，非模型结论」，内部分「可能成因 / 建议动作」两小段。**原来的模板没删**——模型不可用时它比一句「暂无解读」有用。
- 证据快照每行 `E1 · 告警记录 · ok · 1 时 51 分前`，tool 名做了中文映射（认不出原样显示）。

### 6. 顶栏红点改成真实口径

原来红点绑的是 `activeCount`（活动告警数），语义是「有告警」，不是「有未读解读」。现在：

- 红点 = `GET /agent/interpretations?attention=true&pageSize=1` 的 `total`（后端口径：未读 且（24 小时内 或 事件未恢复））；
- 接口失败时**保留上一次的值**，不清零——清成 0 会让红点骗人；
- WS `interpretation_updated` 触发刷新，1.2 秒合并一次，避免 worker 批量落结果时打满接口；
- 面板里读一条就 `POST .../read` 并通知父层刷新。

### 7. 假后端重做（4 处）

1. 原来那三条解读路由返回的是 3 条手写记录（id 7000+、字段不全、`POST read` 直接回 `{}`）→ 删掉，按生产 v2 形状重做：26 条告警各一条记录，`facts` 由告警+设备算出，模板 `{{F1}}` 占位再渲染成 text，`evidence_hash` 用 sha256，`request_id` 用 uuid。
2. **异步时序**：`5002` 这条第一次被请求才挂 6 秒定时器，到点落结果并广播 `interpretation_updated`——否则「生成中」这一态在本地永远看不到（一开机就算完了）。
3. 三条演示分支固定按告警 id：`5005` = 额度用尽（`degraded`）、`5007` = 证据不足拒答（`unable_to_determine`），其余 `answered`；另有 4 条预置已读，红点才有变化。
4. 顺带修**一个真 bug**：`GET /alarms` 从来没处理 `device_id` 过滤（真后端支持），导致解读面板「该设备告警」把全平台条数（26）当成单设备的。现在按 `device_id` 过滤。

### 9. 本批没做的

- 结论按纯文本渲染，没走 markdown：生产 v2 的 `conclusion.text` 是事实句拼接，目前没有需要渲染的结构。
