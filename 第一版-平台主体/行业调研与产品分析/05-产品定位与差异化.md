# 05 · 产品定位与差异化

> 回到 [[00-索引·行业调研与产品分析]]

前四章回答了「行业值不值得做、国家支不支持、技术上到哪了、竞品缺口在哪」，本章把结论收敛为**明确的产品定位**。

## 一、目标用户

| 用户 | 特征 | 核心诉求 |
| --- | --- | --- |
| 中小型新能源场站业主 | 装机规模中小、预算有限、无自研 IT 团队 | 低成本、开箱即用、少用人 |
| 新能源发电专业运营商 | 管多个场站、需集中监控 | 一体化集控、可复制部署 |
| 场站值班员 | 面对海量告警、需快速处置 | 告警收敛、故障早知道、可解释 |

**不做**：大型央企/跨国集团的定制化重项目（那是华为/远景/金风的主场，我们拼不过，也无需拼）。

## 二、产品定位

**一句话定位**：面向中小新能源场站的**低成本、可解释、云边协同**智能运维平台。

- **低成本**：全栈 Docker 化一键部署，边缘网关软件化适配现有设备，无需更换硬件；部署成本较商业平台降 50% 以上。
- **可解释**：XGBoost 故障预测输出特征重要性，值班员"知其然更知其所以然"。
- **云边协同**：边缘网关断网缓存 + 恢复补传，弱网环境数据完整率 ≥99.9%。

## 三、功能架构映射

产品四大子系统与定位一一对应（源自申报书研究内容）：

| 子系统 | 对应定位 | 核心能力 |
| --- | --- | --- |
| 数据感知与边缘接入 | 云边协同 | 机理仿真模拟器、Go 网关、断网补传 |
| 后端服务与告警引擎 | 低成本、告警闭环 | 认证鉴权、设备台账、告警收敛、WebSocket 推送 |
| 故障预测模块 | 可解释 AI | 滑动窗口特征、XGBoost、特征重要性、FastAPI 服务化 |
| 可视化平台与部署 | 开箱即用 | Vue3 六大页面、实时大屏、Docker 编排 |

## 四、SWOT 分析

| | 有利 | 不利 |
| --- | --- | --- |
| **内部** | **S（优势）**：完整技术栈团队；机理仿真数据正面回应"数据从哪来"；可解释小数据 AI；全栈工程化交付 | **W（劣势）**：学生项目缺真实场站数据；无商业落地背书；工业协议适配经验不足 |
| **外部** | **O（机会）**：千亿级高增长市场；政策强风口（[[02-政策环境与驱动力]]）；竞品碎片化、中小场站长尾空缺 | **T（威胁）**：巨头下沉挤压；开源方案免费替代；比赛节奏/时间压力 |

**策略**：以「仿真+真实开发板」混合接入补数据短板；以「可解释性 + 低成本」错位竞争，避开巨头正面战场。

## 五、差异化三条（对标竞品缺口）

对照 [[04-竞品分析]] 的三个缺口，我们的三条差异化正好一一补齐：

1. **vs 通用平台（重而不专）**：我们不是 IoT 底座，而是「新能源运维业务 + AI 预测」的一体化成品，无需二次开发。
2. **vs 开源平台（全而不易）**：我们补齐了开源平台缺失的「告警闭环 + 可解释 AI + 一键部署」，把门槛降到中小场站可用。
3. **vs 垂直平台（强而绑定）**：我们「软件化、协议中立、跨品类」，不绑定任何硬件厂商，可复制到光伏/风电/储能异构场站。

## 六、切入点与 MVP 路径

**切入点**：先打「告警闭环 + 数据链路」这一个最痛的场景（遥测越限秒级告警、断网不丢数据），再叠加「故障预测」形成护城河。

- 阶段一（1–4 周）：跑通数据链路（M1：数据连续落库 1 小时无丢失）
- 阶段二（5–8 周）：后端 + 告警闭环（M2：接口全通过、越限秒级告警）
- 阶段三（9–12 周）：XGBoost 预测（M3：预测接口 + 评估报告）
- 阶段四（13–16 周）：前端 + 上线（M4：公网可访问 + 演示视频）

> 上述为原四阶段路线图，保留当时的产品规划。第一版现已将阶段五飞书设备/AI 业务告警纳入主业务，与 M4 一起验收；视频复盘和对外材料不再是发布门槛。当前事实以 [[项目验收与收尾清单]] 为准。

## 七、本章小结

1. **定位**：中小场站的低成本、可解释、云边协同智能运维平台。
2. **用户**：中小场站业主 / 专业运营商 / 值班员，避开巨头定制化主战场。
3. **差异化**：可解释小数据 AI + 低成本复制 + 协议中立，逐一补齐竞品缺口。
4. **切入**：先告警闭环再预测，MVP 小步快跑。
