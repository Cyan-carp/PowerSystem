## 二、日常检查与排障

#### 步骤 1 · 看运行状态

在 R730xd 的 `/opt/powersystem` 执行：

```bash
docker compose --env-file .env -f stages/04-frontend/deploy/compose.yaml ps prometheus alertmanager feishu-adapter
docker compose --env-file .env -f stages/04-frontend/deploy/compose.yaml logs --since=10m alertmanager feishu-adapter
```

> 分享日志前先脱敏；不要输出或转发机器人 URL、签名密钥、群标识和完整事件载荷。

#### 步骤 2 · 按链路定位

- **规则未 firing：** 核对 Prometheus targets、`alerts.yml` 表达式和持续时间。
- **已 firing 但适配器无请求：** 核对 Alertmanager 配置、服务发现和 Compose 内网连通性。
- **适配器返回 502：** 核对私有文件存在性及权限、服务器到飞书 443 的连通性；只记录错误类型，不打印私密值。
- **适配器返回 200 但群里没有消息：** 由群成员核对群机器人是否仍在目标群、消息是否被策略拦截；仅保存脱敏时间和结果。

## 三、改动后复测

改 `app.py` 或消息格式后运行适配器全部本机测试；改 Compose、Prometheus 规则或 Alertmanager 配置后做对应配置检查。更新镜像后核对 API、Prometheus、Alertmanager 与适配器的健康状态和日志。需要重新声明“实际送达”时，在约定时间注入可控故障，记录触发/恢复、适配器响应和群成员确认；失败与复测分别保留。密钥轮换只在服务器私有文件操作，完成后重启适配器并重新验收，不把新值写入笔记。

## 四、业务告警变更后的排查

设备与 AI 告警的第一版测试矩阵、现场运行结果、群内确认和验收边界统一见 [[03-阶段五测试与交付]]。业务链路与监控链路须分别复测；API 宕机的历史群消息不能替代设备或 AI 事件的送达核对。

改动业务投递逻辑或机器人配置后，运行 `stages/05-feishu-notification/deploy/verify-business-notifications.py`，按事件 ID 对照 `business_notification_outbox` 与适配器响应，并请群成员确认可见性。重复遥测不应产生新的同状态任务；更换机器人或群后要重新核对。测试结束清理临时规则和设备，公开记录不保存机器人凭据或群成员信息。

```bash
docker compose --env-file .env -f stages/04-frontend/deploy/compose.yaml exec -T postgres \
  psql -U powersystem -d powersystem -Atqc \
  'SELECT COUNT(*) FILTER (WHERE sent_at IS NULL), COUNT(*) FILTER (WHERE sent_at IS NOT NULL), MAX(attempts) FROM business_notification_outbox'
```

此查询只统计任务数量，不输出消息负载。飞书群内可见性需项目所有者确认；适配器 HTTP 200 本身不能证明群成员已经看到消息。网络确认丢失时，同一事件 ID 可重复投递，不能宣称严格一次。
