# 架构设计 · 索引

> 本文件夹是「源网智联」在**写代码之前**的设计文档：把 [[第一版-平台主体/技术选型/00-索引·技术选型]] 定下来的一堆「零件」，组装成一台「机器」。回答四个问题：**系统长什么样（架构图）、数据怎么流（数据流）、数据存哪（数据库）、接口怎么调（API）。** 对应手册第四章（任务 9–12）。

## 一句话定位

技术选型选出的是零件清单，架构设计决定它们怎么组装。本项目套用工业物联网**五层骨架**（设备层 / 边缘层 / 网络层 / 平台层 / 应用层），核心是三点：**云边协同**（网关就近处理 + 断网续传）、**服务化解耦**（AI 预测独立成 FastAPI 服务）、**读写分离**（遥测走 TDengine、业务走 PostgreSQL、最新值走 Redis）。

## 一页读懂（给团队与评审）

> **五层结构**：模拟器（设备层）→ MQTT/EMQX（网络层）→ Go 网关（边缘层）→ Gin 后端 + TDengine/PostgreSQL/Redis + FastAPI（平台层）→ Vue3 大屏（应用层）。
>
> **一条数据的旅程**：逆变器每 5 秒发一条温度 JSON → 网关解析校验 → 批量写时序库 + 更新最新值 → 越限触发告警 → WebSocket 10 秒内推到前端弹窗。断网时网关本地缓存、恢复后 30 秒内补传，数据完整率 ≥99.9%。
>
> **为什么这样设计**：AI 不放 Go 后端、单独起 FastAPI 服务，训练/上线互不拖累；遥测与业务数据分开存，查询各走各的库；所有接口 JWT 鉴权、密码 bcrypt 加密。

## 四件套自洽核对（设计闭环的验收标准）

手册导师说：架构图、数据流、数据库、API 四份文档必须**互相一致**，才叫设计闭环。落盘前逐项核对：

| 核对项 | 结论 |
| --- | --- |
| API 需要的字段，数据库里都有表/列可存吗？ | ✅ 见 [[03-数据库设计]] 表结构 ↔ [[04-API接口设计]] 响应示例 |
| 数据流经过的组件，架构图上都画了吗？ | ✅ 网关/时序库/Redis/告警引擎/WebSocket 均在图 |
| 架构图的协议标注，和数据流时序图一致吗？ | ✅ MQTT/JSON、HTTP/REST、WebSocket 三处对齐 |
| 每条 Must 级需求有对应的表 + 接口吗？ | ✅ FR-01~FR-13 映射见 [[04-API接口设计]] |

## 与上游的衔接

架构设计不是重新发明，而是把 [[第一版-平台主体/需求分析/04-非功能需求清单]] 的量化约束、[[第一版-平台主体/技术选型/00-索引·技术选型]] 的选型结论，翻译成「结构、流程、存储、接口」：

- NFR-01「200 台设备 / 5 秒上报」→ 网关 goroutine+channel 解耦、批量写 TDengine；
- NFR-03「告警 ≤ 10 秒」→ 网关写库后即触发规则匹配 + WebSocket 直推；
- NFR-04/NFR-05「断网 99.9% 不丢 / 30 秒补传」→ 网关本地 SQLite/文件队列缓存；
- NFR-11「分层架构」→ Gin 按 handler/service/model 分层，数据访问隔离。
