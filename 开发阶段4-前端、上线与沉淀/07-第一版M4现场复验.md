# 07 · 第一版 M4 现场复验

> 2026-09-29 北京时间。本页记录第一版部署后的新证据；旧 P0 的 HTTP 演示与历史备份事实仍保存在 [[06-P0收尾与M4验收记录]]。阶段五业务通知见 [[开发阶段5-飞书告警通知/02-验证与运维]]。只依据实际核对结果判定，不以脚本退出码代替用户可见性。

## 公网安全

- 云端 `8.138.10.222:443` 使用受信任的 Let's Encrypt IP 证书，外部 `curl` 校验证书成功，`https://8.138.10.222/api/v1/ping` 返回 HTTP 200、业务码 0。云端 Nginx 终止 TLS 并经本机回环 `127.0.0.1:3667` 转发 FRP，WebSocket Upgrade 头已配置。
- 本项目旧 TCP `3667` 仍由共享 `frps` 监听，但 `powersystem-public-firewall.service` 在 IPv4、IPv6 拦截外部访问；外部 HTTP 旧入口已超时，HTTPS 正常。该服务随开机启用。共享主机其它 FRP 监听属于其它业务，没有擅自关闭。
- 证书续期计时器 `powersystem-cert-renew.timer` 每日两次触发；手工运行续期服务成功，`certbot renew --dry-run` 成功，当前证书在测试时剩余超过 48 小时。短周期证书须持续监测计时器和续期日志。
- R730xd 与云端 `sshd -T` 均显示 `passwordauthentication no`、`pubkeyauthentication yes`、`permitrootlogin without-password`；公钥会话可登录。R730xd 的前端、Prometheus、Grafana 仅映射到宿主机回环地址，数据库、MQTT、Redis、TDengine、AI、API、飞书适配器没有单独映射公网。

## 备份与隔离恢复

- 更新前加密包 `powersystem-20260929T082605Z.tar.gz.gpg` 已上传专用 SFTP 目录，云端与 R730xd 的 SHA256 相同。隔离恢复核对 PostgreSQL 与 TDengine 各 43,113 条、两个 SQLite 队列。
- 第一版部署后加密包 `powersystem-20260929T085852Z.tar.gz.gpg` 已上传并校验 SHA256。隔离恢复核对 PostgreSQL 与 TDengine 各 44,295 条、两个队列、`business_notification_outbox` 表及 `.env`、飞书 Webhook、签名密钥、业务通知令牌、模型资产的校验和。
- R730xd `powersystem-backup.timer` 已启用，每天 02:30 北京时间附近执行显式目标加密备份；接收端账号限制为 SFTP，目录权限为 700。两次演练的独立 Compose 项目、测试卷和解密目录已在核对后清理，生产卷和异地密文保留。
- **剩余恢复风险：** 解密口令目前仅在 R730xd 私有文件 `/etc/powersystem/backup-passphrase`；若整机丢失，仅有云端密文无法恢复。项目所有者选择自行离线保管，步骤见 [[备份口令离线交接与整机恢复步骤]]；截至本页更新时，所有者明确回复“尚未完成”，因此整机灾难恢复不能判为通过。

## 第一版部署与功能

- `/opt/powersystem` 已更新，`docker compose config --quiet`、构建与 `up -d --remove-orphans` 成功，旧高权限 cAdvisor 已移除。API、前端和通知服务运行；公网 `/api/v1/ping` 返回成功。
- 阶段五业务投递表迁移已应用；设备越限、操作员确认、自然恢复、规则关闭及失败重试的真实适配器 HTTP 响应已取证。真实模型对合成逆变器先后给出高风险 0.9942、低风险 0.0125，AI 告警触发与自然恢复两条业务事件均标记发送成功；临时设备已软删除。项目所有者确认目标群可见设备与 AI 新消息。

## 容量与浏览器

200 台、每 5 秒、持续五分钟的隔离环境复验使用独立 `powersystem-m4-load` Compose 项目，七项核心服务固定到同一组两个 CPU（R730xd 物理主机有 56 个逻辑 CPU、64 GiB RAM）。第一次仿真包的功率值违反网关物理校验，虽然 MQTT 确认 12,000 条，但收件表为零，该次 **失败**，不能作为吞吐证据。修正为与电压、电流一致的功率后用新运行编号重测：60 轮、12,000 条 QoS 1 发布确认，最慢一轮 0.108 秒，无延迟轮；PostgreSQL 收件表 12,000 条，200 个不同设备，待处理为零；TDengine 12,000 条。中途七项核心服务合计约 1.1 GiB 内存，未达 4 GiB。测试固定了两个 CPU，但没有给整个隔离项目施加统一 4 GiB 硬限制，因此可证明双核调度下的本次吞吐和实际内存占用，不能外推为任意 2 核 4G 主机的稳定性保证。

公网 HTTPS 路径使用服务器私有测试管理员账号测得 20 次设备列表与 20 次一小时温度历史查询：列表中位 139.5 ms、最慢 155.4 ms；历史中位 164.5 ms、最慢 189.9 ms；均小于 NFR-02 的 2 秒目标。测量脚本 `stages/04-frontend/deploy/m4-http-latency.py` 只打印统计，不输出口令或令牌。

网关停机补传在同一隔离项目中单独计时：网关停止期间再发布 200 台 × 6 轮 = 1,200 条；重启后 13 秒内 PostgreSQL 总数从 13,200 增至 14,400，待处理为零，TDengine 最终也为 14,400 条，低于 NFR-05 的 30 秒目标。该结果证明本次有界停机与持久 Broker 会话下的补传；真实弱网与硬件故障仍须按实际场站另测。测试后按精确项目名删除七项隔离容器及其专属卷，生产 `powersystem-stage4` 服务保持健康。

当前电脑安装 Chrome 154 与 Edge 154。用真实 Chrome/Edge 内核、临时内存登录会话分别访问公网 `/dashboard`、`/devices`、`/alarms`、`/predictions`，四个页面在两浏览器均有认证后内容，无登录回跳或加载失败。公网 API 的 ≤2 秒目标已取得重复实测；浏览器端首次加载的单独计时未做。按项目所有者 2026-09-29 的明确选择，第一版接受 **Chrome/Edge 154** 的核心路径验收，上一主版本 153 的矩阵补测转为发布后任务；不得写成 NFR-12 原始“双版本”目标已经全部验证。Chrome 与 Edge 官方发布资料见[Chrome 154](https://developer.chrome.com/release-notes/154)及[Edge 154/153 发布计划](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-release-schedule)。

## 判定

公网加密与最小暴露、更新前后异地加密备份和隔离恢复、第一版部署、双核容量、补传、API 响应及约定的 Chrome/Edge 154 核心路径已完成现场核对；阶段五群内可见性亦由项目所有者确认。**M4 当前唯一尚需所有者完成的恢复门槛是口令独立离线保管及 MATCH 核对。** 完成前不标记正式验收或 GitHub 第一版 Release。153 浏览器补测及真实场站模型效果属发布后边界。
